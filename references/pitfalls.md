## 一、输入类

### P1 输入法吞字（最高频）
- 症状：`keybd_event` 打 `wbtest123`，输入框只剩 `25123`。
- 真因：搜狗等 IME 把字母当组字过程吃掉。
- 对策：**任何中文/长文本/甚至 ASCII 短串都走 `set_clipboard(text)` + `Ctrl+V`**。

### P2 64 位指针截断
- 症状：`GlobalLock` 返 0 → access violation。
- 真因：ctypes 默认 `restype=c_int`，64 位句柄被截成 32 位。
- 对策：`GlobalAlloc/GlobalLock/GetClipboardData` 必须设 `restype = ctypes.c_void_p`（脚本已设）。

### P3 剪贴板被占用
- 症状：`OpenClipboard` 返 False。
- 对策：重试 10 次、每次 sleep 0.3（脚本已内置）。

## 二、坐标与显示类

### P4 高 DPI 偏移
- 症状：坐标整体偏移 / 截图与预期不符（125%、150% 缩放屏尤其明显）。
- 对策：进程启动先 `shcore.SetProcessDpiAwareness(2)`，失败回退 `user32.SetProcessDPIAware()`（脚本已自动做）。

### P5 多显示器/负坐标
- 症状：窗口在副屏时 `GetWindowRect` 返回负 left。
- 对策：截图 bbox 直接用 rect，不要自己 clamp；点击坐标用物理像素原值。

### P6 SetCursorPos 看似失效
- 症状：设 (312, 500)，读回 (889, 500)。
- 排查顺序：① 用户的手是不是正在动鼠标（争夺光标）→ 等 1 秒再读；
  ② 是否管理员权限目标 + UIPI（见 P8）；③ 目标窗口是否卡死（见 P9）。

## 三、窗口与焦点类

### P7 SetForegroundWindow 静默失败
- 对策：兜底 `AttachThreadInput`（**属 user32！** 曾误写成 `kernel32.AttachThreadInput` → 一走兜底就 AttributeError）。
- 另：`ShowWindow(9)`（SW_RESTORE）即可，**别用 `ShowWindow(3)`/MAXIMIZE**（实测会把窗口搞成空白态）。

### P8 ⛔ 权限墙 UIPI
- 症状：`taskkill /PID x /T /F` 拒绝访问；`PostMessage(WM_CLOSE)` 返 False；点击/按键**完全无效果**。
- 真因：目标以管理员运行，低完整性进程不能给高完整性窗口发消息。
- 关键认知：**截图与 `SetCursorPos` 不受 UIPI 限制** → **"能截图、能移鼠标" ≠ "能点击"**。
- 对策：请用户人工处理（任务管理器结束任务；权限不足就点左下角"以管理员身份重新启动"）。

### P9 窗口"假活"（Chromium/ Electron / NW 系）
- 症状：连点十几下毫无反应，但 `IsHungAppWindow()` 报健康、`SendMessageTimeout(WM_NULL)` 也有应答。
- 判定三步法（写成 `probe_alive()`）：
  1. **悬停高亮探针**：鼠标移到已知按钮上，1.2s 后截图与基线比对（Chromium 悬停必高亮，无差异 = 渲染进程死）。
  2. **多帧字节比对**：连拍 3 帧，md5 全同 = 屏幕根本不重绘。
  3. **结论**：UI 活不活看**会不会重绘**，不要问消息队列。
- 对策：只能让人重启该 App。

### P10 窗口标题不按你想的来
- 微信开发者工具顶层标题是 **`WeChat Web Devtools`**，**不含项目名**（项目名只在内部标签里）。
  → 用 `find_window(title='Devtools')`（子串匹配），别用项目名，否则返回 None。
- 很多 App 有隐藏小窗（IME、托盘、`SoPY_*`），枚举时按尺寸/类名过滤。

### P11 单实例守卫
- 旧实例还在时再启动 exe，新进程**立即 exit code 0**。→ "重启 App"必须先真正结束旧进程。

## 四、关闭与进程类

### P12 SendMessage(WM_CLOSE) 永久阻塞
- 症状：脚本假死。
- 真因：被关窗口弹模态（记事本"是否保存"），SendMessage 不返回。
- 对策：一律 `PostMessage`；必要时挂 `threading.Timer` 看门狗。

### P13 Git Bash 转义坏参数
- 症状：`taskkill //PID 37976 //T //F` → `无效参数/选项 - '//PID'`。
- 对策：用 Python `subprocess.run(['taskkill','/PID','37976','/T','/F'])`，或 `MSYS2_ARG_CONV_EXCL="*"`。

### P14 Git Bash 的 /tmp ≠ Windows 的 C:\tmp
- 现象：脚本写到 `/tmp/x.png`，Windows 程序找不到（实际在 Git Bash 虚拟路径）。
- 对策：统一用 `%TEMP%`（`C:\Users\<用户>\AppData\Local\Temp`）作中转目录。

## 六、读界面类

### P18 不要 OCR，先找导出
- 控制台/日志区域 → **右键 `Save as...`** 导出成文本文件，用 Read 读逐字文本，比截图识别准得多。
- ⚠️ 导出格式**不含级别标记**（`console.error`/`warn` 都只是纯文本行）→ **级别仍需看图**。

### P19 "1 error" 要辨级
- 调试器面板右上角 **`∧`** 可铺满面板（小面板一次只看 3~4 行，极易漏掉那条红的）。
- 左侧图标即级别：⚠ 黄三角 = warning，⊗ 红圈叉 = error。徽标 `⊘1 ⚠6` = 1 error / 6 warning。
- **标红 ≠ 你的代码有错**：微信开发者工具就曾把"以 `__` 开头结尾的目录为保留目录，`__tests__` 下文件将被忽略"标成 error——而忽略测试目录正是期望行为。
- `Clear console history` 能清列表，但**徽标计数不会归零**（累计值），别被误导。

### P20 用颜色定位按钮（坐标不必靠猜）
- 扫全幅找亮绿色像素团取中心，同排其它按钮按固定像素偏移推算。
  ```python
  pred = lambda r,g,b: g>150 and r<120 and b<140 and (g-r)>60 and (g-b)>40
  x, y = find_color_center(r'C:\tmp\a.png', pred)   # 绿色「暂停模拟器」中心
  click(x-343, y)                                    # 实测：关闭 = 绿钮中心 x-343，同 y
  ```
- 🔴 **`min/max` 取中点不抗噪，必须用「x 众数 ± 固定窗」收敛**（2026-09-17 实测踩穿）：
  微信云开发控制台里扫描框 `png x∈[1000,1400], y∈[300,900]` 内除「确定」按钮（**328 像素**）外，
  还有 **2 个游离绿像素**在 `png x≈1390, y≈305`（右上角一个小绿元素）⇒ 中点被从 `1186` 拉到 **`1269`**，
  据此算出的「取消」落在 `1228`（**弹窗外**）⇒ 连点 4 次全落空、弹窗关不掉。
  **最坑的地方**：4 次截图**逐字节相同**（md5 一致），看起来像"窗口不接受输入"（P25 那类问题），
  于是会去怀疑焦点/权限/窗口状态 —— **方向完全错**。事后手工点同一坐标立刻生效，才反证出"是坐标算错了"。
  ```python
  from collections import Counter
  pts = [...绿像素...]
  if len(pts) < 60: return None              # ① 最小像素数门槛：真按钮 328、游离点 2
  xm = max(Counter(x for x,_ in pts), key=Counter(x for x,_ in pts).get)
  sel = [(x,y) for x,y in pts if xm-45 <= x <= xm+45]   # ② 只收众数附近的一簇
  center = (sum(p[0] for p in sel)//len(sel), sum(p[1] for p in sel)//len(sel))
  ```
- **判据要能自证**：定位到按钮后，先确认"点上去画面确实变了"（md5 比对），再往下走；
  否则一次坐标错误会伪装成"应用坏了"。

### P21 Bash 里调 PowerShell 被安全策略拦截
- 曾试图用 `powershell.exe` 截屏失败。→ 走 Python + ctypes/PIL。

### P22 安全软件
- 本机装 360 主动防御 + 金山毒霸，输入注入**曾整体失效数天**。→ **每次代点前先 `selfcheck`**，通了再动用户窗口。

### P23 长跑脚本别用 `| tail`
- 管道缓冲会让你误判"没输出"。→ 不加管道，或把日志写文件。

### P24 同文件多次 Edit 的竞态（顺带记）
- 同一文件在一条消息里发多个 Edit，只有最后一个生效。→ 串行 Edit 或整文件 Write。

### P25 「半死」窗口会骗过 probe：能重绘、能响应悬停，但**不接受点击**
- 现象（微信开发者工具实测，2026-09-16）：工具执行「重新打开此项目」后弹出模态保存框，状态栏显示 `Closing the window is taking a bit longer...`；
  - `probe` 返回 `alive: True`、`hover_diff: True`（鼠标移到按钮上画面**确实变了**）、`IsHungAppWindow = 0`；
  - 但点「保存」（坐标已裁图放大核到按钮中心）**无反应**，按 `ENTER` **无反应**。
- 结论：`hover_diff=True` **只证明"合成鼠标事件进了窗口"，不证明"业务逻辑还活着"**。应用在"关闭/重载项目"的收尾阶段让出了 UI 线程，输入进队列但没人处理（画面由合成器继续重绘）。
- 对策：**别硬怼**（继续狂点可能把它推到真死，只能人工重启）。识别信号 = **状态栏出现"正在关闭/重开"这类进度文案 + 模态点不动** → 立刻停手，把「点哪个按钮」交给人，并在回报里写清"我停在哪一步、你要点哪一个"。
- 反例（同一天、同机、同工具）：普通编译/预览流程里合成点击**完全正常** ⇒ 这不是权限/DPI 问题，是**应用状态**问题。判据要绑"应用正在做什么"，不能绑"上次行不行"。

### P26 微信开发者工具：**不要先 kill GUI 再用 `cli open`** —— 会留下零窗口实例永久占锁
2026-09-16 实测踩穿的完整链条，照着避坑：
1. 菜单「项目 → 重新打开此项目」会触发 **VSCode 系保存冲突**：`未能保存 "settings.json"：文件的内容较新。请将你的版本与文件内容进行比较。`
   （磁盘文件 = `project.private.config.json`，通常已 gitignore）。保存失败 → 关闭流程卡住 → 退回询问框 → **死循环**；此时 `取消/不保存/保存` 三个按钮**全都点不动**（见 P25）。
2. 改文件 mtime **救不了**（改旧、还原都无效；它比的是自己记录的 etag，不是 mtime）。
3. `Alt+F4` **也无效**（它已经在"正在关闭"状态，会吃掉关闭指令）。
4. `taskkill /F /PID <主进程>` 可以杀掉 GUI，但**之后千万别用 `cli.bat open` 去开**：
   CLI 会起一个**零窗口的 IDE 服务进程**（占住单实例锁 + HTTP 端口 35237），
   之后再双击 exe 启动 GUI 只会把请求转发给它 → **永远开不出窗口**，且这个残留进程是**提权**的，`taskkill` 返回"拒绝访问"。
5. 想提权杀它：`wscript` 触发 UAC 这条路**被安全策略当 LOLBin 拦**（`Known Windows LOLBin…`），Bash 调 PowerShell 也被拦。
   ⇒ **只能让人在任务管理器里结束 `微信开发者工具.exe`（必要时用管理员任务管理器），再正常双击启动。**
- ✅ 正确姿势：要"重开项目"就用**菜单**（前提是没有未保存冲突）；要"重启工具"就 `taskkill` 主进程后**用桌面快捷方式/exe 正常启动**，不要走 `cli open`。
- 判定残留实例：`enum_windows` 按 PID 过滤 → **窗口数 0 + 内存"暂缺"/CPU 0** = 已变僵尸服务进程。

### P27 动态表格里「加一行」和「删一行」常是两个不同图标 —— 点错就是**删数据**
微信云开发控制台「添加索引」弹窗实测（2026-09-17）：字段行右侧的图标**不是固定的**——
**第 1 行是 ⊕（加行），最后一行是 ⊖（删行）**。
⇒ 冒烟脚本若写「点最后一行右侧的 ⊕」，**1 行时正常、2 行时点的是 ⊖**：把刚加的字段行删掉，
表现为「提交后弹窗未关」，而你会去怀疑提交按钮 —— 方向完全错。
**对策**：加行恒点**第 1 行**的图标；并在加行后断言「行数 = 原行数 + 1」（用结构判据数行，见 P30）。

### P28 深色 UI 的小字用全屏 1x OCR 会**整格丢字**（假阴性）
同一张截图（微信云开发控制台 · 索引列表）：
- 全屏 1x OCR：`idx_openid` 那行的**名称格整格没被识别**（只读到字段列的 `ogEnid升序`）；
  `idx_user_id` 却"通过"了 —— 因为它被切成 `idXuser` + `id` 两片，拼起来恰好等于期望值。
  ⇒ **通过的那条是巧合，不是判据有效。**
- 对**同一张 png** 改 `--crop 600 370 1400 720 --scale 3`：`_openid_l`、`dx_openid` 都读出来了。
**对策**：判定表格内容一律 **裁切目标列 + `--scale 3`**；
且**匹配要容错**（OCR 常丢首字母：`idx_openid`→`dx_openid`）：
```python
def near(a, b):
    a, b = nz(a), nz(b)                  # nz = 去掉所有非字母数字后小写
    if abs(len(a) - len(b)) > 2: return False   # 🔴 长度差>2 直接否，否则 idx_shop_user 吞掉 idx_shop_user_del
    return difflib.SequenceMatcher(None, a, b).ratio() >= 0.86
```
- ⚠️ 反过来：**判据放宽后必须再验「长名不吞短名」**（本仓有 5 组前缀碰撞，如
  `idx_shop_user` vs `idx_shop_user_del`）。认领式匹配：**长名优先认领 token**。
- ⚠️ **"OCR 读不到" ≠ "不存在"**：MISS 必须留证图（裁切放大后的那张）由人看图定夺。**图片证据 > OCR 结论。**

### P29 弹窗里的 y 必须**每次现读**：同一弹窗有三种"高度状态"
同一弹窗（微信云开发控制台 · 添加索引）实测：
1. **行数**每 +1，底部按钮下移 **65px**（顶部标题/标签不动）；
2. 一旦出现**校验红字**（如「请输入索引名称」），名称行以下整体 **+39px**；
3. 第 1 个字段行 **与「索引字段」标签同行**（标签 y **+4**）—— 我曾把这个偏移抄成 `+43`，
   结果点进了两行之间的空隙、字段名没填进去，而报错说"提交后弹窗未关"，误导排查方向。
**对策**：所有 y 从**当次截图**的 OCR 取；能不用公式就不用。必须用公式时，
写成「相对某个**同帧 OCR 到的锚点**」的偏移（如"确定 = 字段标签 y + 86 + 65×(n-1)"，n 1→434 / 2→499 实测吻合），
并把实测值写进注释，否则下一个人一定会重犯。

### P30 弹窗**背后**的同名文字会污染"弹窗内"的行识别 → 用 **x** 一刀切开
云开发控制台弹窗是**非遮罩式**（背后列表仍被 OCR 读到）：弹窗内的方向控件固定在屏幕 `x≈1093`，
而背后列表的「索引字段」列文字在 `x≈1149~1182` ⇒ **`x < 1130` 即弹窗内**。
只按 y 过滤（如 `y<560`）会同时收进背后列表的行，把行 y 算错。
**通用做法**：找出"弹窗内某元素"与"背后同类元素"的**任一不变差异**（x/颜色/尺寸），用它切分；
切不开时再用「弹窗内元素间的固定几何关系」（如行距 65）反推。

### P31 往输入框粘贴前**先 Ctrl+A + Delete**
残留弹窗里可能已有旧值，直接 Ctrl+V 会**拼出新值**：
实测把 `idx_audit_created` 拼成了 `idx_audit_createdprobe_tmp`。
在"批量自动填表"里，这种拼接**不会报错**，会静默建出一个**名字错的索引**。
⇒ `paste()` 一律 = 点击 → `Ctrl+A` → `Delete` → `Ctrl+V`；并且**开工前先确认弹窗是关的**
（弹窗是模态：没关掉时点背后的「+添加索引」不会生效，而弹窗判据仍为真 ⇒ 你会往**旧弹窗**里填)。

### P32 OCR 会「**稳定地**读错」—— 与「抖动」是两回事，调参救不了

**区分**（处置方式完全不同）：

| 类型 | 现象 | 对策 |
|---|---|---|
| **抖动** | 同一 crop 两次结果不同（`winocr` 偶发整格读空） | 重试 / 换窗口 / `near()` 相似度容错 |
| **稳定误读** | 换尺度、超采样、预处理**全都错成同一个值** | 调参无解 ⇒ 只能**白名单 + 人工图佐证** |

**实测（2026-09-17，微信云开发控制台「索引管理」表）**：字段名 `sort` 被 Windows.Media.Ocr
**12 种读取组合全部**读成 `so戊`/`SO戊` —— 原图 crop ×3/×5/×8/×12、LANCZOS 超采样 6/8/12x、
灰度+自动对比度、反相、Otsu 二值化、固定阈值 128（后两者连 `s/o/r` 都丢，只剩 `戊升序`）。
`so戊` 经 normalize 后 = `so`，与 `sort` 相似度 0.67 < 0.86 ⇒ `near()` 这类容错**永远救不回来**。

**处置三步（缺一不可）**：
1. **判据侧显式白名单**，不要放松全局阈值（放松阈值会引入误匹配）：
   ```python
   OCR_VARIANTS = {'sort': ['so戊', 'so成']}   # 每条都要写清证据出处
   by_var = next((v for v in OCR_VARIANTS.get(name, []) if v.lower() in cell.lower()), None)
   ```
2. **白名单命中必须在输出里点名**（`✅ … （1 项走 OCR 变体白名单: idx_plan_enabled.sort←'so戊'）`）
   —— 静默通过等于把守卫关掉一半。
3. **真值证据 = 人眼可读的放大图**：把该格单独 crop 出来 **10x LANCZOS**，肉眼确认后入库
   （本项目：`review/evidence/index_buildout_20260917/08_sort字段_OCR稳定误读_放大佐证.png`）。
   ⇒ 结论：**图片证据 > OCR 结论**；OCR 读空/读歪时先出放大图，再决定是"数据错"还是"OCR 错"。

⚠️ **白名单属"放宽性设定" ⇒ 必须变异回灌**：把白名单清空（`'sort': []`）用**副本**跑一遍，
必须**转红**（实测 RC=1 + `❌ 缺字段 sort`），否则这条白名单就是无用的装饰。
⚠️ 生成变异副本用 `sed ... > xxx_mut.py`（不动原文件，绕开"沙箱删文件不可靠"）。
⚠️ **Git Bash 路径坑**：`$T/xxx.py` 展开成 `/c/Users/...` 会被 Windows python 当成 `c:\c\Users\...`
（`Errno 2`）⇒ 传参给 Windows exe **一律写显式 `C:/...` 绝对路径**，别用 shell 变量拼。

### P33 「IDE 起不来」先看日志最后一行 —— 它的命是挂在 cli 的 WebSocket 上的

**现象（2026-09-25 实测，连续浪费约 40 分钟）**：微信开发者工具**各种方式都起不来**：
`explorer.exe <exe>` 不放心、`os.startfile` 与 `Popen(DETACHED_PROCESS|CREATE_NEW_PROCESS_GROUP|CREATE_BREAKAWAY_FROM_JOB)`
起窗后 **2–30 秒内消失**；`cli.bat open` 能出窗（`IDE server started successfully, listening on http://127.0.0.1:35237`）
**但 20 秒后又没了**。很容易一路误判成"崩了 / 被安全软件拦了 / 单实例锁残留"。

**真因（一眼可证）**：读
`C:\Users\lzj\AppData\Local\微信开发者工具\User Data\<profile>\WeappLog\logs\<日期>.log`
—— 日志**最后一行**是：

```
[2026-09-25 13:35:58.112+08:00][…][MAIN][WebSocket.<anonymous> …] [CLIWebSocketServer] cli ws client disconnect
```

⇒ **IDE 的存活挂在 cli 的 WebSocket 连接上；cli 一结束，IDE 就退。**
（直接启动的实例**连日志都不写**，日志停在编译器 `SummerProcess` 阶段 ⇒ 这也是"看起来像崩溃"的原因。）

**✅ 续命配方（本仓 `_keep_ide.py`）**：后台循环**反复喂** `cli.bat open --project <repo>`。
- 第 1 轮约 51.7 s（要等 IDE 冷启），**后续每轮仅 2.6–5 s**；
- **实测连续保活 9 分 48 秒 / 30 轮全部成功**，期间可正常截图、点击、操作云开发控制台；
- 判成功看输出含 `IDE server started successfully`；判活着用 `win_gui.py list` 看到顶层窗口（**别用截图判，可能拍早**）；
- 🔴 必须显式给 Bash `timeout: 400000` 且 `dangerouslyDisableSandbox: true`（沙箱里 IDE 起不来）。

**⚠️ 续命的副作用**：高频 `cli open` 会让项目**反复重载** ⇒ 模拟器反复卡死、反复弹「模拟器长时间没有响应」（见 P35）。
⇒ **只在自己要连续操作 GUI 的那段时间开循环，操作完立刻停**。

**纪律**：以后凡是"目标程序起不来"，**先找它的日志最后一行**再动手（呼应 P26：那条也是"先 kill 再用 cli open"的顺序问题）。
**"起不来" ≠ "被锁了"**，两者处置方式完全相反。

### P34 两套 DPI 坐标口径 + PrintWindow 主题失真 —— 点击坐标只能有一个来源

**同一天连踩两次，都是"点不中"，成因不同**：

| 来源 | 返回的坐标系 | 实测值（150% 缩放） | 能不能喂 click |
|---|---|---|---|
| `win_gui`（自带 `set_dpi_aware`）`rect/list` | **物理像素** | 1920×1500 | ✅ 与全屏 PNG 一致 |
| 裸 ctypes `EnumWindows`+`GetWindowRect`（临时探查脚本） | **逻辑像素** | 1280×1000 | ❌ 差 1.5 倍 |
| `screenshot_window`（**PrintWindow**） | 图内像素 | 主题/尺寸都可能与屏幕不同 | ❌ 只可"读" |

- **两套口径混用必偏**：我用裸 ctypes 拿到的窗口矩形推屏幕坐标，再和自己写的"物理像素全屏 PNG"混着算 ⇒ 整体偏 1.5 倍。
- **PrintWindow 会换主题**：实测 `screenshot_window` 出的图是**浅色主题**，而真实屏幕是**深色**；连窗口尺寸也不等于屏幕上的尺寸。
  我在它的 PNG 上量到 ∞ 图标 png x≈1386 ⇒ 推屏幕 (1431,24) ⇒ **连点四五次全空**；改用全屏 PNG 量得 **(1429,25)** ⇒ 一次命中。

**✅ 规矩（写死到肌肉记忆）**：
1. **点击坐标只从 `screenshot_screen`（或 `PIL.ImageGrab.grab()`）的全屏 1:1 物理 PNG 上取**（OCR 中心 / 像素簇实测）；
2. **窗口 PNG（`screenshot_window`）只用于"阅读内容"**，绝不用于量坐标；
3. 需要窗口内定位时：`crop(rect)` 后再量，**且 rect 必须来自 `win_gui`（物理口径）、每次现取**；
4. **别自己写裸 ctypes 探查窗口几何** —— 要几何就用 `win_gui`，两套混用是最隐蔽的坑（编译不报错、运行不报错，就是点不中）。

### P35 模态框会"吃掉"点击，而 `frames_hash` 仍在变 ⇒ md5 只可证否，不可证成

**现象（2026-09-25 实测）**：连点工具栏 `∞` 四五次想开云开发控制台，**每次 hash 都"变了"**（于是判"点了、界面在动"），
但控制台窗口**始终不出现**；截图看才发现屏上压着一个模态框：

> 「**模拟器长时间没有响应**，请确认您的业务逻辑中是否有复杂运算，或者死循环」—— 按钮：关闭 / 终止模拟器 / 暂停模拟器

模态框挡住了工具栏 ⇒ **点击落在框上**；而框后面模拟器在重绘 ⇒ **hash 一直变** ⇒ 判据被骗。

**✅ 破法**：
1. **先 OCR 定位模态框按钮并点掉**（实测「关闭」≈(812,241)、「终止模拟器」≈(963,241)）——根治手段是停掉 P33 的续命循环（它在逼项目反复重载）；
2. **"点中了" 的唯一有效判据 = 目标窗口真的出现**：
   `find_window(title='云开发控制台')` 返回 hwnd（或目标控件出现在截图里），**而不是 hash 变化**。

**⚠️ 对 P22 那条"每次点击后比 md5"的修正（重要）**：
> md5/hash 的正确用法是**单边**的 ——
> **相同 ⇒ 肯定没动**（强判据，可放心判"点击无效/界面无反应"）；
> **不同 ⇒ 只说明"有东西在动"，不说明"你点的那个东西动了"**（背景重绘、光标闪烁、进度条都能让它变）。
> ⇒ 证否用 hash，**证成必须用"目标物体的存在性/状态"**（窗口出现、控件文案变化、JSON 出参）。
