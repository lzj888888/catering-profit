## 三、⚠️ 必须纠正：「1 套账套」的语义

**裁定：账套 = 店铺维度，不是月份维度。**

| 理解 | 后果 |
|---|---|
| ❌ 账套 = 1 个月份账 | 用户第 2 个月就无法记账 → 产品直接废掉 |
| ✅ **账套 = 1 家店铺** | 免费用户只能给 1 家店记账，该店月份数据不受限；想给第 2 家店 → 触发付费 |

→ **开发口径**：`shop` 表计数，免费用户 `is_deleted=false` 的店铺数上限 1；`shop_monthly_account` 月份数**不限制**。

### 3.2 M3 导出策略（v1.3 调整：全部禁止）

**免费用户禁止所有导出（含单张 PDF），仅付费后解锁。**

| 方案 | 后果 |
|---|---|
| ❌ 单张免费（v1.1/v1.2 方案） | 免费用户录入 3 张卡即可打印贴后厨，付费动力弱 |
| ✅ **全部禁止（v1.3 采纳）** | 免费仅作"尝鲜录入"，导出一律付费 → 转化点更靠前、更清晰 |

## 四、⭐ 专业模式付费墙 —— 详解（与 M1 收费不冲突）

**一句话**：它不是"第二道墙"，它就是"买了套餐之后解锁的东西"里最值钱的一项。

| 付费解锁项 | 价值 |
|---|---|
| 账套不限（1 → 多店） | 中 |
| 导出全开 | 中 |
| **专业模式**（全要素利润 + 库存倒轧 + 连锁重算） | **🔴 高（真正的付费理由）** |

**没有专业模式，付费就只剩"多存几家店 + 能导出"—— 这两样撑不起 25.9 元/月。**

### 完全不违反解耦原则

业务代码**仍然只读 `expire_at` 一个字段**：

```
expire_at 为空 / 已过期  →  免费档：1 账套 + 经营参考口径 + 禁导出
expire_at 有效（未过期） →  付费档：账套不限 + 专业模式解锁 + 导出全开
```

"专业模式"只是"付费档"状态下同时放开的**一个能力位**，与"账套不限""导出全开"是同一批解锁的兄弟，**不是额外一道独立收费**。

| 口径 | 含义 | 谁用 |
|---|---|---|
| **经营参考利润** | 消耗按**老板直接填写**的数字算（快、粗） | 免费用户 |
| **专业模式·全要素真实利润** | 消耗用**库存倒轧**算（期初+采购-期末=真实消耗）+ 连锁重算 | 付费用户 |

→ **⚠️ UX 防流失要求**：免费 M1 页面必须明确标注"当前为经营参考估算，开通专业模式可查看库存倒轧真实利润"，让用户感知口径差异、引导转化。

> **功能真实性确认（回应豆包核心疑问）**：专业模式 / 库存倒轧**不是商业化凭空加的付费话术，是 M1 模块真实存在且已排期的核心算法**——M1 规范"双利润口径并存"（第 12 行）、库存开关倒轧（第 26/31-32 行）、POC3 双利润引擎（已 Node 验证 12/12 锚点：S1=9160、S2 经营参考=9160/全要素=3476.67/差异=5683.33）、M1.4 专业模式连锁重算（已拍板 14:52）均有据可查。**库存倒轧依赖的「期初/采购/期末」三数，由 M1 内「库存开关」开启后录入（轻量模式，非独立库存模块）**，数据链路完整，不影响功能落地。

## 五、套餐体系（采纳 PRD 四档，纯时效制）

### 通用时效规则

- 全部按**支付成功后顺延自然日**计算，**不按自然月**
- 月包 31 天｜季包 90 天｜年包 365 天

- **一次性套餐到期自动停权，无自动续费**；仅"按月自动订阅"为微信原生自动扣费

## 六、付费弹窗触发逻辑（采纳 PRD）

- **M2 选址沙盘：永不弹付费窗**
- M1 / M3 **共用同一个全局付费弹窗组件**
- **只有两类动作会触发弹窗**：
  1. **保存超限**：M1 已有 1 个账套，点【新建账套】→ 弹窗；M3 已有 3 张卡，点【新建成本卡】→ 弹窗
  2. **导出动作**：点导出报表 / 单张或批量导出成本卡 → 弹窗
- **不触发**：进入页面、录入、修改、在线试算预览
- 弹窗关闭 → 停留在当前页，不执行新建/导出
- **后端必须二次权限校验**，防止前端绕过

## 七、架构解耦要求（采纳 PRD）

### 前端
- 付费弹窗 = **独立全局组件**；M1/M3 业务页**不嵌入支付逻辑**
- 套餐名称 / 价格 / 文案 / 是否展示 **全部由后端接口返回，前端禁硬编码**

### 后端（⭐ 关键简化）
- 业务模块（M1/M2/M3 算账逻辑）与收费模块**完全解耦**
- **业务鉴权只读一个字段：用户权限到期时间 `expire_at`**
- 业务代码**不判断套餐类型、价格、周期**
- 支付成功回调**只做两件事**：生成订单记录、更新 `expire_at`
- 扩展性：后续增删套餐 / 调价 / 换整套收费模块，**M1/M2/M3 核算业务代码无需改动**

### 用户体系与数据规范（采纳 PRD）
- 用户主键 **自建雪花 ID `user_id`**；`openid` / `unionid` 映射绑定
- **M2 支持静默登录**；M1/M3 保存数据时请求头像昵称授权，**不强制手机号**
- 主体信息 / 隐私协议 / 客服信息**后台可配置**，禁硬编码
- 微信商户号 / 证书 / 密钥 **独立配置文件**，与业务代码分离
- **订单表独立存储、永久保存**；更换商户号不丢历史订单
- 数据库定时自动备份，后台支持手动导出对账

## 十、⭐ 生命周期与边界规则（硬约束）

### 10.1 会员到期后的数据处理
- 会员到期 → 权限自动回落至「免费档」（`expire_at` 失效即触发），但**历史业务数据全部保留，绝不自动删除**
- 到期状态：不能新建（账套/成本卡超限即拦截）、不能导出；但**旧数据可查看、可编辑**
- 再次购买 → `expire_at` 更新，权限立即恢复，数据完好无丢失
- 数据默认**永久保存**，不因过期自动清除
- 仅两种清理场景：① 用户主动注销账号（含二次确认 + 冷静期）；② 系统判定违规刷数据（需人工复核）
- 免费额度（M1 1 店 / M3 3 张）**不定时重置**，基于「当前有效保存数量」实时判定

### 10.2 退款场景
- 退款成功 → 权限立即收回，回到未付费状态（`expire_at` 按退款规则处理，不返还已用时长）
- 用户业务数据**不删除**，仅重新锁定「新建 / 导出」
- 订单状态标记「已退款」，留存对账；退款流水与原始订单关联（见 `order_refund` 表）

### 10.3 时区 / 时间校验（防篡改）
- 到期时间以**服务端 UTC 时间**为准，转北京时间（UTC+8）计算展示
- **严禁使用前端本地时间**判定有效期（防止用户改手机时间篡改）
- 前端展示的「剩余天数」由服务端下发，前端只渲染，不自行计算
- 续费 / 购买成功时间戳以支付回调服务端时间为准

### 10.4 后台管理员手动调整有效期
- 运营后台可人工给用户增减有效期（客服补发时长、补偿场景）
- 通过 `shop_subscription.source = 'manual'` 记录，与支付来源区分
- 手动调整仅改 `expire_at`，不触碰业务数据，触发即生效
- 操作留痕（操作人 + 时间 + 原因），供审计

### 10.5 跨端多设备登录数据同步
- 同一微信 `openid`（及 `unionid` 映射）多设备切换登录，数据**实时同步**
- 云端为单一数据源，本地仅缓存；换设备 / 重装不丢数据
- 并发编辑冲突以「服务端最后写入」为准，关键操作带 `client_request_id` 幂等
- 静默登录（M2）与授权登录（M1/M3）共用同一用户身份

### 10.6 ⚠️ iOS 自动订阅合规（多端差异）
- 苹果 App Store 审核指南要求：iOS 端数字商品自动续费必须走 **Apple IAP**（抽成 30%）
- **微信小程序在 iOS 端不展示「按月自动订阅」套餐**（19.9 自动订阅仅安卓 / 鸿蒙端展示）
- iOS 端仅展示一次性套餐：**月包 25.9 / 季包 69 / 年包 199**
- 安卓 / 鸿蒙端：四档全展示（含自动订阅）
- 前端按 `platform` 字段动态决定自动订阅入口显隐，**禁硬编码**

### 10.7 ⚠️ iOS 微信小程序支付通道实测与降级引导（v1.4 新增 · 工程风险）
- **风险事实**：苹果要求 iOS 数字商品自动续费走 IAP；且**微信小程序在 iOS 端对虚拟商品微信支付本身受限**——若 iOS 端连一次性套餐的微信支付都无法调起，则 iOS 用户将**完全无法付费**。
- **开发前必测**：iOS 微信小程序调起微信支付（一次性套餐）是否可用，以真机实测结论为准，不臆测。
- **降级方案（按实测结果触发）**：
  1. 若 iOS 一次性支付可用 → 维持 10.6（仅隐藏自动订阅）；
  2. 若 iOS 一次性支付不可用 → ① 该端展示「请到安卓手机 / 扫码在网页购买」引导；② 跳转 **H5 购买页**（H5 不受小程序 iOS 虚拟支付限制）；③ 或评估接入 Apple IAP（抽 30% 且需额外开发，作为最后手段）。
- 前端按 `platform` 动态显隐支付入口，并**预留 H5 购买跳转入口**，不硬编码。

### 10.8 私域冷启动的手动退款流程（v1.4 新增）
- 当前 `enable_real_payment=false` 阶段走私域收款（如微信转账）+ 后台 `source=manual` 发权益。
- **手动退款流程**：用户申请 → 运营后台核实订单与诉求 → 原路或线下退还款项 → 标记 `order_refund` 状态「已退款」并收回 `expire_at` → 留痕（操作人+时间+原因）。
- 私域退款**不自动调支付接口**，纯人工流程，需有台账登记，与线上自动退款（10.2）分流处理。

### 10.9 支付回调幂等性（v1.4 新增）
- 支付成功回调**必须按 `transaction_id` 去重**，防止微信重复通知导致重复延长 `expire_at`。
- 回调处理前先查订单状态，已处理则直接返回成功，不重复执行延期逻辑。
- 与前端 `client_request_id` 幂等互补（前端防重传、后端防重复回调）。

### 10.10 已过期用户重新购买的有效期起点（v1.4 新增）
- **明确边界**：已过期后重新购买，有效期从「**当前支付成功时间**」起算，**不顺延原到期时间**。
- 仅「会员**有效期内**续费」才累加（见五·通用时效规则）；过期后属于「新购」，重新起算。
- 示例：原到期 9-10，9-20 重购月包 → 新到期 10-21（从 9-20 起 31 天），**不是** 9-10+31=10-11。

### 10.11 软删除不占免费配额（v1.4 新增）
- M3 成本卡、`shop` 账套的**软删除（`is_deleted=true`）不计入免费配额**实时判定。
- 免费限额按「`is_deleted=false` 的有效数量」判定（与 10.1、第八章 `shop` 表说明一致）。
- 避免用户误删后配额被占、需联系客服的体验问题。

### 10.12 发票 / 凭证流程（客服侧）（v1.4 新增）
- 当前阶段（私域收款）无自动开票；用户索要发票 → 客服登记需求 → 执照下来、接入商户号后由系统/财务统一开具，或走电子发票线下流程。
- 订单表永久保存（第七章）支撑开票对账；`order_refund` 关联原单支撑红冲。
- 前端提供「申请发票/凭证」入口，提交后进入客服工单，**不阻塞购买流程**。
