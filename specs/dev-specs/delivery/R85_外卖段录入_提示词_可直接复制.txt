## 2. 完整需求

### 2.1 铁律：后端零改动

- ❌ **不许**修改 `cloudfunctions/` 下**任何**文件（含新增）。`cloudfunctions/common/` 是批次 0 冻结地基，只能调用。
- 外卖组提交时，仍按**现有契约**写入：`category='takeaway'`，`sub_items` = **4 行**（美团外卖 / 淘宝闪购 / 京东外卖 / 其他外卖），每行一个 `amount_fen`（= 该平台小计）。
- **分项的三个明细数（商品总价 / 打包费 / 商家活动补贴）v1.0 不落库**，只参与**本页当场计算**（小计 + 自动带出 + 配平校验）。留证走本地草稿（见 §2.6）。

### 2.2 收入侧 · 外卖组「快速 / 分项」模式开关（严格互斥二选一）

复用堂食 `dineMode` 的**全部既有约定**（照抄，不要另立一套）：
- 模式只存本地：`wx.setStorageSync`，键含 `shop_id`（与 `dineModeKey()` 同法）；换设备/清缓存回默认。
- 默认值**由数据推断**：该组细项行 > 1 ⇒ 分项，否则快速。
- 切换时**快照恢复**：分项→快速 保留分项快照；快速→分项 用快照回填（堂食 `dineDetailRows` 同法）。
- 两个模式**不并存**（互斥单选），因此**不需要**「分项之和 == 总额」这类校验。

| 模式 | 客户要填 | 落库 |
|---|---|---|
| **快速录入**（默认） | 4 个平台各 **1 个**金额框（**现状已有，保留**） | 该数直接作为该平台 `amount_fen` |
| **分项录入**（可选） | 4 个平台各 **3 个**框：`商品总价` / `打包费` / `商家活动补贴` | **三者之和**作为该平台 `amount_fen`（小计自动、不可手填） |

- 平台名与顺序**严格取自** `terms.js::ledger.income[takeaway].items`，**页面禁止写死任何平台名**。
- 营业口径提示（页面文案，走 i18n）：这"一个数" = `商品总价 + 打包费 + 商家活动补贴`；
  ❌ 不是顾客实付 / ❌ 不是银行卡到账 / ❌ 不是账单「商家应收款」；
  ⚠️ **佣金、配送费不要在这里扣**（扣了就成净额，与总额法冲突，且费用侧会无事可填）。

### 2.3 每个金额框旁的「可粘贴」入口（v1.0 就做）

- 从平台账单 Excel 选中一列 → 复制 → 粘进粘贴区 ⇒ 系统**只提取数字并求和**，填入对应金额框。
- 必须**自动跳过**：表头文字、空单元格、说明列。
- 含「合计 / 总计」字样的行 ⇒ **弹确认**（防把已算过的合计再加一遍）。
- **原始粘贴内容留存可回溯**（出错能查）—— 存本地草稿即可，不进数据库。
- 🔴 **不会粘贴的商家照旧手写**：金额框直接写合计数即可。**粘贴是加速器、不是必经路径** ——
  两条路必须都通；**不得**把粘贴做成唯一入口，也不得让粘贴失败时无法手填。

### 2.4 费用侧 · 营销「外卖活动补贴」自动带出

- 分项模式下各平台填的「商家活动补贴」，**求和后自动带出**到费用侧营销类的
  `外卖活动补贴`（`item_key = exp_mkt_takeaway_subsidy`，`sort_order = 30`）。
- 带出后**允许用户手动改**（改了不再被覆盖；除非他再动收入侧的分项值）。
- 「同一笔钱只填一次」：收入侧已含这笔补贴，费用侧带出的是**同一笔**（用于配平时相抵），
  不要理解成"多记一笔费用"——具体口径见规范 §A.11.4(b)。
- 佣金 / 配送服务费 / 配送补贴 / 推广费 / 团购平台佣金：**手填或粘贴，不自动带出**。
- ⚠️ 页面必须对 **`外卖推广费`**（`sort 50`）**单独标注取数路径**：它**不在结算单里**，
  在「推广中心 · 消费明细」，钱从推广账户余额单独扣。**只对结算账单核对一定漏，利润会虚高。**

### 2.5 配平校验（**只做软提示**）

- 收入侧外卖组内新增**选填**框：`账单商家应收款`（客户从平台账单抄一个数）。
- 机器近似校验式（页面实际跑的那条）：

  `应有商家应收款 ≈ 外卖收入合计 − 商家活动补贴 − 佣金 − 配送服务费 − 配送补贴`

  与客户填的实际值比对：
  - **差额 ≤ 50 元**：通过，提示"两侧一致，说明收入与费用都填全了"。
  - **差额 > 50 元**：提示"差 X 元，可能漏填了某项扣款"，并列出常见漏项（**推广费 / 商家配送补贴 / 违规扣款**）。
  - **专项检测**：差额**恰好等于**客户填的打包费金额 ⇒ 提示"差额与打包费金额相等，请核对账单『商品总价』是否已含打包费"（**本方案特有风险**），而不是笼统报"填错"。
  - **不得误报的情形**：若某平台把「用户支付配送费」计入商家应收款（商家自配送常见），差额会**稳定等于该笔配送费** ⇒ 提示"可能是用户配送费未纳入"，**不得判为填错**。
- 🔴 **纪律（不可违反）**：规范 §A.11.7 的 V1–V3（账单列名、打包费是否已含、商家应收款定义）**尚未经真实账单验证**
  ⇒ 配平校验**只做软提示**：**不阻断保存、不参与利润计算、不写入任何金额**。
  最坏结果只能是"多一句提示"，**绝不能影响存进去的钱**。
- 校验用**前端算法**实现；**禁止**为了这个校验去改云函数或新增接口。

### 2.6 本地草稿与留证

- 分项明细、粘贴原文、账单商家应收款 ⇒ 全部进 `DRAFT_KEY`（本页已有草稿机制）随页面草稿一起存本地，
  **不进数据库**。草稿键与现有 `draft_month_input_<month>` 机制保持一致（如需扩展，扩展键名，不要改动已有键语义）。

## 3. 强制遵守

1. **文案零硬编码**：所有新增可见文案（模式标题、按钮、提示、口径句、placeholder）一律走
   `miniprogram/i18n/terms.js`，页面里只留 `{{t.xxx}}`。**判定时先剥 `<!-- -->` 注释再查**（项目既有口径）。
2. **渠道/平台名零硬编码**：平台名只从 `terms.js::ledger.income[takeaway].items` 取；营销项名只从
   `collections.js::SEED_EXPENSE_ITEMS(marketing)` 的单源取，**不得在页面里再列一遍**。
3. **术语双副本逐字一致**（守卫 K11 强制）：改了 `miniprogram/i18n/terms.js`，**必须同步**
   `specs/dev-specs/i18n/terms.js`，两份**逐字相同**（改完自己 `md5`/`diff` 核对）。
4. **新增自测文件必须登记**（守卫 R67 强制）：若新增 `selftest_*.js` 之类自测脚本，**必须**同时把它登记进
   `verify_all.js` 的 `SUITES`，并同步该文件**头部的套件数注释**（当前为 **87**，登记后 +1 ⇒ **88**）。
   —— 这是**纪律要求的例外**：允许你改 `verify_all.js` 的这一处登记区与头部计数，**别处不许动**。
5. **复用既有模式**：外卖模式开关照抄堂食 `dineMode` 的存储/推断/快照恢复约定，**不要另立一套**；
   堂食已有行为**不得回归**（切模式、合计自动、渠道行渲染逐项保持不变）。
6. **金额单位**：前端展示「元」，提交前转「分」整数（沿用现有 `api.yuanToFen/fenToYuan`）。
7. **加行/删行/改名**：外卖组的 4 个平台是**预设项**，名称固定、**不给删除键**（与堂食预设渠道同口径，G10j/G11d 守）。
