## 0.1 部署提醒（本批**不改** `cloudfunctions/common/`）

本批**不新增 / 不修改任何 `common/` 下的文件** ——
`ENGINE_VERSION` 常量放在**引擎源** `cloudfunctions/calcSandbox/service.js`，**不是** `common/indicatorRef.js`
（放 `common/` 会牵动全部函数的派生副本 `cx_indicatorRef.js` ⇒ 要重部署 43 个函数，成本不可接受）。
⇒ **不需要**跑 `node tools/sync_common.js`，也**不需要**重部署其它云函数。只部署**新增的两个** `savePlan` / `getPlan`。

> ⚠️ 两个函数是**新部署** ⇒ 部署后 `timeout` 默认 **3**，必须回读 `info` 抬到 **20**。
> ⚠️ `-r` 参数铁律照旧（`cli.bat cloud functions deploy --names <单个函数名> -r`，**一次一个**）。

## 0.2 四条红线（违反任一条即整批退回）

1. 🔴 **`calcSandbox` / `calcSandboxReverse` 任何一行不动** —— 现有 `cloudfunctions/calcSandbox/service.js` **逐字节不改**；
   本批只**新增**两个云函数目录，并**给引擎源加一个 `ENGINE_VERSION` 常量**（只加常量，不改任何计算）。
2. 🔴 **`savePlan/service.js` 必须是 `cloudfunctions/calcSandbox/service.js` 的逐字节副本**（`md5` 相等，含新加的 `ENGINE_VERSION`）。
   原因：云函数**不能跨包 `require`**（本仓既有约束），而 `savePlan` 要在**服务端**算出结果快照。该引擎是**零依赖纯函数**，所以可以做到逐字节副本。
3. 🔴 **`param_json` 一律 `snake_case`，14 个字段一个不能少**（清单见 §2）。
   我方实测反例：写成 camelCase ⇒ 目标月营收从 `10600000` 分**直接崩成 `null`**（不是"差一点"）。
4. 🔴 **只 INSERT 不 UPDATE**（版本化只增）：每次保存**新建一条**，绝不改旧记录，旧版本走**软删**。

## 2. 数据模型（`shop_sandbox` 集合**已存在**，本期**只加字段**）

### 2.1 新增字段（6 个）

| 字段 | 类型 | 说明 |
|---|---|---|
| `sandbox_id` | STRING | **逻辑沙盘 ID**（同一沙盘的多个版本**共享**它） |
| `version` | INT | 版本号，同 `sandbox_id` 内从 1 递增 |
| `sandbox_type` | STRING | `'site_select'`（选址）/ `'biz_sim'`（经营推演） |
| `param_json` | OBJECT | **全量入参**（14 字段，见 §2.2） |
| `result_snapshot_json` | OBJECT | 结果快照（**只作展示缓存，绝不参与计算**） |
| `engine_version` | STRING | 产出该快照的引擎版本 |

> 旧平坦字段（`fixed_rent` / `var_food_rate` / `target_profit` …）**降为历史只读兼容**，**新记录一律留空**。

### 2.2 `param_json` 形状（🔴 **14 个字段一个不能少** · 一律 `snake_case`）

```json
{
  "mode": "forward|reverse",
  "city_tier": "tier23", "biz_type": "dining",
  "build_items": [], "fixed_items": [], "var_items": [],
  "gross_margin_pct": 65, "target_profit_fen": 1500000, "expected_revenue_fen": 0,
  "rev_price_fen": 4500, "seats": 20, "open_days": 30,
  "target_rent_rate": 12, "pixel_eff_fen": 4000
}
```

### 2.3 `param_json` → 引擎入参 `clean` 的映射表（🔴 **唯一转换处，只在服务端**）

⚠️ 引擎入参 `clean` 是**混合命名**（这是既有实现，别改）：
`cityTier`/`bizType`/`buildItems`/`fixedItems`/`varItems`/`grossMarginPct`/`targetProfitFen`/`expectedRevenueFen` 是 **camelCase**，
`rev_price_fen`/`seats`/`open_days`/`target_rent_rate`/`pixel_eff_fen` 是 **snake_case**。

| `param_json`（存库 · snake） | 引擎入参 `clean` |
|---|---|
| `mode` | `mode` |
| `city_tier` | `cityTier` |
| `biz_type` | `bizType` |
| `build_items` | `buildItems` |
| `fixed_items` | `fixedItems` |
| `var_items` | `varItems` |
| `gross_margin_pct` | `grossMarginPct` |
| `target_profit_fen` | `targetProfitFen` |
| `expected_revenue_fen` | `expectedRevenueFen` |
| `rev_price_fen` | `rev_price_fen` |
| `seats` | `seats` |
| `open_days` | `open_days` |
| `target_rent_rate` | `target_rent_rate` |
| `pixel_eff_fen` | `pixel_eff_fen` |

🔴 **前端不得做这个转换**（本仓铁律：转换只在 DataAdapter / 适配层，业务层禁混用命名）。

## 3. 云函数 `savePlan`（保存 / 复制 / 软删 · **写**）

### 3.1 目录结构

```
cloudfunctions/savePlan/
  index.js          ← Controller：鉴权 → 校验 → Service → 返回
  service.js        ← 🔴 calcSandbox/service.js 的【逐字节副本】（含 ENGINE_VERSION）
  paramMap.js       ← §2.3 映射表（param_json → clean），唯一转换处
  validate.js       ← 本函数入参校验（形状 + 命名口径 + 必填）
  selftest.js       ← 自测（§7）
  common.js + cx_*.js  ← 由 node tools/sync_common.js 生成（照其它函数的既有做法）
  package.json
```

### 3.2 入参 / 出参

```js
// 入参
{ shop_id, plan: { sandbox_id?, name, sandbox_type, param_json, is_copy?, _delete? }, client_request_id }
// 出参
{ plan_id, sandbox_id, version }
```

### 3.3 流程（逐条照做）

```
1. 鉴权：resolveAuth(ctx, db) → 取 userId；assertShopOwner(db, shop_id, userId) → 非店主即 FORBIDDEN
2. 幂等：if (client_request_id) { const prior = await common.idempotency.findPriorResult(db, shopId, client_request_id);
                                   if (prior) return ok(prior); }        // 重复调用直接返回首次结果
3. 校验：validate.js —— 形状 + §2.2 的 14 字段 + 命名口径（出现 camelCase 键 ⇒ INVALID_PARAM）
4. 分支：
   4a. plan._delete === true  → 软删：该 sandbox_id 全部版本 is_deleted=true + delete_at=now
   4b. is_copy === true       → 复制：新 sandbox_id（服务端生成），version = 1
   4c. 有 sandbox_id          → 新版本：version = 同 sandbox_id 的 max(version) + 1
                                🔴 同 sandbox_id 的【旧版本软删】（is_deleted=true + delete_at=now）
   4d. 无 sandbox_id          → 首次保存：新 sandbox_id（服务端生成），version = 1
5. 快照（🔴 服务端算，不接受前端传入）：
     const clean = paramToClean(plan.param_json);
     const snapshot = calcSandbox(clean);
     if (clean.mode === 'reverse') snapshot.reverse = calcSandboxReverse(clean);
     const engineVersion = E.ENGINE_VERSION;      // 来自内联副本
6. 写库：🔴 db.add()（**绝不 update**），一条新记录
7. 审计登记（🔴 与第 2 步【同源键】）：common.audit.writeAudit(db, { action: 'SAVE_PLAN', operator_type: 'user', ... })
8. 返回 { plan_id: sandbox_id, sandbox_id, version }
```

🔴 **幂等两处的键必须同源**（都走单源 `shopKey()`）—— 各自拼字符串会出现"登记了却查不到"的**静默失效**。

### 3.4 惰性清理（顺手做，不新增定时器）

读 / 写路径上，顺手清理**同 `sandbox_id`** 中 `delete_at` **超期**（> 30 天）的旧版本（物理删）。
零新增云函数、零定时器。

## 4. 云函数 `getPlan`（列表 / 详情 · **读**）

### 4.1 目录结构：同 `savePlan` 的 `index.js / validate.js / selftest.js / common.js + cx_*.js / package.json`
（**不需要** `service.js` —— 只读，不重算、不写快照）

### 4.2 入参 / 出参

```js
// 入参
{ shop_id, plan_id?, version? }        // plan_id 即 sandbox_id；缺 plan_id ⇒ 返回列表
// 出参
{ list: [ { sandbox_id, version, name, sandbox_type, param_json, result_snapshot_json, engine_version, updated_at } ] }
```

### 4.3 流程

```
1. 鉴权：同 savePlan（resolveAuth + assertShopOwner）
2. 校验：plan_id / version 类型（缺省即列表）
3. 查询：
   3a. 列表：查该店 is_deleted=false 的记录，按 sandbox_id 分组取【各 sandbox_id 的最大 version】
       🔴 必须有【显式上限】（单源 common/dataAdapter.js::LIST_LIMIT）
   3b. 详情：按 shop_id + sandbox_id + version 取【单条】
4. 返回（🔴 不重算 —— 重算归前端在详情/对比时另调 calcSandbox）
```

⚠️ **不要**在 `getPlan` 里重算：重算会拖慢列表。快照只用于列表卡片快速渲染，**点进详情 / 对比时才重算**。

## 7. 自测要求（`selftest.js`，两个函数各一份）

必须用**生产引擎**（内联副本 / `require('../../cloudfunctions/calcSandbox/service.js')`）实跑，**复现以下数字**：

| 组 | 断言 |
|---|---|
| **① 旧锚点回归（正算）** | `660000 / 17000 / 21000 / 38000 / 50% / 76000 / 106000 / 44 个月`（M2.10 标准工况） |
| **② 往返无损** | `param_json`(snake) → `clean` → `calcSandbox` ⇒ 与首次出参**逐字段 JSON 全等**；反推组同（`R=100000 元` / `房租上限 12000` / `日均客流 74.07` / `翻台 3.70` / `面积上限 300 ㎡`） |
| **③ 反例（必须有）** | ① `param_json` 误用 camelCase ⇒ 目标月营收 **`null`**（不是 10600000）；② 反推漏 `seats` ⇒ 翻台 **非有限值（`Infinity`）**；漏 `pixel_eff_fen` ⇒ 面积上限 **`null`** |
| **④ 边界** | 边际贡献率 ≤ 0（红警）⇒ R 与**全部**派生量 `null`（不编造） |
| **⑤ 副本保真** | `savePlan/service.js` 与 `calcSandbox/service.js` **md5 相等** |

> 🔧 **勘误（2026-10-06 验收时修）**：③-② 原写「漏 `seats` ⇒ 翻台 **`null`**」——**表述有误**，实测为
> **非有限值 `Infinity`**。机理：`seats` 缺失 ⇒ 引擎 `num0(undefined) = 0` ⇒ `turnRate = 月客流 / (0 × open_days)` ⇒ 分母 0。
> 误写来源：我方参考实现 `recalc_anchors.js` 的**打印**用了 `JSON.stringify()`，而 `JSON.stringify(Infinity) === 'null'`
> （该文件断言本身是对的：`Number.isFinite(...) === false`）。⇒ **引擎行为一直正确**，错的是本文档表述；
> 交付方（快马）按"非有限值"实现并经我方复算确认，**无需改代码**。

参考实现：`review/evidence/r229_m2_multiplan/recalc_anchors.js`（我方已跑通 **24/24**，可直接照搬其输入构造）。
