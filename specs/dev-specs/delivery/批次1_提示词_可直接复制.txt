# 批次 1 / 8 · POC3 双利润引擎算法（云函数）

## 1. 批次定位
第 1 批，基于批次 0 的地基（已自带鉴权/错误码/时间工具）开发**业务算法**。
**核心目标**：实现月度双利润计算引擎。这是 **M1 付费墙的核心价值支柱**——算飞了，付费用户拿到的"真实利润"不准，整个付费逻辑就塌了。

## 2. 完整需求

实现一个云函数 `calcMonthlyProfit(input)`：

```
calcMonthlyProfit(input) → {
  营业收入, 食材成本, 菜品毛利, 毛利率,
  经营参考利润, 全要素真实利润, 两利润差异
}
```

**摊销金额本次由外部传入一个数**（摊销算法在第 2 批，本批不实现）。

### 开关来源（防前端篡改）
- ⚠️ **库存开关、摊销开关的状态，优先从 `shop_switch` 表读取（服务端权威），前端传入的值仅作参考**。最终计算口径以服务端读取的开关为准，避免前端篡改开关绕过计算逻辑（例如关掉库存开关让倒轧值失效）。

### 规则
1. **毛利铁律**：`菜品毛利 = 营业收入 − 食材成本`。食材成本**只含食材耗材**；房租/人工/水电属于**费用**，不算进营业成本。
2. **食材消耗两种取数**：库存关闭→直接取用户填的总消耗；库存开启→倒轧 `真实消耗 = 期初存货 + 本期采购 − 期末盘点`。
3. **两个利润口径**：
   - 🟢 `经营参考利润 = 营业收入 − 总费用 − 【直接填的总消耗】`（不含摊销）
   - 🔵 `全要素真实利润 = 营业收入 − 总费用 − 【真实消耗】 − 当月摊销总费用`
   - `两利润差异 = (真实消耗 − 直接填消耗) + 当月摊销`
4. **⚠️ 口径锁（本批核心考点）**：**即使开启库存开关，「经营参考利润」仍必须使用「直接填的总消耗」，不能改用倒轧值**。只有「全要素真实利润」才用倒轧值。这是**刻意设计，不是 bug，不要"修正"它**。
5. **待结算不进利润**：外卖/团购待结算金额是现金流指标，绝不进入毛利或利润。

### 测试数据

**场景 S1（库存关、摊销关，2026-07）**
- 收入：堂食现金 8,000 / 堂食微信支付宝 25,000 / 堂食储值消费 5,000 / 堂食团购券核销 3,000 / 堂食企业挂账 2,000（**堂食合计 43,000**）；外卖商品总价 18,000 / 外卖打包费 500 / 外卖商家活动补贴 1,500（**外卖合计 20,000**）；其他业务收入 1,000 → **收入合计 64,000**
- 成本（库存关，直接填）：当月食材耗材总消耗 = **22,000**
- 费用：门店运营费 10,300（房租8,000/物业500/水200/电800/燃气600/垃圾100/宽带100）／人工总成本 15,000（工资12,000/社保1,500/宿舍800/员工餐500/工装200）／营销推广费 7,240（外卖佣金3,600/配送费1,200/活动补贴1,500/配送补贴300/推广费400/团购佣金240）／其他支出 300 → **费用合计 32,840**

**场景 S2（库存开、摊销开，2026-08）**
- 收入与费用同 S1（收入 64,000，费用 32,840，不含摊销）
- 库存：期初 5,000 / 采购 25,000 / 期末 7,000 → **真实消耗 23,000**
- 当月摊销总费用（外部传入）= **4,683.33**
- ⚠️ 老板直接填的总消耗**仍是 22,000**（与 S1 相同）

**场景 2-R（连锁重算，期初结转）**
- S2 基础上，2026-07 期末盘点 5,000 → 3,000，则 2026-08 期初 3,000 → 真实消耗 = 3,000+25,000−7,000 = **21,000**
- ⚠️ 此处"连锁"=**期初结转**（单店跨月），**不是多门店/连锁分摊**，本批无多店逻辑

## 3. 强制遵守
- 金额一律**分（INT）**计算，展示 ÷100；禁止浮点存金额
- 本批云函数**必须过批次 0 的鉴权中间件**，带 `shop_id` 归属校验
- 所有写操作带 `client_request_id` 幂等
- 时间一律走服务端 UTC 工具
- **计算精度（对齐 POC2 口径 B）**：中间计算过程保留高精度，**最终输出金额统一 round 到分整数**；毛利率保留 2 位小数（如 65.625% → 输出 65.63% 展示；验收锚点误差 ≤0.01 元，65.625% 与 65.63% 视为同口径）。
- **分层归属**：`calcMonthlyProfit` 是 **Service 层纯计算函数**，不直接接触数据库与前端请求；Controller 层调用前**必须先过鉴权中间件 + 参数校验**，再把干净数据传入 Service。

## 4. ✅ 明确禁止
- ❌ 不做前端页面、不做数据库写入（本批只验证算法）
- ❌ 不实现摊销算法（摊销由外部传入）
- ❌ 不把房租/人工/水电算进食材成本
- ❌ **开库存后把经营参考利润改用倒轧值**（违反口径锁）
- ❌ 不把待结算金额算进利润
- ❌ 不让收入合计/费用合计可以被手动编辑（必须系统汇总）
- ❌ 不做多门店/连锁分摊逻辑
