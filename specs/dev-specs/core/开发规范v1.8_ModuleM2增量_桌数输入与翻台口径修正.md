## 〇 一句话结论

把 M2 的输入口径由「**座位数**」改成「**桌数 + 单桌座位数**」；把「翻台率」这**一个数**按业态切成
**两套话术**（火锅/正餐/烧烤说「桌周转」= 行业口径的翻台；快餐/小面/茶饮说「座位周转」，**禁用「翻台」二字**）；

### 1-5 勘误 2 —— 🔴「翻台率」一词**按业态禁用**，不是全局改名

- **依据**：李老师 2026-10-08 原话——
  > 「餐饮老板算账都是按**桌数**来算，比如店里有 20 张桌子，今天火锅卖了 30 桌；但是**快餐小吃有时不讲究桌数**，
  >  因为一个桌都是混着坐的，比如 01 号取餐的顾客和 05 号取餐的顾客有可能在一个桌子上吃饭。
  >  所以**营业额这个指标对餐饮都成立，翻台率只适合一部分餐饮类型**。」
- **处置**：⚠️ 上一轮曾拟把文案统一改成「每个座位一天要接待几位客人」——**该方案已被李老师否决**
  （理由：老板算账按桌，把「翻台」当座位周转会错）。正确做法是**两套口径并存、按业态切**：
  - 火锅 / 正餐 / 烧烤（**按桌点菜**）⇒ 分母 = **桌数** ⇒ 这才是行业说的「翻台」；
  - 快餐 / 小面 / 茶饮（**常拼桌、单人客多**）⇒ 分母 = **座位数** ⇒ 只能叫「**座位周转**」。
- **不变**：引擎仍只算**一个** `turn_rate`（分母 = 座位数）。话术差异**全在前端**（见 §四）。

### 1-6 勘误 3 —— `seats` 的**值来源**变了，字段名与形状没变

| 维度 | 改动前 | 改动后 |
|---|---|---|
| 用户填什么 | 座位数（空白时按「面积 × 业态密度」自动估） | **桌数** + **单桌座位数**（业态给默认、用户可改） |
| 谁换算 | 引擎直接收 `seats` | 前端 `pages/sandbox/index.js::seatsNow()` **唯一换算点**：`seats = 桌数 × 单桌座位数` |
| 引擎入参 | `seats: <用户填的数>` | `seats: <换算结果>`（**字段名、类型、约束全部不变**） |

## 二 统一设计原则（为什么引擎零改动）

### 2-1 数据流

```
用户：桌数 5 张 × 单桌座位数 4 人
        │
        ▼  pages/sandbox/index.js::seatsNow()   ← 全仓唯一换算点
   seats = 20
        │
        ▼  calcSandbox(validate → service.calcSandboxReverse)   ← 引擎一行未改
   turn_rate = round2(月客流 ÷ (20 × 30)) = 3.70
        │
        ▼  前端按业态切话术 + 三档难度（纯展示层，不参与任何金额）
```

### 2-2 恒等性**由构造成立**

座位数 = 桌数 × 单桌座位数，是**一次乘法**。乘积相同 ⇒ 送进引擎的 `seats` **逐字节相同**
⇒ 出参**必然完全相同**。这不是"看起来一样"，而是构造上不可能不一样。

实测四组（桌数,单桌座位数）乘积皆为 20 —— `(5,4) (10,2) (20,1) (4,5)`：
`turn_rate` 全部 = **3.7**，`target_monthly_fen` / `rent_cap_fen` / `daily_traffic` 逐个相同。
（证据：`review/evidence/r237_m2_turn/recalc_anchors.js` B 段。）

### 2-3 展示层分档的边界

`seatsPerTableOf` / `turnModeOf` / `turnLevelOf` 三个纯函数**只决定页面上说什么** ——
叫不叫「翻台」、算术上难不难。它们**不参与任何金额计算** ⇒ 即使阈值设错也不会算错钱（§5-3 已写明回退方法）。

## 三 能力 1 · 桌数输入（新增）

### 3.1 两个输入项 + 一个换算点

| 输入项 | 绑定字段 | 单位 | 是否必填 |
|---|---|---|---|
| 店里能摆多少张**桌子** | `tablesNum` | 桌 | 反推模式**必填**（正向可不填） |
| 一张桌子大概坐几个人 | `seatsPerTableNum` | 人 | 选填（空 ⇒ 取业态默认） |

- **唯一换算点**：`pages/sandbox/index.js::seatsNow()`。**全仓不得出现第二处** `桌数 × 座位数` 的乘法。
- `seatsPerTableNow()`：用户填的优先；空 / 非法 ⇒ 取 `seatsPerTableOf(bizKey)`。

### 3.2 业态默认「一桌坐几人」（`utils/bizPreset.js::SEATS_PER_TABLE`）

| 业态 key | 默认单桌座位数 | 理由 |
|---|---|---|
| `fastfood` | **2** | 小面 / 米线 / 快餐：长条拼桌，单人居多 |
| `dining` | **4** | 川菜 / 中餐：4 人方桌圆桌为主（包间多可手动调大） |
| `hotpot` | **4** | 火锅 / 烧烤：4 人桌为主 |
| `cafe` | **2** | 新式茶饮：堂食位少，以外带为主 |
| 未知业态 | **4** | 兜底为中位值，**不得返回 0 / NaN** |

> 🔴 **取值标记 `src='S'`（我方自定 + 豆包同行经验估值），属"系统给初值、用户可改"的默认值**，
> **不承担任何计算口径**（用户改了就以用户的为准）。**待真实门店样本校准**（见 §十一）。

### 3.3 砍掉「面积 → 座位数」自动估算

- **删除**：`utils/bizPreset.js::SEAT_DENSITY`（6 条席密度表）与 `estimateSeats()`；
  页面 `reestimateSeats()`、`onArea` 里的重估回写一并删除。
- **依据**：李老师 2026-10-08「**桌数和面积没有强关联**，因为有的店要设包间 —— 同样 100 ㎡，
  包间多的店和全散台的店桌数差很远」。
- **后果（接受的代价）**：反推模式**不再有"没填也能算"的兜底** ⇒ 桌数没填 ⇒ `seats = 0` ⇒ 引擎 fail-closed。
  由 §3.5 的前置提示兜住用户体验。

### 3.4 无效值处理（fail-closed）

`seatsNow()` 的语义（对应豆包点名的「最高危静默错」：小数 / 0 / 负数）：

| 输入 | 结果 | 理由 |
|---|---|---|
| `0` / 负数 / 空串 / 非数字 | `0` | 业务无效 ⇒ 归 0 ⇒ 由 §3.5 拦下（**不产生"半张桌子"**） |
| 小数（如 `2.6` 桌） | `Math.floor` ⇒ `2` | 桌子是整数实体，向下取整 |
| 单桌座位数非法 | 回退业态默认 | 不因一个选填项把整条链路打断 |

### 3.5 前置提示（`terms.m2.needTables`）

反推模式在**发请求之前**先判 `seatsNow() <= 0` ⇒ 直接给一句人话
「先填一下「店里能摆多少张桌子」，才能反推营业额」，**不发请求**。

> 🔴 为什么必须前端拦：引擎在 `seats = 0` 时报的是**契约字段名**
> ——「反推模式下 seats（座位数）必须是 > 0 的整数」。刚填完「桌数」的小白看不懂这句，
> 而且会把**我们正要删掉的那个词**（座位数）重新推到用户眼前。
> ⚠️ 引擎侧那句报错**保留不改**（它是契约层信息）；拦截动作放在 UI 层。

## 四 能力 2 · 翻台口径分组与话术（新增）

### 4.1 两套口径的定义

| 口径 | 分母 | 正式名 | 适用 |
|---|---|---|---|
| `table` | **桌数** | **桌周转**（行业口语即「翻台」） | 按桌点菜：火锅 / 正餐 / 烧烤 |
| `seat` | **座位数** | **座位周转** | 拼桌、单人客多：快餐 / 小面 / 茶饮 |

### 4.2 分组表（`utils/bizPreset.js::TURN_BIZ_TABLE`）

```js
const TURN_BIZ_TABLE = ['hotpot', 'dining'];   // 只有这两类允许出现「翻台」二字
```

### 4.3 话术与禁用词

| 口径 | 指标名（反推结果卡） | 灰字中性说明 |
|---|---|---|
| `table` | 每张桌子一天要翻几台 | 按桌算：平均每张桌一天接待了几拨客人 |
| `seat` | 每个座位一天要接待几位客人 | 快餐小吃常拼桌，这只是事前预估，实际看拼桌和单人客占比 |

- 🔴 **禁用规则**：`seat` 业态的前端可见文案里**不得出现「翻台」**。
- 页面实现：`{{reverseResult.turn_is_table ? t.revTurnRateTable : t.revTurnRateSeat}}`（同一个数、两套问法）。

### 4.4 M2 为何可以用「假设满座」简化（豆包第 5 轮裁定）

**先摆反例（证明两口径不等价）**：2 张桌、单桌 4 座、日客流 8 人且全为单人 ——
桌周转 = `8 ÷ 2 = 4`，座位周转 = `8 ÷ 8 = 1`。**两个指标完全不一样。**

**再给裁定**：M2 是**事前反推**（不是收银后台事后复盘）—— 选址反推的逻辑本身就是
「假设达到保本客流时店内达到对应满座水平」。**所以 M2 里后台只算一套数字、前端切话术即可**；
「桌周转 ≠ 座位周转」的差异**只在 M1 事后复盘才需要区分**，M2 不用。

> ⚠️ 这一段是**唯一允许"一个数两套话术"的论证依据**。若将来 M2 变成事后复盘，必须回来改成两套指标。

## 五 能力 3 · 翻台红警退场（新增）

### 5.1 删什么、留什么

| 项 | 处置 |
|---|---|
| 引擎 `warn_keys: turnRate > 8 ? ['turnOverHigh'] : []` | **删除**（两份副本同步） |
| 引擎 `warn_keys` **字段** | **保留**，恒空数组（契约字段、形状不变） |
| 页面 `warn_turn_high` 装配（两处） | **删除** |
| 页面红警提示行（`class="hint"` + 琥珀色） | **删除** |
| 术语 `revWarnTurnHigh` | **删除**（连同上一个版本遗留的死键 `revSeats` 一并清掉） |
| 跳转 / 拦截 / 主结论卡 | **不受影响**（红警从未参与主结论卡的判定） |

### 5.2 替代：中性灰字 + 三档难度

- 位置：反推结果卡的周转行**下方**，用页面既有的 `.row-note`（28rpx / `#9aa4b2`）。
- 内容两行，**互不覆盖**（豆包第 5 轮：「灰字中性提示与难度标签是两套独立内容，可同时出现」）：
  1. **口径说明**（`turnNoteTable` / `turnNoteSeat`）；
  2. **难度一句话**（`turnLevelEasy` / `turnLevelOk` / `turnLevelHard` 三档互斥渲染）。
- 🔴 **边界**：**不标红、不进主结论卡、不产生任何拦截**。难度文案是"一句话读感"，不是判据。

### 5.3 阈值（`utils/bizPreset.js::TURN_THRESHOLD`）

| 口径 | 轻松 | 有点难 | 很难 |
|---|---|---|---|
| `table` | ≤ 1.8 | 1.8 ~ 2.8 | > 2.8 |
| `seat` | ≤ 2.5 | 2.5 ~ 4.0 | > 4.0 |

> 🔴 **这是 `src='S'` 自定值**（我方自定 + 豆包同行经验估值，**非行业强制标准**）：
> 豆包第 4 轮**自己标注**了「以下阈值属于餐饮一线经验估值……可后续由你们微调」。
> **回退方法**：改 `TURN_THRESHOLD` 两行即可推翻；它**不参与任何金额计算**，误设也不会算错钱。

### 5.4 空值护栏（锚点脚本抓出来的真缺陷）

```js
if (value === null || value === undefined || value === '') return '';
```

> 🔴 **为什么必须写这一行**：`Number(null) === 0`、`Number('') === 0` ⇒ 不先挡空值，
> 引擎**红警时返回的 `turn_rate: null`** 会被分档成 `'easy'`，页面就会渲染
> 「这个水平，正常做着就能到」—— **把"算不出来"说成"很轻松"**。
> 这是本轮由锚点脚本（`recalc_anchors.js` B-⑧）当场抓到的缺陷，已修并已补守卫（§八 F-③）。
