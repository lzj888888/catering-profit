## 0 一句话结论

> **只预留数据与边界，不预留代码。**
> 一期用规则引擎把数字做准（零 LLM）；二期把规则能力扩到"菜单评分 / 活动沙盘 / 套餐定价反推"；**三期才让 LLM 上场，且只做"多因素归因候选"，所有数字回填确定性引擎复算**。

**AI 在本项目的唯一角色**：把老板自己录入（或将来授权接入）的数据 → **引擎算数** → AI **只解读** → 输出"哪里有问题 + 怎么改"。
⛔ **AI 永不参与金额/占比/阈值的计算、推断、修正。**

## 3 边界一 · LLM 不碰数字（AI-D2）

```
❌ 禁止：让 LLM 计算 / 推断 / 修正任何金额、占比、阈值
✅ 允许：LLM 只把「引擎已算好的 facts」组织成人话（排序、取舍文体、指代消解）
```

推论（写码时必须遵守）：

1. 任何 AI 调用**入参必须是 `facts`**（数字已算好），**不是 raw 凭证**。
2. AI 输出**不得回写**任何金额字段，只能写"解读文本字段"。
3. **AI 结果可丢弃**：删掉 AI 层，产品功能不得降级 —— 这是 L1 / L2 分层的验收判据。

## 4 边界二 · 文案与计算分离（AI-D3）

**唯一出口契约**：

```js
buildInterpretation(facts) -> { lines: [...] }
// 今天实现 = 模板 + 槽位（零 LLM）
// 将来实现 = LLM 结果（或 L1 兜底）
// 外部调用方不变 —— 换实现不换接口
```

⛔ **禁止**：把句子拼写在 `*.wxml` 里，或在页面 JS 里散落 `if (x > y) 文案 = ...`。
理由：一旦散落，将来换 LLM 要改 N 处且无法保证口径一致。

**输出约束（R165–167 已锁）**：

- 解读输出**必须带 `sourceId` 引用清单**，禁止构造新指标；**缺字段直接丢弃**该条。
- 带「经营行动建议」的输出**必须走规则模板**；LLM 只允许做「现象归纳 + 候选原因」。
- 解读文本**不落库、实时算**。
- 三期上线时必须给 LLM 输出加 **AI 标识**（显式 + 隐式）。

## 5 边界三 · 数据结构化与三级门禁（AI-D4 / D5 / D6）

### 5.1 raw + facts 双件套（唯一的"过期不候"）

> 理由：**数据是历史沉淀的**。今天存的账单没有结构化，明天的 AI 也读不到它；而接口随时能补，**数据不能回溯补录**。

| 层 | 存什么 |
|---|---|
| `raw` | 客户**原始列**，不加工；+ 采集元信息：平台名 / 期间起止 / **符号约定** / 列名映射来源 / 明细行唯一 ID |
| `facts` | 已归一到统一口径的机读事实，每条带 **`sourceId`** |

🔴 **`sign_convention`（平台补贴是负号还是正号）必须显式记录，不靠代码猜。**

### 5.2 三级门禁

| 级别 | 校验什么 | 不通过的后果 |
|---|---|---|
| **甲级**（前置门禁） | 通道连通（DB / 云函数无超时、返回非空）、Schema 校验（字段名/类型/数值范围双向匹配）、关键指标非空 | **直接阻断**，不进入核算 |
| **乙级**（业务质量） | 数值范围、勾稽关系（收入 − 成本 − 费用 = 利润 等） | 出告警、标记可疑 |
| **丙级**（算量可信） | 三方对账、口径一致性、明细可回溯 | **隐藏依赖它的解读 / AI 输出** |

🔴 **丙级门禁是第三期上 LLM 的硬前置**：通过率需稳定 **≥95%**。

## 6 入站数据接入缝（AI-D7 / D8）

> **B2B 定位（R174）**：我们永远是餐饮老板的数据服务方，**不碰消费者端**。
> 入站 = 我们要"拿进来"做诊断的数据；出站（对外档案）= 冻结。
> ⚠️ **以下两张集合本轮均未落库**；落库时须同步 §9 四处。

### 6.1 `external_sales_daily`（入站销售日流水）

| 字段 | 类型 | 说明 |
|---|---|---|
| `shop_id` | string | 门店 |
| `biz_date` | string | 业务日期（YYYY-MM-DD） |
| `external_ref_id` | string | 平台侧菜品 ID |
| `dish_key` | string | 关联本系统成本卡标识 |
| `qty` | number | 数量（**绝不进金额计算**，仅作第 4 个必填项） |
| `amount` | number | 金额（分） |
| `platform` | string | 平台（美团 / 饿了么 / 淘宝闪购） |
| `source` | string | 来源（oauth / excel / manual） |
| `created_at` | number | Unix ms |

**唯一键**：`(shop_id, biz_date, external_ref_id)`

> 将来美团收银 OAuth 落地，只做「对方 payload → 此 schema」的映射，**引擎零改动**。

### 6.2 `shop_dish_mapping`（平台菜品 ↔ 我方菜品映射）

| 字段 | 类型 | 说明 |
|---|---|---|
| `shop_id` | string | 门店 |
| `platform` | string | 平台（美团 / 饿了么 / 淘宝闪购） |
| `external_ref_id` | string | 平台侧菜品 ID |
| `card_code` | string | 我方成本卡标识（对应 `shop_cost_card.card_code`） |
| `created_at` | number | Unix ms |
| `updated_at` | number | Unix ms |

**唯一键**：`(shop_id, platform, external_ref_id)`
**辅助索引**：`(shop_id, card_code)`

#### 🔴 命名与形态定名理由（R176 拍板）

> **问**：`external_ref_id` 是加在 `shop_cost_card` 上，还是新建映射集合？
> **答**：**新建 `shop_dish_mapping`，不往 `shop_cost_card` 加字段。**

三条理由（第 ② 条是决定性的）：

1. **多平台**：同一道菜在美团 / 饿了么 / 淘宝各有一个 ID，单字段存不下 ⇒ 必须带 `platform` 维度。
2. 🔴 **`shop_cost_card` 是版本模型（只 INSERT）**，而"平台菜品 ID 映射"是**会变的运营配置**（换平台、换对应关系）。把它放进版本模型 ⇒ **每次改映射都会产生一张新版本成本卡 ⇒ 污染成本卡历史与版本哈希链**（与 §AI-D6 可信底座直接冲突）。
3. **语义清晰**：`mapping` 表天然表达"两个系统菜品身份的双向对应"，与成本卡（成本结构快照）职责不混。

⛔ **禁止**：为了省一张表，把 `external_ref_id` 塞进 `shop_cost_card`。

## 7 触发条件（满足才建抽象层 / 才上 LLM）

**全部满足**才动工，缺一不动：

1. **账单导入已上线并跑满 1 个月** —— 有真实覆盖率数据（L1 到底覆盖百分之几）
2. **出现 ≥3 类模板覆盖不住的提问**（真实日志，不是"可能覆盖不住"）
3. **合规路径已确认** —— 主体具备资质 + 「深度合成-AI 问答」类目 + 算法备案号到位
4. **Provider 已选定** —— 微信 AI 成长计划额度是否申领成功（免费 Token 是关键变量）

**"该上 LLM 了"的三条可测量条件**（R168 原案，待确认是否照此写入门禁）：

1. 用户月度利润波动类查询中，规则模板无法覆盖的场景占比 **≥12%**
2. 丙级门禁通过率稳定 **≥95%，持续 2 个月**
3. 付费用户调研中，多因素利润归因诉求占比 **≥20%**

**放弃信号**（一出现就该停）：连续 3 个月丙级门禁通过率 <85%；或二期菜单/活动沙盘使用率 <5%。

## 8 明确不做（防过度设计清单）

| 不做 | 为什么 | 复查触发条件 |
|---|---|---|
| **AIProvider / adapter 工厂 / model 枚举** | provider 未定，必错；届时抽比现在抽准 | §7 四条全满足 |
| **AI 开关配置项**（`shop_switch.ai_enabled`） | 无调用方的开关 = 死配置，还要背维护与同步成本 | 有第一个调用方时 |
| **prompt 模板管理系统** | 强依赖所选 provider 形态 | 选定 provider 后 |
| **提前在 DB schema 加 `ai_summary` 等字段** | `check_schema_sync.js` 双向校验，空字段白付同步成本 | 三期落地时 |
| **采购小票拍照 OCR** | 需 OCR 服务/资质/费用；**识别错误会静默污染原料库**（与"静默失败"同族病） | 有稳定 OCR 服务 **且** 有"识别→老板确认→才入库"的防污染链路 |
| **语音录入** | 小程序录音权限 + 语音识别服务 + 审核成本；收益/成本比差 | P3 排期到位 |
| **出站对外档案**（`shop_public_profile` / `agent_session` / `webhook_subscription` 等） | B2B 不对外曝光；且被主体资质闸死 | 主体资质 + 业务确认 |
| **食客 Agent / 数字孪生 / 多平台 OAuth 自动同步** | R174 认定属 B2C 过度解读 | 不作为 |
| **同类门店对标参考** | 门店差异巨大，简单对标极易误导；外部基准口径不一致 | 不作为（伪需求） |
