## 1.1 一句话定位

面向**中小餐饮老板**的微信小程序，解决三件事：

| 模块 | 回答老板的哪个问题 |
|---|---|
| **M1 月度盈利核算** | "这个月我到底赚了多少？" |
| **M2 选址盈利沙盘** | "这个铺子每天要做多少才不亏？" |
| **M3 菜品成本卡** | "这道菜成本多少、该卖多少钱？" |

**Module A（收入费用核算）不是独立页面**，是 M1 的**录入口径与字段字典**，决定 M1 算得对不对。

**目标用户画像决定设计取舍**：用户是老板不是会计 —— 输入要快、要少，利润要准；精确流水账、平台自动对账等对老板属过度设计，一律推 v1.1。

## 1.2 技术栈

- **前端**：微信小程序**原生**开发（不用 uni-app / Taro / mpvue）
- **后端**：微信**云开发** —— 云函数（Node.js）+ 云数据库 + 云存储
- **不自建服务器、不买域名**
- **所有计算放云函数 Service 层**，前端只做展示与录入

## 1.4 分层架构（AI 宪法）

```
小程序页面 (Page)
   │  只做：渲染、录入校验、调用云函数
   │  ❌ 禁止：算毛利、算摊销、算成本、算保本
   ▼
云函数 Service 层
   │  ✅ 全部计算在这里：毛利/双利润/摊销/倒轧/BOM/保本/反算
   │  ✅ 二次重算：不信任前端传入的任何计算结果
   ▼
云数据库
   ✅ 按 shop_id 隔离，复合索引
```

**铁律**：前端传**原始录入数据**，Service 重算后返回结果。前端传来的 `total_cost` / `profit` / `毛利率` 等**一律丢弃不采信**（防抓包篡改）。

## 1.5 全局铁律（12 条，违反即打回）

| # | 铁律 | 说明 |
|---|---|---|
| 1 | **金额 = 整数分** | `INT`，禁 JS Number 原生浮点运算；展示 ÷100 保留 2 位 |
| 2 | **重量 = 克** | 采购单位（斤/公斤/包）经 `换算系数` 换算到 g |
| 3 | **时间 = Unix 毫秒**；**年月 = `YYYY-MM` 字符串** | 记账月用字符串索引 |
| 4 | **百分比 = `DECIMAL(5,2)`** | 存储 35.00 表示 35%，不是 0.35 |
| 5 | **shop_id 隔离** | 所有查询/写入强制带 `shop_id`，建复合索引 |
| 6 | **计算下沉云函数** | 禁前端算毛利/摊销/成本/保本 |
| 7 | **配置读表，禁硬编码** | 套餐价格、功能限额（如 M3 免费 3 张（按 user_id 跨店共享）、M1 账套 1 个）**必须读 `subscription_plan` / `feature_permissions`**，不得写死在代码里。**v1.1 起权限判定统一只读 `expire_at`**（M2 已改永久全免费，无 3 套限制） |
| 8 | **归档不可改** | `is_archive=true` 后禁 update 主记录金额；错账只新增"往期业务调整"记录 |
| 9 | **操作必留痕** | 所有影响利润/成本的操作写 `audit_log`，**只 INSERT 不可删改** |
| 10 | **删除 = 软删除** | `is_deleted` + `delete_at`，30 天内可恢复，到期物理清理 |
| 11 | **待结算不进利润** | 外卖/团购待结算是现金流指标，**绝不进入毛利/净利计算**（A.0-6） |
| 12 | **开关纪律** | "收入的开关""其他方面接触的开关"等用户配置项**原貌保留**，不得清理/合并/删减 |

### 补充铁律（模块级，同样重要）

- **毛利铁律**：毛利 = 收入 − **营业成本（仅食材耗材）**。**房租/人工绝不算进营业成本**（A.0-2）
- **双口径锁**：开库存后**经营参考利润仍用"直接填的消耗"**，只有全要素真实利润用倒轧值（M1.1，测试 S2 验证）
- **成本卡只 INSERT 不 UPDATE**：改卡 = 另存新版本，历史不可覆盖（M3.4）
- **辅料同损耗口径**：辅料与原料**一并**按 `(1−制作损耗率)` 放大，锁定 9.75 不可"优化"（M3.5）

## 1.7 精度与尾差规则

| 项 | 规则 |
|---|---|
| 金额存储 | 整数**分**；除法 `Math.round()` 四舍五入到分 |
| 展示 | ÷100，保留 2 位小数 |
| **摊销尾差** | 月摊销 = `原值 ÷ 总月数`（四舍五入 2 位）；**末月用 `原值 − 前N-1期合计` 倒挤**，保证总和严格 = 原值 |
| **验收容差** | 系统输出与测试集预期值误差 **≤ 0.01 元** 视为通过 |

**摊销尾差示例**：120,000 ÷ 36 = 3,333.33/期；前 35 期合计 116,666.55；第 36 期 = 120,000 − 116,666.55 = **3,333.45**（不是 3,333.33）。

### 1.8.3 「账套」语义澄清（v1.1 新增，纠正 PRD 冲突）

- **账套 = 店铺维度，不是月份维度。** 免费用户 `is_deleted=false` 的**店铺数上限 1**；`shop_monthly_account` 的**月份数不限制**。
- 理由：月度盈利核算的价值在于**连续看趋势**（本月 vs 上月）。限制月份数会让用户第 2 个月就无法记账 → 产品直接废掉，且违反本文件已锁定的"月份数量不限"。
- 限制"店铺数"才是自然的商业化维度（多家店 = 进阶用户）。

### 1.8.4 M3 导出策略（v1.4 终稿：导出全禁，仅付费解锁）

- **所有导出（含单张 PDF、批量 Excel）均仅付费解锁**；免费用户可录入 / 查看 / 试算，但**不能导出 / 打印**。
- 变更沿革：v1.1 曾保留单张 PDF 免费（理由：打印贴后厨是成本卡第一场景）；**v1.3 用户决策改为全部禁止**，收紧钩子、转化点更靠前（免费用户录满 3 张后即触发付费墙）。
- 仍保留「录入 / 查看 / 试算」全免费，核心算账场景不废；只是把「导出 / 分享」作为付费转化点。

## 1.10 v1.5 新增决策（2026-09-09 晚确认）

### D1 · 支付功能预留（营业执照未下来）

- 全局配置 **`enable_real_payment = false`**
- 支付入口 UI、商户号配置页、`shop_payment_flow` 流水表**全部预留**；执照下来后**改配置即可启用，不重构**
- ⚠️ **关键澄清：订阅状态不得依赖支付**
  - `shop_subscription` 记录门店当前套餐（`plan_id`），**支付只是"自助升级"的入口之一**
  - 支付关闭期间，**运营后台可直接手动改 `plan_id`** 发放订阅版
  - 否则会出现"支付没开 → 没人能升级 → 订阅版逻辑无法验证"的死结
- 配额判定链路统一为：`shop_subscription.plan_id → subscription_plan → feature_permissions`，**与是否开启支付无关**
- ⚠️ **v1.1 简化**：上述链路仅用于**后台配置管理**；**业务层权限判定统一只读 `expire_at`**（权限到期时间）一个字段，不感知套餐类型 / 价格 / 周期（见 1.8 与 `OBSOLETE_商业化方案_v1.1_融合版.md` 第七节，该文件已作废，当前以 `商业化方案_v1.4_融合版.md` 为终稿）

### D2 · 收支项配置化（平台已确认支持动态增删）

- 收入项 / 费用项**不再硬编码字段**，改用配置表 `shop_income_item` / `shop_expense_item`
- 老板可自行增删费用项（如加"消杀费""外卖包装费"）
- 系统预置默认项（对应 Module A 字典），`is_system=true` 的项**不可删、只可停用**（避免历史账目引用断链）
- 呼应**铁律 12**："收入的开关"本质就是 `shop_income_item.enabled`
- 对验收无影响：测试集 S1 的费用项 = **默认配置下的值**，S1 只验"汇总与公式"，自定义项不影响

### D3 · calculator 公共函数复用（平台已确认支持）

- 计算逻辑统一封装 `calculator` 公共函数，前端与云函数 Service **调用同一套代码**，根源避免两端口径不一致 ✅ 采纳
- ⚠️ **但权威值仍以 Service 重算为准**（此条为对原表述的必要限定，避免与铁律 6 冲突）：

| 场景 | 谁算 | 用途 |
|---|---|---|
| 录入时实时预览 / 试算 | 前端调 `calculator` | 提升交互体验（改数字立刻看到结果） |
| **落库与对外展示的权威数值** | **Service 层重算** | 唯一可信来源 |
| 前端传来的计算结果 | **Service 一律丢弃不采信** | 防抓包篡改 |

- 一句话：**同一套函数保证"口径一致"，Service 重算保证"数值权威"** —— 二者不矛盾，缺一不可。
