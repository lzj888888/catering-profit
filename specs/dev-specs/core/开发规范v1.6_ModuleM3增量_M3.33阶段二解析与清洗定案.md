### 3.4 形态判定算法（**fail-closed**）

```
detectShape(matrix):
  A ← 存在列名 '菜品名称' 且 存在列名 '销售数量' 且 R2 含 '销售方式'
  B ← 存在列名 '套餐' 且 存在列名 '单品名称'

  命中 1 个 → 返回；命中 0 或 ≥2 → 返回 null（提示用户"这张表不认识"）
```
🔴 **零命中不许兜底猜**（沿用阶段一 `billParse` 的 fail-closed 纪律）。

| # | 规则 | 依据 |

## 5 落库（`external_sales_daily` · R174 已落库，**零 schema 改动除 enum**）

### 5.1 🔴 `external_ref_id` 编码（**不解决则写库必失败**）

```
现状：idx_esd_uniq = unique( shop_id, biz_date, external_ref_id )      ← 🔴 不含 dish_key
      阶段一填 external_ref_id = 'BILL:<platform>:<biz_date>'、dish_key = ''（占位）
⇒ 阶段二若沿用同一编码 ⇒ 同平台同一天的所有菜**共用同一个三元组** ⇒ 唯一索引只允许 1 条。
```
**定案**：`external_ref_id = 'DISH:<platform>:<biz_date>:<dish_key>'`
`_id` 确定性形态：`'SALE_<shop_id>_<platform>_<biz_date>_<seq>'`（`seq` = 该批次内行序，保证幂等：同表重导覆盖同文档）。

### 5.2 🔴 `qty` 取整口径（撞 `SALES_SCHEMA::qty integer`）

```
schema： qty = { type:'number', required:true, integer:true, min:0 }
实测： 合计 3280.3；菜品行 `加工` 16.5 / `泡椒酸菜鱼` 4.8
```
**定案**：`qty = Math.round(原始 qty)`；
🔴 **且**解析报告必须单列「非整数 qty 行（原名 + 原始值 + 取整后）」，**不静默**。
⚠️ 已知代价：`总成本 = qty × unit_cost_fen` 会带 ≤0.5 份误差。**金额 `amount` 不受影响**（独立列）。

### 5.3 `amount` = **营收**（转分整数）

- 取**菜品收入(元)**列（= 销售额 − 优惠，已实测恒等）而非"销售额"列 —
  理由：复盘看的是**实际实现收入**，与 M1 权责口径一致（R129 同族）。
- `amount_fen = Math.round(收入元 × 100)`；`SALES_SCHEMA::amount` 亦要求 integer ✅

### 5.4 `platform` —— 渠道区分（**唯一需要动的 schema**）

```
现状 enum = ['taobao','meituan','eleme','other']   ← 单源 utils/gradeGate.js:18
```
**定案**：**新增 `'pos'`**（堂食收银）⇒ enum = `['taobao','meituan','eleme','pos','other']`。
- 堂食（美团收银 POS）⇒ `platform='pos'`；外卖 ⇒ 各自 `meituan`/`eleme`/`taobao`。
- 🔴 **代价**：`utils/gradeGate.js` 与 `cloudfunctions/importSalesBill/service.js` **两份同源副本都要改**
  （后者第 137 行内联同款 enum，**无 md5 守卫**）⇒ 漏一处 = 前端放行、云端拒收（或反之）。
- **回退**：删该枚举值即回退（新值向后兼容，不动历史行）。

### 5.5 `dish_key` = **归一后的导入名**（不是成本卡 ID）

- 映射关系（导入名 → 成本卡）落 `shop_dish_mapping`（G3 已建空集合，唯一键 `(shop_id, platform, external_ref_id)` 已于 R174 建）。
- 理由：`dish_key` 语义单一（"这张表里这道菜"），映射是**多对一**且会变 ⇒ 拆开两层。
- `idx_esd_dish_key = (shop_id, dish_key)` ⇒ 支持"按菜品看历史销量"。

### 5.6 🔴 不使用 v1.5 的 `external_raw_staging`

v1.5 §3 的脏数据落点**尚未落库**；本批若使用 ⇒ 须同时建表 + 索引 + 权限矩阵 + schema 守卫 ⇒ **破"零新建集合"**。
⇒ **本批只落清洗后结果**（代价见 P2-D6）；v1.5 落地后，历史批次可**用原文件重导**补洗。

## 6 🔴 重复计算禁令（本文件**最重要**的一条）

```
菜品表 R2 自述：销售方式【单品+套餐明细】  ⇒ 套餐组分**已并入**菜品表
套餐表 24 个组分名 ⇒ 24/24 **全部命中**菜品表
⇒ "菜品表 + 套餐表" 相加 ⇒ 销售额虚增 887.8 元（2.68%），且**不会报错**
```
**定案**：**只用餐品表**；套餐表仅用于 §6.1 交叉校验。**禁止两条路线同时入 `external_sales_daily`**。

### 6.1 套餐表用作交叉校验（对应 v1.5 §6.2）

- `套餐销量 × 子单品配比` ⇒ 应等于子单品用量；不等 ⇒ **告警**（常见于退款/改单/赠品）。
- 校验失败**不阻断导入**（fail-open），进"告警清单"。

## 7 菜品名归一

### 7.1 近似重复 SKU —— **显式别名表**（对应 R227 §五-1）

实测：`小料` ↔ `自助小料`、`联系吧员免费停` ↔ `联系吧员免费停车`。
⇒ **必须走显式别名表**（用户可编辑 + 保存复用）。
🔴 **禁止模糊匹配/自动归并**：归并错 = 把两个真菜品合成一个，且静默。

### 7.2 非菜品 SKU —— **可配置排除名单 · 默认 fail-open**

实测混入：`鞋刷` / `洁柔抽纸` / `真知棒棒糖` / `旺旺碎冰冰` / `雪糕` / `瓶装饮料` / `龙凤呈祥香烟` / `打包盒` …
**定案**：提供**默认名单**（只含**明确非厨房出品**：烟草、日用百货、包装耗材）+ **用户可增删**；
🔴 默认行为 = **提示而非静默剔除**（在解析报告里分列"疑似非菜品"区，用户勾选是否排除）。
理由：误杀真菜品（如"小料"）比漏放更贵；且烟酒是**真实营收**，不能从收入里抹掉 —— 只从**毛利口径**里排除。

### 7.3 🔴 「菜品大类」列不可信（对应 R226 §四-⑤）

实测错配：`小料 → 锅底`、`红汤大锅（真锅底）→ 抖音团购套餐`、`联系吧员免费停 → 美团团购套餐`。
⇒ **只按"套餐定义"取组分**（POS 后台套餐配置），**绝不按本表大类列归类**。

| 9.4 | **快照类指标不可求和**（`上架商品数`/`有交易商品数`/`近7日复购人数`）| 解析器须标 `snapshot`，聚合取**末值或均值**（形态 C 才涉及）|
| 9.5 | `投入产出比` / `营销力度` 口径**无法反推** | 🔴 **判不了** ⇒ **不许当前置依赖** |

### 9.3 诚实存疑（不静默跳过）

1. 本数据是**单店 7 天**（2026-09-07~09-13，医院店 + 开学季）⇒ 季节/商圈偏差未评估；
2. **佣金计提基数（含不含打包费）本数据判不了**（两侧极差几乎无差）⇒ R223/R224 悬案**保持未结**；
3. 两平台销售额口径差异**成因未知**（只知差 2 倍）。
