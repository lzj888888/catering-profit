## 2 🔴 统一设计原则：三处皆是「入参变换 + 后置渠道层」，引擎零改动

生产引擎 `calcBom/service.js::calcCostCard(p)` 的入参形状是：

```
p = { lines:[{ quantity, net_unit_cost }], auxFen, lossPct, mode:'A'|'B', batchOutput?, priceFen?, targetMarginPct? }
```

其中 `lineNetCostYuan = quantity × (net_unit_cost / 10000)`（`net_unit_cost` 单位 = 万分之一元，即 0.0001 元）。

**因此三件事都可以不碰引擎**：

| 要做的事 | 做法 | 为什么不需要改引擎 |
|---|---|---|
| **多规格（大小份）** | 按 `line_kind` 缩放 `quantity`、缩放 `auxFen`，再把结果喂**同一个** `calcCostCard` | 系数全 1 ⇒ 入参与原值**逐字节相同** ⇒ 输出必然相同（**恒等性由构造成立**，不靠约定） |
| **套餐** | 把「子卡单份成本」当作 `net_unit_cost = 成本分 × 100` 的行，`quantity` = 份数 | 套餐行与原料行在引擎眼里**形状相同** |
| **外卖单均** | 菜品成本取 `unit_cost_fen`；渠道费用层（佣金/配送/补贴/包材）是**纯算术**，不进 BOM 引擎 | 渠道层不是配方 |

> 🔴 **这句话是本规范的技术核心**：它使 D7 与 D3 的“红线风险”归零 ——
> 5 份 `service.js`（`calcBom` / `saveCostCard` / `syncCostCard` / `getCostCard` / `getCardVersions`）的
> **引擎段（具名函数 `netUnitCostWan` / `buildSnapshotLines` / `calcCostCard` / `wouldCreateCycle`）一字不改**；
> **唯一例外是 M3.22#5**：允许在 `saveCostCard/service.js` **新增**非引擎纯函数 `judgeCardQuota`（不得改动引擎段）。
> `detectCycle` 的 DFS 也不用为套餐扩层（套餐根本不在引用图上）。

## M3.14 组件分组与耗材分类（纯展示层 · 新增字段）

**目的**：让老板"看得懂"（烤鱼 = 鱼 + 底料 + 配菜 + 烤纸；小面 12~15 种调料折叠成一组）。
**成本合计一分不变** —— 分组只是视图。

### 字段（`shop_cost_card_line` 新增 2 个）

| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `line_kind` | enum | `main` | `main` 主料 / `aux` 辅料 / `season` 调料 / `semi` 半成品 / `pack` 耗材包装 |
| `group_name` | string | `''` | 自由文本分组名（可空）。**仅展示折叠用** |

- 引擎**不认识**这两个字段（`calcCostCard` 只读 `quantity` / `net_unit_cost`）⇒ 对成本**零影响**。
- `line_kind` 是 **M3.15 多规格的前置**（没有分类就无法按类缩放）⇒ 见 M3.28 批次顺序。
- 存量行**缺字段时按 `main` 兜底**（fail-soft），但**不得**据此改写存量数据（存量卡只 INSERT 不 UPDATE，改写 = 破红线）。

### 耗材分摊（炸油 / 炭火）—— 用现有模式 B 表达，零新增机制

行业量级：炸油一锅可炸固定重量、按炸制重量分摊；燃料费约占销售额 **3.8%~4.9%**（S6）。
**落法**：把"炸油"做成一张 **模式 B 批量卡**（产出单位 = "斤炸制品"），炸鸡卡引用它、填炸制重量。
⇒ 与豆包的"耗材分摊机制"等价，但**不必新增任何机制**。

## M3.15 多规格（大小份 / 半份 / 例份）

### 为什么值得做（行业本质）

半份菜的**调料不会减半** —— 否则没味。这就是行业里"半份定价是全份 **65%** 而不是 50%"的原因：**固定成本不减半**。
（⚠️ 65% 仅作**软提示参考**，**不是判定阈值** —— 本仓 round113 已因"把行业常见区间当警戒线"栽过一次。）

### 数据模型

`shop_cost_card` 新增 `specs_json`（TEXT，JSON 数组，默认 `'[]'`）：

```json
[ { "spec_key": "half", "name": "半份",
    "coef": { "main": 0.5, "aux": 0.7, "season": 1.0, "semi": 0.5, "pack": 1.0 },
    "price_fen": 1820 } ]
```

- `spec_key` 由用户可读名（`name`）解耦：**可见名可改，机器键不变**（R129 同族纪律）。
- 规格**随版本一起 INSERT**（改规格 = 生成新版本），**不产生额外的版本行**。

### 计算（唯一允许的实现形式）

```
deriveSpec(lines, auxFen, coef) → { lines', auxFen' }
  lines'  = lines.map(l => ({ ...l, quantity: l.quantity × (coef[l.line_kind] ?? 1) }))
  auxFen' = auxFen × (coef.aux ?? 1)          // 辅料桶归 aux

规格成本 = calcCostCard({ lines: lines', auxFen: auxFen', lossPct, mode:'A' }).unit_cost_fen
```

### 🔴 三条硬约束

1. **`specDerive` 不得内联进任何一份 `service.js`** —— 放 `cloudfunctions/common/specDerive.js` 单一文件（+ 扁平副本按既有 `sync_common.js` 机制），**5 份引擎副本都不碰**。
2. **规格成本不得写入 `total_cost`** —— 基础份 `total_cost` 永远 = 派生系数全 1 时的值（= 9.75）。规格成本是**展示/试算**值。
3. **恒等性必须由守卫证明**：系数全 1 时，派生结果 ≡ `calcCostCard` 原值（R132，正负互证）。

### 复算锚点（已实测）

| 锚点 | 输入 | 结果 |
|---|---|---|
| **A-d 恒等** | 系数全 1 | `unit_cost_fen` **仍 975**、`material_total_fen` **仍 876**（逐项相等）|
| **A-e 半份** | main .5 / aux .7 / season 1.0；辅料桶 .7 | 缩放后用量 `ji=100, hua=35, gan=10, cong=21, you=20`、`auxFen'=35`；**成本 567 分** |
| **A-e 半份定价** | 按行业参考 65% ⇒ 1820 分 | 毛利 **1253 分**、毛利率 **68.85%** > 全份 65.18% ⇒ **印证"半份更赚"** |
| **反例** | 若按 50% 定价 ⇒ 1400 分 | 毛利率仅 **59.5%**（⚠️ 我首版手算估成 37.9%，被复算脚本推翻 —— 故本仓纪律「未实测不写数字」）|

## M3.16 套餐成本卡（落地 v1.0 待补项 **#16** 的"有坑无设计"）

### 定位（D3 定案）

套餐 = **引用型成本卡**，是**终端聚合**：消费者看到的是套餐，但**没有任何卡能引用套餐**。
⇒ BOM 仍是"原料 → 半成品 → 成品菜"两层，套餐**站在 BOM 之外**，M3.6 红线不动。

### 数据模型（复用 `shop_cost_card` / `shop_cost_card_line`，**不新建集合**）

`shop_cost_card` 新增 `card_type`（TINYINT，默认 `1`）：

| 值 | 含义 |
|---|---|
| `1` | 单品（默认，含模式 A/B 两种核算模式，沿用 v1.0） |
| `3` | **套餐**（= 引用型卡；`calc_mode` 无意义，固定按"份"聚合） |

> ⚠️ `2` **空置不使用**（历史讨论中曾拟作"批量预制"，但 v1.0 已用 `calc_mode='B'` 表达，**不再引入第二个维度** ⇒ 避免两套真相源）。

`shop_cost_card_line` 新增 `line_type`（默认 `1`）：

| `line_type` | 含义 | 字段语义 |
|---|---|---|
| `1` | 原料行（v1.0 语义，不变） | 沿用全部快照字段 |
| `2` | **子卡行** | `sub_card_ref` = 被引用卡的**逻辑卡号**；`sub_version` = 锁定的版本号；`material_name` ← 子卡名称快照；`net_unit_cost` ← **子卡单份成本（分）× 100**（即"万分之一元"表示，与引擎同尺度）；`quantity` ← 份数 |

> 🔴 **字段命名以实现为准**：v1.0 规范写 `card_id`，实现用 **`card_code`**（`initDb/collections.js` 唯一索引 `idx_card_code_version` 即 `(shop_id, card_code, version)`）。
> 该命名不一致**已在 `core/13` 登记为待裁决项**，本文件**不擅自改名**；新增字段一律以实现的 `card_code` 为准，并在实现批次**只用一个名字**。

### 计算

```
套餐行 = 子卡的 unit_cost_fen（**该版本锁定值**）× 100 → net_unit_cost
套餐成本 = calcCostCard({ lines: 子卡行 + 套餐自有行, auxFen: 套餐辅料/包材桶, lossPct: 套餐制作损耗, mode:'A' }).unit_cost_fen
```

### 三个必须显示的信息（"好用"的落点）

1. **顾客省了多少** = `Σ 子菜单点挂号价 − 套餐售价`
2. **我少赚了多少** = `套餐毛利 − Σ 子菜单点毛利`（**为负 ⇒ 红字提示"这个套餐在拉低你的毛利"**）
3. **成本结构** = 各子菜贡献的成本占比（谁在吃利润）

### 校验（新增）

- 引用对象必须是**同类店铺**、**最新版本**（该 `card_code` 下 `version` 最大者 —— **生产实现不写 `is_latest`**，见 `saveCostCard/index.js:11` 与 `getCostCard/index.js:5`）、且 **`card_type ≠ 3`**（禁套餐含套餐）⇒ 否则 `COMBO_NEST_NOT_ALLOWED`。
- 引用时**记录 `sub_version`**；子卡后续升版**不影响**本套餐（锁版本，D5）。

### 复算锚点（已实测）

| 锚点 | 输入 | 结果 |
|---|---|---|
| **A-a 套餐成本** | 宫保(975) + 米饭(120) + 例汤(180) | **1275 分** |
| **A-a 毛利（售 25）** | 2500 − 1275 | 毛利 **1225 分**、毛利率 **49%** |
| **A-a 对比** | 单点毛利合计 2425 | **少赚 1200 分**（红字）；顾客省 **1200 分** |
| **A-b 锁版本** | 鸡胸肉 15→20 元/斤（宫保→1208） | 套餐**仍 1275**（不回溯）；「同步至最新」⇒ 套餐新版本 **1508 分**（毛利率 39.68%） |

## M3.17 外卖单均与挂牌价反算（D15：套餐交叉并入本章）

### 计算对象是「一单」，不是「一道菜」

```
一单 = [{ 卡或套餐, 份数 }] + [包材项 × 数量] + 平台参数
```

### 🔴 口径一：到手口径（默认 · 现金视角）

```
① 顾客支付 P   = Σ(商品标价 × 份数) + 打包费 + 配送费(顾客承担)
② 平台扣项     = 佣金(率 c × **商品总价**，可设保底 min) + 配送服务费 d + 配送补贴 + 商家活动补贴分摊 s + 推广费分摊
③ 商家实收 R   = P − s − 佣金 − d − 配送补贴
④ 菜品成本 Cf  = Σ(卡/套餐 unit_cost_fen × 份数)
⑤ 包材成本 Cp  = Σ(包材采购单价 × 数量)
⑥ 单均理论利润 = R − Cf − Cp
⑦ 到手率       = R ÷ P    ← 行业实测 70%~75%（S4）⇒ **软提示**，不阻断
```

### 🔴 口径二：总额法口径（会计视角 · 与 M1 对得上）

```
收入 = 商品总价 + 打包费 + 商家活动补贴      （对齐 core/14 收入种子 income_takeaway_*）
费用 = 佣金 + 配送服务费 + 补贴 + 推广
```

**同一单两种口径的"毛利"必然不同**（补贴在总额法里既进收入又进费用）⇒ **页面顶部必须显示当前口径名 + 一句人话解释；两套数字不得混进同一个总数**。

### 🔴 佣金基数铁律（本仓复算实证）

佣金（技术服务费）的计费基数是 **商品总价，不含打包费**。
误用"顾客支付额（含打包费）"作基数 ⇒ 上例佣金 150 → **162 分**、单均利润 **差 12 分/单** ⇒ 单量一大就是系统性偏差。
**必须在页面口径说明里点名这一句。**

### 外卖挂牌价反算（D6）

```
P* = (Cf + Cp + M + s + d − 打包费收入) ÷ (1 − c)

     M = 目标到手利润
```

> `P*` 是**商品挂牌总价**（不含打包费）；分母 `(1 − c)` 体现佣金按商品总价计。

## M3.21 ★ 留存：M1↔M3 率对率对账（第二个月回来的理由）

### 问题

豆包问对了问题（**M3 是低频工具**），但答案全是"增加打开频次"（后厨视图、今日菜价）。
**频次 ≠ 付费意愿** —— 老板打开看了配方，也不觉得每月值 25.9 元。

### 只有我们能给的那一枪

- **M1 有**：本月**实际**食材成本（真实发生，权责发生制）
- **M3 有**：**理论**成本
- **两者差额** = 这个月漏在哪（采购涨价没发现？出菜份量超标？损耗失控？）

> **"你本月理论食材成本 3.2 万，实际花了 4.1 万，多出的 9000 块，你得知道去哪了。"**
> 一个月 25.9 元，换一次"我知道我漏了 9000 块"。

### 🔴 本轮已查证的事实（决定本能力**必须降级设计**）

| 查证项 | 结论 | 证据 |
|---|---|---|
| M1 是否有**菜品级销量**（份数）| 🔴 **没有** —— M1 的食材成本是**月度整笔**，不是「份数 × 单份」 | `specs/.../开发规范v1.0_ModuleM1_*.md` 全文无菜品级销量；`saveLedger`/`shop_monthly_*` 无菜品明细 |
| 因此能否算"理论总成本差额（金额）" | 🔴 **不能**（缺销量权数） | 同上 |

⇒ **对账形态定为「率对率」，不是「金额差」**（诚实降级，而非硬算）。

### 计算（率对率）

```

M3 侧  标准菜单毛利率 = 1 − Σ(卡 unit_cost_fen) ÷ Σ(卡挂牌售价)
        · 权重 = 售价（隐含"各菜品销售额均匀"假设）
        · **默认排除套餐**（card_type=3），避免同一道菜被计两次；页面可切换"含套餐"
M1 侧  实际菜品毛利率 = (菜品口径收入 − 食材成本) ÷ 菜品口径收入
        · 菜品口径收入 = income_dine_* + income_takeaway_goods
        · **排除** income_takeaway_pack / ..._subsidy / income_other_*（D18）
输出   差值(pp) + 折算金额 = 差值 × 本月菜品口径收入
```

### 🔴 覆盖率闸门（D17 · fail-closed）

- 覆盖率 = 已建卡菜品数 ÷ 菜单菜品数。
- **覆盖率 < 60% ⇒ 抑制**：只显示两个数，**不给差值、不给金额、不给归因**（样本偏差会让差值失真）。
- 理由：若只建了 3 张卡且都是高毛利菜，差值会把人引向错误结论。该闸门**不参与任何成本计算**。

### 归因清单（只列方向，**不许自动下结论**）

① 有菜没建卡（覆盖率缺口，可直接算） ② 卡内价 ≠ 原料现价（多少张卡用旧价，M3 自算） ③ 出品超耗 / 损耗 / 报废 / 赠送 ④ 口径差异（外卖到手 vs 总额法）

### 🔴 三条边界（否则会变成 M1 的污染源）

1. **只读对照，绝不自动写入 M1 任何字段**；
2. 差额**只做归因提示**，不许下结论"你被偷了"；
3. 无销量口径时**不碰差额**（本能力已按此降级）。

### 复算锚点（已实测）

| 锚点 | 输入 | 结果 |
|---|---|---|
| **D 标准菜单毛利率** | 宫保 2800/975 + 糖醋里脊 3200/1120 + 米饭 300/120 | (6300−2215)/6300 = **64.84%** |
| **D 差值** | M1 实际 55% | **9.84pp** ⇒ 折算 **9840 元**（营业额 10 万）|
| **D 抑制** | 覆盖率 3/12 = 25% | 25% < 60% ⇒ **抑制生效**，只显示两个数 |

### 未来扩展路径（写明，不实现）

若 M1 后期引入**销量**口径（或 M3 侧记"售出份数"），则本能力可**升级为金额差额** —— 届时新增锚点，不改本章口径。
