## 0. 为什么必须有这一份

前三份模块规范（A / M1 / M2 / M3）把"怎么算钱"定死了，但下面这些问题**一直没有答案**，属于真实盲区：

- 写完一块定型了，后面出问题从哪修？

- 没营业执照，这小程序到底能不能上线？

**没有这一份，前面写得再对，也会在第一次改需求时失控。**

## 1. 环境隔离（第一优先，开局必须建对）

### 1.1 云开发必须建两套环境

| 环境 | 命名建议 | 用途 | 数据 |
|---|---|---|---|
| **dev** | `catering-dev` | 开发联调、POC 验证、体验版演示 | 测试数据（可随意清空） |
| **prod** | `catering-prod` | 正式发布 | 真实数据（严禁造脏数据） |

> ⚠️ **不建两套环境的后果**：你在 dev 里灌的测试数据（宫保鸡丁、红油底料、模拟月账）会跟老板真实录入的数据混在一起，正式上线后清不掉，且**无法用"回档"单独清除**（回档是按整个集合回滚的）。

### 1.2 小程序三个版本 × 两套环境

微信天然提供三个版本，与云环境的对应关系**必须这样配**：

| 小程序版本 | 谁可见 | 指向云环境 | 说明 |
|---|---|---|---|
| **开发版** | 仅开发者（你） | **dev** | 微信开发者工具里预览，改一行代码刷新一下就变 |
| **体验版** | 体验成员（你自己 + 可信老板朋友） | **dev** | 上传后生成二维码，真机测试用；**不要给真实客户** |
| **正式版** | 所有用户 | **prod** | 提审通过后发布 |

**切换方式**：只改一个常量，不改动任何业务代码。

```js
// config/env.js —— 全项目唯一的环境开关
const ENV_MAP = {
  dev:  'catering-dev',    // 开发版 / 体验版
  prod: 'catering-prod'    // 正式版
}
const CURRENT = 'dev'      // ← 发版前只改这一个字符串
export default { env: ENV_MAP[CURRENT], isProd: CURRENT === 'prod' }
```

### 1.3 环境 ID 禁止硬编码（铁律补充）

- 云函数内统一使用 **`cloud.DYNAMIC_CURRENT_ENV`**，禁止写死环境 ID 字符串。
- 小程序端 `wx.cloud.init({ env })` 只允许从 `config/env.js` 取值。
- 任何在业务代码里出现 `catering-dev` / 环境 ID 字面量的，视为违规。

### 1.4 测试数据纪律（写死）

1. **prod 环境内严禁录入任何测试/示例数据。** 新店初始化只有空账，不预置示例。
2. dev 环境用 `02_模拟测试数据集.md` 的 S1~S4 全部灌一遍，作为**长期冒烟数据**。
3. dev 环境可随时清空重建；**清空前不做备份**（它是测试数据）。
4. 每次正式发版前，必须在 dev 环境完整跑一遍 22 项验收清单，全绿才允许切 prod 提审。

## 2. 代码版本与分支（GitHub 是唯一事实源）

### 2.1 仓库与分支策略

仓库：`https://github.com/lzj888888/catering-profit`

| 分支 | 用途 | 保护 |
|---|---|---|
| `main` | 已验收、可部署/可提审 | ✅ **受保护**，禁直推，只能 PR 合入 |
| `feature/inscode-<模块>-<日期>` | InsCode 生成的模块代码 | 否 |
| `feature/local-<模块>` | 本地 WorkBuddy 细化/修计算逻辑 | 否 |
| `fix/<问题简述>` | 缺陷修复 | 否 |

**协作口诀**：InsCode 写代码 → 推 GitHub → 本地验收 → 合 main → 部署/提审。
**InsCode 与本地不直连**，只通过 GitHub 交换代码。

### 2.2 语义化版本 tag

格式：`v<主>.<次>.<修订>`，例 `v0.1.0`

- **主版本**：数据模型破坏性变更 / 大重构
- **次版本**：新增模块或功能（如"M2 反推上线"）
- **修订**：缺陷修复、文案调整

每个 tag 必须附 `CHANGELOG.md` 一条记录（日期 + 变更 + 影响范围 + 是否需要数据迁移）。

> GitHub tag 与 InsCode 版本历史**双备份**，冲突时**以 GitHub 为准**。

### 2.3 密钥与配置纪律

- 任何 AppKey / 商户号 / API Secret **只放云函数环境变量**，**绝不进客户端代码、绝不进 Git**。
- 仓库内只提交 `.env.example`（键名留空，不含真实值）。
- `.gitignore` 必须包含：`.env`、环境 ID 配置文件（如含真实 ID）、`node_modules`、`project.config.json` 中的个人配置段。

## 3. 数据版本与迁移（schema_version 预埋）

### 3.1 每条记录带版本

所有业务表（含 A 类 6 张 + B 类 9 张）**从第一版建表起**就必须带：

```
schema_version  INT  DEFAULT 1     -- 记录结构版本
```

> **现在不加，v1.1 加字段时就没有凭据判断"这条老数据要不要迁移"。** 这是 P0 预埋项，不能省。

### 3.2 字段变更三档处理

| 档 | 场景 | 处理 | 是否需要迁移脚本 |
|---|---|---|---|
| **兼容** | 新增可空字段 | 老数据默认为空/默认值 | ❌ 不需要 |
| **需迁移** | 字段改名、类型变更、单位变更（如元→分） | 写迁移脚本 | ✅ 必须 |
| **破坏性** | 结构重排、表拆分 | 写迁移脚本 + 双写过渡期 | ✅ 必须 + 主版本号 +1 |

### 3.3 迁移脚本规范（四条铁律）

1. **幂等**：可重复执行，重复运行不产生脏数据（靠 `schema_version` 判断跳过）。
2. **可回滚**：迁移前自动导出受影响集合到云存储。
3. **留痕**：每跑一次写一条 `audit_log`（action = `SYSTEM_SCHEMA_MIGRATE`）。
4. **不删老字段**：v1.1 迁移时老字段保留至少一个版本周期，确认无人引用后再下掉。

### 3.4 迁移前必做

> **任何迁移脚本执行前，先按第 4.3 节做一次全量导出快照。** 没有快照不执行。

## 4. 备份与回滚（用户问的核心：改坏了从哪回滚）

### 4.1 四层回滚对照表 ⭐

**回滚不是一个动作，是四件不同的事。** 先判断你坏在哪一层：

| 层 | 坏了的表现 | 在哪回滚 | 时间窗 | 粒度 |
|---|---|---|---|---|
| **① 代码** | 改了代码后功能不对 | **GitHub**：`git revert` 到上一个 tag → 重新部署云函数 | 永久 | 整个版本 |
| **② 云函数** | 只改了一个云函数就出错 | **云开发控制台 → 云函数 → 版本管理 → 回退上一版本** | 保留最近若干版本 | 单个函数 |
| **③ 数据库** | 批量写错 / 误删大量数据 | **云开发控制台 → 数据库 → 选集合 → 回档**（可选 7 天内任意时间点） | ⚠️ **仅 7 天** | 整个集合 |
| **④ 业务数据（最常用）** | 单条记录错了 / 删错了 | **用我们自己的功能**（见 4.2） | 30 天或永久 | 单条 |

> **③ 的警告**：回档是**整个集合**回滚到某一时刻，回档期间该集合的**所有新数据都会被覆盖**。所以它能救急，但不能当日常工具用 —— 日常靠 ④。

### 4.2 业务级回滚（我们自建，粒度最细）

| 场景 | 在哪回滚 | 时限 |
|---|---|---|
| 成本卡删错了 | 回收站 / 软删除恢复 | **30 天内**（到期物理删） |
| 成本卡改错了 | 成本卡「版本历史」→ 恢复为最新版（本质 INSERT 新版本，旧版本永不丢） | **永久** |
| 原料删错了 | 原料回收站（软删除恢复） | **30 天内** |
| 沙盘方案删错了 | 沙盘回收站 | **30 天内** |
| **某月账目算错了** | ⚠️ **不回滚，新增调整记录**（见 5.4） | 永久可追溯 |
| 专业模式重算错了 | 再次重算（连锁）+ 留痕；或回退开关 | 永久 |

### 4.3 备份节奏（写死）

| 频率 | 做什么 | 存哪 | 保留 |
|---|---|---|---|
| **自动** | 云开发数据库自动备份 | 云开发托管 | 免费版 7 天 |
| **每周** | 定时云函数导出全部集合为 JSON | 云存储 `/backup/weekly/` | **12 周** |
| **每次发版前** | 手动导出全量快照 | 云存储 `/backup/release/` | 保留最近 5 个版本 |
| **每次迁移前** | 导出受影响集合 | 云存储 `/backup/migrate/` | 永久 |

导出走**异步任务**（`export_task`），禁止同步大文件导出（云函数 60 秒超时，铁律）。

### 4.4 回滚演练（每季度一次，首次必做）

首次上线后一周内做一次演练，验证三件事：
1. 从 GitHub 上一 tag 重新部署，能否跑通；
2. 从周备份 JSON 恢复到 dev 环境，数据能否完整还原；
3. 软删除恢复 30 天机制是否真的生效。

**演练必须在 dev 环境做，禁止在 prod 练手。**

## 5. 出问题的修复流程

### 5.1 缺陷分级

| 级别 | 定义 | 响应 | 举例 |
|---|---|---|---|
| **P0 阻断** | 钱算错了 / 数据丢失 / 无法登录 | 立即停新功能，当天修 | 双利润口径串了、9.75 算成 9.73 |
| **P1 严重** | 功能不可用但有替代路径 | 3 天内 | 导出失败、循环拦截误报 |
| **P2 一般** | 体验问题、文案错误 | 下个版本 | 排序不对、颜色错 |
| **P3 建议** | 优化项 | 排期 | 加载慢 |

> **涉及金额计算的一律按 P0 处理**，不管影响范围多小 —— 假账比没账更可怕。

### 5.2 定位路径（按顺序排查，别乱猜）

```
现象 → 属于哪个模块？（A 收入费用 / M1 月度 / M2 沙盘 / M3 成本卡）
     → 属于哪一层？（前端显示 / Service 计算 / DataAdapter 存取 / 数据本身）
     → 用测试集锚点复现：
         金额不对 → 先跑 POC3（双利润）或 POC1（摊销）或 POC2（BOM）
         数据不对 → 查 audit_log，看是谁在什么时候改的
         显示不对 → 查单位换算（分↔元、克↔斤）与四舍五入
```

**黄金规则：先用测试集锚点复现，再动代码。** 复现不了的问题不许猜着改。

### 5.3 修复纪律（四条）

1. **不在 prod 环境直接改数据救急。** 要走功能或迁移脚本，留 audit_log。
2. **不在 prod 环境热修代码。** 必须在 dev 修完 → 跑通 22 项验收 → 合 main → 部署。
3. **修完必跑回归**：动过哪个模块，就跑哪个 POC 的锚点（POC1 摊销 / POC2 BOM / POC3 双利润）。
4. **改一处要问连锁**：改 M3 成本卡 → 影响 M1 毛利？改摊销 → 影响专业模式重算链？

### 5.4 已归档月账出错怎么修（重要，规范里没写清）

M1 铁律是"归档不可改"，那错了怎么办 —— **不回滚、不删，新增调整记录**：

1. 在原月账上**新增一条调整记录**（`adjust` 类型），记明：调整原因、调整金额、调整人、时间。
2. 原记录**永不修改、永不删除**，保持可追溯。
3. 报表展示时 = 原值 + 调整值；**同时展示"原始值"与"调整后值"两行**，不掩盖。
4. 调整记录本身写 `audit_log`，action = `M1_ADJUST_CREATE`。
5. **反归档**（把已归档月改回可编辑）：仅限老板/管理员角色，且必须二次确认 + 留痕；**已出过对外报表的月份不建议反归档**。

### 5.5 每个模块定型后的"改动守则"

用户原话："写完一块定型了，然后再往下写出了问题从哪修"

| 情况 | 从哪修 |
|---|---|
| 定型模块本身有 bug | `fix/<模块>-<问题>` 分支 → dev 修 → 回归该模块 POC → 合 main |
| 新模块开发时，发现定型模块设计有缺陷 | **停下来**，先记入 `05_审计单.md` 变更单，评估影响面；不许"顺手改" |
| 改定型模块的字段/公式 | 属于**破坏性变更** → 主版本号 +1 + 迁移脚本 + 重跑全部 POC |
| 只是文案/显示调整 | `fix/` 分支，不跑 POC，但需过一遍 22 项验收中的相关项 |

## 6. 并发与幂等（防重复、防覆盖）

### 6.1 幂等（必须做，MVP 就要有）

弱网点两下提交 → **两条账**，这是餐饮老板最常踩的坑。

- 所有**写操作**必须带 `client_request_id`（前端生成 UUID，同一动作重试时不变）。
- Service 层建唯一索引 `(shop_id, client_request_id)`，重复请求直接返回首次结果，**不报错、不重复写入**。
- 适用场景：录入收入/费用、保存成本卡、保存沙盘、月度归档。

### 6.2 乐观锁（防覆盖）

- 月度账、成本卡、沙盘方案加 `version` 字段。
- 更新时带 `WHERE version = <读取时的 version>`，不匹配则提示"数据已被他人修改，请刷新"。
- MVP 若确定单人使用，可降级为"后写覆盖 + audit_log 留痕"，但**字段要先留着**。

### 6.3 归档锁

- 月度账 `is_archive = true` 后，除"新增调整记录"外**拒绝一切写操作**，Service 层拦截。

## 7. 角色与权限（MVP 简化，结构预埋）

### 7.1 三角色定义（来自历史素材）

| 角色 | 能做什么 | 金额可见性 |
|---|---|---|
| **老板 / 店长** | 全部：维护进价、看报表、导出、归档 | ✅ 全部可见 |
| **厨房主管** | 审核、设标准、录成本卡 | ✅ 可见成本与毛利 |
| **厨师** | 称重录入、看自己那张卡 | ❌ **后端不返回金额字段** |

> **"后端对厨师角色直接不返回金额字段"** —— 必须在 Service 层过滤，不是前端隐藏（前端隐藏可被抓包）。

### 7.2 MVP 落地建议

- **v1.0：默认单角色**（老板），所有用户 = 老板权限。因为 MVP 面向夫妻店/单店，角色隔离是过度设计。
- **但数据结构从第一天就带 `role` 字段**，v1.1 加角色时不用改表。
- 多店场景：`shop_id` 隔离已实现，v1.1 再加"跨店汇总"视图。

## 9. 合规与审核（决定"能不能上线"，不是"好不好用"）

### 9.1 主体资质现状（当前最大外部约束）

| 现状 | 影响 |
|---|---|
| **营业执照未下来** | 只能注册**个人主体**小程序 |
| 个人主体 | ❌ **不能开通微信支付** ❌ 不能开虚拟支付（会员订阅） |
| 后果 | 订阅收费在执照下来前**物理不可行** → 只能靠 `source=manual` 人工开通 |
| 执照下来后 | 换/升级为**个体工商户主体** → 可申请虚拟支付（2026 年个体户可开，审核更严）→ 打开 `enable_real_payment` |

> 这与 D1「支付预留 + `shop_subscription` 双来源」完全吻合：**现阶段订阅就是靠人工开通**，支付只是未来的自助入口。现在不用纠结支付。

### 9.2 类目选择

- 建议类目：**「工具」类下的信息查询/效率工具**（或"生活服务 - 工具"方向）。
- 避免选：金融、投资理财、商业服务-企业管理（后者可能要求资质）。
- 描述中**不出现**：投资回报、回本周期、收益率、理财。

### 9.3 术语双轨表 ⭐（内部术语 ≠ 外显文案）

**规范里怎么叫都行，小程序界面上必须换词**——这是审核风险的实操解法：

| 内部术语（规范/代码/数据库） | 小程序外显文案 | 原因 |
|---|---|---|
| 选址盈利沙盘 | **开店测算 / 选址测算** | "盈利"带收益暗示 |
| 月度盈利核算 | **月度经营** | 同上 |
| 菜品成本卡 | **成本卡** | 精简、口语化 |
| 回本周期 | **收回投入期**（或干脆不展示） | 金融色彩重 |
| 目标利润 | **目标收益** | 同上 |
| 投资回报率 / ROI | **（不出现）** | 高危词 |
| 净利率 | **净收益占比** | 同上 |
| 保本点 / 盈亏平衡 | ✅ **可直接用** | 属经营测算，安全 |
| 毛利率 / 成本卡 | ✅ **可直接用** | 属经营测算，安全 |
| **专业模式**（M1 付费能力位） | **「真实利润」** ⭐ 2026-09-10 拍板 | 对比感最强：免费=经营参考估算 / 付费=库存倒轧真实利润 |
| 付费墙 / 订阅 | **开通 / 升级解锁** | 规避"付费/订阅/会员"虚拟支付审核词 |

**执行方式**：代码与数据库沿用内部术语（保证与规范一致、可检索），只在**页面文案层**做映射。前端建 `i18n/terms.js` 文案表，一处修改全局生效，**禁止硬编码在 wxml/wxss**。

### 9.4 隐私授权

- 首次启动必须调 `wx.requirePrivacyAuthorize()`，弹出《隐私保护指引》。
- 用户协议 / 隐私政策需部署到**可访问 URL**（可放云存储静态托管）。
- 采集范围：**只采集微信 openid**，不强制手机号、不采通讯录、不采位置。
- 明确承诺：**不做数据变现、不出售给第三方**。

### 9.5 免责声明（常驻，不只是提示）

每个结果页底部固定一行：

> 本工具计算结果仅供参考，不构成任何投资、经营决策建议。请结合门店实际情况判断。

### 9.6 账号注销（合规硬要求）

- 必须提供「注销账号」入口。
- 注销 = **物理删除**数据库 + 云存储全部数据（不是软删）。
- **删前强制导出备份**给用户（合规要求，违反《个人信息保护法》有风险）。
- 注销写 `audit_log`，action = `SYSTEM_ACCOUNT_DESTROY`。

## 10. 数据可携与退出（老板要换系统怎么办）

- **导出**：全部业务数据支持导出 Excel/CSV（走 `export_task` 异步）。月报支持 PDF。
- **导出走异步**，禁止同步大文件（云函数 60s 超时铁律）。
- 导出文件设**有效期**（建议 7 天），过期自动清理，避免云存储堆积。
- 免费版导出次数/条数受 `feature_permissions` 限制，订阅版不限（读表，禁硬编码）。
