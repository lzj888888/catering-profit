## 0 定案表（D25~D32）

| 编号 | 决定 | 理由（为什么不能反过来） |
|---|---|---|
| **D25** | `saveDishMapping` 增批量入参 `items[]`，与单条入参（`dish_key`）**互斥**，同时给 ⇒ 拒 | 单条形态必须保持向后兼容（旧客户端在跑）；互斥而非"优先取其一"是为了避免"我传了 items 却被当成单条"这种静默语义漂移 |
| **D26** | 单批上限 `MAX_BATCH = 20`；**分块在前端**（⌈N/20⌉ 次调用） | 🔴 云端新部署 timeout **默认 3s 且只能控制台改**（`config.json` 不生效）⇒ 单批写库次数必须小。**上限写进纯函数单源**，前端不得自己抄一个数 |
| **D27** | 批内按 `(platform, dish_key)` **去重**，有重复 ⇒ **整批拒** | 同一键写两次 = 后写覆盖前写，而**两次都返回成功** ⇒ 用户看不出哪次生效 |
| **D28** | 卡存在性**先整批校验**；任一 item 的 `card_code` 不在本店（或已软删）⇒ **整批一条不写**，回 `rejected[]` 指出是哪几行 | 原子语义 + fail-closed。若逐条跳过，用户会以为"51 条都挂上了"，实际少了 3 条且无感 |
| **D29** | 落库键**仍用原始 `dish_key`（绝不归一）**；归一**只用于前端的「建议卡」** | 读侧 `mapIndex` 按原样查（R255 铁律）；建议是 **UI 便利**，一旦让它改写数据键就变成"永久查不到"的死输入 |
| **D30** | 未匹配行**就地选择、暂不保存**；底部「保存全部关联（N 项）」**一次提交** | 现状每选一次就 `await this.load()` 重算整页 ⇒ 把 N 次全页往返压成 ⌈N/20⌉ 次 |
| **D31** | 本轮**不做**「忽略 / 不核算」（饮料、配料、"来点辣椒吗"这类口味询问 SKU 无卡可挂） | 需要新语义 + 新数据模型（`card_code=''` 已被「**解除**」占用）⇒ 单独一轮，见 §3 遗留 |
| **D32** | 建议算法 = 归一后 **完全相等 → 双向包含 → 前缀**；**只预选，绝不自动提交** | 归一化匹配**必然会误判**（`★发鱿鱼`→`发鱿鱼` 对；但"来点辣椒?吗"这类**口味询问 SKU 不该匹配任何菜**）⇒ 自动提交＝把误判写进库 |

## 1 入参 / 出参契约（与 `core/10` 同源）

### 单条形态（R255，**不变**）
```
入参 { shop_id, dish_key, card_code, platform?, client_request_id? }
出参 { shop_id, platform, dish_key, card_code, card_name, action, client_request_id }
```

### 批量形态（本版新增）
```
入参 {
  shop_id,
  items: [ { dish_key, card_code, platform? }, ... ],   // 1 ≤ len ≤ MAX_BATCH(20)
  client_request_id?                                    // 整批一个（块级幂等）
}
出参 {
  shop_id,
  batch: true,
  counts: { created, updated, cleared, noop, total },
  results: [ { dish_key, platform, card_code, action }, ... ],   // 与入参同序
  client_request_id
}
```
**失败（`rejected`，不写任何一条）**：
```
{ code: INVALID_PARAM, msg, data: { rejected: [ { index, dish_key, reason } ] } }
```

## 2 判据（机器守，见 `tools/check_dish_mapping_write.js` 段 D）

| # | 判据 |
|---|---|
| D-① | 两种形态互斥：同时给 `dish_key` 与 `items` ⇒ 拒（源码条件-返回形态，非"提到过这个词"） |
| D-② | `items` 非数组 / 空数组 / 超 `MAX_BATCH` ⇒ 拒；上限**取自纯函数单源**（前端不得另抄一个数） |
| D-③ | 批内 `(platform, dish_key)` 去重，重复 ⇒ 整批拒（含"同一菜同平台出现两次"与"空平台与显式平台各一次"两类样本） |
| D-④ | 卡存在性**整批先校验**，且校验位置**早于任何写库**（位置判据，防"先写后拒"） |
| D-⑤ | 落库 `external_ref_id` 仍写**原始 `dish_key`**（不得出现归一化调用） |
| D-⑥ | 前端批量模式：选择只改本地状态（**选择路径内不得出现 `saveDishMapping` 调用**），提交是**独立方法**且分块 ≤ MAX_BATCH |
| D-⑦ | 建议算法**只预选**：`suggestCard` 的返回值不得直接进入提交载荷（提交载荷只来自用户确认后的选择集） |
| D-⑧ | 行为面：真调 `planBatchActions` / `suggestCard` 多组样本（含"口味询问 SKU 不该匹配"的反例） |
