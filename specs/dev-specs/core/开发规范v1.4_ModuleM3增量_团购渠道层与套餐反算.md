## 1 🔴 核心设计原则（沿用 v1.1 §2）：**加一层渠道，不加一层卡类型**

李老师问："做菜品成本卡时，有没有必要让菜品名多个选择（如'团购套餐'）？"

**定案：不要新增卡类型。** 同一份 88 元烤鸭套餐，堂食卖、抖音卖，**成本一模一样**，变的只有费用侧。
若按渠道拆卡类型 ⇒ 同一道菜出现两张卡、两份成本真相 —— **这正是成本卡版本模型踩过的坑**。

```
成本算一次（card_type 只分 1 单品 / 3 套餐）
到手算多次（渠道层：堂食 / 外卖 / 团购）
```

`card_type` 仍**只有 1 和 3**（2 继续空置，v1.1 §M3.16 已定）。

## M3.37 到店团购渠道层

### 计算（纯前端，单源 `utils/grouponDerive.js`）

```
① 团购价 P   = 顾客实付（如 88 元）          ← 🔴 不是原价（188）
② 佣金       = P × 佣金率 c ÷ 100            ← 🔴 基数 = P
③ 推广费     = 商家自填（选填）
④ 到手 R     = P − 佣金 − 推广费
⑤ 成本 Cf    = 本卡 unit_cost_fen（引擎算，与单品/套餐同一条路）
⑥ 到手毛利   = R − Cf
⑦ 到手率     = R ÷ P
⑧ 到手毛利率 = 到手毛利 ÷ R
⑨ 比堂食少赚 = (挂牌价 − Cf) − 到手毛利      ← 仅当填了挂牌价；>0 ⇒ 红字
```

### 复算锚点（已实测，`node utils/grouponDerive.js`）

| 锚点 | 输入 | 结果 |
|---|---|---|
| **C-a 佣金基数** | 团购价 88、成本 30、c=6%、挂牌 188 | 佣金 **5.28**（= 88×6%；误用原价会得 11.28）|
| **C-a 到手** | 同上 | 到手 **82.72**、到手率 **94%** |
| **C-a 毛利** | 同上 | 到手毛利 **52.72**、到手毛利率 **63.73%** |
| **C-a 对比** | 堂食毛利 158 | **比堂食少赚 105.28**（红字）|
| **C-b 不填费率** | c 未填 | 佣金 **0.00**（不替用户编数，R128 同族）|
| **C-c 无挂牌价** | dineFen=0 | `hasDine=false`、`vsDineFen=0`（不猜）|

### 落法（引擎零改动）

- 新建 `utils/grouponDerive.js`（纯计算，与 `utils/takeawayDerive.js` 同构）
- 页面：`pages/card/edit` 增加「团购到手」块 + `calcGroupon()`
- **不新增云函数、不新增集合、不新增字段、不改引擎**（v1.1 §2 铁律）

## 3 🔴 红线（违反即判错）

1. **佣金基数恒为顾客实付价**，用原价算即错（差 6 元/单量级误差）。
2. **佣金率无默认值**：不填即 0，不替用户编。
3. **团购结果不落库、不进 M1**（R135）。
4. **套餐禁嵌套**（`COMBO_NEST_NOT_ALLOWED`）仍生效 —— 子卡候选恒过滤 `card_type !== 3`。
5. **套餐 `calc_mode` 无意义** ⇒ 前端隐藏、后端恒按 A 算。
6. **成本唯一来源 = 引擎** `calcBom`，团购块不得自行另算一份成本。
