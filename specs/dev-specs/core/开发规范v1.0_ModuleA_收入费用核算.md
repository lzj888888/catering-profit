## A.0 记账总铁律（贯穿全模块，写码必须遵守）

1. **权责发生制**：收入按业务发生日确认（外卖=订单日 / 团购=核销日），现金看到账日，二者可跨月。
2. **毛利铁律**：毛利 = 收入 − 营业成本（**仅扣食材耗材**）；净利 = 毛利 − 运营费 − 人工 − 营销 − 其他。**房租 / 人工绝不算进营业成本**。
3. **记账口径**：默认版本 B 实操版（费用合并），连锁可切版本 A 财务版。
4. **精度**：金额统一 Decimal，禁 JS Number 原生运算。
5. **归档**：`is_archive=true` 后禁 update 主记录金额，错账只新增调整记录。
6. **待结算不进利润**：外卖 / 团购待结算是**现金流 / 应收指标**，仅影响现金口径（A.4），**绝不进入月度盈利（毛利 / 净利）计算**。月度盈利只看权责发生制的收入与费用。

## A.3 台账与平台对账（MVP 极简：老板只填 1 个到账数；待结算系统粗估仅供参考）

### 核心原则：MVP 不为中小老板做精确流水账
- 目标用户是**中小餐饮老板**，最关心**本月利润（必须准）**，现金流大致准即可，待结算只是参考。
- 原"外卖 / 团购待结算四字段台账（期初 / 新增应收 / 回款 / 期末）"对目标用户属**过度设计**，MVP **整体删除**。
- 精确四字段台账 + 按平台分列（外卖 / 团购）+ 导入结算明细自动匹配 → 移到 **v1.1 高级开关"精确平台对账"**（面向连锁 / 有财务的老板）。
- > **范围变更说明**：此前 14:03 确认的"D-团购待结算分列"是针对四字段台账的；台账删除后，分列降为 v1.1 高级开关选项，MVP 不区分外卖 / 团购到账。

### MVP 字段（老板手动，仅 1 个平台相关字段）
- **本月平台实际到账合计**（外卖 + 团购合并，1 个数）：老板看银行流水或平台"已结算"汇总，填总数即可。
  - 不拆外卖 / 团购、不填期初 / 期末、不做任何流水账。

### 系统自动估算（仅供参考，不参与利润）
- 🔒 **平台待结算估算** = 本月平台收入合计 − 本月平台实际到账合计
  - ⚠️ **粗估值**：含跨月差异（上月单本月到账、本月单下月到账）及平台已扣费用，仅作"平台大概还欠我多少"的参考，**不做精确对账、不进利润计算**。

### 挂账台账（唯一需手动的账，事件式轻录入，保留）
- 挂账无平台数据，必须手动，但做成**事件触发**而非月度流水：
  - 顾客挂账消费时 → 录一条"挂账增加"记录（金额 + 对象 + 日期）。
  - 顾客还款时 → 标记"已收回"（金额 + 日期）。
- 系统字段（同结构）：挂账期初（= 上月期末滚转）/ 本期新增 / 本期收回 / 🔒 期末。
- 首月种子值：期初挂账余额（用户读一次或默认 0）。

## A.4 现金口径公式（收付实现制）

```
当月现金流入 = 堂食现金微信刷卡 + 私域外卖实收 + 当月储值充值
              + 当月收回往期挂账 + 平台实际到账合计（外卖+团购，MVP 填1个总数）
当月现金流出 = 当月食材实际采购付款 + 所有费用实际现金支付 + 储值退款 + 缴纳税款
当月现金结余 = 流入 − 流出
```
> 注：平台现金流入用 MVP 的"**平台实际到账合计**"（老板看银行流水填的 1 个数），不是本月平台收入（账期 T+3 / T+1 导致跨月）。v1.1 精确版可拆外卖 / 团购到账。

## A.5 核销时点铁律（团购，新增）

- 收入按**核销日**确认（非买券日、非到账日）。
- 顾客上月买券、本月核销 → 收入算本月；本月买券、下月核销 → 收入算下月。
- 平台打款日只影响现金流，不影响收入确认。

---

## A.6 总额法（外卖）vs 净额法（团购）说明（非矛盾）

- **外卖**：账单显式拆出"商家活动补贴" → 总额法（补贴计入收入，同时作费用）。
- **团购**：账单只给净成交价（原价168是划线参考价、无交易意义） → 净额法（商家自促费只作费用）。
- **结论**：两套平台账单结构不同导致两套准则，**会计上均正确，非冲突**。按平台账单实际能取到的数填即可。

## A.7 录入方式（MVP 手动基线，导入为 v1.1 便利）

- **MVP 基线 = 手动填**（更诚实、更好建）：
  - 老板每月导一次平台账单 → 照着填**收入 + 费用**（算利润，必须准）。
  - 看银行流水 → 填**平台实际到账合计**（算现金流，1 个数）。
  - 不做 Excel 解析、不接 API，2 分钟填完，符合小老板习惯。
- **v1.1 便利 = 导入平台账单自动填**：
  - 上传美团 / 饿了么 / 抖音月度账单 Excel → 系统自动解析归类（收入 / 各费用 / 结算金额），自动填入上述相同字段。
  - 平台 API 自动同步（美团 `connectivity-adapter` / 饿了么 `alibaba.wdk.eleme.bill.get`）需商家授权 + 审核，对接成本高，放 v1.1+，MVP 不做。
- **方式 B 净额兜底**：用户只肯填结算金额 → 收入按净额、费用字段隐藏，页面提示"毛利率偏低、看不到费用明细"。整店锁定一种口径，切换提示"月度对比会失真"。

> 👉 **本节是"方式总纲"**：外卖段落到每个字段的**取数路径、填几个数、页面交互、配平校验**，见 **§A.11**（2026-09-22 李老师拍板）。
> ⚠️ A.11 的「粘贴求和」**不属于**本节所说需要 v1.1 的"导入账单 Excel 自动填"——边界见 §A.11.6，两者不冲突。

### A.11.1 设计目标（一句话）

把外卖段要客户填的数字，从 **10 个压到 4 个**，且**每一个数都能在平台后台找到出处**。
- 快速模式：4 个平台各填 **1 个**数（默认路径）。
- 其余数字由**系统自动带出**（活动补贴）或**从账单一次求和**得到。

### A.11.2 收入侧 · 4 个平台 × 1 个数

平台名与顺序**严格取自** `miniprogram/i18n/terms.js::ledger.income.takeaway.items`：

| 序号 | 平台 | 填什么 |
|---|---|---|
| 1 | 美团外卖 | 该平台账单三项之和 |
| 2 | 淘宝闪购 | 同上 |
| 3 | 京东外卖 | 同上 |
| 4 | 其他外卖 | 同上（私域自配送等归此，或按 A.1「私域外卖」单列） |

**这"一个数"的口径（= A.1）**：`商品总价 + 打包费 + 商家活动补贴`。
- ❌ **不是**顾客实付（顾客实付已扣掉平台/商家优惠）
- ❌ **不是**银行卡到账（那是收付实现制，见 A.4）
- ❌ **不是**账单「商家应收款」（那是净额，见 A.6）

### A.11.4 配平校验（把"收入"与"费用"两侧锁在一起）

**目的**：解决老板"收入 ≠ 到账"的困惑，并让"漏填"当场可见。

**(a) 账单内部恒等式（用于理解，不作为机器校验式）**

```
商家应收款 = 商品总价 + 打包费 + 平台补贴 + 用户支付配送费
           − 商家活动补贴 − 技术服务费 − 履约服务费 − 商家配送补贴 − 其他扣款
```
> ⚠️ 此式由平台账单列名**推导**，**尚无真实账单验证**（见 A.11.7 V1–V3）。

**(b) 机器近似校验式（页面实际要跑的）**

因收入口径含「商家活动补贴」、费用侧又把同一笔自动带出，两者相抵，得：

```
应有商家应收款 ≈ 外卖收入合计 − 商家活动补贴 − 佣金 − 配送服务费 − 配送补贴
```
- 客户**另填**一个账单上的「商家应收款」实际值 ⇒ 两侧比对。
- **差额 ≤ 阈值（默认 50 元）**：通过，提示"两侧一致，说明收入与费用都填全了"。
- **差额 > 阈值**：提示"差 X 元，可能漏填了某项扣款"，并列出常见漏项（**推广费 / 商家配送补贴 / 违规扣款**）。
- 🔴 **成立条件（必须写进页面提示，否则会误报）**：上式成立要求「平台补贴」与「商家份额的用户配送费」**不参与**商家应收款。若某平台把「用户支付配送费」计入商家应收款（商家自配送模式常见），差额会**稳定等于该笔配送费** —— 此时应提示"可能是用户配送费未纳入"，**不得判为填错**。

**(c) 专项差额检测：打包费被重复计（本方案特有风险）**

若某平台的「商品总价」列**已包含**打包费，而客户又单独填了「打包费」，收入侧会**多计一次打包费**。
⇒ 症状：差额**恰好等于**客户填的打包费金额。
⇒ 处置：系统对该情形**专项提示**"差额与打包费金额相等，请核对账单『商品总价』是否已含打包费"，而不是笼统报"填错"。

> 🔴 **纪律**：在 A.11.7 的 V1–V3 落定之前，配平校验**只做软提示** —— **不阻断保存、不参与利润计算、不写入任何金额**。

### A.11.5 录入交互（v1.0 定稿）

| 模式 | 客户要做什么 | 适用 |
|---|---|---|
| **快速录入**（默认） | 每个平台填 **1 个**金额框 | 绝大多数老板 |
| **分项录入**（可选） | 每个平台填 **3 个**框（商品总价 / 打包费 / 商家活动补贴），小计自动 | 想逐平台对账 |

**每个金额框旁的「可粘贴」入口（v1.0 就做）**：
- 从账单 Excel 选中一列 → 复制 → 粘进粘贴区 → 系统**只提取数字并求和**。
- 自动跳过**表头文字**、空单元格与说明列。
- 含「合计 / 总计」的行 ⇒ **弹确认**（避免把已算过的合计再加一遍）。
- **原始粘贴内容留存可回溯**（出错能查）。
- 🔁 分项模式填的三个数，**在费用侧自动带出**「外卖活动补贴」（同一笔钱只填一次）。

🔴 **不会粘贴的商家照旧手写** —— 金额框直接写一个合计数即可（快速模式本来就这样）。**粘贴是加速器，不是必经路径**；两条路必须都通，不得把粘贴设为唯一入口。

### A.11.6 与 A.7 的边界（防"规范自相矛盾"）

A.7 写明「MVP **不做 Excel 解析**」、把"导入平台账单自动填"列为 **v1.1**。本节划清界线，否则两条并列即构成矛盾：

| 维度 | A.7 的「导入」（v1.1） | A.11 的「粘贴」（**v1.0**） |
|---|---|---|
| 载体 | 上传 `.xlsx` **文件** | 复制**纯文本** |
| 系统要做的事 | 解析工作簿结构、识别表头、多 sheet、合并单元格、字段自动归类 | 只做「提取数字 + 求和」 |
| 是否读文件格式 | 是 | **否** |
| 是否需要平台字段映射 | 需要 | 不需要（客户自己选列） |

⇒ **两者不冲突**：A.7 所指的"Excel 解析"是**读文件**；粘贴不读文件格式，故不属于该范畴。
