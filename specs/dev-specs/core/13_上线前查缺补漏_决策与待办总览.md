### 5. 云函数 `timeout` 没有单源钉住 — 🔴 上线前必须先改（R86，2026-09-18 实测）

- **实测事实**（`review/evidence/realcloud_20260917/47_timeout_all.txt`，纯读操作）：
  - 线上 dev **实际只部署了 2 个函数**：`initDb` / `smokeTest`（`cli cloud functions list` 原文）。
  - **两个都是 `timeout=3`**（`cli cloud functions info` 原文，`status=Active` / `Nodejs16.13`）。
- **单源缺口**：全仓只有 1 个 `config.json`（`cloudfunctions/initDb/config.json`），内容只有 `envVariables.DEV_ENV_ID`，**不含 `timeout`**
  ⇒ **3 秒是平台默认值，没有任何单源钉住它**，它不是为这 44 个函数做过的决策。
- **与本仓铁律冲突**：`core/06:410` 写「导出走异步，禁止同步大文件（**云函数 60s 超时铁律**）」；
  本仓是按 **60s** 设计的，线上实际是 **3s**。
- 🔴 **风险（按风险处理，不按观测）**：`initDb` 要建 **25 集合 + 40 索引 + 种子**，3 秒内跑不完
  ⇒ **会在建到一半被杀，留下"部分建库"现场** —— 而这正是上线第一步要跑的。
  ⚠️ 该风险**尚未实测**：`initDb` 已初始化过，"已存在即拒绝"的前置会把重跑直接拦下（这正是那条 fail-closed 设计），
  所以**无法用"重跑一次"测时长**；在没有别的证据前不得写成"已经会失败"。
- **波及面**：其余 44 个业务函数**尚未部署** ⇒ 其 timeout 当前不可观测。若部署时同样吃 3s 默认，
  `adminExport`/`exportData`/`calcAmortize`/`adminQueryUser` 这类重活都会撞（导出类本应按 60s 铁律走）。
- **处置（三步，先证后改，不要只把 `smokeTest` 调到 10s 就收工）**：
  1. **定值**：`smokeTest` ≥10s；`initDb`/`adminExport`/`exportData`/`calcAmortize`/`adminQueryUser` 按实际耗时定（导出类对齐 60s 铁律）。
  2. **试单点**：只在一个函数上给 `config.json` 加 `"timeout": <N>`，重发后 `cli cloud functions info` **回读**是否生效。
     ⚠️ 该字段是否被平台接受**尚未证实**，这一步就是去证它。
  3. **二选一**：生效 ⇒ **推广成单源**（合"配置从单源"铁律）；不生效 ⇒ 退在控制台手改，并把最终值补回本表。
- ⚠️ 判"超时值"**只能看 `info` 的 `timeout` 列**；界面「测试结果：成功」只表示**调用**成功，与函数是否跑完无关。

#### ✅ 第二步已实测（2026-09-18 05:2x）：`config.json` 的 `timeout` **不被采纳** ⇒ 只能退控制台

- **实验设计（单点、可回退、dev-only）**：给 `cloudfunctions/smokeTest/config.json` 写 `{"timeout": 20}` → `cli cloud functions deploy -r` 重发 → 回读。
- **执行证据（四个观察点）**：

| 观察点 | 结果 | 出处 |
|---|---|---|
| 部署是否成功 | `success=true` / `13 files` / `packSize=14.6 KB`（上次 14.5 KB） | `cli` 部署输出 |
| 文件是否随包上传 | ✅ 探针 `fsDiag.root` 出现 `config.json` | `review/evidence/realcloud_20260917/48_result_raw_afterdrop.txt` |
| 部署是否生效 | 「最后更新时间」`2026-09-18 03:34:55 → 05:24:52` | 控制台函数列表（点刷新后） |
| **超时值** | ❌ **仍是 3**：`smokeTest \| Active \| timeout 3` | `cli cloud functions info` |
| **超时值（权威面）** | ❌ **仍是 3**：高级配置 → 执行超时 = `3` 秒 | 控制台 → 云函数 → 版本管理 → 「配置」 |

- 🔴 **结论（否定式，附替代路径）**：`cloudfunctions/<fn>/config.json` 里的 `timeout` 字段**不被 IDE CLI 部署通道采纳**
  —— **"该文件随包上传" ≠ "该字段生效力"**。实验文件已**删除还原**（库里不留"看着像生效"的死配置），
  完整留痕见 `review/evidence/realcloud_20260917/47_timeout_all.txt §F`。
- ✅ **唯一可行路径（第三步 · 退控制台）**：
  **控制台 → 云函数 → 选函数 → 版本管理 → 「配置」→ 高级配置 → 执行超时（±秒）→ 确定**。
  取值范围 **1–300 秒**（官方「上传云函数配置」接口 `type=3` 的 `timeout`，单位秒，默认 3 秒）。
  ⚠️ 属**云侧配置变更，必须人工手点**（自动化不代改控制台里的配置值）。
- **待定值（需拍板）**：`smokeTest` ≥10s；**`initDb` ≥20s（建议）**；导出类（`adminExport`/`exportData`）对齐 `core/06:410` 的 **60s 铁律**；其余按实测耗时定。
  **改完必须回读 `info` 的 `timeout` 列复核**（控制台绿字"成功"不算证据）。
- ⚠️ **平台默认运行环境 = `Nodejs16.13`**（`info` 与「配置」对话框两处一致）：该版本已 EOL，是否随上线一并评估**另立待办**，本项不掺进来。

#### 🔴 F1【中】`pages/month/result` 在"无账本 / 加载失败"时**永久显示「加载中…」**
- **判据（源码）**：`pages/month/result.wxml:1` = `wx:if="{{!loading && r}}"`；`:67` = `wx:else` 渲染 `{{t.loading}}`（"加载中…"）。
  ⇒ **`&& r` 让 else 分支同时承接"加载中"与"r 为空"两种状态**：只要 `r` 为假（账本不存在，或 `getLedger` 报错被 catch），页面就停在"加载中…"。
- **实测**：`r3`（等 8s）/ `r4`（等 4s）两次复跑，`page.data().loading === false`、`r === null`，界面仍是"加载中…"
  （`06_month_result.png` / `r3_month_result.png` / `r4_month_result.png` 三张同形态）。
- **反例已排除（防误判为系统性问题）**：`grep` 全 `pages/**/*.wxml` —— 其余 **12 页**均为 `wx:if="{{!loading}}"`，
  else 分支**只在 loading 时触发**，属正确写法；`card/index`、`mine/index` 无此分支 ⇒ **本条只针对 `month/result` 一页**。
- **修法（属快马）**：拆三段 —— `wx:if="{{loading}}"` 显示加载 → `wx:elif="{{!r}}"` 显示**空态/错误态**
  （需新增文案，如"本月还没有账本，先去录入" + 跳 `/pages/month/input` 的按钮）→ `wx:else` 显示结果。
- **验收（可证伪）**：无账本 / 断网时**不得再出现"加载中…"**；有账本时结果页渲染与现状逐字一致。

#### 🟡 F2【低】两处"数值占位缺失"（首屏 / 失败态渲染出半截 UI）
- **(a) `pages/month/amortize`**：`amortize.js:38` 的 `data` 只初始化 `totalFen: 0`，**未初始化 `totalYuan`**；
