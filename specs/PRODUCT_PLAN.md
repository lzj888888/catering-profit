## 0. 一句话结论（先给你定心丸）

> **InsCode 是"开发侧的 AI 代码工厂 + 预览/部署沙箱"，它不是运行时依赖。**
> **GitHub 是"代码的单一事实源 + 中立桥"，InsCode 和我（本地 WorkBuddy）都只通过 GitHub 双向同步。**
> **运行时只认"我们自己的后端 + 三端前端"，数据 100% 握在自己手里。**
> **三个模块物理独立，成本核算是 system of record，其他两个模块只读它、不重复存。**

一句话记住：**InsCode 写代码 → 推 GitHub → 我本地验收 → 合并 → 部署/上微信审核。运行时跟 InsCode 一句交道都不用打。**

## 1. 角色与边界（谁干什么，谁不越界）

很多人卡在"AI 平台太多、到底谁管什么"。把边界钉死，后面才不会乱。

| 角色 | 干什么 | 不干什么（边界） |
|---|---|---|
| **你（人/老板）** | 注册个体户主体、微信认证、过审核、做行业决策、录入真实数据、定价 | 不写代码、不配服务器 |
| **InsCode(快马)** | 用自然语言/截图/博客链接**生成**小程序前端+后端代码；提供浏览器内云端 IDE；**一键部署预览**；版本历史/回滚；**Git 直连 GitHub** | 不碰你的用户数据；不做最终审核决策；不持有你的业务 know-how |
| **本地 WorkBuddy(我)** | 写/细化**核心计算逻辑**与复杂业务；**验收闸门**（跑公式单测、扫 110 规范、核对字段）；自动化脚本；把验证过的代码 push 回 GitHub | 不替代 InsCode 的"快速生成"；不替你做主体注册/审核 |
| **GitHub(仓库 catering-profit)** | 代码的**唯一事实源**；InsCode 与我之间的中立桥；分支/PR/历史 | 不存业务数据（只存代码与 spec） |
| **运行时后端（自建 Node / 或 MVP 云开发）** | 真正跑计算、存数据、做用户隔离 | 与 InsCode 无运行时耦合 |
| **三端前端（微信/抖音/小红书）** | 获客/留存/展示，统一调后端 API | 不直连对方库、不存核心数据 |

**为什么不让 InsCode 进运行时？** 三个原因：① 数据自主（用户隔离/隐私合规全在你手里，不依赖第三方平台是否在线）；② 避免厂商锁定（InsCode 停服也不影响已上线小程序）；③ 成本可控（运行时走自己后端，不为"AI 平台常驻"付费）。

## 3. 三模块深度整合（需求 + 公式 + 字段 + 边界）

> 三个模块相互独立部署，但**成本核算是地基**。月度盈利用"标准成本/毛利"做输入，选址用"行业毛利率基准"做输入——都来自成本卡或配置，不重复存。

### 3.1 模块一 · 餐饮月度盈利计算

**定位**：单店月度经营快照 + 盈利诊断。双视角：经营视角（含摊销/权责发生制）vs 现金流视角（不含摊销）。

**输入（每条记录 = 一个月一个店）**
- 收入 `revenue`
- 食材成本（**倒挤**，非手填）：`期初库存 + 本月采购 − 期末库存`
- 包装成本、人工、房租、能源(水电燃气)、营销、其他经营费
- 三个**独立开关**（false 时该项金额=0 且不写入汇总）：
  - `enableInventoryDiff` 库存差开关
  - `enableAssetDepreciation` 固定资产摊销开关
  - `enableFranchiseFee` 加盟费摊销开关

**核心公式**
```
食材成本   = 期初库存金额 + 本期采购金额 − 期末库存金额      // 倒挤，方向绝不能反
毛利       = 收入 − 食材成本 − 包装
经营利润   = 毛利 − 人工 − 房租 − 能源 − 营销 − 折旧摊销 − 其他经营费
净利       = 经营利润 − 税费 ± 非经营收支
月摊销     = 原值 ÷ 摊销总月数                            // 直线法；开关关则当月不扣
保本营业额 = 固定成本 ÷ 毛利率                            // 变动成本已含在毛利率分母里
```
**⚠️ 核验点**：PRD 写"保本 =（固定+变动）÷毛利率"，数据规范写"固定成本÷毛利率"。二者不冲突——毛利率分母已吃掉食材/包装等变动成本，分子只放**固定/半变动成本**（房租/人工/能源/摊销）。口径统一为：**保本营业额 = 固定成本 ÷ 毛利率**。

**警戒线（监控用，区别于 PRD 的"4 红线诊断"）**
| 指标 | 健康 | 预警 |
|---|---|---|
| 毛利率（快餐/正餐） | 55–65% / 60–70% | 低于下限预警 |
| 人工占比 | 18–25% | >25% 预警 |
| 房租占比 | <15% | ≥15% 预警 |

**数据集合（云开发文档型 / 自建关系型映射）**
```json
profit_records {
  "_id","userId","workspaceId","recordName","yearMonth",
  "enableInventoryDiff","enableAssetDepreciation","enableFranchiseFee",
  "inventory":{openingStock,closingStock,diff},
  "assetDepreciation":{totalValue,months,elapsedMonths,monthlyAmount},
  "franchiseFee":{totalFee,months,monthlyAmount},
  "expenses":[{id,name,amount,category:"fixed|variable",seasonalMonths}],
  "resultSnapshot":{grossProfit,netProfit,netProfitRate,breakEvenRevenue},
  "version","isDeleted","createdAt","updatedAt"
}
```

### 3.2 模块二 · 选址毛利倒推

**定位**：给一个"想开/在看的店"，输入房租/人工/水电/毛利率，反推"要做到多少营业额才保本、要赚 1 万/2 万要多少营业额"，并做风险评级。

**输入（全部变量联动可改）**
- 房租（可按面积×单价预估）、人工（可按人数×人均）、水电燃气（按面积或参考值预估）、其他费用
- 毛利率（自选 55%/56%…，或选行业参考值）
- 目标盈利（1 万 / 2 万…）
- 品类（火锅/奶茶/快餐…），决定读取哪组行业参考
- 选址硬条件勾选清单：上下水、明火、燃气、三相电、排烟

**核心公式**
```
保本营业额   = 固定成本总额 ÷ 毛利率
目标营业额   = (固定成本总额 + 目标利润P) ÷ 毛利率     // 元宝#8 修正：分母是毛利率不是利润率
房租占比     = 房租 ÷ 营业额          // 与行业阈值比
人工占比     = 人工 ÷ 营业额
风险评级     = 房租占比/人工占比 是否超行业上限 → 高/中/低 + 风险原因数组
```
**⚠️ 核验点**：倒推不是正向计算。用户输"想赚 1 万"，求的是"所需营业额"，不是"营业额 X 时能赚多少"。分母必须用**毛利率**（(营收−食材)/营收），不能用误混的"利润率"。

**行业参考值（独立配置集合，绝不在代码里写死）**
```json
app_config.industry_ref {
  "火锅":   {defaultMargin:0.60, rentRatioLimit:0.20, laborRatioLimit:0.25},
  "奶茶":   {defaultMargin:0.70, rentRatioLimit:0.15, laborRatioLimit:0.20},
  "快餐":0.65, "正餐":0.68, "茶饮咖啡":0.75, "烘焙":0.70, "烧烤":0.66  // 品类毛利率基准
}
```
**数据集合**
```json
location_analysis {
  "userId","workspaceId","storeName",
  "inputs":{rent,rentArea,laborCost,laborCount,utilitiesBase,utilitiesPerArea,otherCost,grossMarginRate,targetProfit,category},
  "industryRefSnapshot":{maxRentRatio,maxLaborRatio,riskLevel},  // 写入时冗余快照，允许与当前配置不同
  "locationTags":["明火","上下水","三相电","排烟"],
  "result":{totalFixedCost,breakEvenRevenue,targetRevenue,riskLevel,riskReasons[]}
}
```

### 3.3 模块三 · 菜品成本核算（成本卡 / BOM）—— system of record

**定位**：餐厅配方保险柜。称重出标准成本卡 → 老板填售价 → 算毛利/毛利率 → 版本沉淀 → 离职交接不丢。是最该先做、价值最直接的模块。

**底层统一公式（万变不离其宗）**
```
单份成本   = 实际投料总重量 × 当前单价 ÷ 实际出品份数
毛利额     = 售价 − 单份成本
毛利率     = (售价 − 单份成本) ÷ 售价 × 100%
目标售价   = 单份成本 ÷ (1 − 目标毛利率)        // 例：成本8元要60%毛利→8÷0.4=20元
净料率     = 净重 ÷ 毛重                          // 例：毛芹菜500g→350g
半成品单位成本 = 总投入成本 ÷ 总产出净重           // 高汤/老卤/底料
实际成交毛利率 = (实收均价 − 标准成本) ÷ 实收均价  // 套餐/满减后的真实毛利（宪法#9）
偏差率     = (实际单份成本 − 标准单份成本) ÷ 标准单份成本
```
**大份/小份系数**：大份 1.5、小份 0.6（同一张卡的系数缩放，重量与成本同乘，禁止只乘重量）。
**单位铁律**：重量全存**克**，金额全存**整数分**（¥1=100）。

**三种诞生方式**
1. 称重建卡（最标准）：主管+厨师称重→输份数→系统算单份成本→老板填售价→存 v1.0
2. Excel 批量导入（冷启动）：老板下模板→一键导入→每道菜自动 v1.0（创建人"系统迁移"）
3. 校准后自动新版本：抽检称重→算偏差→≤5% 自动 v1.1 / 5~10% 自动+通知主管 / >10% 老板审批后新版本

**系统宪法（#1–#10 + 3 暗坑，写入给 AI 的指令，逐条必须落实）**
| # | 铁律 | 落实动作 |
|---|---|---|
| 1 | 厨师端金额物理隔离 | 后端对 ROLE_COOK **直接不返回** price/gross_profit/unit_cost 字段 |
| 2 | 厨师端不显示任何金额 | 连"本次总花费"都删，只显"本次称重总克数" |
| 3 | 偏差>5% 强校验 | 保存按钮置灰直到原因文本框有内容 |
| 4 | 改单价不回溯历史 | 食材 current_price 变，**禁止 UPDATE 历史成本卡**；新卡取当前价写 JSON 快照 |
| 5 | 半成品不递归拆分 | 成本=引用重量×(总投入÷总产出)，只扣库存不展开原料 |
| 6 | MVCC 只增不改 | 禁止 UPDATE 成本卡版本表，任何修改 INSERT 新行、旧行 is_latest=0 |
| 7 | 净料率 NOT NULL + 0<rate<1 校验 | 否则报错 |
| 8 | 份数+金额不同屏 | 页面有"出品份数"输入框时，该页所有金额字段自动隐藏 |
| 9 | 毛利分两层 | 成本卡算理论毛利；驾驶舱导入实收均价算实际毛利；实际连续 7 天低于理论 10pp 预警 |
| 10 | 预警最小样本量 | 触发 L2/L3 前近 7 天该菜订单≥5 笔，否则只记日志不报警 |
| 暗坑2 | 超时自动采纳 | 待审批超 24h 降级黄、超 72h 系统自动批准+日志 |
| 暗坑3 | 基准锚定 | 新版本生效清空该菜挂起 L2/L3 偏差预警，旧记录打 baseline_version 标记 |

**6 张表（开发直接建）**
```
ingredients(食材: id,名称,单价,默认净料率)
semi_finished(半成品: id,名称,总成本,总净重,单位成本,衰减阈值,风味系数)
cost_card_versions(MVCC核心: JSON快照, 只增不改, is_latest)
calibration_records(偏差率 GENERATED 列, 审批状态机)
order_summary_import(实际毛利, CSV 导入, MVP 不接收银 API)
alert_records(级别 L1/L2/L3 + 超时状态机)
```

**模块独立性（R15–R16 用户拍板）**：三模块各自独立库+独立后端+独立前端页面，**仅通过只读 HTTP GET API 通信**。月度盈利/选址调成本卡的查询接口拿标准成本/毛利，禁止直连对方库、禁止写对方库。好处：AI 写错一个模块只修一个，不连坐。

## 4. 用户隔离方案（核心，必须做对）

### 4.1 账号与租户（单库多租户）
- 微信 `openid` → 映射为内部 `userId`（云函数 `getWXContext().OPENID` 取，**禁止前端传**）。
- 预留 `tenantId` / `workspaceId`：现在多默认 `ws_001`（单店），未来多店/连锁/品牌总部直接扩，不重构。
- 所有业务表**必带** `userId` + `workspaceId`；查询必带 `userId == 当前用户` 过滤。
- 关系型库用行级安全策略（RLS）或中间件统一注入 `WHERE tenant_id=? AND user_id=?`，前端永远拿不到别人的数据。

### 4.2 角色隔离（成本核算模块特有）
- 三角色：厨师（称重录入/看自己卡）/ 厨房主管（审核/设标准）/ 老板店长（维护进价/看报表/导出）。
- **物理隔离优于时间隔离**：宪法 #1/#2/#8 让后端对厨师角色直接不返回金额字段，前端根本没数据，杜绝抓包篡改。
- 夫妻店/3–4 人极简版可砍掉角色隔离（老板即厨师，看啥都透明）。

### 4.3 订阅隔离
- `user_subscriptions { plan:'free'|'pro'|'flagship', status, expiresAt, graceDays, autoRenew }`
- `feature_gate` 表控制功能分级；过期用户**可看历史/可导出**，但新建/编辑按钮 disabled + 引导续费（不重构即可收费）。
- 订阅价格存 `app_config`，**前端读取不写死**，改价只改数据不发版。

### 4.4 多端打通（来自 PRD）
- 三端（微信/抖音/小红书）独立前端、统一后端；**手机号作 union key** 归一。
- 每端首次使用绑定手机号，三端 openid 关联；抖音做的测评/记录微信里也能看。

### 4.5 合规硬要求
- 手机号、位置信息弹窗**单独同意**，不可默认勾选。
- **数据可携带权**：提供"导出全部个人数据"（JSON+Excel 压缩包）。
- **账号注销物理删除**：数据库+云存储真删，删前强制导出备份（违反《个人信息保护法》会出大事）。

## 5. 数据存储方案（核心，防紊乱）

### 5.1 单位铁律（违反即返工）
- 金额：**整数分**（¥1=100），展示时 ÷100；除法统一 `Math.round()` 四舍五入，禁止截断。
- 重量：**克**。录入时做单位选择器（斤/两/件/箱→克自动换算）。
- 时间：**Unix 毫秒时间戳（Number）**，禁止混用 Date/字符串/ISO；查询用 Number 范围比较。

### 5.2 集合/表总览（13 + 6 融合）
账户店铺：`user` `store` `store_member` `workspaces`(账套)
月度快照：`month_snapshot` `profit_records` `voucher_detail`
库存/摊销：`inventory_snapshot` `purchase` `amortization_rule` `asset` `amortization_detail`
成本卡：`ingredients` `semi_finished` `cost_card_versions` `calibration_records` `order_summary_import` `alert_records`
订阅权限：`subscription` `payment_order` `feature_gate` `user_subscriptions`
配置/支撑：`app_config`(行业参考/订阅价/模板ID) `operation_logs` `feedback` `events` `feature_flags`

### 5.3 隔离 / 版本 / 快照 / 删除 四件套
- **隔离**：每表 `userId` + `workspaceId`，云开发规则 `doc.userId == auth.openid && !isDeleted`；关系型库 RLS。
- **版本**：每条业务记录带 `version`；成本卡用 MVCC（只增不改）。
- **快照**：盈利/选址记录冗余存储当时完整数据（含 `industryRefSnapshot`），禁止只存 ID 引用——历史翻阅永远自洽。
- **软删除**：所有表 `isDeleted` + `deletedAt` + `deletedBy`；查询默认过滤已删。
- **操作日志**：`operation_logs { action, targetId, before, after, time }`，数据被改可溯源。

### 5.4 索引 / 备份 / 导出
- 索引：`createdAt:-1`、`{userId:1, yearMonth:-1, isDeleted:1}` 等复合索引带排序方向，上线前必建。
- 备份：云开发自动备份（免费版 7 天）+ 定时云函数导出；关系型库每日快照。
- 导出：CSV/Excel 加 `\uFEFF` BOM 头（防 Windows 乱码）；导出文件 7 天过期清理；导出限频（同用户 60 秒内拒绝）。

## 7. 更新升级机制（现在就防，以后不重构）

| 维度 | 做法 |
|---|---|
| **代码版本** | GitHub tag（`v0.1.0` 语义化）+ InsCode 版本历史双备份；每次发版附 `CHANGELOG` |
| **数据迁移** | 每条记录带 `schemaVersion`；**任何字段改名/类型变更/结构变更，必须同时写迁移脚本**（读老格式→转换→写新格式→标记完成），旧数据不丢 |
| **功能开关** | `feature_flags` + `app_config` 控制订阅价/功能分级/灰度；新功能先白名单小流量再全量 |
| **热更新** | 小程序 `wx.getUpdateManager()` 检测新版本→弹窗→用户确认 `applyUpdate()`（不能强制重启）；后端配置热加载，改价/改阈值只改数据 |
| **从 MVP 迁自建后端** | 数据模型从第一天就带 `tenantId`/`userId`，计算逻辑抽象在 `server/` 独立服务；云函数逻辑平移到 Node 服务，前端请求地址切换即可，数据零迁移 |
| **防止"写完就要改"** | 模块串行（先菜品卡→再盈利→最后选址）；架构一次性定死；给 InsCode/AI 的 prompt 把公式与开关钉死 |

## 8. 合规 / 上线 / 成本（速查，来自 PRD + 规范）

- **主体**：个体工商户注册 + 微信认证 300 元/年（个人主体开不了虚拟支付）。
- **隐私**：首次启动 `wx.requirePrivacyAuthorize()` 弹《隐私保护指引》；用户协议/隐私政策部署到可访问 URL。
- **支付**：微信虚拟支付 `wx.requestVirtualPayment`（首笔1%/后续10%/iOS12%）；抖音担保支付 `tt.pay`（0.6%/1%）。
- **分销**：**代码里分销页面/云函数全部用 `// TODO` 占位，不提交审核版本**（微信禁多级分销，否则必拒）；只留 `reserved_1~5` 字段和空函数。
- **类目**：选"生活服务-工具"，描述不出现"投资回报/回本周期"，用"经营测算"替代。
- **成本预估**：10 万用户云开发约 3000 元/月（占营收<0.3%）；自建后端更低。**成本不是瓶颈，架构才是。**
