# R742 · 摊销「万无一失」不变量守卫（李老师五问）

李老师原话：「关于摊销这块，尤其跨月数据是否正常，包括增加新的摊销、重叠摊销是否随店铺随月份变动，
这点很重要，你有何良策，把这块数据能确保后面万无一失？包括数据库的正常。」→ 拍板「听您的」。

## 把五问拆成可判红断言 → tools/check_amort_invariants.js（21 条，已注册进 verify_all，套件 321→322）

| 原话 | 风险 | 断言段 |
|---|---|---|
| 跨月数据是否正常 | 逐月求和蒸发/错位 | C 闭包：摊销和+残值 ≡ 原值 |
| 增加新的摊销 | 中途加一笔，前期月份被偷偷改动 | D 可加性：只从 start_month 起生效 |
| 重叠随店铺/月份 | 同月多笔被合并尾差/漏计、跨店串数据 | E 重叠不重复 + F 店铺纯度 |
| 数据库正常 | 重复行/孤儿shop/非法字段/归档漂移 | G 模拟对账 |

七段：A 三副本同源 + B 朴素/UTC 双口径 336 点一致 + C 闭包 + D 可加性 + E 重叠 + F 店铺纯度 + G 模拟对账。每条带变异回灌。

## 摸现状（读码+实测，不采信自述）
- 生产三副本（getLedger/saveLedger/getAmortSchedule 的 amountForMonth）**当前逐字同源**，但**无守卫钉死**（A 段正是为此）。
- 第四套引擎 calcAmortize（批次2 POC1，走 UTC 锚点）与朴素版从未比对（B 段证明 336 点一致，但纯属"还没人改"，不是有人守）。
- **店铺隔离扎实**：全仓 6 处 shop_amortize 读取全部带 {shop_id}；引擎是纯函数 ⇒ F 通过。
- **归档锁已接上**：saveAsset 新增/编辑/删除三路径都过 decideArchiveLock+applyLockPlan ⇒ 新增 start_month 早于已归档月的摊销被拒。
- **唯一 DB 缺口**：同笔实物资产录两次（两个 asset_id）→ 摊销翻倍，无签名去重（同 shop_id+name+start_month+value_fen+mode）。

## 守卫细节坑（三条）
1. **夹具字段错**：引擎只读 total_value，控制器才把 value_fen 映射成它 ⇒ 夹具必须两条都给，否则 NaN。
2. **闭包判据写反**：提前终止资产未摊余额是残值单独计，正确不变量是「摊销和+残值≡原值」，不是「摊销和≡原值」。
3. **整除资产尾差=base**：用 36000/36 这类整除值做"去掉尾差"变异测不出差异 ⇒ 必须用不整除值（36010）证明 C/B 有牙。

## 需用户拍板的两项（改写入行为 / 新增部署，按先审后合不擅自动）
- **第三层 写入去重**：saveAsset 新增按签名 upsert，从根消灭"同笔资产录两次翻倍"。
- **第四层 真实云端对账 reconcileAmort**：只读云函数扫 dev 的 shop_amortize，跑 G 四类 + 逐归档月"现算 vs 落库快照"漂移，出报告（读操作 fail-safe）。
