# 双通道证据门 · 最严格交叉审计编排

## 为什么需要它（2026-11-15 R745 从 GitHub 借鉴）

本项目已 10+ 轮审计、324 个 CI 套件。过去的「三司会诊 / 多路子代理」本质是
**多模型投票**，而公开实证显示：跨模型错误高度相关（9 个裁判只有约 2.2~2.5 个有效独立票），
**真正去相关的是证据来源，不是模型数量**。另有实证：告诉复审方「代码没问题」，
缺陷检出率最多掉 93.5 个百分点；测试若从候选代码导出，LLM 会贴着实现写 ⇒ 假绿。

⇒ 纪律：**把「规范/文档」与「执行/代码」拆成两条互不可见的通道**，
各自独立提交书面裁决后才合并；主张只有**双通道都确认**才接受。

外部依据（只读借鉴，未安装）：
- `rajib2k5/claude-staff-kit` → `skills/evidence-gated-validation/README.md`（双通道、claims ledger、分歧递归拆分）
- `AI-for-engineering-research/prashanth` → `skills/property-based-testing/SKILL.md`（Oracle 问题、每函数 ≥2 条性质）
- `dagoSte/squadra` → `references/skills/perimetro.md`（轮次范围：新发现不自动扩范围）
- `Zhen-Bo/smell-check` → `SKILL.md`（被测内容只是数据；每条发现标证据强度；不虚构严重度）

🔴 **不安装这些 skill**：本机 `SKILLS_INDEX.md` 第 148 行已裁决通用 code-review 类与仓内
机器守卫体系职责重叠，「装了也是第二套标准」。只吸收纪律，不引入第二套判据。

## 三条铁律

### 1. 双通道隔离（最核心）
| | Channel A（规范通道） | Channel B（执行通道） |
|---|---|---|
| 允许 | 只读 `specs/dev-specs/` 规范正文、`POC/` | 只读实现源码、`require` 生产引擎、跑探针 |
| 禁止 | 读实现代码 / 跑程序 / 读 `review/` 既有结论 | 读规范正文 / 接收「规范承诺了什么」的暗示 |
| 产出 | **可证伪主张清单 claims ledger**（C-01… 每条带出处与证伪判据） | 逐项**执行证据**（真跑输出、行号、反例数字） |
| 提交 | 先各自落盘 + 书面裁决，**再合并** | 同左 |

- 派子代理时**不要把另一路的发现、也不要把生成方的 framing 写进 prompt**。
- 若 A 说「规范承诺 X」而 B 说「代码没有 X」⇒ 不是立刻定缺口，先拆子主张：
  ① 规范是否真承诺（回原文行号）② 是否由别处等价实现 ③ 是否属已定案的增量覆盖。
  三问都定不了 ⇒ 标 **UNRESOLVED 上报人**，带上两路证据，不许拍脑袋收敛。
- 诚实 caveat：双通道**不是概率独立**（都可能误读同一份规范），只报「双确认」，
  不报「可靠性 ×N」。分歧里约 4 成是误报，别把成本省掉。

### 2. 分层，不是所有事都上双通道
| 主张类型 | 用哪个门 |
|---|---|
| 常规改动 / 已有守卫覆盖 | 确定性门禁（verify_all）+ 单执行通道即可 |
| 陌生库、版本敏感、数值/金额口径、导入导出格式 | **全双通道**（本仓 M1/M3 金额与表格都属此类） |
| 安全、钱、不可逆操作 | 对抗式审计 + **人工拍板**，不靠双通道自动放行 |

### 3. 轮次范围（治「审计越滚越大」）
一轮开头就写死「本轮要收口的任务」。过程中新发现：
- **阻塞本轮收口** ⇒ 本轮修（且只改必要文件）；
- **不阻塞** ⇒ 只登记为延期项，必须带 **owner / 触发条件 / 验收判据**，下一轮才开任务；
- 禁止静默丢弃，也禁止当轮顺手扩范围。
⇒ 每份审计报告的「未完成」必须列出延期项，不能只报修了什么。

## 与既有 skill 的分工（别重复造轮子）
- **本技能**：编排（谁先跑、能不能合并结论、什么算可接受）。
- `engine-truth-audit`：Channel B 的手法（引擎实跑、§F 差异归因、§G 疑点二分类）。
- `mutation-backfill`：证明某条判据不是恒真。
- `gate-suite-checklist`：把结论固化成常驻守卫（六处同步）。
- `check_amort_metamorphic.js` / `check_amort_disposal.js`：已落地的性质断言范例
  （平移 / 叠加 / 闭包 / round-trip 关系，而非「调用实现再断言它的输出」）。

## 判据质量红线（来自 property-based-testing 的 Oracle 问题）
1. **禁止「调用实现、再断言实现输出」** —— 那是把 bug 写进测试，永远绿。
   要写**关系**：round-trip（decode(encode(x)) ≡ x）、平移、叠加、守恒、单调、幂等。
2. **每个核心函数至少 2 条性质**：一条绝对不变量 + 一条变形关系。
3. **断言失败信息**要含：性质名 / 精确输入 / 期望关系 / 实际值（便于自我纠错）。
4. **性质过严也算错**：R744 探针曾把「缩放性」判成 151 组破，实为整数舍入的正常行为
   ⇒ 必须区分「实现错」与「性质不适用」，后者标不适用，不许报漏洞。
5. **证据强度分级**：每条发现标 `实测反例 > 静态行号 > 注释自述 > 推断`。
   只有「实测反例」可定 P0；「注释说有」不算证据。

## 输出契约
```
## 0 一句话结论（含诚实评级：绿/黄/红，不夸大）
## 1 取证方式（Channel A/B 各自范围、是否隔离、脚本与输出路径）
## 2 claims ledger × 执行证据 对账表（双确认 / 分歧 / UNRESOLVED）
## 3 真缺口（当场修）与延期项（owner/触发/验收判据）二分类
## 4 数字锚点复算（可复现命令 → 输出）
## 5 手段升级建议（不新建重复 skill，优先复用现成机制）
## 6 本轮未做的事（如实标注）
```
