## 二、订正提案 C-1 ~ C-7

### C-1 🔴 `detectShape` 规则 C 列名 **硬阻断**（最高优先级）

```
现状（规范 §3.4）：C ← 存在列名 '商品名称' 且 存在列名 '商品销量'
实测：                                    '商品名称' ✅   '销量' ❌（不是 '商品销量'）
```

**⇒ 原样启用则形态 C 永远判不出**（contradiction：零命中 ⇒ 走 fail-closed ⇒ 提示「这张表不认识」）。

**提案**：规则 C 改为**任一命中即可**（放宽但不失 fail-closed）：

```
C ← 存在列名 '商品名称'（或 '菜品名称'）且 存在列名 ∈ {'商品销量','销量'} 且 存在列名 '销售额'
    且 **不含** '销售方式'（用于与形态 A 区分 —— A 的 R2 含 '销售方式'）
```

🔴 **必须保留与 A 的区分项**（`销售方式`）：否则形态 A 的表（有 `菜品名称`）可能同时命中 C。

### C-2 表头行位置参数化

形态 A = 两行表头（R3/R4）；形态 C = **单行 R1**。
**提案**：`detectShape` 返回值从 `string` 改为 `{ shape, headerRow }`，消去「表头行硬编码」的隐含假设。

### C-3 🔴 `amount` 取数口径改写（§5.3 不适用）

```
§5.3 现状：amount = 「菜品收入(元)」= 销售额 − 优惠
实测形态 C：**无「优惠」列**、**无「收入」列** ⇒ §5.3 无法执行
           且 `销售额` ≠ `订单交易额`（49/49 全不等）
```

**提案**：
- 形态 C 的 `amount_fen = Math.round(销售额 × 100)`
- 🔴 **`订单交易额` 严禁取用**：它是**整单口径**（一单多菜时分摊后仍为整单额）⇒ 取用会**重复计钱**。
  规范须**明文写死禁用**并给理由（否则下一批实现者会「看着也像收入」而误用）。

### C-4 漏斗列不入库（白名单化）

18 列里 **10 列**是规范未预期的漏斗/互动指标（`下单人数`/`带来订单数`/`近30日复购*`/`曝光人数`/`点击人数`/`加购人数`/`加购率`/`点赞数`）。
**提案**：解析采用**白名单取列**（只取 `日期`/`门店编号`/`商品名称`/`销量`/`销售额`），其余列**一律丢弃**且不报错。
理由：与「零新建集合」一致；且这些列的语义（人数类去重口径）未经核对，入库即造脏。

### C-5 🔴 新增告警：`amount=0 且 qty>0`

实测 `来点辣椒吗` qty=43 / amount=0（**占全表销量 36.4%**）。
若不复核，单品毛利复盘会出现「**销量第一、营收为零**」的行 ⇒ 用户会以为程序算错。
**提案**：解析报告单列一类 **`zeroAmountQty`**（原名 + qty + 0 元），并在复盘页对这类行加**「口味询问类 SKU，不计营收」**标注。

### C-6 网格可不完整 ⇒ 禁止补零

实测 51 × 7 = 357 但实得 354（`粑粑肠` 缺 3 天）。
**提案**：规范明文 **「无行 = 无销售，**不补零行**」**。
理由：补零会与「真卖 0 份」不可区分 ⇒ 破坏 §5.1 幂等（重导时 `_id` 序列会变）。

### C-7 形态 C 的 `biz_date` 取自**行内 `日期`**列（非 R2 参数行）

形态 A 从 R2 参数行提「至」日；形态 C **无参数行**，但**每行自带 `日期` 列**。
**提案**：形态 C 按**行**取 `biz_date`（`YYYY-MM-DD`），`_id` 序列 = 该 `(biz_date, 商品)` 组内行序。
⇒ **一表多天**（本例 7 天）⇒ 落库时按天展开为 7 组，**不是** 1 组。

## 三之二、🔴 C-9 · 交付后新发现：**菜品名归一函数双副本、零守卫**（建议并入批次 H）

> 本节为本轮**验收时新查出的**缺口，**与形态 C 无关**，是批次 G 交付本身的问题。
> 但它与形态 C 同批改的量级、且都不涉引擎 ⇒ 建议**并入同一批 H**。

### 事实

| 处 | 副本 | 位置 |
|---|---|---|
| 写侧 | `normalizeDishName()` | `cloudfunctions/importSalesBill/service.js` |
| 读侧 | `normName()`（注释写「与 service.js 同口径」） | `cloudfunctions/getDishReview/index.js` |
| `cloudfunctions/common/` | **无** | ⇒ 未走 `cx_*` 派生机制 |

写侧用它生成 `dish_key` 入库，读侧用它匹配成本卡 `name`。**两份独立实现，零机器判据守着它们一致。**

### 为什么现在必须修（三个理由叠加）

1. 🔴 **微信云函数不能跨函数 require** —— 每个函数独立打包（`tools/sync_common.js` 头注有 2026-09-15 云端实测证据：
   Windows 打包把子目录拼成 `"common\xxx.js"`，云端 `MODULE_NOT_FOUND`）。⇒ `getDishReview` **物理上拿不到**
   `importSalesBill/service.js`，抄一遍是当时唯一出路 —— 但由此埋了漂移种子。
2. 🔴 **失效是静默的** —— 规则一漂移 ⇒ 全部菜匹配不上 ⇒ 落进 `getDishReview` 的 `unmatched`，
   用户看到**「所有菜都没有成本/毛利」**，而**全程无报错**。这正是 PITFALLS 最怕的「静默算错」类。
3. ✅ **现在成本最低** —— 只有 2 份副本、且尚未上云（零真数据）。上云后再发现就是脏数据。

### 修复方案（走既有范式，非新造）

```
① cloudfunctions/common/dishKey.js  ← 单源，导出 normalizeDishName
② node tools/sync_common.js         ← 自动派生 *_/cx_dishKey.js（既有机制，零新逻辑）
③ 两侧改为从 require('./common') 取  ← 共 2 处调用点
④ 新增守卫 C-9：断言仓内不再有本地重写的归一实现 + 两侧归一结果一致
```

合规性：**零新增集合 · 引擎四函数零改动 · 复用已有派生机制**。

## 三之三、🔴🔴 C-10 · 比 C-9 更严重：时间口径违反铁律，**现在已经算错**

> 同族第二例。C-9 是「将来可能漂移」，**C-10 是「现在就算错」**。

### 事实

| | 实现 | 时区 |
|---|---|---|
| 单源 `cloudfunctions/common/utilTime.js::toMonth()` | `getUTCFullYear()` / `getUTCMonth()` | **UTC** |
| `getDishReview/index.js::monthOf()`（重写） | `getFullYear()` / `getMonth()` | **本地时区** |

而单源文件头注释**明文**写着：

> `// 服务端 UTC 时间工具（批次 0 §2.5）。⚠️ 禁止使用前端传入时间。`
> `// 铁律：时间统一 Unix 毫秒 BIGINT / **UTC**；月份 YYYY-MM 字符串。`

### 后果（不是理论，是已有错误路径）

`monthOf(card.created_at)` 的返回值落在 **`snapshot_month`**，前端据此提示用户
**「该卡成本为 X 月快照」**。

中国时区 UTC+8 ⇒ **每月 1 日 00:00~08:00 之间创建的成本卡，两者算出不同月份**：

```
卡 created_at = 2026-10-01T07:00 CST  ( = 2026-09-30T23:00Z )
  monthOf  → "2026-10"   ← 本地时区（错）
  toMonth  → "2026-09"   ← UTC 单源（正确）
```

⇒ 用户被告知「**10 月快照**」，实际与铁律口径差一个月。

🔴 **触发窗口窄（每月前 8 小时）但后果是静默错报**，且**违反明示铁律** ——
与 C-9 同属「明明已有单源、却在函数里重写一份」的同族病。

### 修复（量最小 —— 甚至不需新增 common 模块）

```
删 getDishReview/index.js::monthOf()，改用已派生的能力：
  const { toMonth } = require('./common');      // ← cx_utilTime.js 已在包内
  snapshot_month: toMonth(card.created_at)
```

### 守卫（与 C-9 同组）

① 扫描各云函数 index.js，**禁止**出现 `getFullYear()` / `getMonth()` 等非 UTC 月份构造；
② 禁止出现本地重写的月份格式化 / 菜名归一实现。

## 三之五、🔴🔴🔴 C-11 · **潜伏雷（已实证 0/4 全错）**：Excel 日期单元格会让 `biz_date` 系统性早一天

> 本轮最重的一条。**不是理论推断，是拿真实营业日做的闭环实测：现状 0/4 正确、修后 4/4 正确。**

### 事实（两步实证）

**第一步**：Node 里 `new Date(1899, 11, 30, 0, 0, 0)` 落在 **`GMT+0805`** ——
1899 年中国尚未采用标准时区，tzdata 保留的是 **LMT 地方平时**（比 +0800 少约 5′43″）。

```
basedate 本地 = Sat Dec 30 1899 00:00:00 GMT+0805 (中国标准时间)
basedate UTC  = 1899-12-29T15:54:17.000Z          ← 不是 16:00，差了 5'43"
```

而 SheetJS（`xlsx` 包，`cellDates: true`）正是用这个 basedate 做 `setTime(serial*86400000 + basedate)`
⇒ 得到的 Date **不是整点午夜，而是 23:54:17** ⇒ 取日历日时**系统性早一天**。

**第二步**：拿真实营业日的序列号做闭环验证（`_fixcheck.js`，本机实跑）：

| serial | 期望 | 现状 `fmtCell`（本地 get*） | 修后（UTC基准+四舍五入） |
|---|---|---|---|
| 46278 | 2026-09-13 | **2026-09-12** ❌ | 2026-09-13 ✅ |
| 46272 | 2026-09-07 | **2026-09-06** ❌ | 2026-09-07 ✅ |
| 46296 | 2026-10-01 | **2026-09-30** ❌ | 2026-10-01 ✅ |
| 46250 | 2026-08-16 | **2026-08-15** ❌ | 2026-08-16 ✅ |

⇒ **现状 0/4 · 修后 4/4**

### 🔴 为什么现在还没炸（这点最关键）

不是代码对，是**样例运气好** —— 两张样例表的日期**都不是真的日期单元格**：

| 表 | 日期来源 | openpyxl 实测 |
|---|---|---|
| 形态 A | R2 参数行 `营业日期：【2026/09/07 至 2026/09/13】` | **纯文本长串**（该类 cell 非 Date） |
| 形态 C | 第 1 列 `日期` | `type=str` · 全 **354** 行 · `number_format='General'` · `is_date=False` |

⇒ `fmtCell` 的 `instanceof Date` 分支**从未被触发**，走的是 `String(cell).trim()` ⇒ 恰好正确。

**⚠️ 但 Excel 导出的日期列默认是真日期格式**（`yyyy-mm-dd` 单元格）。李老师下一张表只要日期列被引擎
导出成**日期单元格**而非文本 ⇒ **整张表的 `biz_date` 全部早一天 ⇒ 落库数据全部错位一天，且全程零报错**。
这是「某天突然炸、且炸得静默」的典型。

### 修法（已验证）

```js
// cloudfunctions/importSalesBill/service.js::fmtCell 的 Date 分支
const UTC_BASE = Date.UTC(1899, 11, 30);            // 🔴 必须是 Date.UTC，不能 new Date(1899,11,30)
function fmtDateCell(d) {
  const serial = Math.round((d.getTime() - UTC_BASE) / 86400000);   // 四舍五入消掉 LMT 偏移
  const t = new Date(UTC_BASE + serial * 86400000);
  const p = (n) => String(n).padStart(2, '0');
  return `${t.getUTCFullYear()}-${p(t.getUTCMonth()+1)}-${p(t.getUTCDate())}`;
}
```

### 🔴 由此得到的一条**守卫写法纪律**（重要）

我最初打算给 C-9/C-10 写的守卫是**字面扫描 `getFullYear()` / `getMonth()` 并判红** ——
**这个守卫本身是错的**！因为：

| 数据来源 | 正确读法 |
|---|---|
| `created_at`（= `nowUtc()`，**真 UTC 时间戳**） | **必须** `getUTC*`（→ C-10 的 `monthOf` 确实是 bug） |
| SheetJS 的 `cellDates` Date（**本地构造**） | **必须** `get*`（改成 `getUTC*` 反而更错） |

⇒ **同族病第 N 例的教训：判行为不判字面。** 守卫必须按**数据来源**分开判定，
禁区不能是「出现 `getFullYear()`」这种字面做派。

## 三之四、⇒ 更新后的 C-8 建议（批次 H 范围）
