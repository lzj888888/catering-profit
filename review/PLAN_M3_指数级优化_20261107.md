## 0 一句话诊断

**M3 的「账」已经很扎实，问题不在算得准不准，而在「按渠道建页面、按页面各自装配」——数据层本来是一份，界面把它切成了五六份，于是改名、导入、改价、排行每做一件事都要跨好几页。**

您举的例子不是文案小毛病，是这个结构病的**症状**：全渠道销量导入被塞进标题叫「外卖每单赚多少」的页面第二个 tab；而 hub 判定「第③步做完了没」用的是通用 `getSalesBills`（`pages/m3/hub.js:99`）——**数据层早就统一了，只有视图和名字没统一**。

**指数级的那一刀**：把「单品 / 套餐 / 外卖 / 成本变动 / 排行 / 四象限」从**六个功能**还原成**一份事实行的六个切片**。之后新增一个分析视图，从「建页面 + 装配 + 口径 + 守卫一整轮」变成「加一条聚合 + 一条守卫」。

## 2 命名方案（您要的「部分的名字」）

原则：**按「对象 / 动作」命名，不按渠道命名**；tab 名说结果，不说原料；每个名字自带「拿它干什么」。

| 位置 | 现在 | **建议** | 理由 |
|---|---|---|---|
| 底部 tab | 配方 | **菜品利润** | 「配方」只覆盖配比；老板进来是想知道「哪道菜赚钱」。4 字、与 M1「核算」/「我的」同级 |
| hub 标题 / 副标题 | 配方 / 原料、成本、毛利核算 | **菜品利润** / **一张卡算清单品、套餐、外卖；改价看影响** | 副标题把四类能力一次说全，替代现在藏在副文案里的承诺 |
| 分区① | 每道菜/套餐成本毛利表 | **菜品成本卡** | 对象名，短；「反推该卖多少钱」放副文案 |
| 分区② | 进货原料价表 | **原料进价** | 与 M1「原料」口径统一，去掉会被误读成食材成本率的词 |
| 分区③（**新增一级**） | 藏在外卖页 tab2 | **销量 / 账单导入** | 全渠道、非外卖专属；这是 #113 要的提级，见 §8 |
| 分区④ | 外卖每单赚多少 | **外卖到手测算** | 保留外卖专属，但明确它只测「一单到手」，不是数据入口 |
| 分区⑤ | 团购每单赚多少 | **团购到手测算** | 与上同构 |
| 分区⑥ | 菜品赚多赚少排行榜 | **菜品利润盘** | 一个结果页同时装排行 + 四象限 + 改价影响，不再「一个视图一张卡」 |
| 分区⑦ | 账上利润和实际营收对不对 | **账实对账** | 短，动作清楚 |
| 三步走第③步 | 「导入销量，看哪道菜赚多少」→ 跳外卖页 | 文案不变，**跳转改到新的一级导入页** | 语义与落点终于一致 |

> 图标单字（卡/料/外/账/榜/团）保留——`terms.js:2557` 记录过不用 emoji 的真机理由，别为改名顺手换掉。

## 3 指数级主线：一份事实行 × 六个视图

### 3.1 提议的「利润事实行」（查询时装配，不新增集合）

```
fact(dish_id, card_version, channel, period) =
  销量      ← 销量账单（形态 A/B/C/D，已归一）
  实收金额  ← 账单金额 + amount_basis 标签（见 §4.3）
  成本      ← 成本卡版本快照 × 销量（单品直接、套餐按子卡展开）
  到手      ← 实收 − 渠道费率/佣金/配送/补贴（外卖、团购才扣）
  单份毛利  = 到手 − 成本
```

四类利润不是四个模块，是这张表的四种聚合：

| 您说的 | 其实就是 | 现在的问题 |
|---|---|---|
| 单品利润 | `GROUP BY dish`（堂食） | 有，但只在复盘页 |
| 套餐利润 | `GROUP BY combo`，子卡展开 | 有，成本在成本卡里；复盘不按套餐给结论 |
| 外卖利润 | `GROUP BY channel=takeaway` | 有「单均测算」页，但和「导入」共用一个页面 |
| 食材成本变化的影响 | **同一份事实行换 `card_version` 重算，取 Δ** | 🔴 没有。现在靠手动逐卡 `syncCostCard` + 新版本，老板看不到「改这一下整体差多少」 |
| 排行 | `ORDER BY 单份毛利×销量` | 有 |
| 四象限 | `散点(销量占比, 单份毛利) + 本店中位数分界` | 零实现 |

### 3.2 为什么这是「指数级」，不是「多修几个 bug」

- **现在**：一个口径变更要同时碰 `card` / `takeaway` / `groupon` / `dishreview` / `recon` 五个页面，以及 `calcBom` / `comboDerive` / `specDerive` / `takeawayDerive` / `grouponDerive` / `reconDerive` 六份派生逻辑；每个视图各写一遍「金额是哪个口径」的解释（`dishreview/index.wxml:203-208` 就是典型）。
- **事实层之后**：装配只在**一个函数**，视图只做 `GROUP BY / ORDER BY / 分界`；口径标签 `amount_basis` 跟着数据走，**不需要每个页面再写一段人话提醒**。
- **边际成本**：新增第 5 类利润、第 6 个分析视图，从「一轮投喂 + 一轮守卫」降到「一条聚合 + 一条断言」。这是结构收益，不是「速度快几倍」——我不编倍数。
- 约束：**不新建集合**（沿用 `规范v1.1 §1` 的硬约束）、不推翻快照隔离（历史可比性是对的），只加「装配层 + 视图层」。

## 5 四个重点细节方案

### 5.1 入口错觉（您点名的）

不是改标题能解决的，是**归属错**：一个全渠道的写操作放在了一个渠道专属的读页面里。改法三层一起动：

1. hub 新增一级卡「**销量 / 账单导入**」，`goStep(2)` 改指新页（或复用现有 import tab 但**独立路由 + 独立标题**）；
2. `takeaway/index` 只保留「单均测算」，tab2 改为「本页数据从哪来」的说明 + 跳链；
3. 页标题、卡名、三步走文案、完成态判定**四处同源**（现在 `terms.hub.takeawayTitle` 与 `TERMS.ledger.takeaway.title` 已经是两套名字，`terms.js:2521-2524` 自己记录了「点进去标题换了个名字」的历史）。

⚠️ 这条就是队列 **#113**，您 2026-11-01 明确「入口提级暂时不做，标注以后探讨」。这次您主动重提，我理解为**可以重新拍板**——但它需要您一句话确认，见 §8。

### 5.2 食材成本变化：保留快照，补「影响面」

不推翻 `saveMaterial/index.js:11` 的快照隔离（历史成本必须可查、不能被悄悄改掉，这是对的）。补的是**可见性与批处理**：

- 原料库每条原料上（现有「涨价影响面」入口）从「只看这一条影响哪几张卡」升级为「**按上月销量算出四类利润各变多少**」；
- 一键「按当前进价重算」：批量生成新版本，明确列出「将产生 N 个新版本，旧版本仍可查」，可取消；
- 套餐 / 引用卡也算进去（`syncCostCard/index.js:6` 现在明写引用卡不受影响 ⇒ 这是传导链断点，必须补齐或显式标注）；
- 结果页给「改价前 vs 改价后」的四类利润差值表，数字全部由生产引擎重算。

### 5.3 排行 → 四象限（不违反 D14 的做法）

D14 禁的是**用无来源的 30:60:10 给菜贴「明星/瘦狗」档位**，不是禁把销量和毛利画成散点。所以：

- **X = 本店该菜销量占比**（本店当月，可复算）；**Y = 单份毛利额**（可切换毛利率）；
- **分界线用本店当月中位数**，并在界面写明「分界线 = 本月 62 道菜中位数：销量占比 1.6% / 单份毛利 8.2 元」——**可复算、有来源、不是行业教条**；
- 象限名用**纯描述**，不贴档位：「卖得多·赚得多 / 卖得多·赚得少 / 卖得少·赚得多 / 卖得少·赚得少」；
- 每象限给一句预设动作（带本店数字、来自规则表、不是 AI 生成），与刚上线的 M2 处方层同构；
- **样本不足 fail-closed**：有效菜数 < 10 或覆盖率 < 60% ⇒ 不画象限，改显示「再关联 N 道菜就能看」（复用现有覆盖率闸门）；
- 四象限与排行**共用同一份事实行**，切换视图零重复装配。

> 这样既满足您要的四象限，又守住「不拍脑袋阈值」的科学性红线，还不用去推翻已定案的 D14。

### 5.4 套餐 / 外卖交叉

`规范v1.1 D15` 已定「外卖一单可直接选套餐」，代码里 `comboDerive` 也在。缺的是**结论层**：复盘按 dish 聚合，套餐被拆成子菜，老板看不到「这个套餐整体赚不赚」。在事实行上加 `combo_id`（可空），让「按菜看 / 按套餐看」成为一个切换，而不是两套数据。
