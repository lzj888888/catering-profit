## 二、C-11：Excel 日期单元格失准（**实证修前 0/4 全错**）

### 2.1 根因（Node 时区史）

```
new Date(1899, 11, 30)          → 落在 GMT+0805（1899 年中国 tzdata 是 LMT 地方平时，比 +0800 少约 5′43″）
⇒ basedate 的 UTC 值 = 1899-12-29T15:54:17.000Z（不是 16:00:00）
⇒ SheetJS 用它做 basedate ⇒ 整天戳落在 23:54:17
⇒ getFullYear/getMonth/getDate 取日历日 → 系统性早一天
```

### 2.2 为什么**现在没炸**

两张样例的日期都是**文本**，所以 `fmtCell` 的 Date 分支从未被走到 —— **只是运气好**：

- 形态 A：日期在 R2 参数长串里（普通文本）；
- 形态 C：第 1 列 openpyxl 判定 `type='str'` × 354 行、`number_format='General'`、`is_date=False`。

而 **Excel 导出日期列默认就是真日期格式** ⇒ 换张表 → 整表 `biz_date` 错位一天且零报错。

### 2.3 修复（`cloudfunctions/importSalesBill/service.js`）

```js
const EXCEL_UTC_BASE = Date.UTC(1899, 11, 30);   // 🔴 不是 new Date(1899,11,30)
const MS_PER_DAY = 86400000;

function fmtCell(cell) {
  if (cell == null) return '';
  if (cell instanceof Date) {
    const p = (n) => String(n).padStart(2, '0');
    const serial = Math.round((cell.getTime() - EXCEL_UTC_BASE) / MS_PER_DAY);
    const d = new Date(EXCEL_UTC_BASE + serial * MS_PER_DAY);
    return `${d.getUTCFullYear()}-${p(d.getUTCMonth() + 1)}-${p(d.getUTCDate())}`;
  }
  return String(cell).trim();
}
```

并补 **`fmtCell` / `EXCEL_UTC_BASE` 导出** —— 此前 `fmtCell` 未导出，
导致「改了也没人能验证」（首版验证脚本跑出来 **0/4 全错**，就是这个原因）。

## 三、C-10：月份口径违反 UTC 铁律

`cloudfunctions/getDishReview/index.js` 里的本地 `monthOf()` 用 `getFullYear()/getMonth()`，
而单源 `cloudfunctions/common/utilTime.js::toMonth` 用 `getUTC*`（该文件头明文：
**「铁律：时间统一 Unix 毫秒 BIGINT / UTC」**）。

修复：删除本地函数，改走单源（与 `adminExport` / `adminInit` 已有惯例完全一致）：

```js
const { toMonth } = common.utilTime;
...
snapshot_month: toMonth(card.created_at),
```

## 四、🔴 元教训：**判行为不判字面**

我原本打算写的守卫是「字面扫 `getFullYear()` / `getMonth()` 就判红」—— **这个守卫本身就是错的**：

| 数据来源 | 正确读法 | 若按字面统一改成 `getUTC*` |
|---|---|---|
| `created_at`（`nowUtc()`，**真 UTC 时间戳**） | **必须** `getUTC*` ⇒ C-10 确实是 bug | — |
| SheetJS `cellDates` 的 Date（**本地构造**） | **必须** `get*`（改 `getUTC*` **反而更错**） | 把**正确**实现改成**错误** |

正解：判据落在**行为**上 —— 把真实序列号喂进**生产函数**断言**返回值**，
期望值由 **Python 侧独立算出**做交叉验证，而不是比对代码字面串。
