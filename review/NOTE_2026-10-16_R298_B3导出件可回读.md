## 2 为什么改判：侦察取证（4 出口 / 3 入口，**零交集**）

PLAN 原文的预设是「导出件能再导入回来，往返等值」。侦察后**前提不成立**：

**导出出口 4 个**（全部走单源 `utils/exportFile.js::deliver`）：

| # | 页面 | scope | 云函数 | 产物 |
|---|---|---|---|---|
| 1 | `pages/month/result.js` | `m1_report` | `exportData` | **多表** xlsx（利润表 / 收入费用明细 / 摊销来源 / 口径说明） |
| 2 | `pages/card/index.js` | `m3_cards` | `exportData` | 单表 xlsx（菜品成本卡，7 列） |
| 3 | `pages/sandbox/list.js` | `m2_compare` | `exportData` | 单表 xlsx（方案对比） |
| 4 | `pages/sandbox/matrix.js` | `m2_matrix` | `exportData` | 单表 xlsx（场景矩阵；**免费引流豁免**，见 MEMORY §1） |

另有 `cloudfunctions/adminExport`（管理端）出 **csv/json**（网页端 Blob 下载）⇒ **不属 xlsx 读回面**，
守卫 S5 显式登记，防复审误判「漏了一项」。

**导入侧入口 3 处**（**全部与自产导出件零交集**）：

| # | 入口 | 云函数 | 读什么 |
|---|---|---|---|
| 1 | `pages/takeaway/index.js`「数据导入」tab（形态 A 堂食《菜品销售统计》/ 形态 C 外卖《商品销量》） | `importSalesBill` | 平台后台导出的**原始表** |
| 2 | 同上（形态 D 订单级账单） | `importSalesBill` | 平台账单（**R259 起暂停展示**，见 MEMORY §9） |
| 3 | `pages/material/batch.js` 原料档案批量导入 | `saveMaterial`（逐条） | 用户**自备** Excel（原料单价） |

⇒ **没有任何一条导入链路会去读自家产出的 xlsx** ⇒ 「往返等值」这条链路在业务上根本不存在。

⇒ 「往返」这条链路在业务上根本不存在；**真正有风险的是「导出件本身能不能被读回、读回的值对不对」**
（导出件是给老板存档、给会计记账的东西，**少一行不报错**）。

## 4 守卫设计（`tools/check_export_roundtrip.js`）

### 4.1 🔴 为什么不设 stub：自写自读**恒真**

「自己造一份 base64，再自己解析」永远通过 ⇒ 正是 PLAN 要防的东西。因此：
- 依赖必须是**真 xlsx 库**，三级解析、全不可得即**响亮红**（fail-closed），并打印全部候选路径；
- 被测代码（`exportData`）内部的 `loadXlsx()` 是 `require('xlsx')` 相对解析，本机仓内没装 ⇒
  守卫在**模块解析层**（`Module._resolveFilename`）把真库路由给它（**先试原解析、失败才回退**）——
  喂进去的是**同一个真库**，不是桩，语义不变；
- 另用 **Python openpyxl**（完全独立的实现）读同一份产物 ⇒ §7。

## 5 关键发现（本轮新查出的两条抛异常路径 + 缺口登记）

用 `probe_behavior.js` 把 SheetJS 0.18.5 的**真实边界行为**测准（8 组），其中两条此前无人知道：

| 场景 | 真实行为 | 可达性 | 处理 |
|---|---|---|---|
| **空 `sheets` 数组** | `XLSX.write` **抛 `Workbook is empty`** | **0**（`m1_report` 恒 4 表；`xlsxBase64` 恒 1 表） | **W1 登记**：`xlsxSheetsBase64` **无异常兜底**；`main` 里的 `if (!content) return fail(...)` 只兜得住「返回假值」，**兜不住抛异常** |
| **工作表重名** | `book_append_sheet` **抛 `already exists`** | **0**（4 表名硬编码唯一） | **W2 登记**：`xlsxSheetsBase64` **无重名去重**；且 `slice(0, 31)` 截断本身会**制造**重名（两个长名共享前 31 字符），`(s.name \|\| 'Sheet1')` 的缺省兜底还会让**两个缺名表**都落成 `Sheet1` |

> 定性：这两条**当前不是 bug**（可达性为 0），但 `xlsxSheetsBase64` 是 `exports` 暴露的通用函数、
> 注释明确写着「可单测」，且注释里 `(s.name || 'Sheet1')` 说明作者**预期过 name 缺失**。
> ⇒ 登记为**防御缺口**，守卫用「形态判据」钉住（若有人加了 try/catch 或去重，W 组转红逼更新登记，
> 而不是让它被无声修掉/无声退化）。**修与不修属 C 段拍板**（见 §9）。

另外两条**有利**发现（排除疑点）：
- 金额单元格是**真数字**（`t='n'`，`typeof number`），不是文本 ⇒ 会计 SUM 不会得 0；
- 空行 `['','','']` 在 `blankrows:true` 下**完整保留**（`t='s' v=''`），且 openpyxl 读回同样保留 ⇒ 行数守恒可判。

## 7 为什么要 openpyxl 交叉验证

守卫里是「**SheetJS 写 → SheetJS 读**」= **同源往返**，只能证明「自己和自己一致」，
证明不了「Excel / WPS / 别的库也认这份文件」——这恰恰是「可回读性」的本义。

因此另做一层**独立实现**验证：`cross_check_openpyxl.py`（Python 3.13 + **openpyxl 3.1.5**）
读**同一份落盘产物** `_probe_tmp/b3_export/月度报表.xlsx`，用 `Decimal` 精确回算（不经二进制浮点）：

| 判据 | 结果 |
|---|---|
| X1 工作表名与顺序 | ✅ `['利润表','收入费用明细','摊销来源','口径说明']` |
| X2/X6/X8 行数（16 / 7 / 5，**含 2 个空行**） | ✅ |
| X3 表头逐字 | ✅ |
| X4 金额列 `data_type == 'n'`（数字型） | ✅ 全数字 |
| X5/X7/X9 逐点回算分（10 + 6 + 4 点） | ✅ 与源分完全一致 |
| X10 口径说明零数字格 | ✅ |
| X11 金额均为「分」整数倍（23 格） | ✅ |
| X12 空行在 openpyxl 读回时依然保留 | ✅ 2 个 |

**13 通过 / 0 失败** ⇒ 该产物能被**另一个实现**正确读回。
