# 深度诊断 · 现状梳理与方案候选（R612 草案 · 2026-11-06）

> 触发：李老师指出「经营客流（选填）不该放在录入页，这是深度诊断；现在太浅，决定生死的指标都没体现；应该做成硬数据 + 问卷 → 综合结论」。

## 0. 先说一个关键事实（这改变了问题的性质）

**深度诊断引擎已经写好了，但从来没有被调用过。**

- `cloudfunctions/common/diagnosisEngine.js`（A5 · 2026-11-05）已实现：
  - **11 项加权 100 分**（盈利 15 / 亏损持续性 10 / 现金流 15 / 客流趋势 10 / 毛利率 8 / 人工 7 / 房租 10 / 口碑 5 / 商圈 10 / 租约 5 / 资金链 5）
  - **6 条红线一票否决**（R1 现金枯竭 / R2 长期亏损仍失血 / R3 商圈结构性流失 / R4 食安重大事件 / R5 借贷输血失控 / R6 租约断崖）
  - 缺项不计分母 + 归一化、覆盖率闸门（<70% 不出等级）、短板 Top3、免责兜底键
  - 守卫 `tools/check_diag_engine.js` **42 条断言**全绿（含 6 条红线的命中/不命中双向验证）
- 但 `grep evaluateDiagnosis` 全仓：**除自测外零调用**。没有任何页面、没有任何云函数用它。
- 现有唯一相关页面 `subpkg/biz/diag/input.js` 只是**采 7 个字段**，采集完就存 `shop.diag_facts`，**不计算、不展示结论**。

⇒ **所以"太浅"不是模型浅，是接线没接。** 引擎躺着，界面只做了半个录入表单。
⇒ 这也解释了李老师看到的现象：填了客流三项，只在结果页看到两个百分比，没有任何"这家店还能不能撑"的判断。

## 1. 三个问题的准确拆解

### 1.1 「经营客流」为什么在录入页、为什么感觉不对

现状：`input.wxml` ③ 段（本次刚修好文案）采三项：本月客流 / 其中老客 / 会员销售额。

| 判断 | 依据 |
|---|---|
| 这三项**是月度数据**，必须跟当月账走 | 落库在 `shop_monthly_account.traffic_count / old_customer_count / member_sales_fen`（`saveLedger` 写入），按月存 |
| 但**不该打断录账主流程** | 它们是"诊断用的补充观测"，不是"这个月的收支"。老板来录账，目标是把钱记清楚；客流是另一件事 |
| 李老师的直觉对：它属于"看结果/做诊断"那边 | 这些数**唯一的用途**就是算复购率、会员占比、客流同比——全是诊断指标，不参与利润计算 |

⇒ 结论：**数据归属不变（仍存当月账），交互位置要挪。** 挪到结果页「经营客流」卡里就地补录（结果页已有 `onCash` 现金就地输入的同类先例）。

### 1.2 「太浅」到底缺什么——逐项对账

引擎要 18 个输入，现有采集覆盖 7 个。逐项对账：

| 引擎输入 | 含义 | 现状 | 缺口类型 |
|---|---|---|---|
| `revenueFen` / `netProfitFen` | 营收 / 净利 | ✅ M1 当月账自动 | 自动 |
| `foodCostRatePct` / `laborCostRatePct` / `rentRatePct` | 食材/人工/房租率 | ✅ M1 自动 | 自动 |
| `trafficThisMonth` | 本月客流 | ✅ M1 已录 | 自动 |
| `trafficLastYear` | 去年同期客流 | ✅ diag 已采 | 已有 |
| `rating` / `reviewTrend` | 评分 / 差评趋势 | ✅ diag 已采 | 已有 |
| `businessDistrict` | 商圈五档 | ✅ diag 已采 | 已有 |
| `leaseMonthsLeft` | 剩余租期 | ✅ diag 已采 | 已有 |
| `debtLevel` | 借贷三档 | ✅ diag 已采 | 已有 |
| `cashOnHandFen` | 账面现金 | ✅ diag 已采 | 已有 |
| **`lossMonths`** | **连续亏损月数** | ❌ **无**（M1 有每月账，但没有任何地方算"连亏几个月"） | **必须补算** |
| **`monthlyRigidFen`** | **月刚性现金支出** | ❌ **无**（可从当月账派生：人工+房租+水电） | **必须补算** |
| **`renewIncreasePct`** | **续租预期涨幅** | ❌ **未采集** | **必须补采**（R6 红线三条件之一） |
| **`foodSafetyEvent`** | **食安处罚/重大客诉** | ❌ **未采集** | **必须补采**（R4 红线唯一输入） |

⇒ **缺的正是李老师点的那几项**：连续亏损月数（已点名）、月刚性支出（决定"现金能撑几个月"）、续租涨幅、食安事件。
⇒ 这四项补齐后，11 项里 **11 项全覆盖**、6 条红线 **6 条全可判**。

### 1.3 「像问卷」怎么改成「硬数据 + 问卷 → 结论」

现状 diag/input 是 7 个平铺输入框，填完点保存就走人 —— **没有反馈，所以像问卷**。
引擎里其实已经有答案（11 项分 / 6 红线 / 短板 Top3），只要接上就有输出。

⇒ 形态改造：一页三段
1. **诊断总览**（进页面第一眼）：等级 + 分数 + 覆盖率 + 命中红线 + 短板 Top3
2. **分组补录**：财务与现金（自动为主）/ 经营与口碑 / 市场与合同 / 风险信号（四个小模块，正是李老师要的分组）
3. **缺什么补什么**：按 `missing` 出参逐项列，填一项就少一行

## 2. 位置方案（三选一）

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A · 结果页底部入口（推荐）** | 结果页在「三项刚性 / 行业对照 / 兜底声明」之后加一张「深度诊断」卡 → 点进独立页 | ① 诊断依赖 M1 真实月度数据，结果页是"看完这个月的账"的落点，接得上；② 不占 tabBar；③ 与「免费简诊 vs 深度诊断」的付费分层天然对齐（免费看简诊、付费看完整报告） | 入口偏深，新用户可能不知道有 |
| B · 首页第 4 张模块卡 | 首页三大模块下加「经营体检」 | 曝光最好 | 与 M1/M2/M3 语义并列会让人以为"第四个独立工具"，而它其实**只能吃 M1 的数据**，独立成模块会造出"没录账也能诊断"的错觉 |
| C · 独立 tab | tabBar 加第四个 | 最显眼 | tabBar 三入口已定（核算/配方/我的），加第四个破坏已定结构；且诊断低频（1 次/季），不配占常驻位 |

**推荐 A**，理由一句话：**诊断的输入 100% 来自 M1，它的位置就不该脱离 M1。**

补充：首页 hero 卡可以加一行轻提示（"这个月能撑多久？去看一眼"），做低频入口，不新增模块。

## 3. 形态设计（硬数据 + 问卷 → 结论）

```
结果页底部
  └─ 「深度诊断」卡（显示当前等级 + 覆盖率，如「需关注 · 数据覆盖 78%」）
       └─ 深度诊断页
            ├─ 第一段：诊断总览（等级/分数/红线/短板）
            ├─ 第二段：分组补录（四组，已有的折叠展开，缺的高亮）
            │    ├─ 财务与现金：连亏月数(自动) / 月刚性支出(自动) / 账面现金
            │    ├─ 经营与口碑：本月客流(自动) / 去年同期客流 / 评分 / 差评趋势
            │    ├─ 市场与合同：商圈五档 / 剩余租期 / 续租涨幅
            │    └─ 风险信号：食安事件 / 借贷程度
            └─ 第三段：缺项清单（按权重降序，告诉他补哪项最值）
```

**关键纪律（沿用引擎既有底线）**：
- 全部可留空，留空 = 该项不进分母，**绝不按 0 分算**
- 覆盖率 <70% **不出等级**，只显示「数据不足 + 还差哪几项」
- 红线用**真实数据**才判，缺数据判「未判定」而不是「安全」
- 输出只给数字与事实，**不给"建议闭店"**（责任边界）+ 底部免责
