> ② 外卖**通常是几个平台的**，费用侧要不要**和收入侧对应**？
> ③ 这些数据**有科学来源吗**？

## 0. 一句话结论

**会计口径是对的，不会重复扣**（总额法，佣金只在费用侧记一次）；
**但「填少」有三个真实风险**，且**多平台对不上**（收入侧分 4 平台、费用侧只有 1 个总额）、**最主流的快速模式没有任何自查手段**；
**数据来源真实可查**（本轮拿到一手账单字段证据），**但「商品总价是否已含打包费」两种官方说法并存，仍未验证**；
**店铺自己的活动**：平台内活动已有专项，**平台外活动规范设计了 3 项但实现里没有**。

## 1. Q1 会不会填少 / 扣重？—— 口径对，但三个「填少」风险是真的

### 1.1 设计上不会重复扣（三处机制 + 三处文案）

| 机制 | 锚点 | 说明 |
|---|---|---|
| 收入侧**不扣佣金** | `ModuleA:32`（A.1）、`terms.js:363` | 外卖收入 = `商品总价 + 打包费 + 商家活动补贴`；规范明写「佣金/配送费不要在这里扣，记到下面的营销费用」 |
| 佣金/配送费**只在费用侧记一次** | `terms.js:209` | 营销类 6 项，与收入侧无重复字段 |
| 活动补贴**两侧同名但净影响为 0** | `ModuleA:110-112`（A.6） | 总额法特征：按原价认收入、把让利认费用 ⇒ 收入 +X、费用 −X，**净 0，不是扣重** |
| 页面口径句 | `terms.js:318`（scopeGuide） | 「佣金与配送费不要在这里扣（**扣了就成净额，费用侧会无事可填**）」 |
| 填写指引 | `terms.js:379`（fillGuide ⑤） | 「外卖、团购的佣金不要在收入里扣，统一记到「费用 · 营销」」 |
| 类口径 | `terms.js:363/369` | incomeScope.takeaway / expenseScope.marketing（含「不要与收入重复扣减」） |

⇒ **口径结论：不会扣重。** 这是规范 A.6 明确设计过的（外卖走总额法、团购走净额法，两套准则均正确）。

### 1.2 🔴 R1（真缺口）多平台要手工汇总成一个数 ⇒ 容易漏平台

- 收入侧：**4 个平台分列**（`terms.js:191`：美团外卖 / 淘宝闪购 / 京东外卖 / 其他外卖）
- 费用侧营销：**6 项店铺级总额，不分平台**（`terms.js:209`）
- ⇒ 客户必须**把 4 份账单的「技术服务费」列分别求和、再相加**，填进**一个**「外卖平台佣金」框
- ⇒ **漏了某个平台 = 佣金少记 = 利润虚高**，而页面**没有任何逐平台核对机制**（费用侧无平台字段，见 §2）

### 1.3 🔴 R2（真缺口）快速模式下「外卖活动补贴」**不会自动带出** ⇒ 默认路径漏填

- 自动带出函数 `syncSubsidyCarry()` 第一行：`if (this.data.takeoutMode !== 'detail') return;`（`input.js:735`）
- ⇒ **只有分项模式才带出**。而**快速模式是默认**（`input.js:137` `takeoutMode: 'fast'`）
- 快速模式收入侧那个数**已经含活动补贴**（口径句写得很清楚）⇒ 用户看到收入里含了补贴，**费用侧大概率不再填一次**
- 后果：费用侧「外卖活动补贴」= 0 ⇒ 费用少记 ⇒ **但**：因收入侧是总额法照记，会计上**净影响其实为 0**（补贴两侧同额相抵）；真正的问题是**配平算式里 subsidy 取 0 会让差额变大**（见 R3）与**用户无法核对**

> ⚠️ 这一条要区分「会计影响」与「配平影响」：**会计上不构成错误**（净影响 0），**但会让核对机制失效**。规范 A.11.5 只承诺「分项模式的三项**在费用侧自动带出**」（`ModuleA:257`），**快速模式确实没承诺**。

### 1.4 🔴 R3（真缺口）**配平校验只在分项模式存在** ⇒ 最主流用法没有自查

- 配平输入框写在 `<block wx:else>`（分项模式）内：`input.wxml:182-192`
- 触发也限死：`if (this.data.takeoutMode === 'detail') this.runReconcile();`（`input.js:322`，注释明写「配平仍只在分项：快速模式拆不出『活动补贴』」）
- `reconcile()` 本身：`if (!(actual > 0)) return null;`（`takeaway.js:242`）—— **客户不填「商家应收款」就完全不校验**
- ⇒ **默认路径（快速模式）: 填 4 个数、交，无任何交叉检查**

### 1.5 小结（Q1）

| 问题 | 答案 |
|---|---|
| 会**扣重**吗？ | **不会**（口径正确，且有三处文案防错） |
| 会**填少**吗？ | **会，且有三个专门通道**：① 多平台汇总漏平台 ② 快速模式补贴不带出 ③ 快速模式无配平 |
| 页面能当场发现吗？ | **只有分项模式能**（且需客户额外填「商家应收款」）；快速模式**不能** |

## 2. Q2 多平台要与收入侧「对应」吗？—— 现在是结构性不对应

### 2.1 现状（三处粒度不一致）

| 侧 | 粒度 | 锚点 |
|---|---|---|
| 收入侧外卖 | **4 平台分列**（每平台 1 个数 / 分项 3 个数） | `terms.js:191`、`input.wxml:122-175` |
| 费用侧营销 | **6 项店铺级总额，不分平台** | `terms.js:209`、`input.wxml:239-260` |
| 配平校验 | **总量级**：全部平台收入合计 vs 一个「商家应收款」 | `takeaway.js:240-270`、`input.js:698-720` |

`reconcile()` 的取数实证（`input.js:706-719`）：

```js
const mk = (this.data.expenseGroups || []).find((x) => x.category === 'marketing');
const mrow = (name) => { const r = (mk && mk.rows || []).find((x) => x.subItem === name); return r ? (Number(r.amountYuan) || 0) : 0; };
// incomeTotal = Σ 全部平台；commission/deliveryFee 只按项名取「一行」
```

⇒ **费用侧按项名精确匹配取一行金额**（`reconcileRoles` = 平台佣金 / 配送服务费 / 配送补贴，`terms.js:335-339`），**没有平台维度**。

### 2.2 三条可选路（需李老师定）

| 方案 | 做法 | 代价 | 我的看法 |
|---|---|---|---|
| **甲** 维持现状 | 仍填总额，只在提示里写清「先下 4 份账单、各列求和再相加」 | 零成本，但 R1 仍在 | 至少要把提示补上（现在**没有任何这样的提示**） |
| **乙** 费用侧按平台拆 | 4 平台 × 5 项 = 20 行 | 太重，小老板填不动；且与规范 A.11.3「6 项」冲突 | **不建议** |
| **丙**（推荐）**加「分平台小计区」** | 费用侧营销段给一个 **只回显、不入库** 的 4 平台小计区（照抄收入侧 4 平台），客户逐平台填佣金 → 系统自动汇成「外卖平台佣金」那一行 | 中等：要改造 + 守卫 | **贴合李老师「要和收入侧对应」的诉求**，且不动会计口径与库结构 |

> ⚠️ **丙方案的关键设计点**：小计区只回显（像配平一样），**入库仍只写「外卖平台佣金」这一个数** —— 这样不破坏 `shop_monthly_account` 结构与既有守卫。

### 2.3 另一个不对应：**团购平台佣金**与外卖收入侧完全无关

- 「团购平台佣金」在**同一个营销大类**里（`terms.js:209` 第 6 项），但团购是**堂食渠道**（`terms.js:272-276` 别名归并到「团购/代金券核销」）
- 「团购/代金券核销」在**堂食收入**里（`terms.js:185`），不在外卖收入里
- ⇒ 客户看「营销费用」大类时，**一半是外卖、一半是堂食**，容易混

### 3.2 🔴 仍未验证的关键项：**「商品总价」是否已含打包费**（V2 未解决，且两种官方说法并存）

| 来源 | 说法 | 推论 |
|---|---|---|
| 美团开放平台 API 文档 | `商品金额 = 商品原价 + 包装盒费用 + 赠品原价` | **含**打包费 |
| 美团导出账单列名 | `商品总价 / 餐盒费 / 打包费` **分列** | **不含**（否则不会分列） |

⇒ 若「商品总价」已含打包费、而客户又填了「打包费」⇒ **收入多算一次打包费（收入虚高）**。

## 4. Q4 客户好不好拿到数据？

**结论：对懂的人不难，对不懂的人是门槛，且门槛集中在三处。**

| 维度 | 事实 |
|---|---|
| ✅ 渠道 | 都是**网页后台自助导出 Excel**：美团 `财务管理→下载专区`；饿了么 `财务→财务下载`；抖音来客另有后台 |
| ✅ 一次可得 | 选月份导一次 = 整月数据，**不用逐单加**（`PITFALLS §7`：「逐单相加是伪需求」） |
| ✅ 我方已做 | 「粘贴」入口就是为「复制一列 → 求和」设计的（`input.wxml:149/158/167`，`takeaway.js::extractPaste`） |
| 🔴 门槛① | **要跑多个平台**：收入侧列了 4 个平台 ⇒ 最多要登 4 个后台各下一份 |
| 🔴 门槛② | **字段名各平台不同**：美团「商家应收款」= 饿了么「结算金额」；美团拆「技术服务费/履约服务费」，饿了么只有「服务费费率」 |
| 🔴 门槛③ | **推广费不在结算单里**，要去「推广中心 → 消费明细」另取（`terms.js:350` 已标注取数路径） |
| ⚠️ 现实 | 外卖大战下商家承担补贴可能极大（§3.1），**不看账单根本不知道自己在补多少** |

## 5. Q5 店铺平时做的活动，要自己加细项吗？—— 分三类，答案不同

### 5.1 🔴 平台内活动（满减 / 折扣 / 红包 / 代金券）→ **不用自己加，已有专项**

- 平台账单里有「**美团活动补贴**」列 ⇒ 收入侧「商家活动补贴」（分项模式）+ 费用侧「外卖活动补贴」（自动带出）
- 锚点：`ModuleA:187/201`、`terms.js:174`（A.11.1「其余数字由系统自动带出（活动补贴）」）

### 5.2 🔴 平台外自己的推广 / 物料 → **规范设计了 3 项，但实现里没有**（本轮新发现）

规范 A.2 的营销推广费**总共列了 9 项**（`ModuleA:44-54`）：

```
团购平台佣金 / 外卖平台佣金（技术服务费） / 外卖配送服务费 / 外卖活动补贴（商家承担）
/ 外卖配送补贴（商家承担） / 外卖推广费（点金/竞价）
/ 线上广告推广（抖音/美团到店投流）   ← 未实现
/ 宣传物料印刷                        ← 未实现
/ 其他营销费                          ← 未实现
* 汇总行（可选）：平台佣金合计 = 团购佣金 + 外卖佣金   ← 未实现
```

而**实际单源只有 6 项**（`terms.js:209` + `collections.js::SEED_EXPENSE_ITEMS(marketing)`，两者一致），
⇒ **少了 3 项 + 1 个汇总行**：`线上广告推广`、`宣传物料印刷`、`其他营销费`、`平台佣金合计`。
⇒ 现状：老板做地推、印传单、投抖音到店流，**只能靠「+ 添加细项」手打**（`input.js:380-391`，加的是空白行）。

> ⚠️ 注：A.11.3 的「6 项」与 A.2 的「9 项」**不是矛盾**——A.11.3 只规范**外卖/团购平台相关**的 6 项（`ModuleA:193` 标题即「费用侧 · 营销段 6 项」）。但**实现只落了这 6 项，A.2 的另外 3 项与汇总行都没落**。

### 5.3 ⚠️ 堂食折扣（店内满减 / 会员折扣）→ **口径空白**

- 收入侧堂食**只有收款渠道**（现金/微信/支付宝/银行卡/储值卡/挂账/团购核销，`terms.js:185`），**没有「折扣」「让利」字段**

- ⇒ 老板填的时候：填实收（体现不出让利）还是填原价（收入虚高）？**规范没定**
