# R387 · M3 解释锚点（inputs_ref 契约）

> 2026-10-20 · 承接 `PLAN_2026-10-20_AI路线与边界.md` §6 第 2 条；队列 #14（R386 只做了 M2）。
> 目的不是"接模型"，是让每条结论**能被指回输入**：这条毛利是哪张卡的哪一版算出来的。

## 一、问题

M3 的结果只有数字。老板问"凭什么"，我们只能翻页面；以后要接解读，更会出现
"同一个 card_code 改过 3 版，旧结论到底基于哪版"无法回答。R386 给 M2 加了版本号，**M3 缺的正是这一环**。

## 二、契约（先定，再改）

出参统一带：

```js
inputs_ref: { kind: 'cost_card', card_code: 'C0001', version: 3 }
```

三条理由：

1. **只用业务键**（`card_code` + `version`）。`_id` / `card_row_id` 是库内主键，**跨 dev/prod 不稳定**
   —— 换环境引用即失效；而且一旦出现在出参里，前端就会有人去存它。
2. **两处同形状**（`saveCostCard` 保存出参 / `getCostCard` 卡映射出参）。消费方不必按来源分支判断。
3. **`kind` 字段**：留给以后 M1 月度（`kind: 'month'` + `account_id`）复用同一形状，避免每模块一套。

契约已写进权威文档 `specs/dev-specs/core/10_云函数清单与接口契约.md`（两行出参 + 一条专注）。

## 三、落地

| 位置 | 改动 |
|---|---|
| `cloudfunctions/saveCostCard/index.js` | 主出参 `out` 带 `inputs_ref` |
| `cloudfunctions/getCostCard/service.js::cardToOutput` | 卡映射带同形状 `inputs_ref`（**列表与详情同一函数** ⇒ 一处覆盖两路） |
| `tools/check_m3_card_roundtrip.js` | 新增 ⑤-1/②/③ 三条断言（34 → 37） |

## 四、验证

- 单跑：`node tools/check_m3_card_roundtrip.js` → **37 通过 / 0 失败**
- 变异（`review/evidence/r387_mut.py`）**3/3 全部点名目标断言**：
  ```
  [抓到了] M1 保存出参去掉 inputs_ref   → ❌ ⑤-1
  [抓到了] M2 列表映射去掉 inputs_ref   → ❌ ⑤-2
  [抓到了] M3 塞入库内主键 _id          → ❌ ⑤-3（含主键）
  [通过] 还原后复跑 : 37 通过 / 0 失败
  ```
  ③ 这条是**方向判据**：不是"有没有 inputs_ref"，而是"里面**不许有**库内主键"——否则日后有人图省事塞 `_id` 也不会红。

## 五、如实登记的边界

- **幂等回放**：`saveCostCard` 的重复调用分支 `return ok(prior)` 返回的是**首次落库的结果**。
  R387 之前产生的旧结果没有 `inputs_ref` ⇒ 这类回放会缺键。**不补写库**（补写要改历史审计记录，风险大于收益），
  在契约注里记为可选字段，消费方 fail-soft。
- **`saveCostCard` 软删分支**（`_delete`）返回 `{deleted:true}` 语义，不带 `inputs_ref`——它不是"结论"，无需锚点。
- M1 月度（`kind:'month'`）**本轮不做**，只在形状上留位。
