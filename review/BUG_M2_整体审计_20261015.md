## B1 · 【P1】`list.js` 图片导出**第一次点击必然失败**（画布初始化恒返回 null）

- **现象**：在「我的方案 → 并排对比」页点【导出图片】，**第一次点必定弹提示、不出图**；再点第二次才成功。
- **根因**：`pages/sandbox/list.js`
  - `onExportImg()` L189：`const ctx = this._ctx || this.initCanvas();`
  - L190：`if (!ctx) { api.toastError({ msg: P.exportImgHint }); return; }`
  - `initCanvas()` L215-234：选择器查询是**异步**的（`wx.createSelectorQuery().exec(cb)`），
    函数体末尾 **L233 无条件 `return null`** ⇒ 首次调用**一定**返回 `null`；
    真正的 `this._ctx` 只在异步回调（L228）里才被赋值。
  - ⇒ 首次点击走 `!ctx` 分支 → 弹 `exportImgHint` 并 return；用户不点第二次就拿不到图。
- **影响面**：`initCanvas()` 全仓只有 L189 一个调用点（已 grep 确认）⇒ 必然复现，非竞态偶发。
- **为什么既有守卫抓不到**：`check_m2_matrix.js` 只守 matrix 面（matrix action / 免费导出豁免 / 术语键），**不覆盖 list 页 canvas 链路**。
- **为何值得 P1**：与记忆里「导出/打印按钮点击后无反馈、文件去向不明」是**同一族**（用户点了没结果）。
- **建议修法（待拍板）**：三选一
  1. 进入对比态时（`onCompare` 成功后）预先跑一次 `initCanvas()` —— 把异步预热掉，导出时 `_ctx` 已就绪；
  2. `onExportImg` 改 `async`，把 `initCanvas` 改写为返回 Promise（`resolve(canvas/ctx)`），导出前 `await`；
  3. 首次点击不报错而是提示「正在准备画布，请再点一次」—— **不推荐**（仍是两次点击）。
  推荐 **①**：改动最小、导出路径保持同步、首次点击即出图。

## B2 · 【中】`compare.js` 不读 `snapshot.reverse` ⇒ 与 `list.js` 对同一反推方案给出**不同**数字

- **现象**：同一份反推（寻找铺面）方案，从两个入口看「目标月营收」不一样：
  - 入口 A `pages/sandbox/compare`（沙盘页【对比】/ 矩阵页【去对比】）→ 读快照 **顶层**
  - 入口 B `pages/sandbox/list`（沙盘页【我的方案】→【并排对比】）→ 读快照 **`reverse` 块**、且实时重算
- **根因**：
  - `cloudfunctions/savePlan/index.js` L90-93：**恒定**先算 `snapshot = calcSandbox(clean)`（正向口径），
    再 `if (clean.mode === 'reverse') snapshot.reverse = calcSandboxReverse(clean)` ⇒ 反推方案的快照**同时含两份**：
    顶层（房租按固定成本/或为 0）与 `reverse` 块（真正的反推答案）。
  - `pages/sandbox/compare.js` L95-98：只读 `s.break_even_monthly_fen` / `s.target_monthly_fen` ⇒ **拿的是顶层正向数**，
    却在 wxml 里贴「寻找铺面」场景标签 ⇒ 口径与标签不符、且与 B 入口的数不同。
  - `pages/sandbox/list.js` L78-79 / L136-138：`snap.reverse.target_monthly_fen` 优先 ⇒ 拿的是反推数。
- **影响面（诚实标注）**：`pages/sandbox/index.js` L347 起 `data.mode` **恒为 `'forward'`**（`onMode` 已删，全文仅 1 处赋值），
  `savePlan` 前端唯一调用点 L894 传 `buildPresetParam('forward')` ⇒ **当前新保存的方案全是正向**。
  ⇒ B2 **只影响历史存量反推方案**（反向 Tab 下线前保存的）。故定「中」而非「高」。
- **建议修法（待拍板）**：`compare.js` 与 `list.js` 统一取数口径 —— 反推方案取 `snapshot.reverse`，
  或干脆**下线 `compare` 页、只保留 `list` 页的并排对比**（消除"两份对比实现"这个结构性隐患）。
  ⚠️ 该项涉及「两个页面是否合并」，属产品决策，**需李老师先定**。

## B3 · 【低·潜在】`onCalcPresetFwd` 的 payload 漏传 `valid_days`（注释声明要喂）

- **现象**：同一页面上，「主测算」与「敏感度」的**日折算口径**理论上可不同源。
- **根因**：
  - `pages/sandbox/index.js` L1192-1268 `buildPresetParam` **明确返回** `valid_days: this.validDaysNow()`（附 30 行口径注释）。
  - `buildForwardPayload()`（L654-668，敏感度用）**带** `valid_days: p.valid_days`（L665）✅
  - `onCalcPresetFwd()` 的 payload（L1307-1315，**主测算**用）**不带** `valid_days` ❌
    ⇒ 云端 `calcSandbox/service.js` L98 `num0(c.validDays) > 0 ? … : 30` 回退 **30**。
- **为什么现在看不出来（诚实标注）**：`validDaysNow()` L984 在 R290 后**恒返回 30**（该项已改为常量、老板不再填）
  ⇒ 两条路当前都落到 30，**数字一致**。一旦「每月营业天数」重新放开为可填，两条入口立刻分叉
  （主测算 ÷30、敏感度 ÷用户值）⇒ 典型的「单源判据被另一条入口架空」（同族病第五例）。
- **建议修法（待拍板）**：`onCalcPresetFwd` payload 补 `valid_days: p.valid_days`（一行），并把该字段纳入
  `tools/check_m2_entry_parity.js` 的用例表（现在没有 validDays 维度）。

## B10 · 【中】`onPreset` 无条件覆盖用户手填的「单桌座位数」

  「只补用户没改过的字段」；旧注释自己写着"用户改过就以用户的为准"，**代码没判**。
- **后果**：包间大桌的店手填 6 人/桌 ⇒ 一切业态预设就被静默重置回默认（火锅/正餐 4、快餐/茶饮 2）

- **状态**：✅ 已修（`fieldTouched.seatsPerTable` 纳入既有机制；`onSeatsPerTable` 标手填）。

## B11 · 【中】点【开始测算】整页 loading 重绘、滚动位置丢失

- **根因**：`index.wxml` 原为 `bindtap="onCalc"` ⇒ tap 事件会把**事件对象**当第一个实参传给
  `onCalc(isFirst)` ⇒ `isFirst` 恒为真 ⇒ `setData({loading:true})` ⇒ 根节点 `wx:if="{{!loading}}"`
  **整页切走再切回**（重绘 + 滚动回顶）。这与 round114 明确修过的"改一个数就整页闪成加载中"**同一条**
  ——修复只保住了自动重算路径，**按钮这条路被漏掉**。
- **状态**：✅ 已修（新增 `onCalcBtn()` 显式传 `false`；`onCalc` 收紧为 `isFirst === true`）。

## B12 · 【低】吸底条点击可能静默失效（锚点条件渲染）

- **状态**：✅ 已修（改为**无条件空锚点** `<view id="m2result"></view>`，两处旧 id 卸掉）。
