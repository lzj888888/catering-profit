## 0 一句话结论

**建议不隐藏。** 因为"外卖导入"这个名字底下其实是**两件已经分开处理过的事**：

| | 是什么 | 现状 | 该不该藏 |
|---|---|---|---|
| ① 外卖**账单**导入 | 平台「结算账单」导出，**订单级、无菜品行** | 🔒 **已于 R259 上午隐藏**（`BILL_IMPORT_ENABLED=false`，双保险） | 已藏，不用再动 |

⇒ 藏② = 砍掉外卖单品核算的数据来源，而外卖单品核算正是你上午点名要重点做的。

## 1 "修复慢"的归因：慢在下游，不在导入

这两天体感慢，但拆开看，慢的**不是导入本身**：

| 环节 | 状态 | 证据 |
|---|---|---|
| 形态判定（A/B/C，按表头自动判） | ✅ 已修完 | `check_formc_shape` **15/0**（R232 曾因真表第 4 列是「销量」而非「商品销量」⇒ 形态 C **永远判不出**，已修） |
| 形态 C 解析 | ✅ 已修完 | `check_formc_parse` **16/0**（真样例复算：354 行 / Σ销量 118 / Σ销售额 **1823.08** / 51 商品） |
| 堂食表解析（形态 A） | ✅ 已修完 | `check_m333_parse` **23/0** |
| 真表是否真的落库 | ✅ 已落库 | 淘宝闪购《商品下载》355 行 = 7 天 × 51 商品，与 R254 真云探针逐位吻合 |
| 账单解析 / 落库 / 读清 | ✅ 已上云 | `selftest_bill_parse` **70/0**、`check_salesbills` **43/0** |
| **导入之后：51 道菜要挂成本卡** | 🔴 **这才是慢的源头** | 真机所见：店里只有 **3 张**成本卡（鱼香肉丝/炸鸡腿/肥炸鸡腿）⇒ 51 行 picker 只有 3 个可选 ⇒ 挂不上、挂了还是错的 |

**所以：藏导入，慢的那一段（建卡）一点没少，还把唯一的数据来源也砍了。**

### 1.1 一个必须摆上台面的硬约束

**M3 免费档成本卡上限 = 20 张**（单源 `initDb/collections.js::SEED_FEATURES`）。
外卖 51 道菜 + 堂食 270 行 ⇒ **免费档最多覆盖 20 道菜，覆盖率 ≤ 39%**。

这不是缺陷，是分层设计（"套餐/外卖/全菜单诊断进付费域"）。但它决定了两件事：
- 免费用户**注定**只能算一部分菜 ⇒ 界面**必须明说覆盖率**，否则他会以为"我导入了 51 道，怎么只算出 3 道"；
- "全量覆盖"本身就是付费价值点 ⇒ 不该为了让它看起来完整而砍功能。

## 2 方案（不隐藏）：把"导入后"从「51 行等你关联」改成「告诉你现在能算几道 + 一键去建卡」

### A. 覆盖率条（复盘页顶部）— 必做

显示：`共 51 道 · 已关联 K 道 · 可算毛利覆盖 Σ 销售额的 Y%`，未关联的明确写 **"暂不计入毛利合计"**。

- 价值：即使只有 3 张卡，用户看到的是"3 道能算、48 道待建卡"，**而不是"51 行等你填"**；
- 同时堵住"我导入了 51 道怎么只算出 3 道"的困惑（免费档 ≤20 张卡的必然结果）。

### B. 建卡提速：未匹配行「去建卡」**带菜名预填** — 必做（最大提速点）

现状路径：退出复盘 → M3 → 菜品卡 → 新建 → **手打菜名**（51 道菜来回切，最容易忘的就是菜名）。
改后：未匹配行点「去建卡」⇒ 跳 `/pages/card/index?dishName=<菜名>` ⇒ **菜名已填好**，只填原料。
- 需改：`pages/card/index.js` 加 `onLoad` 读参预填（该页**当前无 onLoad**，不支持入参）。

### C. 卡不够时，**不给「批量关联」主按钮** — 必做（防乱挂）

🔴 理由（R262 已立的红线）：**挂错卡 = 食材成本算错，且毛利照常出数，用户会信那个数** —— 比"暂时不算"更坏。
⇒ 卡数 < 未匹配数时，只给「新建成本卡」；批量关联按钮**仅在卡够用（可真正选对）时才出现**。

### D. 账单导入的恢复条件 — 记下来，不现在做

R259 的开关随时能翻回来，但翻之前要先补齐三件事（否则还是不成熟）：
① **京东口径未证**（`外卖核算_专项核对.md` §7-4）；② **账期归月只淘宝实测**（结算日 = 账单日 +3 天）；
③ **阶段①真机从未点过一次**（路线单序 9）。

## 3 验收判据（机器可验，不靠目视）

| 项 | 判据 |
|---|---|
| A 覆盖率条 | 新增断言：覆盖率按「已关联行 Σ 销售额 ÷ 全部行 Σ 销售额」算，**不是**按行数（行数会把 0 元口味询问类 SKU 算进去） |
| B 带菜名跳转 | 断言：跳转 URL 带 `dishName` 且**已 encode**（菜名含空格/中文）＋ 建卡页 `onLoad` 真读该参并预填 |
| C 按钮降级 | 断言：卡数 < 未匹配数 ⇒ 批量关联按钮**不渲染**（复用 R262 的 `shortCardGap`） |
| 通用 | 每条配**变异回灌**（点名转红）+ 自失效护栏；门禁须 **163/163 · rc=0** |

## 4 如果坚持要藏：怎么藏才不误伤

🔴 **只能按「有没有 shape」藏，绝不能按卡片整块关**（R259 已踩过一次）：
`pages/takeaway` 那个 tab 是**统一导入器**，`importSalesBill` **按表头自动判形态**
（A 堂食菜品 / B 套餐明细 / **C 外卖商品销量**）⇒ 整块关会**连带砍掉堂食单品与外卖单品的输入**，
且页面上只表现为"按钮不见了"，看不出砍了什么（守 `check_bill_import_gate`）。

⇒ **结论：账单那块已经按这个规矩藏了；再往下藏，砍的就是外卖单品本身。不建议。**
