## §0 一句话结论

**采用 A′（融合方案）：原料档案免费无限 + 录入不设限 + 计算设限（阶段 1 q=20）+ 套餐/外卖/导出/全菜单诊断付费。**
比 A 更准的地方在于：**免费的边界不在「能建几张」，而在「能算几张」**；比 B 更准的地方在于：**计算闸门不能架在第一次使用上（信任未建立就撞墙）**。

### 1.1 双向纠错各一次（交叉核验的真实价值）
- **豆包纠我方**：① 我把它的「加权覆盖率」引用成「全满足率」，口径错误，它当场纠正；
  ② 我方对引擎红线理解过窄——红线是**禁止改源码**，不是**禁止调用**，所以 draft 路径**应当**调用 `wouldCreateCycle` 做写时防环。
- **我方纠豆包**：① 它给的百分比无来源分级，被我方门禁纪律钉出→它承认是自造估算模型；
  ② 它写错配置单源名 `limits.cost_card_free`（现网不存在），被纠正为 `plan_free.limits.cost_card`；
  ③ 它的「价值菜覆盖率」定义与用户真实动机（诊断「我怀疑这道菜不赚钱」）可能不重合。

## §2 最终方案（v1.5 收敛版）

### 2.1 三层边界【已确定】
| 层 | 能力 | 免费 | 付费 |
|---|---|---|---|
| 地基 | 原料档案 | ✅ **无限**（现网 `limits` 里本就无此项；需**显式写入规范**防止后人误加限制） | ✅ |
| 核心 | 成本卡**录入/保存**（含 draft） | ✅ **无限**（档案域） | ✅ |
| 核心 | 成本卡**计算**（生成快照） | ✅ **q=20**（阶段 1） | ✅ 不限（硬上限 2000） |
| 高级 | 套餐核算 / 外卖核算 | ❌ | ✅ |
| 高级 | 全菜单毛利诊断 | ❌ | ✅（**待拍板**，建议"是"） |
| 横切 | 导出 / 打印 | ❌（沿用 v1.3 全禁，对齐 M1） | ✅ |

> **关键**：免费的边界是「**能算几张**」而非「能建几张」。录入不设限 ⇒ 用户不会因"装不下"流失（资产沉淀、留存强）；计算设限 ⇒ 付费点清晰。

### 2.2 免费档专属前置闸门【已确定】
- **位置**：云函数入口层新增守卫 `assertCostCardQuota(user, dishId)`（业务外、引擎外）。
  **不放** `validate` 层（那层只做参数合法性）；**不做**全局开关层（`enable_real_payment` 只管支付行为，与配额无关）。
- **原路径保留**：付费档 + 配额内免费档（`count < q` 或该菜已有快照）→ 原样走 `saveCostCard`（保存即计算 + 生成快照）。
  **否决全量改双态**——那会把付费用户的"保存即算"也拆掉。
- **超额分支**：免费档第 21+ 张（该菜无快照）→ 新函数 `saveCardDraft`：只写配方 + `status='draft'`，
  **不调用** `netUnitCostWan` / `lineNetCostYuan` / `calcCostCard`；返回 `QUOTA_EXCEEDED` 给前端。
- **红线（精确表述）**：4 个具名引擎函数 `netUnitCostWan` / `lineNetCostYuan` / `calcCostCard` / `wouldCreateCycle`
  **源码零改动；禁止改源码 ≠ 禁止调用**（这是本轮最重要的认知修正）。

### 2.3 统一重算集规则（零状态迁移，覆盖降级与免费档）
```sql
SELECT dish_id FROM cost_snapshot WHERE user = ? GROUP BY dish_id ORDER BY MAX(created_at) DESC LIMIT q
```
- **重算集 = 此结果**；新菜计数用 `COUNT(DISTINCT dish_id)`。
- 名额内重算会刷新该菜快照时间，**只会让它继续留在前 q 内，不会踢走其他菜**（非名额菜无法重算、无法刷新）⇒ 集合天然稳定。
- 软删释放名额后，第 21 名自动顺延进入重算集 —— 与"软删不占配额"裁定一致。
- **与 M1 对齐**：到期后"历史可读、可编辑、不能新建、不能导出、续费立即恢复"；
  M3 的"不能新建"精确对应"**不能产生新计算**（新菜计算或名额外重算）"；
  **`expire_at` 是唯一权限判定字段，没有第二个到期概念**。

### 2.4 计数维度表
| 维度 | 载体 | 计数规则 |
|---|---|---|
| 档案数 | `shop_cost_card` 行（含 draft） | 不限量、不计 |
| **可计算数** | `status='calculated'` 的 distinct `dish_id` | 首次计算时校验占用；复制新菜占、重算不占 |
| 快照数 | `cost_snapshot`（不可变，含价格时间点） | 永存、不计 |
| 套餐 / 外卖 | `combo` / `takeout_plan` | 无免费配额 |

### 2.5 配额动作表（洞 7 闭环）
| 动作 | 计数影响 | top-q 排序影响 |
|---|---|---|
| 软删 | −1（移出活卡） | 排除出排序 |
| 恢复（undelete） | +1（重新成为活卡） | 按 `MAX(created_at)` 排名 |
| 版本回滚 | 不变（`dish_id` 去重） | 按该 `dish_id` 的 `created_at` |
| 新菜首次计算 | +1（须计数 < q） | — |

**三条硬规则**：① 恢复是**纯档案操作**——不触发重算、不自动占配额、**不生成新版本**，重算资格完全由统一 top-q 规则决定。

### 2.6 重叠防守
- **draft 禁导出（双拦截点）**：draft 无成本结果，导出 PDF 的"成本"栏无值；且放行 = 免费拿走配方数据 ⇒ **一律禁导出**。
- **saveCardDraft 单副本 + sync 跳过 draft**：新函数只加在 `saveCostCard` 侧；`syncCostCard`（同步至最新价）对 draft **跳过**（draft 无快照可重建）。
- **存量迁移**：读侧 **fail-soft**（缺 `status` 视为 `calculated`）+ 一次订正，订正条件用 `has_snapshot = 1`
  （**不是全表**——万一有无快照的孤儿卡，应归入 draft 语义，别把脏数据洗成 calculated）。

### 2.7 超额交互稿
- `QUOTA_EXCEEDED` → 弹**全局付费弹窗**（对齐 M1/M3 共用同一个弹窗的约定），只有 `title` 随触发点变化，`confirmText` 统一短键：
  | 付费域 | title（不限长） | confirmText |
  |---|---|---|
  | 配额墙（20/20） | 免费额度已用完（20/20） | **去开通**（3 字 ✓） |
  | 套餐核算 | 开通套餐核算，解锁套餐利润测算 | 同上 |
  | 外卖核算 | 开通外卖核算，解锁外卖佣金利润测算 | 同上 |
  | 导出打印 | 开通导出，解锁成本卡 PDF 导出与打印 | 同上 |
  | 全菜单诊断 | 开通全菜单诊断，解锁菜单毛利体检 | 同上 |
  > 🔴 约束来源：微信 `wx.showModal` 的 `confirmText` **上限 4 字符**（我方 2026-09-26 刚因按钮文案 6 字出过线上 bug，已挂 **R145 守卫**把守）。
  > 付费按钮「开通+功能名」的铁律与 4 字上限**天然冲突** ⇒ 长命名只放 `title`，按钮位另配短键。

### 2.8 配置单源（真实结构，豆包原稿写错已纠正）
```js
// cloudfunctions/initDb/collections.js → SEED_FEATURES（唯一真相源）
{
  plan_id: 'plan_free',
  limits: {
    shop: 1,        // M1 账套（不变）
    cost_card: 20,  // ★ M3 免费可计算成本卡数：5 → 20
    hard_shop: 200,
    hard_card: 2000,
  },
}
```
> 🔴 `subscription_plan` **是付费价格表**（`payCreateOrder` 按 `plan_id` 读它下单）⇒ 免费档**绝不能**塞进去，否则免费档会变成可下单的付费档。
> 🔴 凡新增种子行**必跑** `{only:'seed_missing'}` 轻量通道（r122 教训：已建库环境补不进新种子行 ⇒ 直接 `SYSTEM_ERROR`）。

### 2.9 实施顺序【已确定】
- **R144（快照 5 字段守卫）先合入，本次改动紧随其后，两批各自独立可回滚**。
- 理由：本次改动是快照的**消费者**不是**生产者**（不生成快照）——碰的是入口守卫、`saveCardDraft`、`status` 读写、配额计数/排序；
  `calcCostCard` / `buildSnapshotLines` / `rebuildSnapshotLines` **一行不动**。但配额逻辑**依赖快照字段**（`dish_id`、`created_at`）⇒ R144 要先立住。
- 四批次顺序：① R144 守卫 → ② 前置闸门 + 计数规则（地基） → ③ 超额交互 + 付费墙接线 → ④ 套餐 / 外卖付费域。
  **红线：墙必须先于付费域功能**（否则功能做完了没有墙 = 白送）。
