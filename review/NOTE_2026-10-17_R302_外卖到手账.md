## 2 设计取舍（留痕）

| 决策 | 选择 | 理由 |
|---|---|---|
| **口径放哪** | 全部下沉 `utils/takeaway.js`，页面只做「名字→数字」解析与格式化 | 金额口径必须可单测、可复算（本仓既有形态） |
| 🔴 **公式单源** | 把 `reconcile` 里内联的「应有商家应收款」抽成 **`expectedReceivable`**，`reconcile`（元）与 `settleSummary`（分）**共用同一份** | 「到手金额」与「配平校验」**本是同一口径**。各写一份 ⇒ 一旦漂移就出现"校验说对、到手账说另一个数"（同一语义两份实现＝本仓最贵的病） |
| **单位** | `settleSummary` **入参出参都是分**（本仓金额单源）；唯一除法（到手率/单均）只在展示层收尾 | 避免元浮点连乘 |
| **缺项** | 营收 0 ⇒ 到手率 `null`（**不是 0**）；无订单数 ⇒ 单均**空串**（**不是 '0.00'**） | 0% 会被读成"一分没到手"；`0.00` 会被读成"每单白干" —— 本仓「**不替用户编数**」同一条纪律 |
| **佣金/配送费未录** | 平台扣费显示「**未填**」而不是 `0.00`，并挂一行 warn 提示去补录 | 全 0 会让到手额**偏高**；显示 0.00 等于告诉老板"平台不扣费" |
| **两条提示文案** | 都**故意 <18 字**（`settleNote` 15 / `settleMissingFee` 16） | 避免触发 `check_hint_fold` 的折叠要求（那要新建折叠手柄 + 登记 EXPECT）⇒ 控制改动面 |
| **项名单源** | `TERMS.ledger.takeawayMode.reconcileRoles`（佣金/配送费/配送补贴）+ `TERMS.semantic.expenseMktSubsidy`（商家补贴） | 页面**零中文字面量**（守 `check_page_terms` 判据③：改名不得静默失效） |
| **收入侧定位** | 机器值 `category === 'takeaway'`（与 `pages/month/input.js` 同一判据） | 与录入侧同源 |
| **有效订单数** | 只从收入侧 `sub_items[].qty` 累加 | R162：qty **不进任何金额**，只派生单均 |

## 6 边界与未闭环（如实）

1. **到手金额是「按你录的数估算」，不是平台结算单** —— 页面已明说。
   真值差异来源：结算期错位（T+1/T+3、跨月）、退款/餐损赔付、平台承担补贴（本就不进商家到手）。
2. **不接入平台任何接口**：本步只做**已有数据的二次利用**，零新增数据源（也就不需要授权/爬取）。
3. **单均到手依赖「有效订单数」**：老板没填 ⇒ 该行**不显示**（而不是显示 0）。
4. **`platformFeeKnown` 只看三项之和是否为 0** —— 若老板确实一分佣金没有（极端场景），会误报"未填"。
   权衡：误报一句提示 ＜ 静默把到手额抬高。**已登记**。
5. **M1 结果页的月份口径**：结果页本身按 `month` 参数取账，与本卡无关（本卡跟着该月账走）。
6. **未做的事（本轮范围外）**：把到手账**下钻**到各平台（收入侧已按平台分，但费用侧佣金/配送费是**合计**，
   分不到平台）⇒ 要"分平台到手"必须改录入侧结构，**不在本步**。
7. C 线冻结；**`getDishReview`（R301）+ `manageShop`（R299）待重新部署**。
