- 时间：2026-10-21
- 结论：**4 处接线完成**，守卫 56 → **63 条**，3 个变异全部被抓到，门禁 203/203。

## 1. 这 4 处为什么之前"看着接了、其实没接"

R419 给金额框接了体检（`updateRow` 那条腿），R425 补了 `onMkByPlat`（独立 handler）。
剩下的 4 处，**两条腿都摸不到**：

| 入口 | 写哪 | 为什么不触发体检 |
|---|---|---|
| `onTwDetail` | `takeoutDetailRows[i].goods/pack/subsidy` | 不走 `updateRow` |
| `onFastSubsidy` | `rows[i].subsidy` | **走了** `updateRow`，但触发条件只认 `patch.amountYuan` |
| `onRecYuan` | `twRecYuan` | 直接 `setData` |
| `onDirectConsume` | `directConsumeYuan` | 直接 `setData` |

## 2. 🔴 `onFastSubsidy` 那条最值得记

它**确实走了** `updateRow`，看起来"应该被覆盖"。但 `updateRow` 的触发条件是：

```js
if (patch.amountYuan !== undefined) this.checkAmounts();
```

而它传的是 `{ subsidy: ... }` —— **字段名不是 `amountYuan`**，于是静默跳过。

**判据盯的是"字段名"，不是"这一格是不是钱"。**
这和 R299 记的"守卫只守分支在不在、不守分支到不到"是同一族病。

## 3. 后果（为什么不是"少提示一次"）

- 分项模式 `subtotalOf` 会把**读不成的按 0** 求和
- 对账"实收"被按 0 ⇒ 差额虚大
- 直接消费被按 0 ⇒ 利润虚高

**全程零报错**。与 #31（佣金行被 `syncMkPlat` 覆写）同构。
按 #24/#25 的原则：**只暴露，不静默清洗、不改 `yuanToFen`、不阻止写入** —— 猜着替老板"修好"比不修更糟。

## 4. 改法

1. `checkAmounts` 的两组 rows 扫描补 `rows[j].subsidy`
2. `checkAmounts` 新增三段：`takeoutDetailRows` 三框 / `twRecYuan` / `directConsumeYuan`
3. 4 个 handler 各补 `this.checkAmounts()`
4. **未改 wxml、无新增文案**（复用 `t.amountBadTip`）⇒ terms 双副本零改动、免出码
5. **零云函数改动** ⇒ 免部署
