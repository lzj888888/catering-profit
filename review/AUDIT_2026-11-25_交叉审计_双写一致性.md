## 1 真缺口（当场修完）

### G4：本地刚填的新值，被云端旧值覆盖

**实测复现**（`_probe.js` B 组）：
```
设备B本地刚填 nonsales=20000 分（200 元），但 localAt=0
云端是旧值 nonsales=8000 分，updatedAt=100
syncFromCloud: 100 > 0 ⇒ 覆盖
结果：本地变回 8000 —— 老板刚填的 200 元没了
```

**根因**：本地写数据时只更新业务 key，**不更新水位线** `consume_sync_at_`。
`cloud.updatedAt > localAt` 这个判据完全感知不到"本地有未推送的新修改"。

**修**：新增 `markLocalNew(month)`，`onNonsales` / `onMatQty` 写本地时立刻把水位线推到 `Date.now()`。
这样云端旧值（t=100）就盖不过本地新值（t=现在）。

**验证**：修复后同样时序，本地 20000 分保住；反恒真（删掉 `markLocalNew`）判据必红。

### G5：设备B只填员工餐，把设备A的原料盘点清空

**豆包 Q4-1 提出，我实测确认**（`_probe_fields.js` D 组）：
```
设备A：填了原料盘点 → 云端 items=[牛肉 95 斤]
设备B：本地只填员工餐 80 元，本地 matinv 为空
B.pushToCloud: payloadOf(month, 8000, []) ⇒ 上传 items=[]
结果：设备A的原料盘点被清空
```

**根因**：`pushToCloud` 只用**本地两栏**组装整个 payload，没读云端。

**修**：`pushToCloud` 改为 `async`，上传前先 `store.loadCloud` 做**字段级合并**（保守：本地缺的字段用云端补，宁可留旧也不清空）。

**代价（已写进代码注释）**：老板想"故意清空"原料盘点时会被云端旧值补回来。清空是低频且可重来，比"另一台设备的数据被静默清空"好得多。

### G6：防抖期间页面被回收 → 数据只在本地

**豆包 Q1-2**：输入后 800ms 防抖，`T+700ms` 小程序被切后台/系统回收 ⇒ `setTimeout` 不执行 ⇒ 没上传。用户清缓存/卸载后丢失。

**修**：加 `onHide` / `onUnload`，有挂起的 `_pushTimer` 就清掉并**立即补发**上传。

## 3 结构性洞察

**上一轮验证的盲区**：我用模拟器跑通了"填数 → 上传 → 清本地 → 从云端恢复"，
那条路径是**理想串行**的。交叉审计打的是**并发/乱序/异常退出**，三个洞全在这类路径上。

⇒ 结论：**"能跑通"与"不丢数据"是两回事**。以后这类双写功能，验证清单必须包含反面时序。
