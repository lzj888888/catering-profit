## 1 通盘核查：三个模块的指标现状（代码实证）

### 全仓唯一指标源 `cloudfunctions/common/indicatorRef.js`
```
REDLINE = { rent: 15, labor: 20, grossMargin: 55, loss: 5 }   // :156
BANDS.fastfood.rent = [8,15] / dining [9,15] / hotpot [8,15] / cafe [9,18] / other [8,18]  // :111-119
```

文件原话（:167 附近）：
> **同一指标两个阈值是最典型的静默分裂** —— 强制 M1 页面与诊断引擎逐业态相等，改一处不改另一处即判红

**一致性守卫（已存在）**：`check_indicator_ref.js`(30处引用) / `check_m1_indicator_view.js`(13) / `check_m3_margin_bands.js` / `check_three_cost.js` / `check_redline_thresholds.js` / `check_audit_redlines.js`

### 三个模块怎么用
| 模块 | 房租占比口径 | 判定来源 |
|---|---|---|
| **M1** | 月租÷月营业额 | `indicatorRef` BANDS + REDLINE + THREE_COST |
| **M3**（getDishReview） | 引用 `indicatorRef`（仓库内有 `cx_indicatorRef.js` 派生副本） | 同源 |

| **M2**（calcSandbox） | `target_rent_rate` 是**用户填的目标值**，引擎用来倒推 `rent_cap_fen`（能租多贵），**不判好坏** | 输入，非判定 |

⇒ **M2 现在不判定，所以不存在"判定不一致"；一旦要判定，必须接 `indicatorRef`，不能自造。**

## 2 🔴 V2 的错误（必须作废）

V2 我写了"正餐>15% 红 / 小吃>20% / 茶饮>28% / 商场>20% 高危"——**这套数来自网上资料，和单源冲突**：

| V2 写的 | 仓库单源 | 后果 |
|---|---|---|
| 茶饮红线 28% | `BANDS.cafe.rent = [9,18]`、`REDLINE.rent=15` | 房租占 22% 的茶饮店，V2 判"健康"、仓库判"超警戒"——**差 10 个百分点，会害老板** |
| "小吃"业态 | 仓库只有 fastfood/dining/hotpot/cafe/other 五类 | 凭空造业态，破坏 C-⑫ 不变式与派生 other 带 |
| 正餐 8–13% 健康 | 仓库 dining rent [9,15] | 口径不一 |

**这正是李老师担心的"各模块指标不一致"。** 我上一轮刚做完判断可靠性审计（命中0/7），这轮又拿外部数字直接套——**同一个错误模式重犯**。记入教训。

## 3 博主借鉴逐条裁决（有没有价值？）

用两把尺子：① 是否含数字阈值（含⇒必须让位单源）② 是否依赖平台数据（依赖⇒合规红线）。

| 借鉴项 | 裁决 | 理由 |
|---|---|---|
| **等时圈**（5/10/15分钟画圈，人口与竞品叠加） | ✅ **保留**（话术，无阈值） | 纯观察提醒，不碰指标，不造数 |
| **竞品吃饱**（排队/翻台/外卖，有竞品不可怕） | ✅ **保留**（话术，无阈值） | 反直觉判决，符合"敢下判决"调性 |
| **空铺率/晚10点/雨天再看** | ✅ **保留**（话术，无阈值） | 零数据，老板自己走一趟 |
| 博主的分业态租金占比阈值 | ❌ **作废** | 与 `indicatorRef` 冲突，见 §2 |
| 抖音搜索指数/流量租金比/日流量>500 | ❌ **不要** | 平台数据 + 假精度 |

⇒ **博主的价值只在"观察话术"，不在"数字指标"。** 用对了是补充，用错了就是这次 V2 的坑。

## 4 V3 最终方案（唯一一件）

### 做：一份「签前清单 + 踩点提醒」文本（零代码、零阈值、零外部数据）

内容两块：

**A. 踩点 5 观察**（博主借鉴，纯话术）
1. 分工作日/周末、早中晚蹲点，别信房东嘴里的"人流量"
2. 画"等时圈"（步行/骑车 5-10-15 分钟），别画同心圆；圈里的人如果更靠近隔壁竞品，真正能争的没那么多
3. 看竞品**吃饱没**：饭点排队吗、翻台快吗、外卖多吗——有竞品不可怕，怕没竞品还没客流
4. 空铺率是街道体温计；晚上 10 点再看一次治安/停车；雨天再看（堂食客流掉约四成）
5. 看硬件：电、水、排烟、燃气、层高、门头展示面

**B. 签前 8 条**（V1 已有 + 保留）
递增% / 免租期 / 能否转租 / 提前解约赔偿 / 水电容量 / 排烟合规 / 租期匹配装修回收 / 备 2–3 个候选

**C. 口径一句话**（不造阈值）
清单里凡提到"房租占比"，统一写：
> 房租占比 = 月租金(含物业公摊) ÷ 月营业额，健康区间与红线见【M1 房租占比】——本工具全模块同一口径。

指向 M1 的判定，**不复制数字**（复制就会腐化成第二个真相源）。

### 不做
- 不改任何指标/阈值/业态/引擎
- 不加新业态、不加红黄绿判定（要判定就等 M2 正式接单源那次，单独立项）
- 不碰平台数据、不做假精度指标

## 5 为什么这是"值得做"而不是"为了改而改"

- **实打实的价值**：老板签租约是 irreversible 的决定；一份"蹲点+签前"清单能在签之前拦住最常见的坑（没雨天看、没查排烟、没算空铺率）——这些是**真会亏钱**的，且**我们零成本就能给**
- **零风险**：不含任何数字阈值 ⇒ 不可能和 M1/M3 冲突；不需要外部数据 ⇒ 不碰合规；纯文本 ⇒ 不动代码/引擎/守卫
- **反面**：如果我按 V2 去做红黄绿判定，那才是"为了改而改"——会引入和单源冲突的假阈值，正是李老师您问"有没有必要"时该被砍掉的那类
