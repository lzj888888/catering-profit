## 一 结论先行（三句）

1. **还需要** —— 但要的是**菜品级销量表**，不是结算账单（您给过的美团/淘宝闪购账单已核实**不含菜名**，见 `r183_m331_gap/probe_r183_billcols.out.txt`）。
2. **要两类**：**堂食（收银机）+ 外卖（平台）**，两个都要；**团购券核销暂不要**。
3. **只要 1~2 份就够** —— 同一套收银/平台导出的模板是统一的，摸一份通吃一类，不是"越多越好"。

---

## 二 三类来源的取舍

| 渠道 | 要不要 | 对应什么 | 优先级 | 从哪儿拿 |
|---|---|---|---|---|
| **堂食**（收银机点单） | ✅ **要** | 堂食菜品销量 | **P1** | 收银系统后台（美团管家 / 客如云 / 银豹…） |
| **外卖**（美团 / 饿了么 / 淘宝闪购） | ✅ **要** | 外卖菜品销量（🔴 **含套餐**） | **P1** | 各平台商家后台 |
| **团购券核销**（到店团购） | ⛔ **暂不要** | —— | P3 | 美团开店宝 |

**为什么堂食 + 外卖两个都要**（不是二选一）：规范 v1.2 §M3.33 第 1 条是**硬约束** —— 只导收银会**系统性漏掉外卖那一半**，反过来只导外卖会漏掉堂食。漏了半边 ⇒ 单品毛利排名直接看不懂（招牌菜可能一半销量在外卖）。

**为什么团购暂不要**：团购券核销在 M1 收入侧**已有独立收入项**（`income_dine_groupon`「团购券核销」，属 `dine_in` 类）⇒ **钱已经记上了**，缺的只是"菜品级"；而团购多为套餐/代金券，菜品级拆解要靠映射且量通常小 ⇒ 排最后，等前两类跑通再说。

## 三 具体导出路径（分渠道，照着点）

### A. 堂食 —— 美团收银 / 美团管家（✅ **李老师 2026-10-01 已确认：本店用的就是美团收银** ⇒ 走这条）

- 后台地址：`https://pos.meituan.com/`（也可从收银 POS 端：左上角三杠 → 导航栏 → 美团管家 PC 进入）

| 想要什么 | 路径 |
|---|---|
| **菜品销售统计**（单品+套餐合计） | 美团管家后台 → **报表中心** → **菜品报表** → **菜品销售统计** → 选营业日期 → 查询 → 右上角 **【导出】** |
| **单品销售统计**（按天看某道菜） | 报表中心 → 菜品报表 → **单品销售统计** → 搜菜名 → 查询 → **【导出】** |
| 🔴 **套餐销售统计**（**外卖卖爆的常是套餐，这份最关键**） | 报表中心 → 菜品报表 → **套餐销售统计** → 统计方式选 **「套餐明细」** → 查询 → **【导出】** |
| 打包费 / 配送费等非菜品收入 | 报表中心 → 菜品报表 → **销售品项统计** |

⚠️ **四条注意事项**：
1. **导出只能在 PC 端**（美团管家后台）。POS 端只能查询/打印，手机 APP（美团管家 → 报表 → 菜品）只能看，都**不能导出**。
2. **套餐要选「套餐明细」统计方式** —— 选「套餐」只给套餐整体销量，选「套餐明细」才会列出**套餐内每个子菜品**的销量；多个套餐含同一菜品时，点套餐名前的 `+` 可展开。
3. **「菜品销售统计」不含打包费/餐盒费/配送费**（这些在「销售品项统计」里）—— 这正好合我们的口径（销量表只管菜品）。
4. 筛选条件容易残留（营业日期 / 菜品分类 / **销售方式：单品 or 套餐**），导出前确认一遍，否则数目对不上。

#### A-附 · 美团收银的**官方字段口径**（来源：美团餐饮系统帮助文档「如何使用菜品排行报表」`rms.meituan.com/FAQ/FAQDetail/3298`）

| 字段 | 官方口径 |
|---|---|
| 名称 | 菜品 / 套餐 / 分类的名称 |
| 销量 | 已售出菜品销量，**不含**退单、撤单、退菜 |
| 🔴 金额 | **店内售出 = 扣除优惠后**金额；**外卖售出 = 原价**金额 ⇒ **两边口径不一致** |

🔴🔴 **三条会直接坑到解析的事实**（均出自上述官方文档）：

1. **金额之和 ≠ 营业额**（官方明写）：抹零 / 减免 / 免找零 / 会员优惠**无法分摊到菜品**，外卖红包 / 满减同样无法分摊
   ⇒ 🔴 **绝不能拿「单品营收之和 == 总营收」当校验** —— 会误判成"导入错了"，而它本来就不相等。
2. **菜名可能是 `-`**：门店绑了外卖但**没建「外卖菜品 ↔ 店内菜品」映射**时，外卖售出的菜品名**显示为 `-`**
   ⇒ 正好是 `shop_dish_mapping` 要补的那个洞；导入时 **`-` 行必须单列提示，不许当菜名入库**。
3. 🔴 **套餐默认按"一道菜"统计**：官方例子 —— 售出「拉面套餐（含拉面+卤蛋）」记为 **套餐 1 份**，
   **不会**拆成「拉面 1 份 + 卤蛋 1 份」⇒ 要拿到子菜品，必须选 **「套餐明细」** 统计方式。

💡 **一条可能省事的发现**：美团收银绑定外卖后，菜品销售统计里**同时含店内 + 外卖**
（筛选项「业务」可选：店内+外卖 / 仅店内 / 仅外卖）⇒ **一张表可能就同时覆盖堂食和外卖**。
⚠️ 但其中**外卖部分的菜名可能是 `-`、金额是原价**（未扣平台优惠）⇒ **外卖仍建议从平台后台导**，两边交叉印证。

#### A-附2 · 字段名的**强预测**（**待真表校验**）

来源：美团开放平台「门店-菜品销售统计」API 文档（与后台报表同源）：

`dishName`（菜名）· `dishSpec`（规格，如"大份"）· `dishCateName` / `secondCateName`（大类 / 小类）·
`orderTypeName`（店内销售 / 外卖）· `dishUnitName`（份）· `dishSaleCnt`（销量）·
`dishSaleAmt` · `dishIncomeAmt` · `dishCmpgnAmt` · `taxAmt` · `noTaxIncomeAmt`

🔴 **金额单位未定**：文档示例 `dishSaleCnt=3`、`dishSaleAmt=308000` ⇒ 若单位是「分」则 3080 元 ÷ 3 份不合理，
疑为「厘（0.001 元）」⇒ **必须拿真表反推，不得假定**（这正是"非要真表不可"的理由之一）。

### B. 外卖 —— 美团外卖商家后台

- 后台地址：`https://waimai.meituan.com/`（另有独立数据中心 `data.meituan.com`）

| 路径 | 说明 |
|---|---|
| 登录 → **经营分析** / **数据中心** → **商品分析**（或「商品销售报表」）→ 选日/周/月 → **导出** | 找「商品」字样，**不要**点「订单明细 / 账单 / 结算」 |
| 美团外卖商家版 **App** → **门店运营** → **经营数据** → **商品分析** | App 一般只能看，导出回 PC 端 |

🔴 **区分业务线**：外卖用「美团外卖商家版 / waimai.meituan.com」，到店团购用「开店宝」，**两套数据不互通，别登错号**。

### C. 外卖 —— 饿了么 / 淘宝闪购

| 路径 | 说明 |
|---|---|
| 饿了么商家后台（网页）→ **数据中心** → **销售数据 / 商品销量** → 设时间范围 → **导出** | 找「商品 / 销量」字样 |
| 饿了么商家助手 **App** → **数据中心** → **销量分析** | 看月销量用这个（淘宝闪购商家走的也是饿了么体系） |

导出来发我就行，**我不需要知道您用的是哪一家**（表头由您在导入页自己点选映射）。

## 四 我要的最小东西（三列即可）

```
菜品名称 | 销售份数 | 销售额
```

**可接受形态（都算数）**：
- 数据**可以脱敏**（菜名改成"菜A/菜B"都无所谓）；
- **金额和份数全填 0 也行** —— 我要的是**表格结构**，不是数字；
- **一两行就够**；
- 实在导不出来 ⇒ **把那个页面截个图给我**（按截图定"表头在第几行 / 有没有小计行 / 有哪些列"）。

🔴 **两种不要**：
- ❌ **不要 Top10 / 排行榜** —— 排行底部截断 ⇒ 「哪道菜拖后腿」算不出来，必须**全量明细**；
- ⚠️ **截图只用来定结构，不用来取数**（OCR 取数早已否决：识别错一行污染整月）。

### 四-附 · 真表到货后**立刻要核的 6 项**（拿到表 10 分钟内对完）

| # | 核什么 | 为什么（猜错的后果） |
|---|---|---|
| 1 | **表头在第几行**（上面有无门店名 / 日期标题行） | 决定从第几行开始读数据；错了 ⇒ 识别 0 行 |
| 2 | 有无 **小计行 / 合计行** | 不排除 ⇒ **小计行静默变成一道菜进排名**（🔴 不报错，给个错数） |
| 3 | 规格（大份 / 小份）是**独立列**还是**独立行** | 决定"一行 = 一道菜"还是"一行 = 一个规格" |
| 4 | 🔴 **金额单位**（元 / 分 / 厘） | 用一行已知数据反推，**不得假定**；错了 ⇒ 毛利差 100 倍 |
| 5 | 「店内 vs 外卖」是**一列区分**还是**两张表** | 决定来源拆分的落法（规范硬约束：两来源分开呈现） |
| 6 | 套餐**是否已拆明细** | 若表里写的是「拉面套餐 1 份」⇒ 未拆，需另导「套餐明细」版 |

> 第 2 项和第 4 项是**最怕的两条**：它们错了**不会报错**，只会给出一个看着合理的错数。

## 五 拿到之后我做什么

1. 写**结构探针**：表头在第几行 / 有无小计行・合计行 / 是否多 sheet / 规格是否独立行 / 日期格式；
2. 定**导入页的列映射交互**（表头列出来由用户点选，**不猜列名**）；
3. 出阶段②（M3.33 单品毛利复盘）**投喂包**，交 InsCode；
4. 🔴 **套餐那条单独处理**：外卖/堂食商品常是套餐 ⇒ 平台名、收银名、我方成本卡名三处对不上 ⇒ 走 `shop_dish_mapping` 映射，**未匹配行单列提示、绝不静默归零**。

## 六 没有样例会怎样（三档，最怕第三档）

| 档 | 后果 |
|---|---|
| 轻 | 走兜底：用我方自定三列模板（`菜品名称｜销售份数｜销售额`）+ 手工映射 ⇒ **能起步**，但用户得自己整理一遍表 |
| 中 | 只吃"我想象的表结构" ⇒ 真实用户一上传「识别到 0 行」 ⇒ **上线即翻车**，且用户不会告诉你为什么，**直接流失** |
| 重 🔴 | **结构猜错会被静默算错** —— 不报错，给一个看着合理的错数（例：小计行被当成一道菜进排名），用户拿它做经营决策 |

> 第三档有前科：美团那份账单若直接抄「账单金额」，会**虚低 78.69 元**（那还是**手里有真表**才挖出来的）。
