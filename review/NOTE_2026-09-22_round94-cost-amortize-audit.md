## §0 一句话结论

费用侧与摊销侧各有 **1 条「钱会算错」的硬缺口**（都朝「利润虚高」方向），另有 2 条**稳定误导用户**的交互缺口、2 条展示/语义可优化点；
其中「提前报废残值不进损益」有**页面文案反向承诺**（页面对用户说"将计入"，实际不计入），建议优先级最高。

## §2 六条发现

### D1（最优先）提前报废残值不进损益，且**页面承诺了却做不到**

**实跑证据**（`probe_amort_gap.out.txt`）：

| 环节 | 实跑结果 | 判定 |
|---|---|---|
| ① 产出侧 `calcAmortize` | `details[0].residual_loss = 6000000`（60,000 元）；`calcResidualFen(A) = 6000000` | 残值**算得出** |
| ② 入账侧 `amortizeTotalForMonth` | `2026-06 → 1000000`（仅当期摊销）；`2026-07 → 0` | **残值不在入账额里** |
| ③ 页面侧 `amortizeForMonth` | `{"asset_id":"a1","name":"门面装修","amount_fen":1000000,"in_period":true}` | 返回体**连 `residual_loss` 字段都没有** |
| ④ 利润引擎 | 入参只有 `incomeItems/expenseItems/directConsumeFen/amortizeFen/inventory/pendingSettlementFen`；返回字段无处置损失项 | **没有消费口** |

**同一场景利润对账**：收入 50,000｜直接消耗 10,000｜摊销 10,000
- 引擎算出：经营参考 40,000 元、全要素真实 **30,000 元**
- 若残值按规范「一次性计入当期」：全要素真实应为 **−30,000 元**
- ⇒ **差 60,000.00 元 = 残值全额**。方向是**利润虚高**（把亏报成赚）。

**为什么这是缺陷而不是取舍**：

1. 规范两处明文要求计入：
   - `specs/dev-specs/core/开发规范v1.0_ModuleM1_月度盈利核算.md:94`「未摊余额 `原值 − 已摊合计` 作为**「资产处置/报废损失」一次性计入当期**，**不继续摊**」
   - `specs/dev-specs/poc/POC1_摊销边界与尾差残值.md` 规则 5；`core/04_核对清单.md:104` 第 21 项判据「残值转处置损失」
2. **页面文案反过来向用户承诺了**：`miniprogram/i18n/terms.js:475` 报废二次确认框写
   「确认提前报废该资产？**未摊余额将作为处置损失计入。**」
   ⇒ 用户在界面上被告知"会算"，系统"没算"。这是**承诺与实现不一致**，不是"未实现的规划"。
3. **三副本输出口径分叉**（本轮新事实）：三份「同源」service 里**只有 POC1 那份实现残值**；入账侧与页面侧都没有。既有的「三副本零改动」防线守的是**已有字段不漂移**，守不住**只有一份有的字段**。
4. **「从未被消费」的历史线索**：历次复审（round7 / 8 / 9 / 11）都只验过**残值算法本身**（`933336` 等锚点全对），**没有一轮**验过「残值是否进了利润」。round7 发现 `calcAmortize` 曾把**月度明细写回资产主档**（判为 **R31**，写回行含 `residual_loss`）⇒ 修法是「删写库、回契约（只算不写）」，此后残值**只存在于返回值里**、连存档都没了。
   ⚠️ 但须说清因果：**即使在写库那一版，写库也只是「留档」，并非进利润** ⇒ **消费口从一开始就不存在**，不是这轮修出来的。这条线索的价值是解释「为什么它能一直不被人发现」：每一轮都在验**它算得对不对**，没人问**它算完去哪了**。
4. `core/04_核对清单.md` 第 21 项末列为 `☐`（未勾）—— 与"从未验收过这条"一致。

**待决**（转 §3-①）：补消费口，还是改页面文案把承诺撤回？

### D2 口径选「一次性计入当月」时，这笔钱在利润表里**一分钱都不出现**

**证据**：

- 开关是**店铺级**：`pages/month/input.wxml:297-308`「② 装修设备」二选一 → `input.js:775-791` 落 `shop_switch` 的 `amortize_switch`（`saveShopSetting/index.js:49-63` upsert，唯一键 `shop_id+switch_key`）。
- 开关关 ⇒ `calcMonthlyProfit` 里 `effectiveAmortizeFen = 0`（`saveLedger/service.js:25`）。实跑：`effectiveAmortizeFen = 0`，同月同资产 → 全要素真实利润 40,000 元，**12 万元在利润表里没有任何一笔**。
- 利润引擎**没有**「资产原值直接进费用」的入参（入参面见 D1 表）。

**两处文案方向相反**：

| 位置 | 文案 | 暗示 |
|---|---|---|
| `terms.js:535-536` | `assetOnce: '一次性计入当月'` / `assetOnceDesc: '金额不大，就当这个月的费用'` | 系统会把它当月费用 |
| `terms.js:367`（`expenseScope.operation`） | 「**不包括**设备与装修购置（走「摊销资产」分期摊）」 | 用户**不该**把这笔填进费用 |

⇒ 用户按开关文案理解 = 以为已计入（实际没有）；按费用段文案行事 = 不填。**两条路都通向"这笔钱不出现"**。
后果：**刚装修完开业的店，首月利润会显著虚高**。

> 说明（防止误判）：也不能排除设计意图是"提示用户自己去费用段手填"。但即便如此，**两处文案互斥**是硬事实，且 `assetCount` 只显示"已登记 N 笔"、不显示金额（见 D5），用户没有任何信号知道这笔钱没进账。

### D3 配平校验：**收入侧做了双模式兼容，费用侧没做** ⇒ 稳定误报「漏填」

**代码不对称**（同一函数内）：

```js
// input.js:701-705 —— 收入侧：fast / detail 双模式都能取到
let incomeTotal = rows.reduce((s, r) => s + (Number(r.subtotal) || 0), 0);
if (g && this.data.takeoutMode === 'fast') {
  incomeTotal = (g.rows || []).reduce((s, r) => s + (Number(r.amountYuan) || 0), 0);
}
// input.js:709 —— 费用侧：只按**精确项名**找
const mrow = (name) => { const r = (mk && mk.rows || []).find((x) => x.subItem === name); return r ? Number(r.amountYuan) || 0 : 0; };
// 三个角色全部走 mrow(roles.xxx)
```

而 `reconcileRoles` 是三个**显示名**（`terms.js:335-339`）：平台佣金 / 配送服务费 / 配送补贴。

**推理**：用户只填「营销费用」总额行（`subItem === ''`，这正是默认形态）⇒ `mrow` 三个角色**全返回 0** ⇒
`expected = incomeTotal − subsidy − 0 − 0 − 0`（`utils/takeaway.js:249`）被**高估约 佣金+配送费+配送补贴**（通常占外卖收入 20%~25%）
⇒ 差额远超阈值 ⇒ 稳定落到 `miss`，给用户看 `recMiss`：「差额 xxx 元，可能漏填了某项扣款」。

**触发条件**：仅当用户填了**选填**的「账单商家应收款」（`takeaway.js:242`：`if (!(actual > 0)) return null`）。
⇒ **越认真（去账单抄了应收款）的用户，越会被误报**；只填总额、不理应收款的用户则完全无感。

**与既有已知项的叠加**：`§A.11.7` V1–V3 已诚实登记"账单列名由 WebSearch 推导、无真实账单验证"（`NOTE_round86:119`）。D3 是**独立于列名的第二个致偏源**：即使列名全对，总额模式下也必偏。

### D4 费用口径提示只对「把项名准确打出来」的人生效 —— 提示的受众错位

**代码链**：

```js
// input.js:440-445
const note = notes[r.subItem] || '';          // 按**细项名精确匹配**取
if (!note) return r;
return Object.assign({}, r, { note,
  promo: r.subItem === (TERMS.ledger.takeawayMode && TERMS.ledger.takeawayMode.promoItem) });
```
```wxml
<!-- input.wxml:255 —— 双前提：类别=营销 AND 该行有 note -->
<view class="exp-note {{r.promo ? 'promo' : ''}}" wx:if="{{g.category === 'marketing' && r.note}}">
```

而默认形态是「**每类单行：细项名空 = 整类总额**」（`input.js:198-214` 注释 + `input.wxml:239/250`）
⇒ 默认行 `subItem === ''` ⇒ **`note` 与 `promo` 双落空** ⇒ 提示不渲染。
⇒ 只有用户主动「+ 添加细项」**并把名字准确打成「外卖推广费」**，提示才出现。

**受众错位**：`expenseItemNotes`（`terms.js:345-352`）挂了 6 项，其中推广费那条自己写着
「推广中心 · 消费明细（⚠️ 不在结算单内）」，配套 `promoPathHint` 更直白：
「外卖推广费不在订单结算单里……**只对结算账单核对一定会漏，利润会虚高**。」
⇒ 这句话**最需要被只填总额的人看到**，而恰恰是他们看不到。**护栏只对"已经知道有这一项"的人生效。**

### D5 录入页只显示摊销「笔数」，不显示本月摊销「金额」

- `input.js:311` `assetSummary` ← `loadAssetCount()`（`input.js:808-820`），文案 `assetCount: (n) => '已登记 N 笔资产'`（`terms.js:540`）。
- 摊销页有当月合计（`amortize.js:49-50 totalFen/totalYuan`），但**录入页的费用段拿不到它**。
- ⇒ 老板在录费用、对利润时看不到「本月摊销合计 ¥X」，必须跳到摊销页。
- 可优化（低风险、纯展示）：摊销开关开时，在费用段显示一行**只读**的「本月摊销合计 ¥X（N 笔，点开看明细）」。**建议排在 D1/D2 之后**。

### D6 归档后修改资产不会回算已归档月份（语义点，非缺陷）

- `amortize.js:78` 明确：`const isArchive = false; // 摊销资产不属于月度归档（可跨月管理）；归档守卫只作用于记账录入`
  ⇒ 归档月之后仍可新增/编辑/报废资产，**不受归档守卫**。
- 归档月的 `amortize_fen` 在 `saveLedger` 时已固化进 `shop_monthly_account`（`saveLedger/index.js:114`）。
- ⇒ 会出现「资产台账已改，但归档月账未变」的状态：符合"摊销资产跨月管理"的直觉，但**历史月与台账不再互证**。
- 可加一句提示（改资产时）：「该变更不影响已归档月份；如需重算请到对应月补录（归档后 7 天内可补录）」。

## §4 我建议明确不动的

- **摊销计算规则**（月摊取整到分 / 末月倒挤吸尾差 / 区间含两端 / 终止当月仍摊、次月停）—— 定稿且有自测与锚点（`S1 9160` / `S2 3476.67` / `S3 末月 3333.45` / 旧空调残值 `9333.36`），改动风险远大于收益。本轮的发现**全在周边**，不在规则本身。
- **配平"只软提示、不阻断、不参与利润"** —— 规范明确要求；D3 只谈**怎么提示才不误导**，不谈硬化。
- **`check_terms_forbidden.js:113` 的装饰性 `check(true)`** —— 维持现状（上方 `catch` 已 `exit(1)`，属 fail-closed 之后的装饰，风险为零）。
