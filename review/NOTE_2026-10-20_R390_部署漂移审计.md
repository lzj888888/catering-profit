# R390 · 线上 vs 本地对拍（部署漂移审计）

> 2026-10-20 · 起因：自动化的部署步骤是我今天新加的，得先证明"现有 5 个函数的线上版本 = 本地"。

## 一、怎么查的（可复跑）

```bash
cli cloud functions download -n <函数> -p <临时目录> --env cloud1-… --project <仓根>
cmp cloudfunctions/<函数>/<文件>.js <临时目录>/<文件>.js
```

比对范围：该函数目录下的全部 `.js`（**排除 `node_modules`**）。

## 二、结果

| 函数 | 结论 |
|---|---|
| `calcSandbox` | ✅ 一致（含 R386 的 `bands_version`） |
| `getCostCard` | ✅ 一致（含 R387 的 `inputs_ref`） |
| `getCardVersions` | ✅ 一致 |
| `saveCostCard` | ✅ 一致 |
| `clearMonth` | ⚠️ `cx_indicatorRef.js` **线上是旧版** |

## 三、那条差异是不是缺陷？——不是，但值得写成规则

`clearMonth` 是在 R386（给 `common/indicatorRef.js` 加 `BANDS_VERSION`）**之前**部署的。
`sync_common` 把那行同步进了全部 52 个目录的 `cx_indicatorRef.js`，但只有 `calcSandbox` 重新部署过。

关键判断：**`clearMonth` 根本没有引用 `indicatorRef`**（已核，`index.js` / `validate.js` 零命中）
⇒ 那份旧副本是**死代码**，不带任何行为差异。

推而广之：

> `common` 的改动会让 **52 个目录的本地副本同时领先线上**。
> 只要某函数**没调用新符号**，线上带着旧副本**无害**；它会在下次部署时自动同步。

## 四、因此立下的部署规则（已写进自动化提示词）

1. **按「行为是否真的变了」部署**，不按「文件有没有变」；
2. **禁止**因为 `cx_*.js` 变了就批量部署 52 个函数——35 分钟、零收益、还有把好函数改坏的风险；
3. 判据：`grep` 新符号在**该函数的 `index.js` / `service.js`** 里是否被引用；
   例子：`BANDS_VERSION` 只被 `calcSandbox/index.js` 引用 ⇒ 只部署 `calcSandbox`。

## 五、没做

- **没有为了"看起来一致"去重部署 `clearMonth`**：它不带行为差异，为了美观动线上是负收益。
- **没有全量对拍 52 个函数**：成本高（每个约 40s + 下载），且上面已证明这类差异无害。
  真需要时，用本文件的两条命令按需抽查即可。
