# R376 · M1「清空某月」（软删 + 复活 + 归档锁）

> 2026-10-20 · 账套裁决（R373）后唯一没闭合的缺口：误建/试算的月份无法退回「未建档」。

## 一、为什么不能硬删（这是本轮的硬约束）

`shop_monthly_account` 上有**唯一索引** `idx_acc_shop_month (shop_id, month)`。
如果清空 = 物理删除，那么：

1. 删掉后当月确实"没了"；
2. 但老板**重新录入同一个月**时，`saveLedger` 会走 INSERT ⇒ 唯一索引里若还留着任何痕迹就撞键；
3. 更根本的是，本仓纪律是「业务数据不硬删，软删优先」。

⇒ 方案定为 **软删 + 保存时复活**：

```
清空：is_deleted=true / deleted_at / deleted_by / updated_at     （行还在，列表看不到）
重录：saveLedger 先查 is_deleted=true 的同月行 ⇒ 复活（is_deleted=false），保住 account_id
```

为什么必须改 `saveLedger`：`dataAdapter.list` 对全树**铁律注入** `is_deleted=false`，
所以软删行对 `saveLedger` 完全不可见 ⇒ 不补这段，清空后该月**永远存不进去**（撞唯一索引）。

## 二、新函数 `clearMonth`

| 项 | 值 |
|---|---|
| 入参 | `{ shop_id, month, confirm: true, client_request_id? }` |
| 出参 | `{ shop_id, month, cleared, client_request_id }`；本来没账 ⇒ `cleared:false, reason:'not_found'` |
| 鉴权 | `resolveAuth` + `assertShopOwner` |
| 归档月 | 拒绝（`ARCHIVED_LOCKED`，提示先取消归档） |
| 留痕 | `audit_log`：action=`clearMonth`，before_data 记 month / account_id / 收入合计 / 费用合计 |
| 幂等 | 覆盖式赋终值（软删两次终态相同）⇒ 登记 `check_idempotency.js::EXEMPT_WRITE` |

⚠️ `confirm` **必须显式为 true** —— 破坏性操作不接受"默认 true"，参数漏传就拒绝。
（自测 6 条：合法 / 缺 confirm / confirm=false / 坏月份 / 越界月份 / 缺 shop_id。）

## 三、前端

月页底部新增「清空本月数据」（红边红字，`#c0392b` 沿用既有危险色），**仅在该月有账且未归档时出现**。
弹窗写清两件事：会回到「未建档」、**能找回**（重录复活 + 客服可恢复）。
清空成功后重拉月份列表 + 重载当月（显示 R372 的空态卡）。

## 六、没做 / 边界

- **不做物理删除与回收站 UI**：没有"恢复"入口；恢复路径＝重新录一次（数据被覆盖）或找客服改库。
- **不动 `shop_monthly_income/expense/inventory`**：这三个集合全仓**零写入**（历史定义），
  一个月的账其实只有 `shop_monthly_account` 一行（收入/费用是内嵌数组）。
  已核（`grep -rn "shop_monthly_income" cloudfunctions/*/index.js` 无写入点）。
- 清空**不影响**资产/摊销（`shop_asset` 不按月归属），故不动。
