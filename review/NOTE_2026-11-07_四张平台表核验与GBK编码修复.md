| **外卖（A 类）** | 有些**走收银系统**：如美团收银会把美团外卖销量统计进来，接单时收银有记录 |

平台记录的是「该平台的那部分」，两者是交叉而非包含关系。**

### 2.2 错误二：「团购菜品只能从收银台拿」——判断过头

修正后的正确表述：

- **要回答「团购这块业务赚不赚钱」** → 平台核销明细（金额级）够用
- **要回答「团购里哪道菜不赚钱」** → 优先看**平台商品销量表**：它按商品列销量，
  套餐会作为商品出现在里面（实测美团表 10 行里 **4 行是套餐**，如

- **只有当套餐消费明细（吃了哪几道单品）需要拆开时**，才必须回到收银台

所以「只能从收银台」是错的，应改成「**平台表能给到套餐级；拆到单品级才需要收银台**」。

## 4 本轮实装：GBK 编码修复（唯一还没修的那道阻断）

### 4.1 为什么只有这一道了

R242 实测「四道独立阻断 ⇒ 进不来」：

| 阻断 | 状态 |
|---|---|
| ① GBK 编码（`日期`→`ÈÕÆÚ`） | 🔴 **本轮修** |
| ② 形态别名（`商品名`≠`商品名称`） | ✅ R245 已修（`DISH_C_ALIAS`） |
| ③ 平台识别（`detectPlatform`=null） | ✅ 不影响：dish 路径的 platform 由前端显式传入（`v.platform`） |
| ④ 日期 `YYYYMMDD` | ✅ R574 已修（`normalizeDate` 第 759 行） |

### 4.2 修法

在**唯一入口** `bufferToMatrix`（全仓只有它调 `XLSX.read`，已 grep 验证）前面加解码：

```js
function decodeTextBuffer(buffer) {
  // zip(PK\x03\x04) / OLE(D0CF11E0) ⇒ 不是文本，原路交 XLSX.read
  if ((b[0]===0x50&&b[1]===0x4B) || (b[0]===0xD0&&b[1]===0xCF)) return null;
  // Excel「Unicode 文本」= UTF-16LE + BOM
  if (b[0]===0xFF&&b[1]===0xFE) return { text: b.toString('utf16le')... };
  const u8 = b.toString('utf8');
  if (countReplacement(u8) === 0) return { text: u8, encoding: 'utf8' };
  const gbk = new TextDecoder('gbk').decode(b);      // 零依赖，Node 全 ICU 内置
  if (countReplacement(gbk) < countReplacement(u8)) return { text: gbk, encoding: 'gbk' };
  return { text: u8, encoding: 'unknown' };          // 不假装成功
}
```

三个设计要点：

1. **按「替换字符个数」比较，不猜字符集**。UTF-8 解出的 U+FFFD 比 GBK 多 ⇒ 认定原文件是 GBK。
   这比「检测中文范围」稳，也不依赖 BOM。
2. **顺序是硬约束**：zip/OLE 判断必须在文本解码之前。反了就会把正常 xlsx 当 CSV 解坏
   （变异 ④ 专测这条）。
3. **不引 iconv-lite**：Node 自带全 ICU，`new TextDecoder('gbk')` 够用，不加包体积、
   不改 package.json、不改部署清单。运行时不支持时 catch 降级（保持原样，不假装成功）。

## 5 🔴 由此暴露的真问题：渠道重叠（新登记 #140）

李老师说的「有的走收银、有的走小盒子、但平台上都有销量」，直接推出一个风险：

**同一笔美团外卖，可能同时出现在「美团商品表」和「收银菜品表」里。**

- 美团收银会把美团外卖统计进来 ⇒ 收银表里有它
- 美团平台商品表也有它
- 两张表都导入 ⇒ **美团外卖被算两次**

而收银表**没有渠道列**（15 列全是菜品维度），**入库后拆不开**。

现有 `detectDupImport` 只防「跨平台 / 同平台重复导入」，**不防「收银表内部混了外卖」**。

两条候选口径（**待李老师拍板，未定前不动代码**）：

| | 口径 A | 口径 B |
|---|---|---|
| 定位 | 收银表**只当堂食** | 收银表当**全店合计** |
| 做法 | 导入时加「这份表是哪个渠道」单选，老板按「订单分类」分别导 | 与平台表相加时自动扣重叠 |
| 优点 | 口径干净、一次说清 | 老板少操作一步 |
| 代价 | 老板要多导 2~3 次；且收银系统未必支持按来源拆 | 要动装配层，且「扣多少」无法验证（没有交集明细） |

我倾向 **A**：B 的「自动扣重叠」在没有交集明细的前提下只能估算，而本仓红线是「不猜」。
但 A 的前提是收银系统支持按「订单分类 / 菜品下单来源」筛选导出 —— 这点需要李老师确认。
