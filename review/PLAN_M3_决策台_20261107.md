## 0 一句话：上一版方向对，但抓错了「第一性问题」

上一版说「把单品/套餐/外卖/成本变动还原成一份事实行的六个切片」——**统一装配是对的**，
但它把「视图数量」当成了目标，把「事实层」排成了第一项。取证后我认为顺序错了：

**M3 现在不缺数据、不缺能力，缺的是「把已有数据组织成老板能用的三张答案」。**

证据（全是现成能力，但没有一处把它们变成结论）：

| 能力 | 代码里早就有 | 现在有没有变成结论 |
|---|---|---|
| 外卖到手率 + 佣金/配送/补贴/推广四项 | `utils/takeawayDerive.js:116-136`（`receipt_rate`、`commission`、`d`、`deliverySubsidy`、`sMerchant`、`promo`） | 🔴 页面只给「到手利润」两个数，没有「平台拿走了多少」的结构 |
| 套餐「顾客省 / 我少赚 / 成本占比」 | `cloudfunctions/common/comboDerive.js:55-57`（`customerSaveFen` / `merchantLoseFen` / `costShare`） | 🔴 只在套餐编辑页给，**不进复盘、不进任何结论** |
| 单品 qty/营收/成本/毛利/毛利率 | `getDishReview` 出参 `dine_in: ranked`（免费档按 `:171` 剥掉毛利三列） | 🟡 有排行，但没有「该动哪道菜」的动作 |
| 覆盖率的 A/B/C 三档 + 未匹配清单 | `pages/m3/dishreview/index.wxml:44-60` | 🟡 藏在「更多分析」折叠里，不是行动指引 |

⇒ **所以「指数级」的那一刀不是加一层架构，而是：用一个纯函数把已有出参组织成三张答案。**

## 1 上一轮吸收什么（保留），改什么（推翻）

### 1.1 保留 ✅

1. **入口归位**（#113 已闭环）：全渠道销量不再挂外卖名下，标题随 tab 走。
2. **假承诺必须修**：`materialSub` 那种「改一次价全都跟着变」与快照隔离矛盾的文案，是信任杀手。
3. **守卫判行为不判形状**：`check_m3_entry_naming` 用页面桩真跑 `syncTitle`，而不是 grep 字面。
4. **不新建集合 / 不动快照隔离**：历史可比性不能为了「好看」牺牲。

### 1.2 推翻 ❌

| 上一版 | 为什么错 | 改成 |
|---|---|---|
| 「六个视图」作为产品目标 | 视图数量 ≠ 决策价值。老板不会「看六个视图」，只会问「我该动哪道菜」 | **三个问题**：该动哪道菜 / 套餐划算吗 / 外卖还赚不赚 |
| 事实行装配层排 P1（第一优先） | 事实层的收益是**维护成本**，老板感知为 0；而三张答案用现有出参就能做，边际成本几乎为零 | **先做决策层（零云函数改动）**，等视图超过 3 个、口径开始打架时再回头抽事实层 |
| 四象限作为主视图 | 四象限是中间产物。老板看到「右上角」还是不知道该干嘛 | 四象限**降为解释层**（点开才看），主视图是**动作清单**（最多 5 条，带数、带依据） |
| 只提「导入三问」 | 三问解决「填得对」，没解决「老板根本没有这份数据」 | 补**数据可得性分层**：有单品销量 / 只有渠道总额 / 什么都没有，三条路径分别给什么答案 |
| 没处理免费/付费域 | `getDishReview` 免费档会剥掉 `grossFen/marginPct`（`:171`），决策台若照算会给免费用户**凭空造出毛利结论** | 决策台按 `tier` 降级：免费只给「销量结构」不接毛利题，fail-closed |

## 2 新方案：M3 利润决策台（三个问题 + 一个试算）

### 2.1 问题一：该动哪道菜？

**输入**（全部现成）：`getDishReview.dine_in` 的 `qty / amountFen / costFen / grossFen / marginPct`。

**算法（可复算、不用行业阈值）**：
- 销量分界 = 本店当月**销量中位数**；毛利分界 = 本店当月**单份毛利中位数**；
- 每道菜落四格，但**对外输出动作清单**，按「可改善金额」降序，最多 5 条：

| 格 | 动作（预设规则，非 AI 生成） | 带什么数 |
|---|---|---|
| 卖得多 · 毛利低 | 提价 / 换供应商 / 减份量，三选一 | 涨价 1 元 ⇒ 月毛利 +X 元；换价 10% ⇒ +Y |
| 卖得少 · 毛利低 | 砍掉或改配方 | 占用了多少成本、砍掉月省 Z 元 |
| 卖得多 · 毛利高 | 主推（放首页/套餐引流） | 贡献了多少毛利、占比多少 |
| 卖得少 · 毛利高 | 搭套餐 / 做引流品 | 与哪个高销量菜搭最划算 |

**fail-closed**：有效菜数 < 10 或覆盖率 < 60% ⇒ 不出动作清单，改显示「再关联 N 道菜就能看」（复用现有覆盖率闸门）；免费档 ⇒ 只给「卖得多/卖得少」两档销量结构，**不碰毛利**。

### 2.2 问题二：套餐比单点划算吗？

**输入**：`comboInsight`（已有）+ 套餐销量（若复盘能按套餐聚合则用，否则先给「按成本/售价」的静态判断）。

**输出**：每个套餐一行——
「顾客省 ¥X ｜ 你少赚 ¥Y ｜ 成本占售价 Z%」+ 一句动作：
- `merchantLoseFen > 0` 且销量靠前 ⇒ 「这个套餐在拉低毛利，建议调价或换掉最贵的子菜」
- `merchantLoseFen ≤ 0` ⇒ 「套餐没让你少赚，可以主推」

**为什么这是指数级**：这个能力代码里早就写完（`comboInsight`），但今天老板在套餐编辑页看不到「跟单点比」的结论；接进决策台的成本 ≈ 一个列表渲染。

### 2.3 问题三：外卖还赚不赚？

**输入**：`calcTakeawayOrder` 出参（`commission / delivery / subsidy / promo / receipt_rate`）。

**输出**：一条**瀑布**（顾客付 100% → 平台佣金 −a% → 配送 −b% → 补贴 −c% → 推广 −d% → 你到手 e%）+ 一句临界点：
「到手率再低 X 个点，这单就白干」。

**为什么有价值**：现在页面给「到手利润 12.3 元」，老板不知道是平台拿多了还是配送贵了；瀑布直接告诉他该跟平台谈什么、该不该继续投推广。

### 2.4 试算：原料涨价 10%，上面三题怎么变？

**输入**：成本卡行的原料用量 + 当前净料成本（快照）；**纯前端按 ×1.1 重算**，零云函数改动。
**输出**：每道菜成本 +Δ、毛利 −Δ；三题里哪些答案翻转（例如「主推」掉成「该提价」）；套餐少赚变多少。
**这叫「食材成本变化的影响」的正确答案**——不是一张 Δ 表，而是「我的决策要不要改」。

### 2.5 数据可得性分层（上一版完全没有）

| 老板手里有什么 | 给什么答案 | 不给什么（明确标注） |
|---|---|---|
| 有单品销量表（堂食/外卖） | 三题全答 | — |
| 只有平台账单总额（没有单品） | 只答问题三 + 成本卡反算「该卖多少钱」 | 不给单品四象限（数据不够，不编） |
| 什么都没有 | 只给「该卖多少钱」+ 一句「导一张销量表就能看该动哪道菜」 | 不给任何排行/象限 |

**判据**：入口页按 `getSalesBills` / `getDishReview` 的实际返回决定展示哪条路径，不靠老板自己选。

## 4 验收判据（先写死，再写码）

1. 决策纯函数：给定 12 道菜的合成样本（含 4 类各 3 道），动作清单顺序 = 可改善金额降序，且每条都带本店数字。
2. 免费档：同一份样本传 `tier:'free'` ⇒ 不产出任何含毛利的动作，`actions` 里 `kind` 只允许销量类。
3. 数据不足：9 道菜 / 覆盖率 50% ⇒ `insufficient=true`，不给清单。
4. 套餐：`merchantLoseFen > 0` 的套餐必须排前面，并给「调价/换子菜」动作。
5. 外卖瀑布：各项占比之和 + 到手率 = 100%（±0.1），且到手率与 `takeawayDerive` 出参一致。
6. 涨价试算：×1.1 后每道菜成本增量 = 原成本 × 0.1（整数分，误差 ≤1 分），且能标出「答案翻转」的菜。
7. 页面桩真跑：复盘页在有数据/免费档/数据不足三态下，区块显示正确、不出现 `undefined`。
8. 变异复核：把「中位数分界」改成「均值」、把免费档拦删除、把瀑布少算一项 ⇒ 守卫必须转红。
