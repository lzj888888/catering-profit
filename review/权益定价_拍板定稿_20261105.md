## 2 🔴 核心新增：定义 + 三道护栏（"不限次"能不能兑现，全看这三条）

### 2.1 先把「深度诊断」钉死，避免日后扯皮

| | 免费简诊 | 深度诊断（付费） |
|---|---|---|
| 输出 | 等级 + 1 个最大信号 + 1 个锚点 | 11 指标加权 100 分 + 6 红线校验 + 短板排序 + 归因 + 改进锚点 |
| 报告 | 不生成 | **永久可看、可导出** |
| 人工 | 无 | **无** |
| 载体 | 页面即时计算 | 落台账、可对比 |

> 🔴 **硬边界：深度诊断 = 引擎自动出，不含任何人工复核、不含线下咨询。**
> 人工复核属另一个高客单商品（人工诊断/陪跑），**永不并入月卡**。这一条不划死，"不限次"必然变成灾难——一个人一个月喊你 50 次人工，25.9 就打穿了。

### 2.2 成本护栏一：两级去重（不限次，但不重复烧算力）

"不限次"是**用户权利**，"每次都重算"不是。落地规则：

| 情形 | 行为 |
|---|---|
| 同一店铺 + 同一份数据快照，24h 内重复跑 | 命中缓存，直接返回上次结果，**不计新成本** |
| 同一店铺，用户改了月度数据后再跑 | 真重算，生成新台账记录 |
| 换店铺 / 换诊断类型 | 真重算 |

效果：名义上"想做多少次做多少次"，实际算力跟着**数据变化次数**走，而不是跟着点击次数走。用户感受无差别，成本可控。

### 2.3 成本护栏二：报告篇幅封顶

| 项 | 上限 |
|---|---|
| 正文 | ≤ 2500 字 |
| 图表/表格 | ≤ 6 张 |
| AI 生成 | 只生成"解读与归因"段，指标计算全部走本地规则 |

理由：成本全在 AI 生成段。指标计算是 JS 规则，耗时可忽略、成本为零。把 AI 限定在解读段 + 封顶篇幅 = 单份成本锁死在分币级。

> 量级估算（**待实测校准，非实测值**）：按当前主流大模型 API 价格量级，单份 2500 字解读约 2000 输入 + 1800 输出 token，成本在**分币级**。即使极端用户一个月跑 100 次，AI 成本也在 1 元以内，25.9 月卡仍有毛利。
> ⚠️ 这条必须由实施窗**真调一次拿账单打点**，不许直接采信本估算。

### 2.4 成本护栏三：额度跟着"店铺数配额"走，不跟账号走

月卡店铺数配额（按现有 `SEED_PLANS` 实测值回填，本文件不臆造）**就是诊断的天然上限**。

- 1 店账号：不限次 = 这 1 店的任意次数
- 多店账号：每店各自不限次

⇒ "不限次"永远被店铺数锁死，不存在一个账号无限铺店的套利。

### 2.5 唯一真风险与兜底

**风险**：脚本化高频调用（有人写脚本 5 分钟一次）→ 云函数调用量费用 + 可能触发风控。

**兜底**（不写在宣传里，只做技术限制）：
- 单账号同店同类型：**每小时 ≤ 5 次、每天 ≤ 30 次**硬限流
- 超限返回"数据未变化，本次为最近结果"，不给报错、不影响体验
- 这个阈值远高于任何真人使用习惯（真人一个月 3–5 次），限流只拦脚本

## 4 要认清的一件事：19.9 不是主力成交品

| 用户真实选择 | 花费 | 拿到 |
|---|---|---|
| 只买 1 次诊断 | 19.9 | 1 次诊断 |
| 买月卡 | 25.9 | 记账 31 天 + **期内不限次诊断** |

**只差 6 元，月卡性价比碾压单次。** 所以：

- 单次 19.9 的真实角色 = **价格锚 + 升单台阶**（"补 6 元就能一个月随便测"）
- 真正收钱的是 25.9 / 69 / 199
- 若指望 19.9 靠量赚钱，会落空——这点必须提前认清，别到月底看数据再怀疑产品

**这恰好是好事**：李老师把诊断塞进月卡，等于把"单次低价陷阱"改造成"订阅升单漏斗"，比会审原方案（月卡 0 次诊断）转化路径更顺。会审里豆包坚持"0 次"的顾虑是"诊断贬值"，用"期内不限次 + 数据去重"这套组合可以化解——贬值的是次数，不是价值。

## 5 对比功能规格（我定的第 3 条，落地细节）

**触发条件（三条同时满足）**：
1. 同一 `shop_id`
2. 同一下诊断类型（闭店诊断 / 开店诊断 **不混比**）
3. 该店该类型已有 ≥ 2 份**已付费**台账

**不满足时的降级**（重要，不能让新用户看到空白页）：
- 若该店无历史 → 不渲染对比区，改为「**业态基准对比**」：本次结果 vs 该业态参考带（这不消耗额度、免费给）
- 若该店有历史但类型不同 → 只出本次 + 一行提示"另测过开店诊断，不可直接对比"

**理由**：会审原方案只说"累计 2 份"，没约束比较对象，会出现"闭店 vs 开店"的无意义对比页。同时纯等 2 份会让新用户第一份报告显得单薄，用业态基准兜底补足价值。

## 6 独立诊断台账（我定的第 4 条，字段规格）

新集合 `shop_diagnosis_report`（**不修改 `common/entitlement.js` 的 `isPaid`**）：

| 字段 | 说明 |
|---|---|
| `_openid` | 用户 |
| `shop_id` | 店铺 |
| `biz_type` | 业态枚举（决定用哪套参考带） |
| `diag_type` | `close` / `open`（闭店 / 开店） |
| `score` / `level` | 总分与等级 |
| `redline_hit` | 命中的红线数组 |
| `metrics_snapshot` | 本次指标快照（用于去重与对比） |
| `snapshot_hash` | 数据快照指纹（**2.2 去重靠它**） |
| `pay_source` | `single` / `month` / `quarter` / `year` |
| `cache_hit` | 是否命中缓存（成本核算用） |
| `model_tokens` | 本次 AI 消耗（成本核算用，可空） |
| `created_at` | 生成时间 |
| `exported_at` | 最近导出时间 |

**三条硬约束**：
1. 判定函数**旁路新增**（如 `canRunDiagnosis(openid, shopId, diagType)`），**绝不改 `isPaid`** —— 它现在是全仓唯一付费判定口径，改它会波及 M1/M3 全部已验付费墙
2. `report_visible_forever = true` 必须硬编码，不参与订阅校验
3. 台账是**付费资产凭证**，删库前必须先备份
