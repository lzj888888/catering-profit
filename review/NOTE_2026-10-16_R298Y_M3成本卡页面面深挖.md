## 2. A 组 · 毛利色阶阈值三处互斥（🔴 用户可见）

### 2.1 缺陷

修前，同一件事（毛利率分档）在**四个地方**有**三个口径**：

| 位置 | 判据 | 档位 |
|---|---|---|
| `pages/card/index.js::applyFilter()` | `mf === 'high'` → `c.margin >= 60`；`'mid'` → `c.margin >= 30`；`'low'` → `< 30` | **30** |
| `pages/card/index.wxml` 色带 | `margin >= 60 ? 绿 : (margin >= 40 ? 橙 : 红)` | **40** |
| `miniprogram/i18n/terms.js`（+ specs 副本）文案 | `marginMid: '中（30%~60%）'` | **30** |
| `specs/.../开发规范v1.0_ModuleM3_菜品成本卡.md §M3.8` | 「建议…**≥40%**…」 | **40** |

**后果**：一张 **35%** 的卡 —— **色带判红**（<40），却会被「中」档（≥30）**筛出来**。
用户看到红色卡混在"中毛利"列表里，无从解释。

### 2.2 修法（单源化，而非改数字）

规范 §M3.8 明写「色阶阈值建议也从**同一配置源**读取，保持全局一致」⇒ 只把 `30` 改成 `40`
是**治标**，下一个人换个地方再写一个数字又会漂。本轮做**单源**：

1. **新建 `utils/marginBand.js`（63 行）** —— 唯一单源：
   ```js
   const HIGH = 60;   // ≥60 ⇒ 高
   const MID  = 40;   // ≥40 且 <60 ⇒ 中；<40 ⇒ 低
   const COLOR = { high:'#22a06b', mid:'#b45309', low:'#e74c3c', none:'#999' };
   const LABEL = { all:'全部', high:'高（≥60%）', mid:'中（40%~60%）', low:'低（<40%）' };
   bandOf(margin) / colorOf(margin) / matchBand(key, margin)
   ```
   边界语义：`null` / `undefined` / `''` / 非有限数 ⇒ `'none'`（**不**当 0）。

2. **`pages/card/index.js` 三处改读单源**：
   - `MARGIN_OPTIONS` 四档 label 改取 `band.LABEL.*`
   - `t` 块删除 `marginHigh/marginMid/marginLow` 三键（只留 `marginAll`）
   - `load()` 的 `all` 映射新增 `margin_color: band.colorOf(margin)`
   - `applyFilter()` 三条 `if (mf === 'high'|'mid'|'low')` 合并为一句
     `if (mf && mf !== 'all' && !band.matchBand(mf, c.margin)) return false;`

3. **`pages/card/index.wxml` 色带改读产物**：内联三元 → `style="color:{{item.margin_color}};"`

4. **terms 双副本删三键**：`marginHigh/Mid/Low` 删除，原位留 5 行注释说明
   「改由 `utils/marginBand.js` 单源」。

### 2.3 🔴 为什么单源**不能**放进 `terms.js`

本仓有一条硬不变量 **K11**：`miniprogram/i18n/terms.js` ≡ `specs/dev-specs/i18n/terms.js` **逐字节一致**。
两份目录**深度不同**（`../../` vs `../../../`）⇒ **无法 require 同一个相对路径**。
而 `utils/` **没有 specs 镜像**（已确认）⇒ 单源必须落在 `utils/`。

> 这条是「**单源选位**」的判据：单源文件本身必须**不在任何双副本约束的目录**下，
> 否则「单源」会被 K11 逼着分裂成两份。

## 3. B 组 · 复制套餐卡 100% 失败（🔴 功能必失败）

### 3.1 缺陷

`cloudfunctions/saveCostCard/validate.js:49-53` 对 `card_type === 3`（套餐卡）**每一行**强制要求 `sub_card_ref`：

```js
if (card.card_type === 3 && !line.sub_card_ref) { /* 拒绝 */ }
```

而 `pages/card/index.js::onCopy` 的行映射是**一刀切**的：

```js
const lines = (src.lines || []).map((l) => ({
  material_id: l.material_id, qty: l.quantity,            // ← 只有档案行形态
}));
```

⇒ **套餐行丢 `sub_card_ref`**，`material_id` 又是空的 ⇒ 提交必被云函数拒绝。
**复制套餐卡 100% 失败。**

### 3.2 修法

`onCopy` 行映射改**三分流**（与 `edit.js:943-973` 的套餐行正确构造法对齐）：

```js
if (l.line_type === 2 || l.sub_card_ref)                       // ① 子卡行
  return { sub_card_ref: l.sub_card_ref || '', qty: Number(l.quantity) || 0 };
if (l.material_id)                                             // ② 档案行
  return { material_id: l.material_id, qty: l.quantity, line_kind, group_name };
return { input_type: 2, name: l.material_name || '', qty, net_unit_cost, line_kind, group_name };  // ③ 手工行
```

三支**都**带 `line_kind` / `group_name`（承 R298W 「修了一半」教训：别只顾补 `sub_card_ref` 而漏掉同行其它字段）。

## 4. C′ 组 · 一个"空修复"（🔴 本轮最大发现）

### 4.1 缺陷

R297-⑥ 的意图是修 `pages/card/version.js` 恢复成本卡时的字段丢失。
它在 `doRestore()` 里写了：

```js
card_type: v.card_type === 3 ? 3 : 1,
specs: v.specs || [],
```

**但 `v` 来自 `load()` 产出的 `list` 映射** —— 而 `load()` 的卡级映射**从头到尾没有产出 `card_type` 和 `specs` 这两个键**：

```js
const list = versions.map((v) => ({ id: v.id, name: v.name, /* … */ }));   // 无 card_type / specs
```

⇒ `v.card_type` 与 `v.specs` **恒为 `undefined`** ⇒ 恢复出来的永远是 `card_type: 1` + `specs: []`。
**该修复整轮空转，行为仍是它描述的 bug。**（同族于「单源判据写了但被另一条入口架空」的极端形态：
判据**根本没接上数据源**。）

### 4.2 为什么既有守卫没抓到

R297 的守卫是 `grep`「`v.card_type` / `v.specs` 是否**出现**」——
而**注释里也写了这两个词** ⇒ 判据**恒真**。
这正是本仓纪律的反面教材：**「写了读取方 ≠ 修好了」**。

### 4.3 修法

1. **`load()` 卡级映射**补 `card_type: v.card_type === 3 ? 3 : 1` 与 `specs: v.specs || []`；
2. **`load()` 行级映射**补 `input_type` / `line_kind` / `group_name` / `line_type` / `sub_card_ref` / `sub_version`；
3. **`doRestore()` 三分流**：`line_type === 2 && l.sub_card_ref` 走子卡行 → 否则 `material_id` 走档案行 → 否则手工行；
4. R297-⑥ 的注释段追加补正说明：「**只写了这两行读取、没把字段搬进 load() 的 list 映射 ⇒ 该修复一整轮内都是空转**」。
