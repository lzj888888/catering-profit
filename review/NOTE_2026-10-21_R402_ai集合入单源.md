## 3 为什么四索引不进本轮（本轮最重要的判断）

设计稿原写「步 1：登记两表 + 四索引」。按原顺序做，`tools/check_index_field_alignment.js` **当场判红**：

```
❌ L1 发现 N 个化石索引字段（字段名在云函数源码里零出现 ⇒ 该索引从未生效、查询走全表扫描）
     shop_ai_consent.idx_ai_consent_user_shop ← consent_id
     shop_ai_consent.idx_ai_consent_shop ← revoked_at
     shop_ai_insight.idx_ai_insight_consent ← consent_id
```

实测确认：`consent_id` / `revoked_at` / `insight_id` / `policy_version` 在 `cloudfunctions/**` 里**各 0 个文件命中**
（`initDb/collections.js` 自身除外）。

**判据没错，是顺序错了。** 该守卫防的正是「索引建在一个没人用的字段上」——
而 `grantAiConsent` / `revokeAiConsent` 尚未落码，此刻这些字段**客观上一个用它的代码都没有**。

两种"绕过去"的做法都被否掉：

| 备选 | 否掉的理由 |
|---|---|
| 给 `check_index_field_alignment` 加豁免表 | 放宽安全判据去迁就一个**可以调换顺序**的计划，代价是永久的盲区 |
| 先写一个 `common/aiConsent.js` 只为让字段进词表 | 该目录有 `cx_*.js` 扁平派生机制（改一个文件要 `sync_common.js` 派生 51 份）；且"为过守卫而提前写用不上的代码"本身违反纪律 |

⇒ 正确处置是**改计划**：先落码（步 2），索引与它同批（步 1b）。已写回设计稿 §7，后来人不会再按错顺序做。

## 6.1 🔴 提交前抓到的一个**非业务**事故：行尾被整体翻成 CRLF

`git diff --numstat` 一读就现形：`collections.js` 报 **272 增 / 261 删**、`init_db.js` **290/287**、`下一步工序清单.md` **285/285**
—— 全是"整文件翻写"的量级，而实际只改了个位数行。

**根因**：仓库里这些文件是 **LF**，被改成了 **CRLF**（`collections.js` 现值 CRLF=272 / LF-only=0，HEAD 是 CRLF=0 / LF=261）。
写回路径里有 Windows 平台默认行尾的环节（`Edit` 工具直接落盘、以及把一份已 CRLF 的文件 `cp -f` 成 `.txt`）。
⚠️ 最坑的是**门禁当时是 192/192 全绿** —— 行尾翻写不会被任何守卫抓到（K13 做了 CRLF 归一、其余按行解析）。

**处置**：4 个文件按字节 `b'\r\n' → b'\n'` 转回 LF，再复核 `numstat`：`collections.js` **12/1**、`init_db.js` **3/0**、`core/15` **4/2**、`工序清单.md/.txt` **1/1** —— 回归到"只改了该改的行"。
转回后 8 个关键守卫（含 batch0 自测、A–L 门禁）**全绿**，并**重跑全量门禁**（不拿"翻写状态下的绿"背书）。

⇒ **新纪律（建议进 `win-cli-pitfalls`）**：改任何既有文件后，**提交前必看 `git diff --numstat`**；
增删行数与实际改动量级不符（例如 200+ / 200+ 而只改几行）= 行尾被翻，**必须先修再提交**，否则 review 里全是噪声、`git blame` 全废。
