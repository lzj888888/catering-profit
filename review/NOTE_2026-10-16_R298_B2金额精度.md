## 0 一句话结论

全仓铁律（`core/01 架构总览` §1）写着「金额 = 整数分，**禁 JS Number 原生浮点运算**」，而
「元 → 分」这个边界上，**单源 `common/money.js::yuanToFen` 写了、也 sync 进 51 个云函数包，业务代码却一处都没用它**——
**35 处各自裸写 `Math.round(<元> * 100)`**（首遍按"命名像分"的标识符抓到 16 处；第二遍改成
**全仓 `* 100` 三形态桶穷尽 + 逐点登记**后又补出 **19 处**，见 §10）。裸写在 IEEE754 下会让
**半步（真值恰为 x.xx5）静默少进 1 分**，方向**恒为偏小**、**零报错**：

| 实测面 | 结果 |
|---|---|
| 三位小数全域 18 万点 | 现状错 **1147 点**（0.145→14 / 0.285→28 / 1.005→100 真值 101 …） |
| 成本引擎路径 `qty × (净料万分之元)` 600 万组合 | 现状错 **3528 处**（qty=0.1 斤 × 净料 14500 万分之元 ⇒ 真值 14.5 分 ⇒ 现状取 **14**） |
| ✅ **两位小数（老板日常输入形态）穷举 100 万点** | 现状 **0 错** —— 这是免责面，**不是"金额体系全错"** |

## 2 真缺陷 ①：单源 `yuanToFen` 浮点半步

**根因**：`yuan * 100` 的二进制结果可能**略小于**十进制真值 —— `1.005 * 100 === 100.49999999999999`，
`Math.round` 于是向下取整。`Math.round` 拦不住这一类偏移（它拦得住的是 Infinity/NaN，那是 D2 的面）。

**可达性（逐环取证，不夸大）**：
1. 输入框 `pages/month/input.wxml:90` 等 **全部是 `type="digit"`**（微信数字键盘**允许任意位小数**）；
2. 绑定 handler `pages/month/input.js::onSubAmount` → `updateRow(..., { amountYuan: e.detail.value })`
   —— **原样存字符串、零清洗**；
3. `pages/month/input.js:1524/1542` 等处 `api.yuanToFen(r.amountYuan)` 落库为分。

⇒ 老板**粘贴**一个三位小数（如从计算器/表格复制 `1.005`）即可触发，**无任何提示**。

**修法（十进制安全，零行为漂移）**：

```js
// 旧：Math.round(yuan * 100)
// 新：Math.round(Number((yuan * 100).toFixed(10)))
```

`toFixed(10)` 只消掉 **1e-13 量级**的浮点噪声、**不动真实半步**。
候选对比（`_probe_tmp/r298_b2_fix_candidates.js`，122.5 万点穷举）：

| 实现 | 两位小数 100 万点 | 三位小数 18 万点 | 四位小数 4.5 万点 | 人工半步 22 点 |
|---|---|---|---|---|
| 现状 `Math.round(y*100)` | 0 错 | **1147 错** | 0 错 | **5 错** |
| 候选 A1 `toFixed(10)` | **0 错** | **0 错** | **0 错** | **0 错** |
| 候选 A3 十进制字符串解析 | 0 错 | 0 错 | 0 错 | 0 错 |

A1 ≡ A3 在 **40 万点**上完全等价 ⇒ 取更简单的 **A1**（不引入新解析逻辑风险）。

**双副本必须同改**（否则两端算出的「分」不同）：

| 副本 | 位置 | 语义差异（**只在非法域**） |
|---|---|---|
| 云端单源 | `cloudfunctions/common/money.js::yuanToFen` | 非数 ⇒ **抛** `INVALID_PARAM`（fail-closed） |
| 前端 | `utils/api.js::yuanToFen` | 非数/负数 ⇒ **返 0**（fail-soft） |

合法输入域两份**逐点等价**（守卫 B-① 80 万点钉住）；差异集合**精确落在非法域**（守卫 B-② 钉住）。

## 3 真缺陷 ②：16 处「元 → 分」同族裸换算（这正是"单源没人用"的实证）

扫描判据 = **「元语义标识符 × 100」**（ident 含 `yuan|price|amount|money`，大小写不敏感），
规避合法的「分→万分」（`unit_cost_fen * 100`）与「百分比」（`pct * 100`）。

| 文件 | 处数 | 语义 |
|---|---|---|
| `cloudfunctions/calcBom/service.js` | 3 | 明细行净成本 / 明细合计 / 单品总成本（**落库值**） |
| `cloudfunctions/saveCostCard/service.js` | 3 | 同上（成本卡保存） |
| `cloudfunctions/syncCostCard/service.js` | 3 | 同上（同步至最新价） |
| `cloudfunctions/calcBom/validate.js` | 2 | `auxYuan` / `priceYuan` 兼容层（元 → 分） |
| `cloudfunctions/saveCostCard/validate.js` | 3 | `auxYuan` / `priceYuan` / `activity_price_yuan` 兼容层 |
| `pages/card/edit.js` | 2 | 团购试算售价 / 规格行售价 |

**三份成本引擎副本必须同改** —— 否则 `tools/check_m3_engine_parity.js`（R131，三副本行为等价）
会在"同一张卡、两条不同成本"的静默错账上失守。

**改法**：就地改算式（**不加 require、不改模块依赖图**、零行为差异除半步）：

```js
Math.round(yuan * 100)  →  Math.round(Number((yuan * 100).toFixed(10)))
```

**锚点回归**：三份成本引擎 selftest 的落库锚点**零漂移**
（calcBom 40/0、saveCostCard 35/0、syncCostCard 4/0、saveMaterial 8/0、getMaterial 7/0；
`syncCostCard` 锚点「同步后新版本总成本 = 12.08（1208 分）」原样复现）⇒ 说明既有锚点**不在半步边界**，
本修复是**严格改进**。

## 4 治理层发现：单源「写了但零消费者」

`cloudfunctions/common/money.js`（4 个导出符号）经 `tools/sync_common.js` 复制进 **51 个云函数包**
（`cx_money.js`，各 1464 字节 ⇒ 约 **74.6 KB 死代码**），**而全仓没有一处业务调用**：

- 前端走**自己的** `utils/api.js::yuanToFen`（98 处调用点）；
- 云端成本引擎走**自己的**内联副本（16 处）；
- `calcMonthlyProfit/service.js` 甚至自建了一份 `fenRoundN(fen) { return Math.round(fen); }`
  —— 与单源 `money.fenRound` **语义完全相同**，但**互不引用**。

⇒ 这就是「**规范说用单源、实现全绕过**」，与 D1 的「术语值当机器键」**同型**（规范与实现脱节）。

**处置**：本轮**不**改消费方（属重构，需先审后合，且会引入跨模块依赖）——
改为**守卫钉住**：单源在扫描面内 + 单源实现本身十进制安全 + 前后端双副本逐点等价。
**登记待拍板**：是否把三份成本引擎的内联元→分收敛到 `common.money.yuanToFen`。

## 7 登记不修（如实记录，非缺陷）

- **B2-④** `calcMonthlyProfit/service.js::rounded2` 用 `(x + Number.EPSILON) * 100 / 100`
  —— 绝对量修正对**大数**失效，但该函数只用于**百分比（值域 0~100）**，实测 10001 点零差异 ⇒ 不修（登记）。
- **B2-⑤** 49 处裸 `Math.round(x * 100)` —— 逐个判语义后**多数是合法的单位换算**：
  `saveCostCard/index.js:409` / `syncCostCard/index.js:358` 的 `unit_cost_fen * 100` 是「**分 → 万分**」
  （1 分 = 100 万分，整数 × 100 在 double 里精确，注释亦已写明）；`pages/sandbox/index.js:672` 的
  `marginPct * 100` 是**百分比** ⇒ 均**不属**「元 → 分」，守卫的元语义判据正确地**未命中**它们
  （由 D-③ 反向护栏钉住）。
- **B2-⑥** `money.fenRound` 负数 half-toward-+∞（`-1.5 → -1`）—— 负数金额不可达 ⇒ 不修。
- **`money.fenRound` / `money.tailDifference` 零调用** ⇒ 归入 §4 治理层登记。
- **B2-⑧（第二遍新判）** 4 处 `Math.round(x * 100 + 1e-9) / 100`（`calcSandbox/service.js:159` ·
  `savePlan/service.js:159` · `pages/sandbox/index.js:734` · `utils/reconDerive.js:18`）—— 逐个取证后
  **全部是「百分数保留 2 位小数」（ratio 类），不是「元 → 分」** ⇒ 登记为 `ratio`，**不进本轮金额修复**。
  ⚠️ 但定量出该写法的**半 ulp 失效边界**：`+1e-9` 的容差在 `n * 100 ≥ 2^24`（即 **n ≥ 167773**）时
  被浮点吸收（≤ 半 ulp）⇒ 退化为 **no-op、容差失效**（`+ Number.EPSILON` 失效得更早）。该边界**落在
  ratio 类可达域之外**（百分比不会到 16 万）⇒ 现状无实害，但**列为本写法的已知上界**（见 §10.2）。
- **`check_money_precision` 只钉 `toFixed(10)` 这一种安全形态**：若将来出现别的等价写法
  （如改走 `common.money.yuanToFen(...)`），**调用点将不含 `* 100`** ⇒ 不被本守卫命中，属**预期行为**
  （走单源由 C-③ 单独钉住）。

### 本轮新坑（3 条）

1. 🔴 **本仓有文件存在「工作树 CRLF / index-LF」的不一致**，而 `git status` 会**假报干净**
   （index stat 缓存跳过内容比较）⇒ 一旦真改内容，git 立刻报**全文件重写**。
   实证：`cloudfunctions/common/money.js`、`cloudfunctions/calcBom/validate.js` 的工作树是 CRLF、
   而 HEAD blob 是 LF。**正解（沿用 D2 定式）**：一律**从 HEAD blob 取内容 → 改 → 按纯 LF 写回**，
   `git diff --numstat` 复核收敛到真改动（本次 8/1、7/1、6/2…）。
   ⇒ 迁移：**写回前先判 `HEAD blob` 的行尾**，别按工作树的行尾写。
2. 🔴 **「扫旧形态」的守卫会随修复而恒真**：第一版扫描正则写成 `Math.round(IDENT * 100)`，
   修完 16 处后**命中 0** ⇒ C-① 永远绿。**正解**：锚在**乘积**（`IDENT * 100`）上，
   安全与否看它**有没有被 `Number((…).toFixed(10))` 包住** ⇒ 修前修后都能命中、都能判。
3. 🔴 **守卫里数据搬运会丢字段**：S 段把扫描结果 push 进 `hits` 时**漏了 `safe`** ⇒ C-① 恒判"不安全"，
   而 C-② 用**同一个** `scanYuanTimes100` 却绿 ⇒ **判据对、搬运错**。这类错只能靠首跑暴露。
   ⇒ 迁移：**同一判定函数的两个使用点结论不一致时，先查各自的数据通路**，别先怀疑判据。

## 10 第二遍收口（本轮）：守卫的**观测覆盖率缺口**

### 10.1 缺口的性质 —— 判据覆盖面由「命名习惯」而非「语义」决定

首遍守卫的元语义判据是**标识符白名单**（ident 含 `yuan|price|amount|money` ⇒ 判为"元"）。它守住了
16 处"名字里有 yuan/price"的裸换算，但**面内共 77~78 处 `* 100`** ⇒ 观测覆盖率只有 **17/77 = 22.1%**。

盲区有**两种成因**，各自实证：

| 成因 | 实例 | 为什么漏 |
|---|---|---|
| ① **命名不像"分/元"** | `utils/takeaway.js::packTotal`、`utils/dineChannels.js::c.sum`、`utils/bizPreset.js::fenOf(n)` 的 `n` | 标识符本身不含金额词 |
| ② **书写形态不是"标识符 × 100"** | `cloudfunctions/calcBom/selftest.js` 的 `) * 100`（括号收尾）与 `448 * 100`（数字字面量） | 正则只匹配 `<标识符> * 100`，PAREN / LITERAL 两形态**结构性看不见** |

⇒ 与 **D1「术语值当机器键」**、首遍 **B2-③「单源零消费者」** **同型**：*判据与它要守的语义之间
没有强制对应*。**覆盖面由命名习惯决定，不由语义决定** ⇒ 谁不起金额名、谁换个写法，谁就永远不被观测。

### 10.2 判据升级：三形态桶穷尽 + 登记清单（fail-closed）

**（a）三形态桶穷尽**（S-⑤）：全部 `* 100` 必须被三桶**穷尽**，且用 `RE_ANY = /\*\s*100(?![\d.])/g`
的总数对账：

| 桶 | 正则 | 语义 |
|---|---|---|
| `IDENT` | `([A-Za-z_$][A-Za-z0-9_$.]*)\s*\*\s*100` | 标识符 × 100 |
| `PAREN` | `\)\s*\*\s*100` | `)` × 100（操作数是表达式） |
| `LITERAL` | `(\d+(?:\.\d+)?)\s*\*\s*100` | 数字字面量 × 100 |

**实证价值**：只做 IDENT + PAREN 时对账 **78 ≠ 77** ⇒ 暴露出第 78 处 `448 * 100`（LITERAL 桶）
—— **不加第三桶，这处永远不入账**。升级后 **78/78 穷尽**（`scan_all.js` / `scan_all_out.txt`）。

**（b）登记清单 fail-closed**（C 组，蓝本 = `tools/check_idempotency.js::EXEMPT_KEY`）：
面内**每一处**命中都必须在 `REGISTRY` 里**具名登记 kind + 语义理由**；未登记 / 登记失效 / 计数不符
⇒ **一律判红**。kind 只准四值：

| kind | 语义 | 是否要求十进制安全形态 |
|---|---|---|
| `money` | 元 ⇄ 分 | **必须** |
| `ratio` | 比率 / 百分数 | 否 |
| `scaled_int` | 整数分 ×100 → 更大整数单位（浮点无损） | 否 |
| `token` | 非数值用途 | 否 |

**键格式**：`<相对路径>::<形态>|<归一化匹配文本>|#<同键序号>` —— **不含行号**（行号随无关编辑
漂移，会把"根本没改语义"误报成"登记失效"）；代价是增删命中会移位后续 `#N` ⇒ **有意要求重登记**。

**（c）防退化下界**：`MIN_MONEY = 34`（实测 37）。**没有这条下界，"批量把 money 改标成 ratio"
就能把 C-④ 清零而门禁照绿** —— 与首遍 §6「变异太弱 = 假绿」同型，故设硬下界 + 四类非空 + kind 合法性。

**（d）safe 判定与书写形态解耦**：正解 = 规范包裹正则 `SAFE_WRAP` 求内层区间 → **区间包含判定**，
不用定宽窗口（见 §10.5-1）。

**升级后登记分布**：`money=37 / ratio=35 / scaled_int=5 / token=1`（共 **78**）。
其中 money 37 = **单源本体 2**（`common/money.js` + `utils/api.js`）+ **首遍 16** + **第二遍 19**。
