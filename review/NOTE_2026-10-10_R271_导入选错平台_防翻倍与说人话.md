# R271 · 导入「平台选错了 / 随手选」—— 防销量翻倍 + 让提示说人话

> 触发：李老师 2026-10-10 真机两问
> ① 「外卖单均测算·数据导入，有的提示『打磨中暂未开放』，有的又可以导入，是不是京东不可以？」
> ② 「导入的订单需要选平台，忘了或随便选它也能导入呀，这个影响大吗？如何规避？」
> 决定：李老师「听你安排，你的立场也要考虑餐饮老板使用过程中出现的情况。你说怎么做就怎么做。」

---

## 一、先把两个事实钉死（源码级，不靠记忆）

### 1.1 「打磨中」的真实判据 = 表里**有没有菜品/商品行**，与平台无关

前端条件：`wx:if="{{!billImportOn && !importShape}}"`（`pages/takeaway/index.wxml`）。
云函数先 `detectDishMatrix()` 认形态，认得出（A/B/C）就回 `shape`；认不出才落到账单分支（不回 shape）。

| 表 | 认成什么 | 结果 |
|---|---|---|
| 堂食《菜品销售统计》 | 形态 A（菜品名称＋销售数量＋参数行含"销售方式"） | ✅ 可导 |
| 《套餐销售统计》 | 形态 B（套餐＋单品名称） | ✅ 可导 |
| 淘宝闪购《商品下载》 | 形态 C（商品名称＋销量＋销售额） | ✅ 可导 |
| 京东《对账单》82 列 117 行 | **订单级、无菜品行** | ⛔ 弹「打磨中」 |
| 京东《sku对账单》27 列 **0 行** | 连平台都认不出 | ⛔ 弹的是**另一句**「无法识别账单平台」 |

⇒ 李老师推测的「京东不行」**归因错**：京东若有《商品销量》SKU 长表照样能导；反过来美团/淘宝的**订单账单**也会弹同一句。

### 1.2 「忘了平台」其实导不进去，真实风险是「随手选」

云函数 `if (!platform) return fail('请选择外卖平台')`，前端也拦一道。所以**不选会报错**。
风险在「随手选了一个」—— 在系统眼里它与「选错」完全一样。

**只有形态 C（外卖商品销量）会踩**：堂食（形态 A）的平台被硬编码成 `pos`，想选也选不了 ⇒ **堂食零风险**。

## 二、影响分三档（按严重度）

| 档 | 后果 | 性质 |
|---|---|---|
| 轻 | **挂过的卡失效**：映射键 = `平台+菜名`。在「淘宝闪购」下挂的卡，同一批数据改用「美团」重导 ⇒ 键全变 ⇒ 覆盖率掉回去 | 白干一次。数据与卡都没丢，**改回原平台重导即恢复** |
| 中 | **归错组**：复盘页按 `platform==='pos'` 分堂食/外卖，外卖内再按平台分组 ⇒ 数据出现在错误标签下 | 总量没错（跨平台汇总），只是标签错 |
| 🔴 重 | **翻倍**：`_id = SALE_<店>_<平台>_<日期>_<序号>`。同一份表先用「美团」导、再用「淘宝」导 ⇒ 平台不同 ⇒ **两组独立文档、互不覆盖** ⇒ 同菜品销量/营收**翻倍**，且分散在两个分组里，单看任一组都"像对的" | **静默错账，且最难发现** |

**一个核实过的好消息**：仓内**没有**「平台 → 佣金率」对照表（佣金率由商家手填，`grouponDerive` 明确不给默认值）
⇒ 现阶段选错平台**不会**让佣金/到手算错。将来若按平台带默认费率，此项立刻升级为硬伤。

## 三、做了什么

### 3.1 P0 · 防翻倍（唯一一条把静默变响亮的）

- 云函数新增**零 IO 纯函数** `detectDupImport(existing, incoming, platform)`（`importSalesBill/service.js`）。
- 🔴 判据 = **日期 + 菜名 + 销量 + 金额** 逐行全等，而不是只看日期/菜名重合。
  为什么：老板常同时做美团与淘宝闪购，两张表**日期必然重叠、菜名也可能同名**（"黄喉"两平台都卖）
  ⇒ 只按日期/菜名判会**误杀合法的多平台真数据**（把真数据挡在门外 = 另一种错）。
- 三道下限（宁可漏判，不可误杀）：扫描 ≥ 20 行、命中 ≥ 10 行、命中率 ≥ 0.8。
- 落点：选完平台**立即**查一次（新增 `refreshDup()`），命中 ⇒ 弹三行提示 + **禁用「确认导入」**；
  云函数 confirm 分支另有**硬阻断**（防旧版本/直调绕过），**早于首个写库**。
- 🔴 **不提供 force 后门**：留后门等于让"随手选"继续发生；正解永远是「改用原平台重导」（同平台同 _id ⇒ 覆盖，不翻倍）。

### 3.2 人话只能走预览通道（一个被逼出来的设计）

`utils/api.js:47` 会把后端 `fail` 的 msg **覆盖成 code→i18n 通用文案**（只落 console.warn）
⇒ 后端写再多中文，真机也只显示「操作失败」。
⇒ 所以 dup 信息与文案一律走 **ok 的 data**（预览返回 `dup`），前端拿到后自己渲染。

### 3.3 P1 · 回执带平台名

成功弹窗从「导入完成」改成「**已按『淘宝闪购』导入完成**」——老板回头看复盘页时，对得上自己刚才选的啥。

### 3.4 P1 · 记住上次平台

按店铺存本机（`last_import_platform_<shop_id>`），下次**预选**（picker 里看得见、可改，不是静默替他选）。

### 3.5 R269 遗留 · 账单暂停态说人话

原来只弹「正在打磨，暂不开放」。现在前面多一行：**「识别到：京东（订单）· 117 行 · 10月」**，
下面紧跟「换成《商品销量》或《菜品销售统计》表即可导入」⇒ 老板知道该换哪张表，不会误判成"京东不行"。

### 3.6 平台显示名单源

前端新增 `platformLabel()`（唯一映射处）：走术语单源 `reviewPlatformNames`，`pos` 单独兜底成「堂食」
（该表不含 pos ⇒ 不兜底界面会漏出机器值）。

## 五、真机怎么验

1. 外卖单均测算 → 数据导入 → 选一张**已经导过**的《商品销量》表；
2. 平台**故意选成另一个**（比如上次是淘宝闪购，这次选美团）；
3. 期望：立刻出现红色三行提示（已用『淘宝闪购』导过 N 行…会翻倍 / 请改选『淘宝闪购』），**「确认导入」按钮变灰**；
4. 把平台改回淘宝闪购 ⇒ 提示消失、按钮恢复 ⇒ 可正常导入（覆盖原来那份）；
5. 导入成功弹窗应显示「**已按『淘宝闪购』导入完成**」。

⚠️ 边界：只有**同一份表换平台**才会拦。两张**不同平台各自的真表**（销量/金额不同）不会被误拦 —— 这是刻意设计，由 F-④ 守着。
