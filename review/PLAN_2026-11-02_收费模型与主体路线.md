# 收费模型与主体路线（个人 / 个体工商户）

> 定位：**决策单 + 执行清单**。回答三件事：主体影响什么、哪些功能收费、钱怎么收。  
> 触发：李老师 2026-11-02「个人也要保留收费方式，主体只是最后对接和材料不同，功能不能关」。  
> 关联：`specs/PRODUCT_PLAN.md`（产品单源）、`review/PLAN_2026-11-02_个人主体上线_不阻塞路径.md`（上线流程）。

## 0 一句话结论

**主体类型对功能零影响，对代码只影响最后一层「拉起支付」的接口，对流程只影响提交材料。**  
所以正确做法是：功能全开、收费设计全留、支付通道按主体切换 —— 而不是把功能关掉。

### 2.1 M1 到底在哪里收费（本轮实测，非推断）

**M1 目前只有 1 个付费点，全程不弹窗：**

| 动作               | 是否弹付费墙  | 依据                                                              |
| ---------------- | ------- | --------------------------------------------------------------- |
| 进月度页 / 切月份 / 看历史 | ❌ 不弹    | 无 `hasFeature`                                                  |
| 录收支 / 填库存 / 存草稿  | ❌ 不弹    | `calcMonthlyProfit` 无权益判定                                       |
| 看结果 / 保本点 / 敏感度  | ❌ 不弹    | 同上                                                              |
| **导出月报 / 打印**    | ✅ 唯一付费点 | `subpkg/biz/month/result.js::onExport` → `hasFeature('export')` |

还有一个**不弹窗的软门槛**：结果页按 `isPaid` 决定显示「真实利润」还是「参考利润」（`month/index.wxml:31-42`）。  
免费期 `isPaid` 恒 true ⇒ 现在所有人看到的都是真实利润。

> 🔴 **收口风险（必须记住）**：开卖那一刻 `isPaid` 会掉回 false ⇒ 未付费用户**同时**从「真实利润」变「参考利润」，  
> 数值会变、口径说明也会变。这是一次体验断崖，不是小事。处置见 §6-O3。

### 2.2 配额语义：20 道是「同时 20 道」，不是「累计 20 道」

**你问的「删一道能不能再加一道」——能，而且这是当前代码的既定行为。**

证据链（三处一致，不是单点推断）：

1. 计数只看活跃行：`checkQuota/index.js` 用 `da.listAll()`，而 `dataAdapter` 把 `is_deleted: false` 强制拼进查询条件；
2. 删除是软删：`card/index.js::onDelete` 发 `saveCostCard { card: { _delete: true } }` ⇒ 置 `is_deleted: true`，历史版本不物理删；
3. 写侧也只算活跃：`saveCostCard/index.js:288-312` 同一口径 `card_code` 去重。

⇒ **used = 当前在用的、算过成本的、去重后的卡片数**。删一张 ⇒ used −1 ⇒ 立刻能再加一张。

| 语义          | 表现           | 现状      |
| ----------- | ------------ | ------- |
| 同时 20 道（现状） | 算完删掉再算，理论可循环 | ✅ 当前实现  |
| 累计 20 道     | 算过就永久占额      | ❌ 非当前实现 |

**要不要改**：建议**保持现状**。理由：① 老板换季改菜单是常态，删了不能再加会被骂；② 漏洞的实际价值被「导出收费」卡住——  
免费用户能算、能看屏幕，但拿不走 xlsx。③ 真按累计算，需要新增一张「已消耗额度」表并处理存量，改动面大、收益低。

> ⚠️ 20 这个数字的出处（可追溯）：`review/PLAN_2026-09-26_M3免费额度决策_与豆包五轮交叉核验.md` ——  
> 当时三选一：q=0（出局）/ q=15（降为阶段 3 回拨值）/ **q=20（采纳）**。依据是「原料档案免费无限 + 录入不限 + 只对**计算**设限」，  
> 且判断「撞到 20 道墙的那批人，正是付费动机最强的人」。  
> ⚠️ 该判断当时就被标注为**存疑**（价值菜定义用销量 top，未必等于老板真关心的菜）⇒ **上线后需用真实数据校准**。

## 5 支付通道（两条路都还没接完）

### 5.0 「虚拟支付」到底是什么（一句话版）

**它是微信给「卖数字东西」开的那条官方收款通道** —— 卖会员、卖解锁、卖次数都用它；  
实物商品、外卖、堂食不收这条。我们卖的是「解锁功能」，所以属于虚拟商品。

为什么不走普通微信支付：普通支付要商户号，商户号要营业执照；2026-04-01 起，**小程序内虚拟商品必须走虚拟支付，禁止外部跳转/私下转账**。  
两条规则叠加 ⇒ 个人主体只能走虚拟支付，且这不是退而求其次，是唯一合规解。

**个人主体的开通条件（官方文档原文口径）**：

| 项    | 要求                                              |
| ---- | ----------------------------------------------- |
| 主体   | 个人，持大陆居民身份证                                     |
| 服务类目 | **必须含「工具」**                                     |
| 前置   | 已完成**小程序认证 + 备案**                               |
| 限额   | **月 10 万元**（全终端合计）                              |
| 费率   | Android 等 1%（T+3 提现）/ iOS 12%（苹果佣金，约 45~60 天结算） |
| 审核   | 提交资料后一般 5 分钟出结果                                 |

开通后后台给三样东西：`AppID`（小程序身份）、`OfferID`（支付账号）、`现网 AppKey`（密钥）；  
再到「道具管理」里把月/季/年建成三个**道具**（商品），拿到 `productId` 与价格。前端调 `wx.requestVirtualPayment`。

> 🔴 iOS 额外一步：虚拟支付默认只覆盖安卓侧；要收 iOS 的钱必须①先在 mp 后台配置**小程序简称**（Apple 要展示名）  
> ②在虚拟支付「基本配置」里**开通苹果 IAP**。这一步不做，iOS 用户点了没反应，且看起来像 bug。

**🔴 个人主体的三条硬约束（会改变排期，必须先知道）**：

| 约束                                            | 含义                                | 对我们的影响                                                                                                 |
| --------------------------------------------- | --------------------------------- | ------------------------------------------------------------------------------------------------------ |
| 道具类型固定 `short_series_goods`（一次性道具直购）          | 不能做代币充值，**不能做订阅/连续包月**            | 月/季/年三档「买断 N 天」**可以**；`plan_auto_subscribe` **做不了**，须升级主体                                              |
| 发货靠微信服务端**异步推送**（`xpay_goods_deliver_notify`） | 客户端 success 回调**可能丢失**，不能作为唯一发货依据 | 必须做「推送 + 主动查单」双保险；推送**必须幂等**（会多次重推，第三方实测称最多 15 次；官方未给具体次数）                                                              |
| 推送要一个**公网可达 URL**                             | 云开发默认没有对外 HTTP 入口                 | 项目当前**零 HTTP 访问配置**（只有 `payExpireNotify` 的定时触发器）⇒ S3 前需开通「云函数 HTTP 访问服务」或走云托管；未开通前只能靠前端支付成功后主动查单，有漏单风险 |

> 上面第一条是**目前最容易被忽略的**：网上多数"虚拟支付接会员"教程是按企业/个体户写的，会直接告诉你"配自动续费"。  
> 个人主体照抄会在后台找不到订阅配置。**别按那些教程排期。**

**费率对定价的实际影响**（按现有四档算到手）：

| 档位 | 标价   | Android 到手（−1%） | iOS 到手（−12%） |
| -- | ---- | --------------- | ------------ |
| 月  | 25.9 | 25.64           | 22.79        |
| 季  | 69   | 68.31           | 60.72        |
| 年  | 199  | 197.01          | 175.12       |

> 结论：iOS 一年少收 24 元/单。**不建议在 iOS 上提价补偿**（苹果规则与用户观感都不利），  
> 而是把「年卡」作为主推（摊销后 iOS 单月 14.6 元，仍在老板可接受区间）。

### 5.1 现状差距

现状：`wx.requestPayment` **从未真正实现**（`utils/paywall.js` 只有注释占位）。  
也就是说，即便现在是个体户，也收不了钱 —— 这一块两条路都要做。

| 环节     | 商户号（个体户）              | 虚拟支付（个人必选）                   | 复用度          |
| ------ | --------------------- | ---------------------------- | ------------ |
| 下单     | `payCreateOrder` 已有   | 同                            | ✅ 共用         |
| 权益/订单表 | 已有                    | 同                            | ✅ 共用         |
| 支付参数   | 调「统一下单」拿 `pay_params` | 调虚拟支付下单拿 `signData`/`paySig` | ❌ 各一套        |
| 前端拉起   | `wx.requestPayment`   | `wx.requestVirtualPayment`   | ❌ 各一套        |
| 密钥     | APIv3 密钥 + 证书 + mchid | OfferID + 现网 AppKey          | ❌ 各一套        |
| 回调/发货  | 支付回调 → 写 `expire_at`  | 发货推送 → 写 `expire_at`（须幂等）    | ⚠️ 结构相同、协议不同 |
| 商品配置   | 后台配价格                 | 后台建「道具」并发布（productId + 价格）   | ❌ 各一套        |

> 结论：**差异集中在「支付参数 + 拉起 + 密钥 + 商品配置」四小块**，订单/权益/幂等/续费逻辑完全共用。  
> 虚拟支付额外注意：`env` 固定 `0`（正式）、金额单位是**分**、道具发布后需等几分钟同步、iOS 需另配小程序简称并开 IAP。

## 6 收费这块还能优化什么（本轮实证清单）

分三类，**别混着做**：必修=开卖前不做会出事；建议=影响转化率；别动=动了会破坏已定策略。

### 必修（开卖前必须完成）

| #  | 项         | 现状（实证）                                                              | 后果                                      |
| -- | --------- | ------------------------------------------------------------------- | --------------------------------------- |
| O1 | 虚拟支付链路    | `grep requestVirtualPayment` **全仓 0 命中**；`payCreateOrder` 只产出普通支付订单 | 现在这个开关翻成 true 也收不到一分钱                   |
| O2 | iOS 闸门要翻面 | `paywall.js:47` `if (isIOS()) return showIOSBlocked()` 一律不卖         | 开了虚拟支付后 iOS **仍然买不了**；而 iOS 是客单价最高的端    |
| O3 | 开卖瞬间的体验断崖 | `isPaid` 从恒 true 掉回按 `expire_at` 判                                  | 未付费用户同一时刻失去「真实利润」，数值与口径说明一起变            |
| O4 | 订单结构与发货   | 现有 `shop_payment_flow` 是普通支付字段；`payCallback` 是商户回调协议                | 虚拟支付有 `productId/orderId` 和「发货」概念，硬套会错账 |
| O5 | 道具 ↔ 套餐映射 | 四档套餐在 `subscription_plan`，虚拟支付要另建「道具」                               | 两边价格一旦不一致 = 用户实付与权益不符                   |

> O2 的具体改法：把 `showIOSBlocked` 从「无条件拦」改成「按虚拟支付是否已开通分流」——  
> 已开通 ⇒ 走 IAP；未开通 ⇒ 保持现在的提示。判据用云端下发的 `ios_iap_enabled`，不在前端写死。

### 建议（影响转化率，不阻塞上线）

| #   | 项          | 理由                                                                                                                |
| --- | ---------- | ----------------------------------------------------------------------------------------------------------------- |
| O6  | **付费漏斗埋点** | 现在曝光/点击/下单/支付成功**零埋点**。收费后不知道掉在哪一步，等于盲飞。建议最简四事件：`paywall_show` / `paywall_click` / `order_create` / `pay_success` |

### 8.3 需要你拍板的一件事（影响 S4）

开卖那一刻，未付费用户会从「真实利润」掉到「参考利润」。三种处置：

| 方案 | 做法 | 代价 |
|---|---|---|
| **A（推荐）** | 开卖前注册的老用户，赠送 30 天权益 | 一批免费额度，换来口碑与转化观察期 |
| B | 开卖即严格执行，不做过渡 | 老用户当天数值变化，投诉风险 |
| C | M1 的「真实/参考利润」永久免费，只对导出/套餐/外卖/复盘收费 | 少一个收费理由，但避免最大争议 |

> 我倾向 **A**：一次性的 30 天成本可控，且能拿到「付费墙曝光 → 转化」的真实数据。
> 但 C 也成立——如果判断「真实利润」是产品核心价值、用它做门槛会伤用户信任。
