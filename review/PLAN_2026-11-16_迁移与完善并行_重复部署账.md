# 迁移动作与功能完善：是不是二选一？（李老师 22:11 追问）

> 李老师问：在完善小程序，还是现在就开始迁移？"迁完了过去最后还得修改，是不是白迁？"
> 结论：**不是二选一，两条线并行。迁移不是白做，重复部署的成本被高估了。**

---

## 一、先回答"迁完还得改"——把账算清楚

### 事实：部署器是增量的，不是全量重推
`review/evidence/_deploy_fns.py` 的用法（源码第 5-8 行）：
```
python _deploy_fns.py <fn1> [fn2 ...]      # 指定函数
python _deploy_fns.py --from-head          # 自动取「最近一次提交动过的 cloudfunctions 顶层目录」
```
⇒ `--from-head` **只推本轮改动的函数**，不是 60 个全量重传。
"改完再部署一次"的实际成本 = 改了几个函数就推几个，**通常 1~3 个，几分钟**。

### 两次部署目的不同，不是重复劳动
| | 迁移这次 | 提审那次 |
|---|---|---|
| 目标 | **验证新账号链路走得通** | 发版给用户用 |
| 验什么 | 环境 ID 对不对、timeout、4 个触发器、`env.js` 静默回落、建表、真机能登录出数 | 最新功能可用 |
| 依赖功能完善吗 | ❌ 不依赖 | ✅ 依赖（功能冻结+打 Tag） |

这些环境类坑**跟功能无关，且只有迁一次才知道**。挤到提审前夜跟审核问题一起爆，才是最糟的。

---

## 二、为什么"等完善再迁"是陷阱

近 6 轮审计每轮都发现一条真缺口（R744 残值 / R746 三缺口 / R747 对拍 / R748 轮次 / R749 对齐）。
⇒ **"完善"没有终点**。若等"完全体"再迁，备案日历（认证 1~5 天 + 备案 5~12 工作日）会被白耗掉——而备案是上线的最长关键路径，跟代码写没写完无关。

**让日历倒逼，别让"完美"拖延。**

---

## 三、执行节奏（两条线并行）

```
现在（认证审核中）：
  李老师 → 开云开发建 1 个 prod 环境，拿环境 ID  → 给我
  我     → 改 2 处配置 + 部署 + 建表 + 传触发器 + 真机跑通（验链路，不提审）
          ⟂ 同时继续在旧 dev 完善功能（测试一天不停）

备案下来前后：
  功能定稿 → 打 Tag → 增量部署改动的函数到新 prod（发版）→ 提审 → 发布
```

---

## 四、一句话

**现在就迁，但迁移只是"验一次链路"，不是发版；功能继续完善不中断，改动最后只推增量函数，不存在"白迁"。真正卡日历的是备案（5~12 工作日），越早启动越好；迁移能提前暴露环境坑，反而给完善功能争取了时间。**
