> 背景：R715 报告建议 1。李老师 2026-11-12 原话「不知怎么填数字…入错了数字怎么办」，
> 以及更早的真机反馈「到手口径 / 总额法口径很多人不理解」。
> 轮次：R716 ｜ 套件 288 → **289** ｜ 提交见文末

---

## 一、要解决的是什么

外卖页此前只有一个数：**标准单应付**

```
标准单应付 = 成本卡售价 × 份数 + 打包费 + 顾客配送费
商家实收   = 标准单应付 − 佣金 − 配送服务费 − 商家补贴 − 配送补贴 − 推广费
本单利润   = 商家实收 − 菜成本 − 包材成本
```

问题出在第一步。「成本卡售价」是**堂食价**，而外卖：

- 普遍在堂食价上加 2~5 元（平台经理会要求做「外卖专享价」）
- 还有满减、折扣菜、新客立减

所以「标准单应付」几乎永远不等于顾客真实支付，**老板拿到的是"估的利润"，不是"这单真赚的"**。

而老板手上确实有一个真数：外卖后台「订单详情 → 预计收入」。

**这就是本轮的改动：给他一个格子填这个数。**

---

## 二、为什么填「商家实收」，而不是「顾客实付」

这是本轮最关键的一个决策，因为两个都叫"实收"、都能从后台看到，但填错后果完全不同。

| 填哪个 | 系统要做什么 | 准确性 | 老板容易搞错吗 |
|---|---|---|---|
| 顾客实付 | 仍要减佣金/配送/推广（还有估算误差） | 部分改善 | **极易**：后台两个数都在，名字都像"这一单多少钱" |
| 商家实收 | 什么都不用减，直接 `实收 − 成本` | **完全准确** | 较难：只有后台明确标「预计收入/结算金额」的那一个 |

填错「顾客实付」的后果：38 元的单子实际到手 25 元，他填了 38 ⇒ 利润虚高 13 元，**接近一倍，且零报错**。

所以：

1. 只给一个框，不给两个（两个框 = 逼老板做一次他自己也拿不准的区分）
2. 标签写「商家实收（元）」，占位写「如 22.5」
3. 说明第一句就是**否定式**：「外卖后台的『预计收入』，**不是顾客付了多少**」

第 3 条是防止填错的唯一有效手段——不是让他理解两个概念的区别，而是直接告诉他哪个才是。

## 三、填了之后，四个连带问题

### 1. 不能再逐项扣费

实收是平台结算**之后**的结果，佣金/配送/推广已经在里面扣过。再扣一次 = 同一笔钱扣两遍。

```
填实收 26.00 → 利润 = 26.00 − 12.00（菜成本）= 14.00  ✓
若再扣佣金 4.80 → 9.20  ✗（且零报错）
```

守卫 B-③ 用「佣金率 15% → 60%，利润必须一分不动」钉住这条；B-④ 是反恒真（不填实收时同一改动必须让利润变，证明 B-③ 不是"费率根本没接上"）。

### 2. 不能给「到手率」

这个字段叫「到手率」，分母只能是**顾客实际付了多少**。而 `payment`（标准单应付）不等于顾客实付——加价和满减都在它之外。

- 加价单：实收 38 / 标准单 34 = **112%**
- 折扣单：实收 22 / 标准单 34 = 65%（而实际到手可能不低）

两种都像 bug。**宁可不给，也不给错的**：实测模式下 `receipt_rate` 返回 `null`，页面整行不渲染。

### 3. 不能画瀑布

瀑布每段的分母也是 `payment`。实测模式下各项占比 + 到手率重加起来对不上 100%，会画出一张自相矛盾的图（「佣金 14% + 实收 76%」）。

### 4. 总额法必须标「算不了」，且**出空串不出 0.00**

总额法要「顾客实付」才能走完 `收入 − 费用`。老板填的是商家到手（已扣完）。

拿标准单凑数会得到**第二个、而且两个都不准**的利润——那正是 R714 记录的「两个口径让人不理解」的加重版。

所以：`accrual.available = false`，三个数给 `null`，页面给**空串**。

> 为什么连 `'0.00'` 都不能给：`0.00` 会被读成"总额法算出来是 0"，而真相是"这套输入下算不了"。
> **缺口要说出来，不要用数字盖住。**

## 四、实测数据（真跑，不是推演）

一单「麻辣香锅」：成本卡售价 32.00 / 成本 12.00，1 份；打包费 2、佣金 15%、配送服务费 3.2、推广费 2。

| | 不填实收 | 填实收 26.00 |
|---|---|---|
| 标准单应付 | 34.00 | 34.00（改标「标准单应付」） |
| 商家实收 | 24.00（估） | **26.00（你填的）** |
| 菜成本 | 12.00 | 12.00 |
| 本单利润 | 12.00 | **14.00** |
| 到手率 | 70.59% | —（null，不渲染） |
| 瀑布 | 3 段 | —（不渲染） |
| 总额法利润 | 12.00（与到手恒等，T-h 仍在） | —（算不了，一句说明） |

**不填实收时，所有数字与改动前逐位一致**（守卫 A-②/A-③ 钉住），所以这个改动对存量用户零影响。

边界验证：

| 输入 | 结果 |
|---|---|
| `0` | 视为未填（0 不等于「这单白干」） |
| `-26` | 拒算（负数被判不可读，不产出任何数） |
| 空 | 视为未填 |
| `22.5元` | 拒算 + 横幅（**不静默退回估算**，否则老板以为按实收算了） |
| 纯函数层直接送 `-2600` 分 | 夹到 0（防线在计算单源里，不靠调用方自觉） |

## 五、一个我自己差点漏掉的矛盾

填了实收后，结果区会同时出现两个数：

```
本单利润          ¥14.00
本单各菜品毛利
  麻辣香锅  ¥20.00   ← 比本单利润还大
```

逐行毛利按**成本卡售价**算，没扣平台抽成。老板第一反应一定是「每道菜赚 20，整单怎么才赚 14，算错了吧」。

这不是 bug，但不解释就是 bug 的观感。加一句灰字（不是橙色块，因为它是解释不是警告）：

> 这些毛利按成本卡售价算，没扣平台抽成 —— 加起来会比上面的本单利润大。

守卫 F-⑩ 先**核实这个矛盾真实存在**（20.00 > 14.00），再守 F-⑪/F-⑫（说明必须在场、且说清原因）。
