## 〇 一句话结论

**豆包这份 v1.0 的架构骨架与我们已有的 M3 地基约 80% 重合** —— 它列的 14 章里，有 **9 条是仓内已落地的能力**（半成品虚拟原料、循环拦截、快照、复制、反算、导出、批量出品、加工系数、配额读配置）。
真正的**新增价值集中在 4 处**：**多规格（大小份）分类系数**、**标准原料库+别名**、**组件分组/耗材分类**、**留存设计（第二个月付费）**。

它的**三处硬伤**：① **外卖完全空白**（全篇 0 字，而这是李老师本轮的核心诉求之一）；② **免费额度又提 8 张**（规范里已明确驳回）；③ **11 业态与仓内 4 业态枚举打架**。

它还**完全没考虑**我们的工程现实：引擎 **5 份副本**、**6 个验收锚点**、**门禁 103 套件**。它给的 11 种业态模板 + 200-300 条标准原料 + 100 道菜品模板，在它那里是"设计"，在我们这里是**要挂守卫、要防漂移、要逐条实测**的工作量。

## 二 建议吸收（按性价比排序）

### A1 ⭐⭐⭐⭐⭐ 多规格（大小份）· 分类系数制
- **豆包原话**：「一张成本卡定义标准份的完整配方，添加多个规格，每个规格有分类系数」——半份：主料 0.5 / 辅料 0.7 / **调料 1.0** / **包装 1.0**。
- **它最值钱的一句**：「半份菜的调料不会减半 —— 否则没味。**这就是行业里"半份定价是全份 65% 而不是 50%"的原因：固定成本不减半。**」
- **为什么值得**：这是**真高频**（大小份/半份/例份几乎每家店都有），而且它解释了一个老板长期困惑的现象（顾客问"半份为什么不半价"）。当前仓内完全没有。
- **我方落法**：卡主表加 `specs[]`（`{spec_key, name, coef:{main, aux, season, pack}}`），**由基础份派生**。
- 🔴 **代价与红线**：
  - ① **不得改 `calcCostCard` 的锚点路径** —— 6 个锚点（9.75 / 4.48 / 12.35 / 12.08 / 24.38）一个都不能漂。规格派生必须是**独立函数**（≥ 规格行只在展示层/试算层），或作为**可选入参**、缺省即现值。
  - ② 引擎有 **5 份副本**（`calcBom` / `saveCostCard` / `syncCostCard` / `getCostCard` / `getCardVersions`），**改一处必同步五处 + md5 守卫**。⇒ 建议：规格系数**不进引擎**，放 `common/specDerive.js` 单一新文件，五副本**都不碰**。
  - ③ 需要新守卫：**证明"加规格后基础份成本仍 = 9.75"**（防派生逻辑污染主线）。

### A2 ⭐⭐⭐⭐ 标准原料库 + 别名匹配（**打折版**）
- **豆包原话**：「内置 200-300 种标准原料 + 多重别名；输入"一品鲜"→ 下拉显示"生抽酱油"」。
- **为什么值得**：治**真痛点** —— "同一个东西N种叫法"（辣椒/辣椒段/海椒/糍粑辣椒）。老板自建必然建出一堆重复料，成本永远对不上。
- **我方落法（打三折）**：
  - ① **不做 200-300 条，先做 60~80 条高频**（生抽/老抽/菜籽油/干辣椒/花椒/豆瓣酱/土豆/鸡胸肉…），**够"新建原料"时给出建议**即可；
  - ② 数据单源：新建 `utils/materialLexicon.js`（+ `specs/dev-specs/` 副本，**同 `terms.js` 的双副本纪律**：改后 `cp` + `diff -q` 校验）；
  - ③ **只做"搜索建议"，不做"自动匹配替换"**。
- 🔴 **两条硬红线**：
  - ① **别名匹配绝不能自动写入/自动合并** —— "辣椒"若被自动换成"干辣椒"，成本**静默变错**（这正是我们刚在 round116 栽过的"静默失败"同类病）。豆包自己也写了"匹配不到才新建"，方向一致，但**我们必须把"只建议不替换"写成守卫能守的规则**。
  - ② 三级分类若落库，必须**与 M1 的 `ITEM_TAGS` 归属体系对齐**（M1 有 4 大类 `manage` 不做的既定口径），**不能出现两套分类**。
- **代价**：数据资产要人工核对（60 条 ≈ 半天）；新增守卫 1 条（防"分类枚举"与 M1 打架）。

### A3 ⭐⭐⭐⭐ 组件分组 + 耗材分类（**纯展示层**）
- **豆包原话**：包子 = 面皮组件 + 馅料组件；烤鱼 = 鱼 + 底料 + 配菜 + 烤纸；奶茶 = 茶汤 + 奶基 + 糖浆 + 小料 + 包装。
- **为什么值得**：**成本合计一分不变**，但老板"看得懂"（一眼知道馅料占多少）。是**低成本高感知**项。它同时解决了豆包的"调料包"（小面 12-15 种调料逐行列会 20 行 ⇒ 折叠成一组）。
- **我方落法**：明细行加两个字段 —— `line_kind`（主料/辅料/调料/半成品/耗材包装）、`group_name`（自由文本，可空）。**小计只做展示，合计口径不变**。
- 🔴 **红线**：必须**证明 Σ 不变** —— 新守卫要能断言"加了分组后宫保鸡丁仍 9.75"。
- **併入项**：豆包的「调料包」**不单独做机制**，用本项目组件分组即可（**少一个机制 = 少一处漂移点**）。

### A4 ⭐⭐⭐ 耗材分摊（炸油 / 炭火）——**零引擎改动**
- **豆包原话**：「炸油一锅 500 元炸 800 斤肉，按炸制重量分摊（0.4-1.2 元/份）」，竹签/烤纸/锡纸是耗材。
- **我方落法（关键技巧）**：**不新增机制** —— 用现有「模式 B 半成品虚拟原料」表达：炸油做成一张批量卡（产出单位 = "斤炸制品"），炸鸡卡引用它、填炸制重量。
  ⇒ **引擎零改动、五副本零改动、锚点零风险**。这是全篇最"省"的一处吸收。
- 配套：`line_kind='耗材包装'` 让这类成本在卡片上可见（依赖 A3）。
- **价值**：也是**外卖包材成本**的落点（我们 PLAN 的外卖单均要用）。

### A5 ⭐⭐⭐⭐ 留存设计 —— **回应李老师点名的"第二个月付费意愿"**
- **豆包的核心洞察（采纳）**：**M3 是低频工具** —— 老板录完菜单一个月才改一次；「把成本卡变成后厨操作手册」的思路是"从老板月看一次 → 厨师每天看多次"。
- **我采纳它的三条 + 补一条它想不到的**（详见 §九）。
- **放弃它的两条**：批发价 API 推送、小票 OCR（理由见 §三）。

### A6 ⭐⭐⭐ 业态模板（**只做 3 种**，但要改名解耦）
- **采纳它的方法论**：「模板的本质是**预设默认值 + 字段显示优先级**，通用卡完全能算，模板只是让老板更顺手」—— **这个判断非常对**，避免了"N 种卡"的分裂。
- **采纳它的克制**：「v1 不做 11 种」。**我建议的 3 种**（按我们客户画像调整）：
  - ① **炒菜单份**（宫保鸡丁型，= 现有锚点菜）
  - ② **批量卤制**（耙三样/卤菜/大锅菜型，模式 B）
  - ③ **粉面**（调料包/浇头型，A3 的组件分组直接用上）
- 🔴 **必须解耦**（见冲突③）：模板枚举**不得复用 `shop.biz_type`**。

### A7 ⭐⭐⭐ 菜品模板库（**打折：20 道起步**）
- **采纳它的"录入门槛是生死线"判断**：*"所有餐饮成本工具的头号死亡原因，不是算不准，是老板录了 3 张卡就放弃了……必须把录入时间从 10 分钟降到 2 分钟"* —— 这句是本篇**最有价值的判断**。
- **我方落法**：`utils/dishTemplates.js` 纯数据单源（+ specs 副本），先 **20 道**，**只预填"行结构 + 用量"**。
- 🔴 **红线（R128 同类）**：模板**绝不预填价格** —— 价格必须取**用户自己的原料库**。否则等于把别人的采购价灌进老板的成本，是**误导**。（本仓已有 R128「参考值不预填」，这里要加一条同族规则并由守卫守住。）

### A8 ⭐⭐ 可选加价项（加珍珠 +2 / 加配菜 +5）
- **落法**：卡上加"加价项清单"（名称 + 成本 + 加价额），**只算不并入** `unit_cost_fen`。
- **优先级低**（客户以正餐/火锅为主，奶茶场景少）。**建议 v1 不做**，等有奶茶客户再加。

| 豆包主张 | 舍弃理由 |
|---|---|
| **免费额度 8 张** | 🔴 **规范已明确驳回**：改为「读 `subscription_plan`，按 `user_id` 跨店共享，默认 3」+ **禁硬编码**（规范 M3.7；对应《与豆包差异修正记录》第 2 行）。豆包这是**重复提议**。<br>⚠️ 但它给的经验论据（"小面馆 8 样"）**有道理** ⇒ 我建议把它变成一个**配置待议项**（3→5 是否更合适），**改配置值 ≠ 改架构**。 |
| **11 业态全量** | 🔴 与仓内 **4 业态**（`cx_indicatorRef.js:59`）**枚举打架**，且规范已注明扩展路径（"若将来要分列，**新增 bbq 业态即可**，不要硬塞进本带"）。11 种是**录入模板**维度，**必须与 `shop.biz_type` 解耦**。 |

| **采购小票 OCR** | 需 OCR 服务/资质/费用；识别错误会**静默污染原料库**（又是"静默失败"同类病）。v1 不做。 |
| **语音录入** | 小程序录音权限 + 语音识别服务 + 审核成本；收益/成本比差。P3。 |

| **"折扣率 75-82% 建议区间"** | 单点来源、无出处 ⇒ **最多做软提示文案**，**绝不能当判定阈值**（否则就是又一个"把行业常见区间当警戒线"—— 我们在 round113 刚栽过这个坑）。 |
| **"套餐 v1.2 再做"** | 🔴 与李老师本轮明确要求冲突（"勾选几个变成套餐成本"）。豆包把它排到 v1.2，**我们不能跟**。 |
| **"M1/M3 不打通"** | ⚠️ **结论对（M3 不得并入 M1 月度账），但理由不同且不完整**：<br>· 我们的理由 = **M3 是权责发生制下的理论试算，M1 是实际发生**（口径不同，不是"粒度不同"）；<br>· **它漏了一个关键机会**：M1 有「食材成本」实绩、M3 有理论成本 ⇒ 差额是**最有价值的对照**（见 §九）。它因为"不打通"就完全没想到这一层。 |
| **"不要做库存"** | ⚠️ 半采纳。M3 **不重复建库存**是对的（M1 已有库存/摊销口径），但表述要改成"**M3 不碰库存口径**"，避免与 M1 的既定机制打架。 |

## 八 ★ 关于"第二个月付费意愿"—— 豆包没打中的那一枪

豆包问对了问题（**M3 是低频工具，第 2 个月凭什么续费**），但它给的答案全部是**"增加使用频次的理由"**（后厨视图、今日菜价、上新菜）。

**问题在于**：增加频次 ≠ 增加付费意愿。老板**不打开**就不会续费，但**打开**也未必续费 —— 因为"看配方"这件事，他觉得**不值得每月 25.9 元**。

**我补的那一枪：把 M3 变成"每月必须对一次账"的工具。**

- **M1 有**：本月实际食材成本（真实发生，权责发生制）
- **M3 有**：每道菜的理论成本 × 销量 ≈ 理论食材成本
- **两者差额** = **这个月到底漏在哪**（是采购涨价没发现？是出菜份量超标？是损耗失控？是偷吃偷拿？）

这个对照**只有我们有**（因为我们同时有 M1 和 M3；豆包认为"不打通"，所以它永远想不到）。而它的**续费理由极强**：

> **"你这个月理论食材成本 3.2 万，实际花了 4.1 万，多出的 9000 块，你得知道去哪了。"**

一个月 25.9 元，换一次"我知道我漏了 9000 块"。**这才是第二个月回来的理由。**
而且它**每晚一个月做，就少一个月的数据** ⇒ 天然制造持续使用动机（数据越攒越值钱）。

⚠️ **但必须守住三条边界**（否则会变成 M1 的污染源）：
1. **只做只读对照，绝不自动写入 M1 任何字段**；
2. 差额**只做归因提示**（列出 N 个可能方向让老板自己点），**不许自动下结论**"你被偷了"；
3. 销量数据来源要明确（若 M1 无权责制的销量口径，就只在 M3 内做"理论成本构成分析"，**不碰差额**）——**这一条需要先核对 M1 有没有可用的销量字段，我尚未查证，须在拍板后补查**。
