# R586 · DSI-1 重导残留清理（"导进去看得见"这一层也查了）

> 起因：李老师「我要晚点验证真机，你接下来想做什么？」
> 我的判断：**真机验证之前，先确认"导进去的数据在毛利榜上真能看见、且金额是对的"**。
> 结果查出两件事：一件是好的（能看见），一件是坏的（重导会残留、金额虚高）。

---

## §1 好消息：读侧不按平台过滤 ⇒ DSI-1 的数据看得见

`getDishReview/index.js:66` 读法：

```js
const salesRes = await da.listAll('external_sales_daily', { shop_id: shopId });
```

**只按 `shop_id` 过滤，不带 platform。** 而 `service.js` 里：
- `buildDineReview`（platform='pos'）→ 堂食毛利
- `buildTakeawayReview`（platform !== 'pos'）→ 外卖，按 platform 分组

DSI-1 落库时堂食写 `pos`、外卖写 `meituan/taobao/jd_order` ⇒ 两条路都能落进对应的榜。
**所以"导进去看不到"这个担心不成立**（值得先查，因为这正是本仓踩过多次的同族坑）。

## §2 🔴 坏消息：同一天重导，菜变少会留下旧行，金额虚高

`_id = SALE_<店>_<平台>_<日期>_<seq>`，重导只覆盖 **seq 重合**的部分。

实测（探针，非推测）：

```
第一次写入 5 条: ..._0 ..._1 ..._2 ..._3 ..._4
第二次写入 3 条: ..._0 ..._1 ..._2
🔴 第二次导完后仍在库里的旧记录: 2 条 → ..._3 ..._4
```

而读侧**不按来源过滤** ⇒ 这 2 条会被算进毛利榜。**错账，且不报错。**

### 什么时候会触发

- 老板先自己导了平台「商品销量表」（形态 C），后来用 AI 整理成 DSI-1 又导一次 —— 同一天同平台；
- 或者修改了表（删掉几个菜）后重导。
- 「午饭高峰期录少了、晚上补录」这种最常见。

## §3 处置：写完之后按「集合差」清掉多余旧行

**顺序刻意是「先写新数据、再删多余」**：新数据先落地，最坏情况只是"多了几条旧行"，
而不是"该有的没有"（后者更糟，且老板完全无从发现）。

**为什么用集合差，不解析 `_id` 取 seq**：
1. 解析是另一份单源（`common/salesBillId.js`），扩展它要连带同步各云函数的 `cx_` 副本；
2. 集合差与 `_id` 形态**解耦** —— 将来 `_id` 里加来源标记也不会让这段失效。

实现（`handleDSI1Import` 每组内）：

```js
// 1. 先取该组已存在的 _id（失败则不清，新数据仍正确）
// 2. 写新数据，同时记 writtenIds
// 3. 差集 = 旧 _id - writtenIds ⇒ 逐条软删
```

**失败不阻断**，但**必须回报**：`pruned`（清了几条）/ `pruneFailed`（几组清理失败）。

## §4 前端也做了两件事

| 场景 | 显示 |
|---|---|
| `pruned > 0` | 「已导入 6 行，含 堂食、美团。**（替换了之前的 2 条旧记录）**」 |
| `pruneFailed > 0` | 「⚠️ 有旧记录没清理干净，金额可能偏高。请再导入一次同一份表，就会覆盖干净。」 |

第一条不说，老板会以为"怎么少了几条"；第二条不说，就是**静默的金额偏高**。
（沿本仓惯例：空串不渲染，不假报"一切正常"。）

## §5 新增断言

**第 225 套件 D6 组（+5，45→50）**
- D6-① 只按 `_id` 覆盖 ⇒ 5 行重导成 3 行**必残留 2 条**（证明问题真实，不是理论）
- D6-② 集合差 ⇒ 恰好清掉那 2 条、且不碰本次写入的行
- D6-③ 行数相同重导 ⇒ 待清理 **0** 条（防"每次重导都误删"）
- D6-④ 静态：清理动作必须**在写库之后**（`writtenIds.add` 的位置 < `toPrune` 的位置）
- D6-⑤ `pruned` / `pruneFailed` 必须出现在返回值里（不静默）

**第 226 套件（+3，13→16）**
- C-④ 回执说明「替换了之前的 2 条旧记录」
- C-⑤ 没清理失败 ⇒ **不得**出现告警（不能每次成功都吓人一跳）
- C-⑥ 后端报 `pruneFailed` ⇒ 页面**必须**显示告警

## §6 已知边界（如实标注，不假装解决了）

1. **老通道同病，本轮没动**：形态 A（堂食菜品统计）/ C（外卖商品销量）/ D（京东订单）都是
   "按 `_id` 覆盖"，同样会残留。它们有历史数据、改动面大（影响 3 个 handler + 已有门店数据），
   需要单独排期。**DSI-1 因为是新通道、没有历史负担，先修它。**
2. **单组上限 500 行**：`limit(500)` 取旧 `_id`；一天一个平台超过 500 行会漏清尾部。
   餐饮单店单日单平台不会到这个量级，但这是硬边界。
3. **软删不是物理删**：清掉的行 `is_deleted: true`，数据仍在（可恢复、可审计），
   但会占存储。将来可加定期清理任务。
