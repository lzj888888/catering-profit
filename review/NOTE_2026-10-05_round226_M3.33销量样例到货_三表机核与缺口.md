## 四 🔴 五条必须进规范的发现（本轮最有价值的部分）

### ① 套餐与菜品表**不能相加**（重复计算）
菜品表 R2 声明 `销售方式【单品+套餐明细】`。机器验证：套餐表的 **24 个组单品名，24/24 全部命中**
菜品表（`停车劵/包包白/双汇火腿肠/土豆/小料/梅林午餐肉/牛肉滑/米饭/红汤大锅/红汤小锅/耙牛筋（半斤）/
耙牛肉（半斤）/耙肥肠（四两）/耙萝卜/联系吧员免费停/联系吧员免费停车/自助小料/豆干/豆芽/起泡豆干/郡花/
餐位米饭/鸭血/鹌鹑蛋`，**未命中 0**）。
⇒ **"菜品表 + 套餐表"直接相加 ⇒ 虚增 887.8 元（2.61%）**，且**不会报错**。
⇒ 阶段② 落库必须**二选一**：要么只用菜品表（套餐已并入）、要么菜品表**剔除**套餐组分再加套餐表；
**推荐前者**（菜品表口径已完整，且能对上 POS 合计）。

### ② 现有解析器**认不出这张外卖表**（生产模块实跑）
用**生产模块**（非读码猜）：
```
require('utils/billParse.js').detectPlatform(饿了么门店下载表头) === null
require('utils/billParse.js').detectPlatform(美团账单表头)      === 'meituan'
require('utils/billParse.js').detectPlatform(淘宝账单表头)      === 'taobao'
```
`detectPlatform` 只认两列：淘宝 `结算金额`、美团 `商家应收款`。
饿了么门店表两列都没有 ⇒ **返回 `null`**（即阶段① 的解析链**吃不进**这张表）。
⇒ 阶段② 若支持这张表，**必须新增第三种形态**（新列常量 + 新 `SHEET` 映射 + 新等式口径），不可复用现有两条。

### ③ 🔴 唯一索引会撞（**不解决阶段② 写库必失败**）
```
idx_esd_uniq      = unique( shop_id, biz_date, external_ref_id )     ← 不含 dish_key
idx_esd_dish_key  =          ( shop_id, dish_key )
```
阶段① 写的值是：`_id = 'BILL_<shop_id>_<platform>_<biz_date>'`、
`external_ref_id = 'BILL:<platform>:<biz_date>'`、**`dish_key: ''`**（占位空串）。
⇒ 若阶段② 沿用同一个 `external_ref_id` 编码写菜品级行，则**同平台同一天的所有菜共用同一个
`(shop_id, biz_date, external_ref_id)` 三元组 ⇒ 唯一索引只允许落 1 条**，其余全被拒（或静默覆盖）。
⇒ **阶段② 必须把 `dish_key` 编进 `external_ref_id`**（如 `'DISH:<platform>:<biz_date>:<dish_key>'`），
或改为按 `_id` 确定性编码；**这条必须在投喂包里写死**。

### ④ 饿了么数值列**文本/数字混排**
588 格中 `str-num` 273 + 真 `number` 266 ⇒ **同一列里两种类型都有**。
`utils/billParse.js::toNum()` 已能处理（去逗号/¥/括号负数/空 `-`），但**上游判空逻辑（如
`Number.isFinite` 直接判）会误杀文本型数字** ⇒ 解析层必须先 `toNum` 再判。
（对照：堂食菜品表**无此问题**，数值均为真 number。）

### ⑤ 套餐表的「菜品大类」列**不可信**
同一套餐的组分被标成混杂大类。例（美团 4 人餐）：
`小料 → 锅底`、`餐位米饭 → 锅底`、`红汤大锅（真锅底）→ 抖音团购套餐`、
`联系吧员免费停 → 美团团购套餐` —— **明显错配**。
⇒ 套餐组分**只能按"套餐定义"取**（POS 后台的套餐配置），**绝不能按本表大类列归类**，
否则 M3 套餐成本卡的组分清单会**错得毫无提示**。

3. **堂食 POS 的 `销售数量 3280.3` 非整数**（合计行）⇒ 存在称重/计量菜品；
   对照 `SALES_SCHEMA::qty` 要求 **integer** ⇒ 取整口径待定（见 §五）。
