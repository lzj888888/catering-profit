# PLAN · AI 授权模型设计（`shop_ai_consent` / `shop_ai_insight`）

> 2026-10-20 · 队列 #12（原为 blocked：需控制台建表）。本文件把**设计做到"建完表就能落地"**。
> 依据：`PLAN_2026-10-20_AI路线与边界.md` §5/§6；豆包第三轮的批评「撤回后若无全链路标识，必返工」。

---

## 0 先定一个前提

老板授权的不是"用我的数据"，而是**"用我的数据做某一类判断"**。所以 `scope` 必须是**能力粒度**，
不能是一个布尔。否则以后加新能力时，旧授权会被当成"已同意"——这是隐私上最常见的越界。

---

## 1 两张表（不是一张）

| 表 | 作用 | 为什么必须分开 |
|---|---|---|
| `shop_ai_consent` | 授权本身（谁、对哪个店、同意哪些用途、何时撤） | 授权是**状态** |
| `shop_ai_insight` | T+1 预计算出的结论（可被 AI 引用） | 结论是**派生数据**，撤回时要能**一次性清掉** |

只建授权表不建结论表 ⇒ **撤回时不知道该删哪些缓存**，就会出现"撤回了但结论还在被引用"。

---

## 2 `shop_ai_consent` 字段

| 字段 | 类型 | 说明 |
|---|---|---|
| `consent_id` | string | `con_` + 随机；业务主键（不要用 `_id` 当外部引用） |
| `user_id` | string | 授权人 |
| `shop_id` | string | 授权范围是**单个店**（多店要分别授权） |
| `scope` | array\<string\> | 允许的用途：`diagnose`（异常核对）/ `pricing`（定价建议）/ `expand`（拓店校准） |
| `policy_version` | string | 老板同意的是**哪一版条款**（条款改了要重新同意，不能让旧同意自动覆盖新版） |
| `granted_at` / `expire_at` | number | Unix ms；`expire_at=0` 表示不自动过期 |
| `revoked_at` | number | `0` = 未撤回；非 0 即失效（**不删记录**，要留痕） |
| `revoke_reason` | string | `user`（老板主动）/ `expire` / `admin` |
| `client_request_id` | string | 幂等（与全仓一致） |

**索引**
- `idx_ai_consent_user_shop`：`{ user_id: 1, shop_id: 1 }` **unique** —— 一店一份授权，重复提交靠它兜住
- `idx_ai_consent_shop`：`{ shop_id: 1, revoked_at: 1 }` —— 查"这个店有没有有效授权"

---

## 3 `shop_ai_insight` 字段

| 字段 | 类型 | 说明 |
|---|---|---|
| `insight_id` | string | `ins_` + 随机 |
| `shop_id` / `month` | string | 结论粒度：**按月**（与 M1 台账同源） |
| `kind` | string | 与 scope 对应：`diagnose` / `pricing` / `expand` |
| `consent_id` | string | **产出它时依据的授权**（撤回时按它批量定位） |
| `payload` | object | 结论本体（只放"方向+幅度+引用"，**不存原始明细**） |
| `inputs_ref` | object | 指回输入（R387 契约：`{kind:'month', month}` 等） |
| `engine_version` / `bands_version` | string | R386 的解释锚点 |
| `computed_at` | number | Unix ms |

**索引**
- `idx_ai_insight_consent`：`{ consent_id: 1 }` —— 撤回时一条 `where` 就能定位全部派生数据
- `idx_ai_insight_shop_month`：`{ shop_id: 1, month: 1, kind: 1 }` —— 读当月结论

## 4 状态机（三条路径，全部要留痕）

```
grant：无记录 → 建记录（granted_at=now, revoked_at=0）
       已有记录 → 覆盖 scope/policy_version/granted_at（**不新建**，靠 unique 索引兜住并发）
revoke：revoked_at=now + reason
        + 删除该 consent_id 下全部 shop_ai_insight
        + 写 audit_log（谁、哪个店、撤了哪些 scope）
expire：读取时判 `expire_at>0 && now>expire_at` ⇒ 视为未授权（**懒过期**，不跑定时器）
```

🔴 **撤回必须同步删派生数据**，不能只翻标记。否则老板撤回后，预计算结果还在被引用——
这正是豆包指出的"全链路返工"根因。

---

## 5 最小样本门槛（k-匿名）——放在"出站"这一刻，不放在存储

```js
// 纯函数，单测锚点：canSendToModel({ consent, sample })
// sample = { lineCount, supplierCount }
// 规则：lineCount >= 5 且 supplierCount >= 3 才允许把"偏离值"送去模型
```
- 存**结论**时不受此限（结论本身就是聚合过的）；
- 只有"要把数据发给外部模型"时才校验；
- 不满足 ⇒ 退回 L0 规则话术（"这项偏离你自己的历史，请核对单据"），**不编同业对比**。

理由（豆包第三轮反例）：单店 1 个 SKU、单日 1 笔订单时，聚合值等于原始值，脱敏失效。

## 8 明确不做

- **不做"一次授权、全部能力"**（scope 必须逐项）；
- **不做全局默认开启**（默认未授权，fail-closed）；
- **不存原始明细进 `shop_ai_insight`**（只存方向+幅度+引用）；
- **不做定时清理**（懒过期即可，定时器是额外的成本与故障点）。
