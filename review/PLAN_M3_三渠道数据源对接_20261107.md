## 1 先说结论（三句话）

1. 🔴 **京东「商品销量表」的真数据从没到过。** 手上是两张别的表：一张 82 列的**秒送结算对账单**（无商品列），一张 **SKU 对账单只有表头 0 行数据**。所以 M3 里「京东哪道菜卖了多少」今天确实一片空白——不是没做，是原料没到。
2. 🟢 **团购核销的正确入口是收银台，不是平台后台。** 因为要回答的是「团购里哪道菜不赚钱」，平台核销明细只有券面额、没有菜品；**核销动作发生在收银台，只有收银台知道那顿吃了什么**。
3. 🔴 **但收银表有个更急的隐患**：《菜品销售统计》**本身不带渠道列**，渠道完全由导出时的筛选条件决定。手上这份参数行写着「订单分类：全部」「菜品下单来源：全部」，实跑后被判成**堂食**入库 265 行 / 3281 份 / 30,319.70 元 —— 如果店里外卖和团购也走这台收银机，堂食就被虚高了，而且**事后拆不开**。

## 3 三处需要纠正的印象

### 3.1 京东：给的是「钱」，不是「菜」

| 以为 | 实际 |
|---|---|
| 给过京东商品销量 Excel | 给过**结算对账单**（82 列，全表无「商品名称/单价/数量」，只有团购商品名/核销码两列且全空） |
| SKU 对账单是明细 | 27 列表头齐全、**数据 0 行**，等于空模板 |
| 契约里「京东订单导出」已支持 | ✅ 是支持的（形态 D），但吃的是**另一张表**：商家后台「订单导出」，签名列是「商品信息」+「顾客实付/订单编号」，商品混装成 `商品名,单价,数量`。**这张表我们手上没有** |

**实跑佐证**：拿 82 列对账单喂生产解析器 `detectDishShape` ⇒ 返回 **`null`**，正确落入账单暂停路径，不产商品行。它本来就不该当商品表。

> 所以队列 #112「京东商品销量表接入」**仍然 blocked 是对的**，不需要改判据，只需要您从京东商家后台导一份「订单导出」。

### 3.2 美团：真表没有

- `meituan.xlsx` 是造的 fixture（见上表第 7 行）。
- `dishIngestContract` 里 `takeaway_goods_daily` 的 `platforms` 已预留 `['taobao','meituan','eleme']`，note 写「美团外卖同名异列版也走这条」—— 那是**契约位**，不是已到货。
- 队列 #9 原文：`只剩美团销量表样例（表名+列名+口径），无样例不猜列`。

**要的东西很具体**：美团外卖商家后台 → 经营分析/商品分析 → 导出「商品销量」，要含 `商品名称 / 销量 / 销售额` 三列 + 日期列。有这份就能直接走形态 C，**零新增解析器**（淘宝那份解析器不分平台）。

### 3.3 收银表：里面可能「涉及团购」，但看不出来

您说「店里的销量表里面涉及团购」—— 从表本身看，**分不出来**：

- 15 列全是菜品维度：菜品名称 / 销售数量 / 销售额 / 菜品收入 / 菜品优惠 / 销售额构成（菜品·关联做法·关联餐盒）。**没有任何「渠道 / 支付方式 / 订单来源」列。**
- 渠道信息只存在于**顶部参数行**（R2 一段文本）：`营业日期：【2026/09/07 至 2026/09/13】；销售方式：【单品+套餐明细】；统计方式：【菜品名称】；…；订单分类：【全部】；菜品下单来源：【全部】；…`

⇒ **这份表是全渠道混在一起的**（如果这台收银机上也走外卖/团购）。总量：`销售额 33,146.20 元 / 菜品收入 30,319.70 元 / 3,280.3 份`（含「合计」行）。

而生产解析器 `detectDishShape` 的形态 A 判据只有两条：`有「菜品名称」+ 有「销售数量」+ R2 含「销售方式」`——**没有校验「订单分类」是不是「全部」**。

## 4 三渠道 × 两口径的正确分工

这不是「三张表」，是**两个问题**用**两套不同的表**回答：

| 渠道 | 回答「这块业务赚不赚钱」（钱） | 回答「哪道菜赚不赚钱」（菜） |
|---|---|---|
| **堂食** | 收银台营业汇总 / 微信支付账单（✅ 已有） | 收银《菜品销售统计》（✅ ready） |
| **外卖** | 京东对账单 ✅ / 淘宝闪购账单 ✅ | 淘宝商品下载 ✅ · 京东订单导出（缺样例）· 美团商品下载（缺样例） |
| **团购** | 平台核销明细（缺） | **收银台按「下单来源=团购」导出**（缺样例） |

**关键判断：团购的「菜」只能从收银台拿。**
平台的团购核销明细长这样：券名、核销时间、券面额、平台抽成 —— **它不知道顾客点了哪几道菜**（券是套餐，套餐消费时才知道吃了什么）。
京东对账单里的「团购商品名称 / 核销码」四列也是券级，一样给不出菜品。

所以：**要「团购 vs 堂食 哪边更划算」→ 金额级就够；要「团购套餐里哪道菜拖后腿」→ 必须收银台。**

## 5 团购核销怎么对接：三条路径（按优先级）

### 路径 A（首选 · 今天就能走）收银后台按「菜品下单来源」分开导

您的判断是对的：**团购核销动作发生在老板的收银台**（顾客到店、拿券、收银员核销、点菜、结账）。所以收银系统里一定有这笔账，而且**带菜品级明细**。

收银表顶部那段参数就是开关：`订单分类：【全部】` / `菜品下单来源：【全部】` —— 说明这套收银系统**支持按来源筛**。老板只要把筛选改成：
- 堂食 → 导一份
- 外卖 → 导一份
- 团购核销 → 导一份

三份表结构完全一样（同 15 列），**只是数据集不同**。技术上只需在导入时**多一个「这份表是哪个渠道」的单选**，解析器一行不用改。

- 成本：老板多点两下鼠标；解析器零改动
- 准确度：最高（菜品级、实际收入口径，正是 `dine_pos_dish_sales` 要的）
- 风险：**必须靠人选渠道**，选错就串账 ⇒ 要配守卫（见 §6）

### 路径 B（平台侧 · 京东已经具备，缺样例）

京东那张 82 列对账单里**已经有团购字段**：

```
19  [订单基础信息] 团购商品名称
20  [订单基础信息] 团购商品ID
21  [订单基础信息] 团购外部拓展信息
22  [订单基础信息] 核销码
```

这说明**京东的到店团购核销和外卖走同一张对账单**，靠 `对账单业务类型` / `订单类型` 区分。手上这份 115 行全是「秒送货款」（外卖），所以四列全空——**不是表不支持，是这份没团购单**。

- 价值：**如果店里做京东到店团购，不用再要新表**，同一张对账单就能吃团购金额
- 局限：只有券面额与核销码，**没有菜品**
- 动作：您从京东商家后台导一份**含团购核销期间**的对账单（业务类型会不同），我据此定签名

### 路径 C（平台侧 · 缺原表）美团/抖音团购后台导「核销明细」

- 美团：商家后台 → 团购 → 订单管理 → 核销明细 → 导出
- 抖音：来客后台 → 订单 → 核销记录 → 导出
- 能拿到：券名、核销时间、面额、平台服务费、结算金额
- 拿不到：菜品
- **用途**：只做「团购这块业务赚不赚钱」，不做菜品毛利

## 6 🔴 比缺表更急的一件事：渠道纯度

### 6.1 事实

用 `tangshi.xlsx` 真跑生产解析器：

```
形态判定 = dish_sales                      ← 判对了（确实是收银菜品表）
periodFrom 2026-09-07 → 2026-09-13         ← 区间端点正确
granularity = interval                     ← 识别为 7 天汇总，不是单日
产出 265 行 | qty 合计 3281 | amount 合计 30,319.70 元
首行 {"name":"快餐15元","qty":930,"amountFen":1184837,"salesFen":1395000,...}
```

**这 265 行会被写成 `platform='pos'`、`channel='dine_in'`（堂食）。** 而参数行明确写着「订单分类：全部」。

### 6.2 为什么会出事

- 如果这台收银机**只收堂食**（外卖在平台接单、团购券在别处核销）⇒ 现在这样是对的，没问题。
- 如果这台收银机**也记外卖和团购核销**（很常见：一台收银机管所有进店消费）⇒ 外卖和团购的销量被算进堂食，**堂食虚高、外卖侧如果又导了平台表就双计**。
- 最麻烦的是：**收银表没有渠道列，入库后拆不开**。错账不可事后修复，只能重导。

### 6.3 怎么修（不猜、可验证）

解析器读 R2 参数行里的 `订单分类：【…】` 与 `菜品下单来源：【…】`：
- 值为「全部」⇒ 不拒绝，但**回执里明确提示**「这份表是全渠道混合，堂食会被算高；建议按渠道分别导出」+ 让老板勾一个「我确认本表只有堂食」
- 值为具体渠道 ⇒ 按该渠道入库，并记录来源标签

**为什么选择「提示 + 确认」而不是直接拒收**：很多单店老板确实只做堂食，直接拒收会把人挡在门外；但这笔账一旦错就是静默错账（本仓红线），所以必须让老板**看见**这个选择。

### 6.4 需要您回答的一个问题（这决定要不要修）

> **您店里那台收银机，除了堂食，会不会也记外卖单和团购核销单？**

- 会 ⇒ 这条必须马上修，属于静默错账风险，优先级高于团购对接
- 不会 ⇒ 现状可用，只需在导入页加一句「请确认本表只含堂食」，成本很低
