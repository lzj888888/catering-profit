## 一、结论速览

1. **M3 的"账"是扎实的**：版本模型单源、引擎三副本行为等价、金额精度、截断可见降级、套餐嵌套/版本校验、跨平台重复导入防翻倍——都有守卫钉着。核心计算可信。
2. **M3 的"结论"是缺的**：复盘页只给**排行 + 阈值筛选**，不给「该砍/该提价/该推」的动作。菜单工程四象限**全仓零实现**（规范 v1.1 D14 明确「不做档位判定」，理由是 30:60:10 无可验证来源）。
3. **⚠️ 勘误（重要）**：此前三司会审与补充核查把「M3 菜品四象限页已上线」当成既有事实引用，AI 规则 #5「四象限失衡」也建立在它之上——**这个前提是错的**。全仓搜「象限」仅命中 `review/` 下我方今天的报告，产品代码零命中。
4. **一条真实的可扩展性风险**：`getDishReview` 每次**全量读该店所有销量行**再在内存里按月份过滤（代码注释自认「读的量不变」），行数随导入月数线性增长，2 万行护栏会随使用常态化触发（虽有一行提示，但复盘数据会"永久不全"）。
5. **一条静默口径风险**：套餐卡的「子卡已改版」提示**只在编辑页**；列表/详情/复盘都不标 ⇒ 套餐成本可能长期用旧版子卡，老板看不到任何异常。

## 二、审计发现

### P1-1 复盘榜全量读销量行：越用越慢，且 2 万行会常态化截断
- **证据**：`cloudfunctions/getDishReview/index.js:55-67`
  ```
  //   而**在内存里过滤与在库里过滤结果逐行等价**（listAll 本来就读该店全量行，读的量不变）。
  const salesRes = await da.listAll('external_sales_daily', { shop_id: shopId });
  const rawSales = ...; filterByRange(rawSales, bizFrom, bizTo);
  ```
  `common/dataAdapter.js:32` `LIST_TOTAL_CAP = 20000`；`index.js:167` 有 `truncated` 透传（**这一点是健康的**，页面也消费）。
- **影响**：一家 50 道菜、双平台的店，日导 ≈100 行/天 ⇒ 约 **6–7 个月**触达 2 万行护栏。此后每次打开复盘：① 读 20 页 × 1000 行（云函数 20s 超时余量被吃掉、DB 读配额消耗）；② 页面出现"数据可能不全"提示并**长期挂着**。
- **根因**：`common/dataAdapter.js` 的 `where` 只支持等值，不支持 `biz_date` 范围；加范围要动单源 + 51 份 `cx_dataAdapter.js` 派生副本（需 `sync_common` + 全量门禁）。
- **修法（低风险版）**：给 `da.listAll` 增加可选 `opts: { whereRaw }`（透传 `db.command.gte/lte`），仅 `getDishReview` 使用；索引 `idx_esd_shop_date`（shop_id+biz_date）**已存在**（`collections.js:171`），无需建索引。

### P1-2 套餐卡「子卡已改版」只提醒编辑页
- **证据**：`subpkg/biz/card/edit.js:306,780`（`comboStaleText` / `comboStaleTip`）；`subpkg/biz/card/index.js`、`detail.js`、`pages/m3/dishreview` 均无该标记。
- **机制**：套餐成本是快照（版本模型，`syncCostCard/index.js:185`「按子卡最新版本重建」需**手动**触发）。
- **影响**：子卡改价后，套餐卡在列表/详情/复盘里继续显示旧成本与旧毛利率，**无任何提示**；老板不打开编辑页就永远不知道。复盘榜里套餐菜品的毛利因此失真。
- **修法**：`getCostCard` 已返回 `byVersion` 全版本映射；在 `comboInsight` 里加一个 `stale_sub_cards` 计数（比较子卡最新 version 与套餐行记录的版本），列表给一个角标、复盘行给一行小字。改动集中在单源派生层 + 一处展示。

### P1-3 菜单工程四象限：未实现（且此前报告误称"已上线"）
- **证据**：全仓 `grep -rn "象限"` 仅命中 `review/**`（我方报告）；`specs/dev-specs/core/开发规范v1.1…:28`：
  ```
  | D14 | 品类毛利结构（菜单工程） | v1.1 只做只读「成本占比结构」；不做引流/利润/形象档位判定（30:60:10 无可验证来源，不作为阈值） |
  ```
  `getDishReview/service.js:105` 只有 `ranked.sort((x,y)=>y.grossFen-x.grossFen)`（毛利降序）。
- **判定**：这是**规范明确暂缓**，不是偷偷漏做 —— 但「只读成本占比结构」这一半是否落地也未见独立视图（现有的是排行 + 阈值筛选 + 套餐 costShare）。列 P1 是因为**下游依赖已经把它当真**（AI 规则 #5、会审报告结论）。
- **修法**：见优化方案 B-2（自店分位四象限，不引外部阈值）。

### P2-1 虚拟半成品回写缺 `stats.updated` 判据（R130 同族）
- **证据**：`cloudfunctions/saveCostCard/index.js:413-424`、`syncCostCard/index.js:365`：`doc(vm._id || vm.id || vm.material_id).update({...})` 后**未判** `stats.updated`。
- **影响**：`vm` 来自 `da.list()` 带 `_id`，正常路径没问题；若遇历史/异常文档缺 `_id`，会退化为按业务键 `doc()` ⇒ 真云静默 0 行 ⇒ 虚拟半成品成本不更新，而接口回 SUCCESS。
- **修法**：三行改动——取 `const r = await ...; if (!r || !r.stats || r.stats.updated === 0) throw ...`。

### P2-2 导出面窄：M3 只能导「成本卡」
- **证据**：`cloudfunctions/exportData/index.js:83` `SHEET_NAME = { m1_report, m3_cards, m2_compare, m2_matrix }`。
- **影响**：复盘榜（菜品销量×毛利）、外卖到手结构、套餐组成**不能导出**。会计/老板要拿去线下用的正是这三张。
- **修法**：新增 `m3_review` / `m3_takeaway` 两个 scope，复用现有 xlsx 生成链路（`export_roundtrip` 守卫已能兜住格式）。

### P2-3 免费档的"啊哈时刻"被锁在付费墙后
- **证据**：免费额度 = 20 张可算数卡（`initDb/collections.js:214`），但 `common/entitlement.js:28` `PAID_FEATURES = ['export','m3_combo','m3_takeaway','m3_dishreview']`——**复盘榜是付费能力**。
- **影响**：免费用户能建 20 张卡、看到单卡毛利色带，但**看不到任何"分析结论"**（排行/未匹配/外卖结构全锁）。M3 的价值主张在免费阶段不可见。
- **注**：这是有意的漏斗设计（v1.3 定案"不够做全菜单工程分析 —— 后者才是付费理由"）。列出来是**待决策**，不是缺陷。

### P2-4 超大单文件（可维护性）
- **证据**：`subpkg/biz/card/edit.js` **1616 行**、`pages/m3/dishreview/index.js` **983 行**、`cloudfunctions/saveCostCard/index.js` 476 行。
- **影响**：改动回归面大（现有 119 断言 + 行为守卫兜底，风险被压住，但每次改动成本高）。
- **修法**：按"纯函数外提"（R232f 已用过的手法）把 dishreview 的视图装配抽到 `utils/dishreviewView.js`；edit.js 拆"单品表单 / 套餐表单 / 导入"三块。

### P2-5 getCostCard 全表读（已优化过一次，仍有线性成本）
- **证据**：`getCostCard/index.js:20-31`（R547 把逐卡 N 次查询降为 1 次全量 + 内存分组）、`:51` `listAll('shop_cost_card')`、`:72` `listAll('shop_cost_card_line')`。
- **影响**：每次打开成本卡列表读两张全表；随版本数增长线性。短期可接受（2000 卡硬上限），长期与 P1-1 同一类问题。
- **修法**：与 P1-1 合并做（范围/增量），或给列表加"只取最新版本"的服务端过滤字段。
