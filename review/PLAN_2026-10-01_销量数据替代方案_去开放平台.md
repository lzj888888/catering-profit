## 二 为什么「不等」—— 三条理由

1. **等不起**：主体变更不在近期计划内（C6 建 prod 环境都还排在后面）。若把数据能力挂在 B2 上，等于把 M3 的付费钩子无限期冻结。
2. **规范早就留了后门**：v1.2 §M3.33 明写销量来源「**不必是 M1**」，可以是用户导出表 —— 这条正是为「拿不到 API」的情形准备的。
3. 🔴 **R174 的预留没白做**：`external_sales_daily` 的唯一键是 `(shop_id, biz_date, external_ref_id)`、
   辅助索引 `(shop_id, dish_key)` —— 这个 schema **对「API 写入」与「文件导入」一视同仁**（`external_ref_id` 可以是订单号，也可以是导入批次里的行号）。
   ⇒ **原以为「卡资质所以白建」，实际是「正好给导入用」。**

## 四 阶段 ①（推荐先做）· 账单导入 → 门店级营收

**能解决什么**：M1 的营收数字**不再靠手敲**（外卖那一半尤其烦，还要扣佣金/补贴）。

| 项 | 设计 |
|---|---|
| 入口 | 新页 `pages/import/index`（或并入 `pages/takeaway` 作第二个 tab —— **待拍板**） |
| 流程 | 用户微信里选文件 → `wx.cloud.uploadFile` 到云存储 → 云函数 `importSalesBill` 解析 → 校验 → 落 `external_sales_daily` |
| 口径来源 | **直接移植**我方已实证的解析器（`review/evidence/r163_waimai/parse_bill.py` + `r177_meituan/`），**不重新摸索** |
| 已锁口径 | ① 到手 = 商品金额 + 打包费 + 商家侧补贴 + 佣金 + 配送服务费 + 其他支出（扣减记负）② 归月按**账单日期** ③ 有效订单不含退单 ④ **美团「账单金额」≠ 外卖收入**（须按「交易类型=外卖订单」筛行）⑤ **复合列×拆分列只许取一组** ⑥ 两平台同构、账期均 3 天 |
| 两个零误差锚点 | 淘宝闪购 2026-08 / 156 行 / 到手 **3779.65**；美团 2026-08 / 97 行 / 外卖订单 50 行 / 应收 **1826.64** ⇒ **移植后必须原样复现这两个数**，否则不算交付 |
| 资质 | **无** |

### 🔴 插入前必须过「甲级门禁」（B 线序 7 已被本方案激活）

导入是**外部数据第一次走进来**的入口 ⇒ 必须与「数据可信度甲级门禁」**同一批做**，否则脏数据会污染 M1/M3：

- 通道连通 + Schema 校验 + 关键指标非空，**不过直接阻断**（fail-closed）
- 导入预览页必须显示「**识别到 N 行 / 归月到 M 月 / 合计 ¥X**」，用户**确认后**才落库（防止静默错批）

## 五 阶段 ② · 销量导入 → M3.33 单品毛利复盘（付费钩子 P1）

**能解决什么**：从「率对率（粗）」升级到「单品排名（细）」—— 这是 v1.2 明确标的**付费钩子**。

**口径已锁（v1.2 §M3.33，五条硬约束原文照搬）**：

```
单品总物料成本 = 销售份数 × 该卡 unit_cost_fen（锁定的标准成本）
单品毛利       = 单品营收 − 单品总物料成本
单品毛利率     = 单品毛利 ÷ 单品营收
```

1. **销量两个来源分开呈现**：堂食收银导出 + 外卖平台导出（🔴 只导收银会**系统性漏掉外卖那一半**）
2. **菜品名映射必须显式确认**：落 `shop_dish_mapping`（首次自动匹配 + 手工确认），🔴 **未确认行单列提示、不许静默归零**
3. **不回写**：结果不回写 M3 成本卡、不自动写 M1
4. **毛利率阈值用户自定义**（默认值仅占位，**不做成"警戒线"**）
5. **成本用卡内锁定值**，若卡用了旧价，页面须提示「该卡成本为 X 月快照」

**资质**：**无**（销量表是用户自己在商家后台/收银机导出的）。
