# R593 · 包体积判据口径修正（分包不该算进主包）

> 2026-11-01 ｜ 由 R592 的一次"卡线"暴露

## 0 一句话

**不是没空间，是尺子量错了。** 主包实际只有 **0.79 MB**（预算 1.9 MB），
旧判据把分包（1.11 MB）也算进主包预算，于是"加一个卡片就超线"。

---

## 1 怎么发现的

R592 加了一张引导卡（三行样式 + 两句文案），门禁报：

```
❌ P-① 入包总量 ≤ 预算 · 实测 1.9008 MB / 预算 1.9 MB
```

只超 **0.8 KB**。我的处置是删注释腾空间，压了两轮才过（1.9002 → 1.8999，余量约 100 字节）。

**但压完我心里不踏实**：一个卡片就能撑爆，说明这个包早就贴顶了——
那下一次任何功能都得先删点东西，这不可能长期成立。

## 2 查清：微信的规则不是这么算的

小程序打包的真实规则：

| 单位 | 上限 |
|---|---|
| 主包 | 2 MB |
| **任一分包** | 2 MB |
| 主包 + 全部分包 | 20 MB |

而本项目的 `app.json` 里 `subPackages` 配了两个 root：`subpkg/tools`、`subpkg/biz`，
`subpkg/` 下也只有这两个目录（**没有孤儿文件**）。

实测：

| | 体积 | 预算 / 上限 |
|---|---|---|
| **主包** | **0.7926 MB** | 1.9 MB（硬上限 2 MB） |
| subpkg/tools（分包） | 0.4122 MB | 1.9 MB |
| subpkg/biz（分包） | 0.6951 MB | 1.9 MB |
| 总包 | 1.8999 MB | 20 MB |

**主包连一半都没用满。**

旧判据 `入包总量 ≤ 1.9MB` 把三者混成一个数，等于**用主包的尺子去量总包**。

## 3 为什么这条必须修（不是"放宽一点算了"）

如果留着，后果是**逼人持续做错事**：

- 每加一个功能就得删注释 / 删文案腾空间；
- 而注释里记的是"为什么这么写"（本仓最贵的东西）；
- 用可维护性换体积，换来的却是**一个根本不存在的空间约束**。

> 判据口径错了，比没有判据更糟 —— 它会让人以"守规矩"的名义做损害。

## 4 改成了什么

按微信规则**分档**，而且**分辨力比原来更强**（不是简单放宽）：

| 判据 | 守什么 |
|---|---|
| **P-①** 主包 ≤ 1.9 MB | 主包体积，**排除所有分包 root** |
| **P-①b** 🔴 每个分包 ≤ 1.9 MB，且 `subpkg/` 下**无孤儿文件** | 新增。孤儿 = 不在任何 `subPackages.root` 下的文件，**它们会被打进主包** |
| **P-①c** 总包 ≤ 20 MB | 微信总上限（原来完全没判过） |
| **P-②** 各档预算自洽 | 改常量绕过（主包/分包/单条目/总包四档都校验） |
| **P-③** 主包内单个顶层条目 ≤ 1.2 MB | 保持；但**只看主包**（分包体积由 P-①b 管） |

### 那条"孤儿检测"是这次最值钱的

原来的判据**不可能发现"分包配置漏了"**：
因为它是把所有文件加起来算总数，配置对不对都不影响那个总数。

现在只要有人新建 `subpkg/xxx/` 却忘了在 `app.json` 注册，
那批文件就会**悄悄进主包**（而开发者以为它是分包）——P-①b 直接点名报出来。

> 顺带一个 fail-closed：`app.json` 解析失败 ⇒ `subRoots` 为空 ⇒ P-①b 判红，不会静默放过。

## 5 断言数

`check_pack_size` 11 → **13**（+P-①b、+P-①c；P-① 语义改写）。已同步知识存储点。

## 6 教训

> **看到"再加一点点就超了"，先怀疑尺子，别急着扔东西。**

这条和本仓反复出现的「判据钉数量 / 钉写法」是同一个病根：
**判据没有对准它真正要守的东西。** 只是这次代价更隐蔽——它让人删注释，而删注释不会报错。
