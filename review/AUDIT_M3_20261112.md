## 一、结论先说

**计算层是可信的；跨模块的口径是不可信的。**

单点公式（净料成本、BOM 汇总、毛利率）有锚点、有 selftest、精度统一走「分」，这部分抽查未发现错。
问题全部出在**同一个数在不同页面用不同口径算**，以及**一个没有上界的闸门放行了失真的对比**。

| 维度 | 判定 | 依据 |
|---|---|---|
| 单点计算正确性 | 🟢 绿 | `calcBom/selftest.js` 有锚点用例；金额一律整数分；`netUnitCostWan` 4 位精度 |
| 跨模块口径一致性 | 🔴 红 | 发现 A / B / C，均可用真实模块复现 |
| 页面状态完整性 | 🟡 黄 | 15 页中 12 页有 try/catch；4 页无空态（多为表单页，非缺陷） |
| 门禁覆盖 | 🟡 黄 | 222 个守卫里 43 个是页面桩真跑型；**4 个页面零桩型守卫**（含对账） |
| 死链 / 入口可达 | 🟢 绿 | 28 处跳转目标全部存在于路由表；15 个页面均有页内入口 |
| 文案解释充分度 | 🟢 绿 | 口径文案偏"长"而非"缺"（如 `netHint` 已 200 余字） |

## 二、发现 A（红）对账覆盖率闸门没有上界，菜单毛利率被停售菜稀释

### 现象
对账页（`subpkg/tools/recon`）的覆盖率 = `卡数 ÷ 在售菜品数`，闸门只判 `< 0.6` 就抑制，
**没有判上界**。而菜单标准毛利率的分母是**全部成本卡**（含早已不卖的菜）。

### 证据（可复现）
```
node -e "..."   # 见 §六 复现脚本 1
菜单标准毛利率 = 32%     （真值应为 60%）
账本实际毛利率 = 60%
覆盖率 coverage = 3.33  ⇒ 闸门(<0.6) 判：放行
对账结论 suppressed = false
  差值 = 28 pp / 25200.00 元
```
构造：30 道在售菜（60% 毛利）+ 70 道停售老卡（20% 毛利），老板**诚实**填了「在售 30 道」。

### 根因
1. `utils/reconDerive.js:101` —— `else if (Number(coverage) < 0.6)`，只有下界。
2. `calcMenuMargin` 的输入是 `getCostCard()` 的**全部最新版卡**，卡上没有"在售/停售"字段 ⇒ 系统无法区分。
3. 覆盖率语义上应是「已建卡的在售菜 / 在售菜」，实际是「历史累计全部卡 / 在售菜」，**可能远大于 1**。

### 影响
老板看到的不是"卡建多了"，而是"实际毛利比标准高了 28 个点、差 25200 元"——
一个**完全错误且金额巨大**的诊断，会把他推向"我是不是成本录低了/偷工减料了"的错误方向。
这与 R298X 修过的「覆盖率文案张冠李戴」是同一族：**闸门放行了不该比的两个数**。

### 建议（按改动成本排序）
1. **最小改动、立刻消除静默误导**：`coverage > 1.2` 追加一个 reason（如 `coverage_over`），
   文案直说「你建了 N 张卡，但在售只填了 M 道 —— 是不是有停售菜没清卡？先把在售菜品数填准，
   或删掉不卖的菜」。
2. 中期：给成本卡加「在售」标记（或"本月有销量"），菜单毛利率分母只取在售卡。
3. 不建议现在动分母算法——它牵动 `reconDerive` 的 selftest 锚点与对账页文案，属独立一轮。

## 三、发现 B（黄→偏红）对账两侧不在同一个时间截面

### 现象
对账比的是两个毛利率：
- **M1 侧**（实际）：`calcActualDishMargin` 用 `ledger.result.material_cost_fen` —— 月报**冻结**的数。
- **M3 侧**（标准）：`calcMenuMargin` 用 `getCostCard()` —— 每张卡的**最新版本**，随改价实时变。

一侧冻结、一侧实时，改一次原料价，差值就凭空出现。

### 证据
```
【同一笔 8 月生意，什么都没变，只因为 9 月改了原料价】
  账本实际毛利率（M1 冻结）= 60%
  菜单标准毛利率（M3 最新卡）= 33.33%
  ⇒ 对账差值 = 26.67 pp / 800.10 元   suppressed=false
  对照：若用 8 月当时在用的 v1 卡 → 菜单 60%，差值 0 pp（自洽）
```

### 影响
老板 9 月改完原料价，回看 8 月对账，会看到"差了 800 元、26 个点"——
而 8 月当时两边本来完全一致。**这会让他对整个对账功能失去信任**（第二次就不看了）。

### 建议
对账页在标题/差值旁**明说**：菜单侧用的是"今天的卡"，账本侧是"当时的账"，
所以改过价的月份，差值是「改价影响 + 真实差异」的混合，不能直接当"我哪里做错了"。
若要做准，需按期取卡（`getCardVersions` 已有版本与创建时间，具备条件），但那是独立一轮的量。

## 四、发现 C（黄）排行榜历史月份毛利被后来改价追溯改写

### 现象
`getDishReview/service.js:33-39` 取「同 card_code 版本最大者」算成本，与「你正在看哪个月」无关。

### 证据
```
看 2026-08 的榜（v1 成本 12 元 / v2 成本 20 元，8 月卖 100 份、收入 3000 元）：
  v2 口径：成本 2000 元，毛利 1000 元，毛利率 33.33%，snapshot_month=2026-09
  按 8 月当时真在用的 v1 复算：毛利 1800 元，毛利率 60.00%
  ⇒ 同一笔 8 月生意，被 9 月的改价追溯改写，差 -800 元
```

### 现状评价（不算 bug，但没讲清）
页面**已经**挂「该卡成本为 X 月快照」提示（`index.js:327-341`，R547/M7 修过基准），
所以"成本是新的"这件事老板看得到。缺的是**后果说明**：
提示读起来像"成本旧了一点"，实际含义是"**你 8 月的毛利被重算了，跟 8 月月报对不上**"。

### 建议
把提示从「该卡成本为 9 月快照」扩成一句带后果的话：
「这张卡 9 月改过价，本月毛利按新成本重算，与当月月报的毛利会不同」。
（口径本身要不要改成 as-of 取版本，属产品决策，建议先讲清再决定，不急着动算法。）

## 五、发现 D（黄）4 个页面零桩型守卫，其中对账最要紧

222 个 `tools/check_*.js` 中，43 个是**页面桩真跑**（`loadPage` / `new Function` 注入 wx，真跑 handler 与载荷），
其余 179 个是字面量断言（查类名、查文案键、查调用名）。

| 页面 | 桩型守卫 | 字面量守卫 |
|---|---|---|
| 成本卡编辑 | **10** | 17 |
| 外卖单均 | **5** | 13 |
| 排行榜 / 渠道营收 | 3 | 7 / 3 |
| 枢纽 / 成本卡列表 / 批量导入 / 版本历史 / 原料编辑 / 团购 | 2 | 5 / 12 / 1 / 2 / 7 / 2 |
| **原料列表** | ❌ 0 | 6 |
| **原料选择** | ❌ 0 | 1 |
| **原料批量** | ❌ 0 | 1 |
| **对账** | ❌ 0 | 2 |

对账页承载发现 A/B 这两条最贵的口径问题，却是**唯一没有任何行为断言**的核心页。
它的计算逻辑（`reconDerive`）有 selftest（`selftest_m3_recon` 33 断言），
但**页面把它们串起来的那一段**（读 shop_switch、算 coverage、选文案键、渲染）没有真跑过。

建议：下一轮给对账页补一个页面桩守卫（约 15~20 断言即可覆盖 A 的文案分支与 B 的提示分支），
成本低、收益直接——修 A/B 时它正好当验收。

## 七、建议的动手顺序

| 顺序 | 事项 | 成本 | 收益 |
|---|---|---|---|
| 1 | 覆盖率加上界 + 一句人话（发现 A 的 1 号建议） | 小（改 `reconDerive` 一个分支 + 一个文案键 + 重跑 selftest） | 立刻消除"虚高 28 个点"的误导 |

| 3 | 对账页讲清"两侧不同时间截面"（发现 B） | 小（纯文案） | 避免改价后被当成系统算错 |

| 5 | 成本卡「在售」标记 / 分母改用有销量的菜 | 中（动数据模型与算法） | 根治 A，但需一轮完整设计与变异测试 |
