# R389 · 出参契约漂移扫描（代码有、文档没有）

> 2026-10-20 · 起因：R388 审计发现 `getCardVersions` 的出参文档漏了 `inputs_ref`。
> 既然能漏一个，就说明**这一层没有守卫**——本文件把它一次性扫出来并分级。

## 一、怎么扫的

对 `cloudfunctions/<fn>/index.js` 里每处 `ok({...})` 抽取**顶层键**（剥注释后花括号配平），
再与契约文档该行的出参列做包含比对。

## 二、先排掉噪音（30 个候选里 24 个不是问题）

| 类型 | 例子 | 结论 |
|---|---|---|
| **公共信封** | `shop_id` / `user_id` / `client_request_id` | 不是漂移：全局约定，逐行重复只会让表更难读 |
| **明细/别名** | `rows` / `list` / `affected` / `groups` | 表里用 `list[]` 概括即可，不是缺陷 |
| **内部量** | `scanned_cards` / `scanned_at` / `refreshed` | 诊断用，消费方不依赖 |

## 三、真漂移（只保留一类：**前端必须据此判断的标记**）

判据：**少了它，前端会把"不完整/降级"当成"正常"**。这类才是必须写进契约的。

| 函数 | 漏掉的标记 | 漏掉的后果 |
|---|---|---|
| `getCostCard` | `truncated` | 已达 2 万行护栏时，前端会把"少了几张卡"当成完整列表 | 
| `getDishReview` | `truncated` / `coverageA` / `coverageC` / `unmatched` | 复盘榜会把"部分覆盖"当成全量，毛利榜据此下结论 |
| `getSalesBills` | `truncated` / `summary` | 同上 |
| `getShopContext` | `no_shop` | 前端分不清"没有店铺"与"读失败" |
| `manageShop` | `replayed` | 幂等回放与真实执行无法区分（审计时最需要） |
| `importSalesBill` | `platform_missing` / `dup` | 平台识别失败会被当成"没有数据" |
| `exportData` | `format` / `encoding` / `content` | 导出件形态不明，前端只能猜 |
| `saveCostCard` / `saveMaterial` | `deleted`（软删分支出参） | 删除成功与普通保存成功无法区分 |

## 四、这一轮做了什么

- 只修了 **1 处**：`getCostCard` 的 `truncated`（与 R387/R388 同一函数族，顺手归位，并写明"不得当完整数据"）。
- 其余 7 组**没有一次改完**：契约文档是写码 AI 的输入基线，一次改 8 行容易改错语义；
  已作为队列 **#15** 交给自驱轮次，逐条带"漏掉的后果"去改，改一条验一条。

## 五、为什么不加机器守卫

想做"出参键 ⊆ 文档出参列"的全量守卫，但实测**误报 24/30**（公共信封 + 明细别名）。
要压到可用，得引入"信封白名单 + 别名表"，那就是**把文档再抄一遍**，比漂移本身更难维护。
⇒ 结论：**这一层保持人工审 + 定期扫描**（本文件就是扫描脚本的产物），不设强判据。
只有"三处必须同形"这种**可枚举**的（R387 的 `inputs_ref`）才值得写判据。

## 六、复跑方式

扫描脚本逻辑：剥注释 → 花括号配平取 `ok({...})` 内顶层键 → 与契约行出参列比对。
需要复现时重跑本节脚本（约 40 行 Python，不入仓，避免和 `tools/` 的守卫体系混淆）。
