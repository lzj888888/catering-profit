## 三、豆包「从头重做」规划（S1 原文 + 我的纠偏）

> 豆包 S1 原文（`豆包_M2_s1_规划.md`）：

**① 三块模块边界**
- 已有铺面正向模块：承接门店经营数据，输出保本点、人效坪效等核心指标及解读。
- 寻找铺面反向模块：录入待租铺参数，倒推达标所需营业额、成本管控阈值。
- 矩阵 what-if 模块：支持多参数联动调整，输出多情景盈亏测算结果。

**② 必填最小化与小白友好原则**
- 仅核心测算字段设为必填，非必填参数预置行业默认值，无需用户填报全量数据。
- 所有输出配直白中文结论，统一数值判定规则，弱化专业术语降低使用门槛。

**③ MVP→增强→打磨 实施路线**
- MVP：跑通单店三类模块核心逻辑，保证数出一源、指标与结论匹配。
- 增强：补全连锁口径、自定义维度、参数配置等扩展能力。
- 打磨：清理冗余代码、优化交互、覆盖边界场景校验。

**我的纠偏 / 补充**：
- 豆包三块边界与我们的需求（A1/A3/C9）完全一致，采纳。
- **必填最小化**应锚定你 R296 上明确说的"房租/人数/工资/面积"四项，而非让 AI 自行决定——否则又会冒出 L2 明细表这类"自加输入"（见第四节纠偏 1）。
- **路线**我细化成下面的"具体整改方案"优先级排序。

## 四、豆包整改清单（S2 原文 + 我的 3 处纠偏）

> 豆包 S2 原文（`豆包_M2_s2_整改清单.md`）：

1. L2 固定支出未入引擎 → 改造 `buildPresetParam` 读 fixedRows → **P0**
2. verdict 文案串台 → 按最差维度匹配文案 + 0 值排除优秀 → **P0**
3. BANDS.manage 连锁口径致单店偏高 → 单店/连锁双分档，下调小微阈值 → **P1**
4. 城市系数乘手填工资 → 冻结错误逻辑，确认后区分预设/手填 → **P1**
5. 矩阵无独立水电维度 → 新增独立水电维度，移除房租派生 → **P1**
6. 反推死代码 → 清理并合 main → **P2**
7. 拍板1：管理费单店/连锁双分档 8. 拍板2：手填工资不乘城市系数

**我的 3 处纠偏（重要，否则会改错方向）：**

**纠偏 1 — 明细表不进引擎：不要"硬塞进引擎"，先判定它该不该存在。**
- 该 L2 明细表是**早期 AI 自加的输入项**，你 R296 上明说"准确填员工人数/工资/房租/面积"——**从没要过"每月固定支出明细表"**。
- 它和主字段重复（房租已在主字段；人工 = 人数×工资已由引擎派生），且当前"界面显示已计入、实则没进引擎"是**信任陷阱**。
- 正确做法二选一，需你拍板：
  - **(a) 删除 L2 明细表**（推荐，最干净，与你"填准确四项"对齐，消除信任陷阱）；或
  - **(b) 降级为"实际支出备忘（明确标注：不参与测算，仅作对照）"**，避免误导。
- 豆包方案"改造 buildPresetParam 读 fixedRows"会制造**双计风险**（用户既填主字段又填明细，引擎以谁为准？），我不建议直接采用，除非先定清楚口径。

**纠偏 2 — 独立水电维度不是"缺陷 P1"，是"设计拍板项"。**
- R296-D 已查证：矩阵倒推所需营业额**已实现**；"独立水电维度"是改**引擎契约**的设计决策，你原话"人工水电等"的"等"是软化表达。
- 豆包把它列为 P1 缺陷属误判。应放进**拍板清单**，不该擅自改引擎。

**纠偏 3 — 城市系数乘手填工资：与豆包结论一致，采纳。**
- 手填实际工资**不乘**城市系数，仅预设基准工资乘系数。这个是明确的口径 bug，直接修。
