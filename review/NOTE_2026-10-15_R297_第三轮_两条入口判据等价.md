## 一、漏洞：M2 两条入库路径，判据只守了一条

| 项 | 内容 |
|---|---|
| 位置 | `cloudfunctions/savePlan/validate.js`（原只判 `typeof number && isFinite`） |
| 对照 | `cloudfunctions/calcSandbox/validate.js::checkClean`（有完整范围判据） |
| 触发 | 老板在开店沙盘把毛利率填 150 / 100.5、房租填负数、年限填 0 |
| 后果 | **假快照落库** |

**为什么这次比以前三次都重**：`savePlan` 是**写操作**，且它**服务端自算快照**（内联引擎副本）。
所以越界值不但不会报错，还会被算成一个"能看但错"的数，**存进方案库**，
方案列表 / 多方案对比页从此拿它当数 —— 前三次（建店年限、出成率、矩阵分支）只影响**当次显示**。

**实测**（探针 `_probe_tmp/r297_saveplan_range.js`）

| 毛利率 | 修复前 | 修复后 |
|---|---:|---|
| 65（合法） | 放行 · 快照保本 42,564.11 元 | 放行 · 42,564.11 元 |
| **150** | **放行 · 快照 18,444.45 元** | ❌ 拒 |
| **100.5** | **放行 · 快照 27,529.02 元** | ❌ 拒 |
| −20 | 放行（引擎返回 null） | ❌ 拒 |

**且保存链路不依赖计算成功**：`pages/sandbox/index.js::onSavePlan` 只校验方案名
⇒ 老板填 150、点「计算」报错、但「保存」照样成功 ⇒ 假快照照样落库。

**同族病第四例**（同一个病：单源判据写了、被**另一条入口**架空）：

| # | 轮次 | 单源在哪 | 被谁架空 |
|---|---|---|---|
| 1 | 第一轮 | `indicatorRef.BUILD_DEFAULT_YEARS` | 前端 `sandbox/index.js` 硬兜 `\|\| 1` |
| 2 | 第一轮 | `saveCostCard/validate.js` 的 (0,100] | 前端只送 `net_unit_cost` 快照，出成率不上云 |
| 3 | 第二轮 | `calcSandbox/validate.js` 全套判据 | 云端 `action:'matrix'` 另一分支 |
| **4** | **第三轮** | **`calcSandbox/validate.js` 全套判据** | **云端 `savePlan` 另一条写入口** |

### 修法

- `savePlan/validate.js` 新增 `checkParamRanges(p, isReverse)`：白名单取自 `indicatorRef` 单源
  （`CITY_KEYS`/`BIZ_KEYS`/`FIXED_KEYS`/`VAR_KEYS`/`BUILD_KEYS`）+ fen 非负整数 + pct ∈ [0,100] +
  年限 1~20（缺省补 `BUILD_DEFAULT_YEARS`）+ 反推专属（客单 > 0 / 座位 > 0 / open_days 1~31 /
  租金率 (0,100] / 坪效 ≥ 0）+ 反推不得含 `rent`（重复计租）。
- `pages/sandbox/index.js` 新增 `badParamOf(p)`：**计算入口与保存入口都前置体检**，给人话
  （云端拒了也只会被 `utils/api.js` 覆盖成通用文案，R271 ⇒ 老板不知改哪一格）。

**为什么是副本而不是共享文件**：每个云函数是**独立上传包**，`savePlan` 无法 require `calcSandbox`
的 `validate.js` ⇒ 用项目既有范式「**副本 + 守卫钉等价**」（同 `utils/bizPreset.js::BUILD_DEFAULT_YEARS`
前端副本的做法）。

## 二、新增守卫：`tools/check_m2_entry_parity.js`（47 断言）

**核心 = 同一张用例表双跑**：16 个用例分别构造「clean 形态」与「param_json 形态」，
喂给 `calcSandbox.validateClean` 与 `savePlan.validateInput`，**两者判决必须同向**（漂移即红）。

| 段 | 内容 |
|---|---|
| P | 12 条：模块可 require、`checkParamRanges` 在位且被调用、页面 `badParamOf` 在两个入口都调、savePlan 确实自算快照 |
| A | 16 例双跑一致（含边界 0 / 100、非整 100.5、负数、年限 0 / 99 / 2.5、白名单、重复 key、反推含 rent、年限缺失） |
| B | 9 类越界**逐个必须拒**（真执行，非文本匹配）+ 2 例不许误杀（合法 / 年限缺省归一） |
| C | 变异互证：绕过校验确实算出假快照，且**比合法值低**（方向 = 更好看 ⇒ 会误导决策）；年限缺失时两入口归一后**同数** |
| D | 单源（白名单不硬编码枚举、上限常量各只定义 1 处）、扫描面非空、断言数 ≥ 25 |

**变异回灌（证明非假绿）**：拿掉 `checkParamRanges` 调用 ⇒ **11 条断言转红**（P-⑨ + A-②③④⑦⑧⑨⑩⑪⑫⑬⑯）；
还原后 47/47 全绿。

## 三、本轮核过、判定**非漏洞**（登记，勿重复开挖）

1. **`saveCostCard` 的 `calc_mode` 静默兜底** —— 代码自述「本仓唯一已知会静默算错成本的开口」，
   **R81 已堵**：白名单只认 `'A'`/`'B'`，其余（`'b'`/`2`/`'C'`/空/缺失）一律响亮拒。
2. **`saveCostCard` 的 `target_margin_pct` 无范围判据** —— 但**云端零消费点**（只写不读的死字段，
   `grep` 全仓无读取）⇒ 不参与算术、不产错数。
3. **`syncCostCard`（M3 同步链路）** —— 客户端入参只有 `card_code` / `material_id`（**无裸数字**），
   数值全部来自已校验的卡文档；引擎对 `batchOutput` 有 `> 0 ? : 1` 兜底 ⇒ 无除零。
4. **`saveLedger`（M1 写入口）** —— 已是严格「非负整数分」校验（`isFenNonNeg`），无范围缺口。
