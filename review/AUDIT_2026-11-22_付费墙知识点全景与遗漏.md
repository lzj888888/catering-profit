# 付费墙知识点全景与遗漏审计

> 2026-11-22 · 只审不改 · 全部结论带代码/文档证据，无一条凭印象
> 触发：李老师「小程序里付费墙这块梳理一下，看看有没有遗漏的知识点」
> **修订**：2026-11-22 晚 · 经三司会诊（豆包 / DeepSeek / 巴迪），P0 由 5 条收敛为 3 条硬门槛 + 2 条降级，新增 3 条会诊独有发现。裁定过程见 `AUDIT_2026-11-22_付费墙三司会诊裁定.md`。
> 结论先行：**墙本身很扎实，墙后面那条收钱链路只有骨架。** 12 套守卫里 9 套守「墙」和「判定」，接支付必经的 5 个环节无人守。

## 1 先把「付费墙」拆成五层（这是最容易漏的认知）

多数人把付费墙理解成「弹不弹窗」。实际上它是五个独立的系统，各有各的失败模式：

| 层 | 回答什么问题 | 载体（单一真相源） | 失败模式 | 本仓守卫数 |
|---|---|---|---|---|
| ① 城墙 | 哪些能力收钱、哪些永远免费 | `entitlement.PAID_FEATURES` + `paywall.PAYWALL_TYPES` + `feature_permissions.plan_free.limits` | 云端登记了付费、前端弹不出墙（曾长期如此）；或反过来把免费功能锁了 | 5 |
| ② 判定 | 这个用户现在解不解锁 | `entitlement.isPaid(expire_at)` ← `shop_entitlement.expire_at` **唯一口径** | 各函数各写一遍 → 谁算付费由各函数自己说了算；读库失败吞异常 → 付费用户被静默降级 | 4 |
| ③ 交付 | 钱怎么进来、权益怎么发出去 | `shop_payment_flow` 订单 + `payCreateOrder/Callback/Renew/ExpireNotify` | 付了没到账、到账没发、发重了、退不了 | 1（只查结构 stub） |
| ④ 经营 | 卖什么价、卖哪档、转化多少 | `SEED_PLANS` 5 档 + 埋点 | 只卖得出一档；漏斗看不到成交 | 1（只查埋点存在） |
| ⑤ 合规 | 这么卖合不合法、会不会被驳回 | 虚拟支付资质 + iOS 政策 + 退款文案 + 提审静默 | 用普通支付收虚拟商品（违规下架）；提审期出现价格（驳回） | 2 |

> 🔴 **本仓最值得记住的一句**：①②层做得好，只能保证「不给白嫖、不误锁人」；**能不能真收到钱，全在③④⑤**。当前 ③ 层只有 `ENABLE_REAL_PAYMENT = false` 的骨架。

## 3 遗漏清单

### ⚠️ 前置认知（三司会诊新增，先看这条）

**现有 `payCallback` 是按「普通微信支付 v3」写的，不是虚拟支付协议。**
证据：`payCallback/service.js:10-12` 注释 = `Wechatpay-Signature` + RSA-SHA256 + `total_fee` + `attach`；而小程序虚拟支付是另一套接口族（`OutTradeNo / Env / WeChatPayInfo / GoodsInfo`），下单、发货推送、查单、退款四组接口都不同。
⇒ 规范 §9 B2「注入官方验签器即可，其余逻辑不改」**与 B1 那句「前端一行不改」是同族错误**。接支付不是改开关，是一次独立开发（验签、字段映射、返回报文三处都要重写，P0-2 的 attach 方案也要按虚拟支付字段重设计）。

### 🔴 P0 · 接支付前硬门槛（3 条，会诊三方零分歧）

**P0-1 回调会撞 `order_no` 唯一索引，且原 pending 单不回写**
- 证据：`initDb/collections.js:70` 有 `idx_pay_order unique{order_no}`；`payCallback/service.js:89` 在回调里 **insert 一条新流水**，`order_no = body.out_trade_no`（`payCallback/index.js:58`）= 下单时已存在的那张 pending 单的号。
- 后果：唯一索引冲突 → 抛错 → 返回 `FAIL` → 微信持续重试 → 永远发不出权益。即使绕开索引，订单页也会出现「pending + paid」两条同号单。
- 知识点：**回调必须「更新原单」而不是「另插一单」**；幂等键用 `transaction_id`，主键仍用 `order_no`。

**P0-2 `plan_id` 来自回调 `attach`，且金额完全不校验**
- 证据：`payCallback/service.js:81` `daysOfPlan(p.planId)`，`planId` 取自 `body.attach || body.plan_id`；而 `payCreateOrder/index.js:51-61` 写订单时**没有 attach 字段**，也没把 plan 传给支付网关。
- 后果：接上真实支付后 `attach` 恒空 → `daysOfPlan('')` 回落 30 天 → **季卡年卡都只发 30 天**。金额同样不比对（`amountFen` 收进来但没跟订单 `amount` 比），签名只证明「这笔钱是微信收的」，不证明「这笔钱买的是这档」。
- 知识点：**回调的唯一可信输入是 `out_trade_no`**；用它反查订单，从订单拿 `plan_id`/`amount`，再校验回调金额 == 订单金额，不等则拒 + 告警。

**P0-3 单次诊断档的 `grants` 分流没实现**
- 证据：`SEED_PLANS` 里 `plan_diag_single` 是 `days:0, grants:'diag_credit', diag_credits:1`（`collections.js:263`）；`initDb` 注释 `:247-250` 明写「`payCallback` 必须按 grants 分流……若不特判就按 days:0 算 expire_at，会把已付费的月卡当场清零」；但 `payCallback/service.js:86` 只有一条 `calcNewExpireAt(...)`，**没有任何 grants 分支**。
- 后果：用户买 19.9 单次诊断 → `newExpireAt = max(now, now) + 0 = now` → 权益等同没买；若他同时有月卡，`updateExpire` 直接把月卡写成 `now` ⇒ **已付费月卡当场清零**（静默、无报错）。
- 这是全仓**唯一一处「代码注释已预警、代码仍未实现」的钱级缺陷**。

**P0-4 权益加时是「先读后写」，并发支付会丢一次时长**（会诊独有发现，两家都没提）
- 证据：`payCallback/index.js:79-92` = 读 `expire_at` → 算 `newExpireAt` → 写**绝对值**。
- 后果：用户连点两档 / 双端同时支付 ⇒ 两个请求读到同一 `currentExpireAt`，后写覆盖先写 ⇒ **买两次只加一次**。不报错、不留痕，用户只发现自己「少了一个月」，事后无法解释。
- 知识点：资产类字段（到期时间、额度）的并发写必须用**乐观锁**（`where({_id, expire_at: 旧值})`，`updated===0` 重读重试）或原子自增；`inc` 不适用（过期用户的起点不同）。

### 🟡 P1（原 P0-4 / P0-5 · 经会诊降级：不是「必炸」，但代码必须现在改）

> 会诊分歧：豆包判「无主动查单」高估（微信有梯度重试），DeepSeek 判 P0-5 高估。巴迪复核后采纳 —— 这两条**后果真实、触发却是低频/低损**，故降级；但**修复动作不变**，因为它们兜的是 P0-1~3 修好后剩下的盲区。

**P1-4 没有主动查单 / 对账，只有被动回调**
- 证据：全仓 `grep queryOrder|tradeQuery|orderquery` 零命中；`payCallback` 头注自述「只做两件事：写流水 + 更新 expire_at」。
- 后果：回调丢失/验签配置错/网络抖动 → 用户付了钱、权益没到 → 只能等他投诉。规范 §6 把「支付成功未到账」列为无条件全额退，但**没有检测手段，退也退不出来**。
- 知识点：虚拟支付必须有「回调 + 定时补单」双通道；补单任务用同一幂等键，天然安全。

**P1-5 `transaction_id` 无索引、无唯一约束**
- 证据：`shop_payment_flow` 索引只有 `idx_pay_user / idx_pay_order(unique) / idx_pay_shop`（`collections.js:68-72`），而幂等预检是 `where({transaction_id})`（`payCallback/index.js:65`）。
- 后果：① 每次回调全表扫；② 微信并发重发时两个请求都查不到 → 都发权益 → **一次付费两次开通**。
- 知识点：幂等键必须**落在数据库唯一索引上**，代码预检只是优化，不是保证。

### 🟢 P3 · 认知项（写进规范即可，不用改码）

1. **到期边界**：`expire_at <= now` 即过期（`isPaid` 是严格大于）；展示转北京时间，判定一律服务端 UTC。
2. **两种「永久」不要混**：已出的诊断报告「永久可看」；导出/复盘是「到期即锁」。混了就会写出「到期还能导出」的错误需求。
3. **免费期 ≠ 关功能**：`FREE_ACCESS=true` 只关售卖，`PAID_FEATURES`/订单表/套餐表全部保留。R602 曾把两者一起关掉。
4. **权益读取成本**：翻成收费后 `fetchEntitlement` 每进一个页面一次 DB 读，**且当前无缓存**（`utils/entitlement.js:14-30`）；免费期被 `FREE_ACCESS_MODE` 短路完全掩盖，翻转当天调用量与首屏延迟同时上涨。需要本地 5 分钟缓存 + 支付/退款后主动失效。
5. **不因欠费删数据**：规范 §7 三条硬规矩已写，但工程上要确认没有「到期清理」的定时任务（当前没有，保持没有）。
6. **`shop_refund` vs `order_refund`**：规范 §6 写 `shop_refund`，仓里实际集合是 `order_refund`（`collections.js:19, 73-76`）。**以代码为准**，文档需改，否则将来有人照文档建新表 → 双表分裂。

## 4 一句话总结每层的「及格线」

| 层 | 及格线 | 当前 |
|---|---|---|
| ① 城墙 | 收费点全部登记、免费点全部不拦、M2 永不加墙 | ✅ 过 |
| ② 判定 | 单一函数判定、失败响亮、免费期一个开关 | ✅ 过 |

| ④ 经营 | 至少两档可卖 + 漏斗能看到成交 | ❌ 只有一档 + 漏斗断底 |
| ⑤ 合规 | 虚拟支付资质 + 购买前明示 + 提审静默 + 退款入口 | 🟡 文案与静默已做，资质/入口待阶段 B |

## 5 建议的动手顺序（会诊修订版，全部不依赖商户号）
