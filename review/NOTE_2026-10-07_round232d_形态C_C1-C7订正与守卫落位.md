## 一、缺陷定性：为什么它比「还没做」更坏

```
v1.6 §3.4:  C ← 列名含 '商品名称' 且 列名含 '商品销量'
真样例 R1:   … '商品名称' … '销量' … '销售额' …
                            ↑ 叫「销量」，没有「商品」二字
⇒ 判定落空 → 返回 null → 前端提示「未识别的形态」
```

**三重遮蔽**：

| 层 | 表现 | 为什么看不出是 bug |
|---|---|---|
| 判定 | 返回 `null`（fail-closed） | fail-closed 本身是对的 ⇒ 没人会怀疑它 |
| 叠加 | 表头在 **R1**（C-2），`detectDishShape` 只扫 **R3** | 即使列名改对，仍扫不到 ⇒ 两处错互相掩护 |
| 呈现 | 界面提示「未识别」 | 与「形态 C 尚未实现」的提示**完全一致** ⇒ 用户/写码方都当能力缺失 |

> 这类缺陷的判据价值：**fail-closed 是对的，但「fail 的原因」必须可区分**，
> 否则「本可识别却判定写错」与「真的没这功能」在界面上无法分辨 ⇒ 缺陷被无限期搁置。

## 四、🔴 对提案的一处**实测订正**：区分项是冗余防御

提案称「必须保留区分项『不含 `销售方式`』」。锚点 C-1i~C-1l 实测：

- 形态 A 表头**不含** `销量` / `商品销量`（它用 `销售数量`）；
- 形态 C 表头**不含** `销售数量`（它用 `销量`）。

⇒ 两套列名**天然不重叠**，删掉区分项后形态 A **仍返回 `dish_sales`**（锚点 C-1h 实测）。
真正承担隔离的是**列名不重叠**，不是那个区分项。

**仍予保留**：将来若某张表同时含两套列名，它是唯一防线；代价仅一个条件。
但规范里必须写清它是**冗余防御**，否则下一位实现者会误以为它是隔离的主承担者，
从而在「列名已天然隔离」的前提下**过度收紧或错误删改其它条件**。
