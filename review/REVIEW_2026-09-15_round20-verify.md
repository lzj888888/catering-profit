## §4 三个新发现（🔵/🟡，均不阻塞）

### R41 🟡 **同一个返回里两个 `_pct` 字段单位不同**（命名陷阱）

`calcSandbox` 出参（`service.js:49/70`）：
```
composite_var_rate_pct = 45     ← 百分数（45 表示 45%）
margin_rate_pct        = 0.55   ← 比率（0.55 表示 55%）
```
`selftest.js:29-30` 正好按这两个单位断言（`=== 45` / `=== 0.55`）。
- **页面这次写对了**（`sandbox/index.js:104` 直接 `toFixed(1)` 得 45.0；`:105` 先 `*100` 再 `toFixed(1)` 得 55.0）—— 我原本怀疑这里算错，**实测证明页面正确，我的怀疑不成立**。
- **但这是"名字相同、单位不同"**：下一个照名字写代码的人（或批次 7 的导出/报表）极可能把 `margin_rate_pct` 当百分数直接显示 ⇒ **用户看到 "0.6%" 而不是 "55%"**（静默显示错值，不崩溃）。这也与项目口径不一致：`core/10 §8.2` 明写「百分比 `DECIMAL(5,2)`（35.00 表示 35%）」。
- **修法（二选一，都很小）**：(a) 把该字段改名 `margin_rate_ratio`（并把 `*100` 的转换留在页面/契约注里写明）；(b) 出参改回百分数 `margin_rate_pct = 55`，引擎内部保留 ratio 局部变量。**建议 (a)**（改动面最小：service 一行 + selftest 两条 + 页面去掉 `*100` + 契约注明）。
- **验收**：出参里凡 `*_pct` 必须都是"百分数"（与新加的断言一致）；页面显示 `55.0`。

### R42 🔵 **iOS 自动订阅的拦截只在"展示层"，建议把这条决策留痕**

`payCreateOrder/index.js:8-9` 注释明说：「`auto_subscribe` 套餐在 iOS 端不展示（前端不传 `channel='ios_auto'` 即可）；**本函数对自动订阅套餐在任意 channel 都放行创建**」。
- 我理解这个取舍：平台信息由客户端上报、**后端判 iOS 本就不可信**（可伪造），所以把约束放在展示层是合理设计。
- **但它是一条"合规约束"（苹果 IAP），且目前**没有任何服务端兜底**——若哪天前端过滤被重构掉，**不会有人报错**（静默回归）。
- **修法**：不必加服务端拦截；建议**把这个决策写进契约/重启键**（一句："iOS 不展示自动订阅 = **展示层约束**，后端有意不拦，因客户端平台不可信；改动前端展示层时必须回归此项"），并给 `pages/pay/orders` 或套餐列表加一条**自测/断言**（iOS 环境下不渲染 19.9 项）。
- 理由同 R30 的先例：**要么收紧，要么留痕** —— 不留痕的"有意不拦"与"漏写"长得一模一样。

### R43 🔵 **孤儿页面目录 `pages/dish/`**

- `app.json` 未声明（现声明 **12** 个页面），但 `pages/dish/` 目录仍在（batch 0 的占位页 `dish.js/json/wxml/wxss`）。
- 影响：包体内多 4 个死文件（极小），且 `tools/check_requires.js` 仍会扫它（当前能解析，所以不报错）。
- **修法**：删除该目录（或明确保留为示例并在 README 注明）。**验收**：`app.json` 声明的页面 = `pages/` 下实际页面组；`git grep pages/dish` → 0。

**另有一处口径待你说清（不算发现）**：批次 4 提交信息写「**8 页面**」，而 `app.json` 现声明 **12** 个页面（其中批次 4 新增 10 个：`month`×5 + `shop` + `sandbox` + `card`×3）。请说明"8"的口径（是否指 8 个页面组 / 8 份页面清单 / 或漏计）。
