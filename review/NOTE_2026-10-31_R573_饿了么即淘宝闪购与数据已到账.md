## 三、手机端经营概览字段名（队列 #78 的另一半，本轮闭合）

过去 #78 挂着「字段名靠推演、双方都无截图」。本轮直接读图得出，与既往 hand-record 取值一致：

**淘宝闪购 / 饿了么——「经营数据 · 历史数据概览」**
- 营业收入 / 优惠前总额 / 补贴及支出 / 有效订单 / 实付单均价 / 活动补贴
- 关系：`营业收入 = 优惠前总额 − 补贴及支出`

**美团——「数据中心 · 营业概览」**（本轮同步读出，用于对照）
- 收入 / 营业额 / 支出 / 有效订单 / 实付单均价 / 活动补贴 / 顾客配送费 / 顾客实付
- 公式原文：`收入 = 营业额 − 支出`；`营业额 = 有效订单 × 实付单均价 + 活动补贴 − 顾客配送费`；
  `支出 = 商家活动成本 + 佣金 + 配送服务费 + 其他支出 + 公益捐款`

⇒ **两套字段名体系明显不同**，所以引导文案里"照抄手机上的营业额"必须**分平台说**，不能共用一句。

✅ **#104 已裁定（本轮后段，机器证据）**：`platform_taobao_shangou.jpg` **确实是美团**。
三个数在美团原始账单里精确复现（跑 `review/evidence/r177_meituan/mt_check.py`）：

```
Σ商家应收款 = 1747.95   ← 截图「营业收入」
Σ商品总价  = 3041.20 + Σ打包费 125.00 = 3166.20 ← 截图「优惠前总额」
Σ商家对顾客的活动补贴 −806.29 + Σ美团活动补贴 123.00 = −929.29 ← 截图「活动补贴」
```

⇒ R177 是对的，我先前"字段名不像美团"的怀疑**不成立**。真相反而更有价值：
**同一个美团，自己就有两套页面字段名**——「历史数据概览」用 营业收入/优惠前总额/补贴及支出，
「数据中心·营业概览」用 营业额/支出/顾客配送费。
⇒ 引导文案里"照抄手机上的营业额"必须**连页面名一起指**，只说平台名仍然会抄错。

## 四、🔴 那个 11.17% 的坑（本轮最值钱的发现）

### 4.1 事实（🔴 已扩证：不是淘宝独有，美团也有）

本轮追加核对美团原始账单（`review/evidence/r177_meituan/mt_check.py`）：

```
=== 等式 E1：平台服务费 = 佣金(实付) + 配送服务费(含补贴) ===
  不符 0 行            ← 美团账单，同样逐行成立
```

| 平台 | 冗余汇总列 | 子列 | 逐行验算 |
|---|---|---|---|
| 淘宝闪购/饿了么 | 平台服务费 | 技术服务费 + 配送服务费 | 156/156 相等，0 反例 |
| 美团 | 平台服务费 | 佣金(实付) + 配送服务费(含补贴) | 97 行中 0 行不符 |

⇒ **「平台服务费是上面两条的重复汇总」是两家平台共有的账单结构，不是某家的特殊情况。**
（上一稿只写了淘宝一家，据此把防呆范围限定在饿了么渠道——那是错的，已更正。）

⇒ **「平台服务费」是两条子列的重复汇总**，不是第三笔费用。

### 4.2 到手链正解（零误差）

探针 `probe_chain.py`：

```
商品 6418.08 + 打包费 167.00 + 商家补贴 -2069.70 + 技术服务费 -158.71 + 配送服务费 -577.02
= 3779.65
Σ结算金额 = 3779.65
差 = 0.00                ✅
```

这个 3779.65 与 R161 时代留档的真值**完全一致**（跨脚本、跨轮次、跨工具复现）。

### 4.3 危害量化

若老板把「平台服务费」当第三笔费用一起抄进来：

```
误算净额 = 3043.92   （真值 3779.65，少 735.73）
少计占营收(商品+打包 = 6585.08) = 11.17%
```

**这意味着：一个本来可能微赚的月，会被算成明显亏损。** 属于"会让老板做错决策"级别。

### 4.4 好消息：生产代码没踩

`utils/billParse.js`、`utils/takeaway.js` 中「平台服务费」出现次数均为 **0**。
它们按既有铁律⑤「复合列 × 拆分列只取一组」，直接取净额列「结算金额」。
**所以已入库的数据是对的，无需订正任何历史账。**

### 4.5 坏消息：手工/快速录入路径没有防呆

023623]`哪里会踩**：老板打开账单 Excel 一眼看到「平台服务费」这个最大负数，很自然会把它抄进费用。
这与 R496 的教训是同一类（"照抄账单列就踩坑"），但 R496 治的是补贴进收入，这里治的是**冗余列重复计费用**。

## 六、口径确定了什么（可直接引用）

淘宝闪购/饿了么**当月**、**单门店**、**156 行**、**零误差**到手链：

```
结算金额 = 商品金额 + 打包费 + Σ商家承担补贴(负) + 技术服务费(负) + 配送服务费(负)
```

其中「Σ商家承担补贴」= 商家活动补贴 + 商家代金券补贴 + 商家智能补贴 + 商家配送费活动补贴 + 商家配送费券补贴。
**「平台服务费」「外部补贴」「代理商×补贴」均不在该链上**（平台服务费是冗余汇总列，其余为零星列，本店当月合计分别为 −735.73 / 1.10 / 6.00）。

## 六之二 · 追加发现：M2 给老板的参考抽成，和真实账单差一个量级

追查减值构成时顺手核了 `terms.js:981 channelRefBody` —— 它用在 **M2 开店盈亏沙盘**
（`subpkg/tools/sandbox/index.js:210` / `index.wxml:255`），是老板判断"这个店该不该开"时读的参考值：

> 外卖平台抽成：商家后台「结算 / 费用明细」里的技术服务费比例，**一般 18~23%**。

探针 `probe_rate.py` 实测：

```
抽佣费率列        = {'5.00%': 151 行, '0%': 5 行}
技术服务费折扣系数 = {'70.00%': 151 行}      ← 佣金再打七折
实测占比（分母 Σ商品金额 6418.08）
  佣金(技术服务费)        = -158.71   占 2.47%
  配送服务费              = -577.02   占 8.99%
  佣金+配送(平台服务费)   = -735.73   占 11.46%
  商家承担补贴            = -2069.70  占 32.25%
```

而**美团那份独立账单的「费率」列也是 50 行 5.0%**（同一家店的两个平台各自开票，名义费率同为 5%）。

⇒ 老板若照 18~23% 填沙盘，等于凭空多算 6.5~20 个百分点的变动成本 ⇒
**会把本可跑通的店算成不能开**（这比利润虚高严重得多：它直接改变"开不开"的结论）。
⚠️ 样本只有一家店，不足以推翻行业区间本身；但足以证明**这句写死的常数字不适合出现在决策工具里**。
已入队 **#106**。
