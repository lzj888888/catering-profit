## 0 一句话结论

三个模块（M1 月度盈利 / M2 选址反推 / M3 菜品毛利）**主干都跑通了，日常自己用没问题**；
真正的短板集中在**「接外部数据」这一条腿**上，共三处：

1. 🔴 **京东数据现在 100% 进不来**（实测硬阻断）——不是"可能不兼容"，是必然被拒；

3. 🟢 **AI 预留：规范做得比代码走得远，且"现在不写代码"是审查过的正确决定**（不是欠债）。

⇒ 你要发数据这件事本身**就是对的方向**：它会一次性把 ①② 从"隐患"变成"必须解决的具体问题"。

## 2 实测结果（全部来自探针实跑，非推断）

### 2.1 平台识别：靠「单列名」硬依赖

| 输入 | 实测结果 |
|---|---|
| 淘宝表头（含「结算金额」） | ✅ → `taobao`（基线） |
| 美团表头（含「商家应收款」） | ✅ → `meituan`（基线） |
| 淘宝表头**去掉**「结算金额」 | ❌ → `null` 认不出 |
| 美团表头**去掉**「商家应收款」 | ❌ → `null` 认不出 |

⇒ 识别条件 = **表里必须出现某一个特定列名**，不是"看整张表的特征"。

### 2.2 各平台准入（模拟 `importSalesBill/index.js:72` 的判据）

| 手选平台 | 白名单 sheet 名 | 结果 |
|---|---|---|
| `taobao` | 「外卖账单明细」 | ✅ 放行 |
| `meituan` | 「订单明细」 | ✅ 放行 |
| `eleme`（**前端选项里有**） | `undefined` | ⛔ 阻断 |
| `other`（前端选项里有） | `undefined` | ⛔ 阻断 |
| `jd`（京东） | `undefined` | ⛔ 阻断 |

⇒ 两条实情：
- **京东必然被拒**，且报错文案是「请确认是淘宝闪购、美团外卖账单，或堂食《菜品销售统计》」——**提示语里没有京东** ⇒ 用户拿京东数据来会一头雾水；
- **前端给了「饿了么」选项，实际进不来**（枚举有、解析无）——这是"看着支持、其实不支持"，比明确不支持更伤。

### 2.3 京东式商品销量表（假设列名，4 组）

| 假设列名 | `detectPlatform` |
|---|---|
| 商家实收 / 结算状态 | `null` |
| 商品实付 / 打款金额 | `null` |
| **含「结算金额」**（与淘宝撞名） | ⚠️ **误判为 `taobao`** |
| **含「商家应收款」**（与美团撞名） | ⚠️ **误判为 `meituan`** |

⚠️ 后两种是**最危险的形态**：平台被认错 ⇒ 按别人家的规则解析 ⇒ **不报错、给错数**。
（探针 §6 已实证同类行为：淘宝格式表若缺「退单」列，退款行会被当正常单照收，**零告警**。）

### 2.4 形态 C（外卖「商品销量」表）的判定与取列

| 项 | 现状 |
|---|---|
| 判定条件 | 需同时有「商品名称/菜品名称」+「商品销量/销量」+「销售额」 |
| 正样本（美团式） | ✅ 判为 `waimai_goods` |
| 假设京东式（销售数量/销售金额） | ❌ 判不出（`null`） |
| 假设京东式（商品/实付金额） | ❌ 判不出（`null`） |
| 取列白名单 | `['日期','门店编号','商品名称','销量','销售额']` —— **不在白名单的列静默取不到数**（实测：行进了、金额记 0、**不报「列缺失」**） |

⇒ 双重风险：**判不出**（进不来）+ **判出了但列名不同**（进来了但钱是 0，且不报错）。

## 4 缺口分级（真缺口 vs 建议 vs 可不动）

### 🔴 P0 · 你发数据前必须先定（否则数据来了也白搭）

**P0-1 京东账单/销量表进不来**
- 现状：账单路径白名单无 `jd`（必然阻断）；形态 C 判定词表对列名敏感（大概率判不出）。
- 影响：你导京东 = 报「无法识别账单平台」或「这张表不认识」，**进不去一分钱**。
- 需要的输入（你发数据时请一并给）：**① sheet 名 ② 完整列名一行 ③ 是否有商品级销量列 ④ 金额列是含佣金的结算额还是商品原价**。

**P0-2 形态 C 取列白名单太窄**
- 现状：只认「日期/门店编号/商品名称/销量/销售额」5 个列名；不在名单的列**静默取空**（不报错）。
- 影响：哪怕表被判出来了，列名对不上 ⇒ **金额全 0、零告警** ⇒ 用户以为导入成功。

### 🟠 P1 · 影响准确度与体验（建议排，但不是"必须现在"）

**P1-1 外卖菜名匹配：映射表建了，没人读写**
- 规范 `开发规范v1.4 §6.2` 定了 `shop_dish_mapping`（平台菜品 ↔ 我方 `card_code`）；`initDb/collections.js:166` **索引都建了**；
- 但实测：`getDishReview` **不读它**，**没有任何云函数写它** ⇒ **一张空表**。
- 现状匹配 = 菜名字面归一（`normalizeDishName`）。平台菜名常带前缀/规格（「【招牌】耙牛肉(小份)」）⇒ 匹配不上 ⇒ 全进未匹配。
- 影响：**这是外卖复盘能不能真正用起来的关键**，比"多支持一家平台"更值钱。

**P1-2 客户端体验细节**
- `eleme` 出现在前端选项里但后端不支持 ⇒ 建议**要么补齐、要么从选项里撤掉**（现状是"看着能用、实际报错"）。
- R239 的 D-2：菜品卡挂牌价 = 0 时，单均测算「商品总价」静默归零，页面**无提示**。

**P1-3 平台被认错时静默出错**
- 实测：任何含「结算金额」的表都会被判成淘宝并按其规则解析，**不报错**。
- 建议：解析后加一道"自检"（如行数/金额量级明显异常则提示），而不是照收。

### 🔵 P2 · 可以不动（记录在案，不再反复）

- **外卖测算的付费墙只有前端拦**（云端零判据，与 R189 记录的缺口一致）——技术上可绕过，实际风险低（需改包）；真要收口再加云端判据。
- **双副本维护成本**（`cloudfunctions/importSalesBill/service.js` ↔ `utils/billParse.js`；`terms.js` 两处）——已有自测与守卫守着，暂不动。
- R239 的 **D-1 推广费在到手口径未扣**（口径决策，已单独登记待你拍板）。

## 6 结构性洞察（我认为最值钱的一条）

**当前的「平台支持」是写死在代码里的，而它本质上是"配置"。**

- 每家平台的差异只有三件事：**① 怎么认出它 ② 哪些列叫什么 ③ 哪些行要筛掉/算什么**；
- 现在这三件事被硬编码成 `COL` / `SHEET` / `detectPlatform` / `if (platform === 'taobao')` 散在 5 个文件里；
- 后果：加一家 = 动 10 个文件 + 上云 + 重跑门禁（每来一家重复一次）。

⇒ **升级方向**：把这三件事抽成「**平台档案**」（数据，不是代码）。加平台的成本从"改 10 个文件"降到"加一条档案 + 复算锚点"。
这也**顺带解掉 P0-1 与 P0-2** —— 京东进来时，你只需要一份京东档案。

⚠️ 注意纪律：这属于**架构调整**，按项目规矩得先出增量规范、你拍板后才动代码。**本轮我只是提出，没有动任何代码。**
