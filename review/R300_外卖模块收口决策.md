## 1 事实底数（**已逐条回源码/外部取证**，不是印象）

### 1.1 「M3 外卖」今天到底有几条链

| 能力 | 输入 | 现状 |
|---|---|---|
| **外卖单均测算**（M3.17） | 手工填：成本卡 + 佣金率 + 配送费 + 补贴 | ✅ **纯试算，不依赖任何导入** |
| **外卖商品销量导入**（形态 C）→ **外卖单品毛利榜** | 平台《商品销量》表（**名/销量/金额**） | ⚠️ **＝李老师拿不到的那张** ⇒ 这条链断供 |
| **外卖订单/结算账单导入**（形态 D）→ 平台对账 | 平台结算单 | ⛔ **10-13 已关**（`BILL_IMPORT_ENABLED=false`） |
| **M1↔M3 率对率对账**（`pages/recon`） | **M1 手填账 + 成本卡** | ✅ **不依赖导入**（我核了：它只调 `getLedger`/`getCostCard`） |

⇒ **结论：真正失去输入的只有一条链 = 「外卖单品毛利榜（形态 C 派生）」**。
「外卖对账」有两层含义，李老师说的应是**平台账单对账**（已关）；而**产品内那个 `recon` 页**是「M1 实际 ↔ M3 理论」的率对率对账，**它不依赖任何导入**，因此**不必也不该动**。

### 1.2 M1 早就支持「外卖整体口径」（**这是本决策的关键**）

`miniprogram/i18n/terms.js` 实测：
- **收入侧**：外卖按平台分（美团外卖 / 淘宝闪购 / 京东外卖 / 其他），每平台填「商品总价 + 打包费 + 商家承担全部补贴」合计；另有**快速录入**（每平台一个数 + **有效订单数**）与**分项录入**两模式。
- **费用侧**：`varItems.takeawayComm`「**外卖平台佣金**」、`deliveryFee`「**外卖配送服务费**」（营销类细项，团购与外卖佣金**分列**不合并）。
- **已有自检**：`selfCheckMiss`「外卖收入已填，营销费用里的佣金与配送费还是空的 —— 这两项记得按账单记上，不然利润会偏高」。
- **已有差异提示**：`recDeliv`「差额与您填的配送费相近，可能是"用户支付配送费"已计入商家应收款…」。

⇒ **老板手机上能看到的汇总数（营业额 / 佣金 / 配送费 / 补贴 / 订单量），M1 全部收得到**。
⇒ 豆包要我核实的前提（"算到手率是否需要新字段"）**答案是不缺** ⇒ **方案 D 零新建输入即可落地**。

### 1.3 外部市场调研（`domain_search`，12 个来源，含美团官方培训/商家版 App 说明/行业报告）

| 结论 | 证据要点 |
|---|---|
| **老板每天只看平台汇总级** | 平台官方接口到「结算日汇总」为止；美团账单三 sheet 也到订单级，**到不了单品成本** |
| **对账的真实动作 = 核对三口径差异** | 「营业额 ≠ 结算金额」是平台官方自己解释过的（T+1/T+3 结算期 + 跨天营业）；行业标准动作 = **按日汇总差额 + 按单抽查 3~5 笔** |
| **单品级是"未被满足的刚需"，但不是"当下习惯"** | 81.41% 餐饮商户年交易额 <20 万；SaaS 渗透率 38.6%；**超 60% 中小餐企数字化卡在"流程不匹配"、约 80% 小程序上线即闲置** |
| **给单品毛利报表会闲置** | 行业反复指向：**不要默认商家已建好成本卡**（强制建卡＝放弃这批用户）；应给行业均值起步（外卖食材成本率约 35%~50%） |
| **三层指标才是完整答案** | 菜品毛利率（判定价）· **订单贡献毛利率**（判是否投流）· **现金回款率**（判对账/现金流） |

### 1.4 豆包的底数纠正（**我采纳，并已回源码验证**）

1. 我说"M1 已有外卖整体口径"**不够精确**：那是**收入侧总额**；算到手率还需**费用侧**字段 —— ✅ **实测已有**（§1.2）。
2. 「商品总价+打包费+商家承担补贴」的**方向**要验。⇒ 实测 `terms.js:463` 原文已写明「佣金与配送费**不要在这里扣**（扣了就成净额，费用侧会无事可填）」⇒ **口径自洽，无冲突**。
3. 断掉的是**「外卖单品归因」**；M1 整体 + 单均试算**不能替代"哪道菜赚钱"** —— 我同意，这句要写进产品话术，不能糊过去。

## 2 我的拍板（四个候选 → 定案）

| 方案 | 我的决定 | 理由 |
|---|---|---|
| **A 收（删掉形态 C 入口 + 撤下外卖单品榜）** | ❌ **暂不做** | 会让产品**永久失去"哪道外卖菜赚钱"**这个能力；而它恰是老板"最需要却拿不到"的那块（§1.3）。且数据将来可能回归（官方 API / ISV 授权是行业演进方向）⇒ 删了要重建 |
| **B 留但降级（独立开关 + 高级入口 + 空态引导）** | ✅ **采纳（作为"暗"面）** | 主入口不再宣传"自动外卖单品毛利榜"（做得到才承诺）；形态 C 收进「**我有商品销量明细表**」的折叠高级位，**独立开关**控制（与 `BILL_IMPORT_ENABLED` 同法，不动账单开关）；无数据时**空态直接引导**到 M1 到手账 + 单均测算 |
| **C 新开外卖汇总输入页** | ❌ **不做** | 与 **M1 已有的外卖口径重复** ⇒ 制造**第二套口径**（本仓最贵的病）。要补就补在 M1，**不新开页** |
| **D 不新增输入，只把 M1 已有的数"用起来"** | ✅ **采纳（作为"主"面）** | 零新建输入、零新口径；对准**老板手机上看得懂的粒度**（豆包：D 主）。这正是外部调研说的「**汇总级做入口、单品级做下钻**」 |

### 2.1 定案（一句话）

> **D 主 + B 暗；不做 C；暂不 A。** —— 把 M3 外卖的**主价值**从"单品毛利榜"改判为
> **「外卖到手账（汇总级）+ 单单盈利试算（单均测算）」**，单品榜降为**有明细表才出现的下钻**。

### 2.2 具体要做的事（按依赖排序）

**第 1 步｜M1 结果页新增「外卖到手账」区块（纯前端零新建输入）**
用 M1 **已录入**的数反算，全部是老板能在平台 App 上对上的口径：
- 外卖营收（各平台合计，总额法）
- 平台费用 = 外卖平台佣金 + 外卖配送服务费
- 商家承担补贴
- **到手额 = 营收 − 平台费用 − 商家补贴**
- **到手率 = 到手额 ÷ 营收**（外部调研点名的「**现金回款率**」层，比"毛利率"门槛低得多）
- **单均到手 = 到手额 ÷ 有效订单数**（对应行业实操线「单均贡献 <3 元要警惕」）
- 缺项时**不编数**：哪个数没录就显示"未录"，并指向 M1 录入页对应字段（复用 `selfCheckMiss` 已有的引导）

**第 2 步｜形态 C 降级为独立开关的"高级入口"**
- 新增单源开关（如 `utils/featureFlags.js::SHAPE_C_IMPORT_ENABLED`），**与账单开关相互独立**
- 入口文案改为「**我有商品销量明细表（可选）**」，收进折叠位；无数据 ⇒ 空态引导到第 1 步
- **代码、解析、表结构、历史数据全部保留**（只隐藏入口）⇒ 数据回归时可灰度打开

**第 3 步｜定位与话术迁移（⚠️ 需李老师点头，涉及付费点）**
- M3 外卖对外表述：从「自动外卖单品毛利榜」→「**外卖到手账 + 单单盈利试算**（有明细表可下钻单品）」
- 付费点 `m3_takeaway` 的**卖点描述**随之迁移（`TERMS.paywall.takeaway`）—— **我是建议迁，不擅自改**，因为动的是商业化口径

**第 4 步｜回归与废弃机制（豆包提的，我采纳）**
- 数据回归**按平台/用户灰度**打开，先补验再承诺（沿用本仓既有口径：先补验、窄范围承诺）
- **设观测期**：隐藏后监控"是否有老板真的来问"，到期决定归档（避免永久背包袱）
- 中长期数据源（官方 API / ISV 授权 / 第三方聚合）**只做预研，不承诺时间**

## 6 追加：李老师第三问「**M3 是独立模块，取不到 M1 的值怎么操作？**」

> 这一问打在我 §5.5 第 3 条（对拍自检）的最脆弱处：**对拍要拿 M1 的外卖营收当基准**，
> 而 M3 在架构上是独立模块。下面先给**设计答案**，但**先报一个更要紧的发现**。

### 6.1 🔴 先报发现：复盘榜**连自己的月份都没锯**（这比对拍更根本）

**取证**：`cloudfunctions/getDishReview/index.js:56`
```js
const salesRes = await da.listAll('external_sales_daily', { shop_id: shopId });   // ← 只按 shop_id 过滤
```
- **不按 `biz_date` / 月份过滤**；落库主键 `SALE_<shop>_<platform>_<biz_date>_<seq>` **含日期** ⇒ **多月数据并存**。
- 页面侧 `curMonth` 只用于**成本卡快照提示**（`snapshotNote`「该卡成本为 X 月快照」），**不锯销量**。

**后果（静默错数）**：老板 9 月导一次、10 月再导一次 ⇒ 毛利榜是**两个月的累计**，
而页面按"当前月"呈现、**没有任何期间标注**：
- 「共 N 道」「各渠道均建卡 M 道」「覆盖 X% 营收」「合计份数/营收/成本/毛利」**全是跨月累计**；
- 老板会以为"这道菜这个月卖过"（其实只有上月卖过）；
- 真样本就是**7 天表**（`service.js:399`：淘宝闪购 355 行 = **7 天** × 51 商品）⇒ **"一段"冒充"整月"**。

⇒ **结论：在谈"跟 M1 对拍"之前，M3 必须先有自己的月份口径。** 否则对拍比的是
「**跨月累计** vs **单月账**」，**必然对不上**，对拍会变成一个恒假的噪声源。

### 6.2 设计答案：校验**分级**，M1 只是"可选加强项"（M3 自洽优先）

| 级别 | 校验项 | 依赖 | 取不到 M1 时 |
|---|---|---|---|
| **一级（永远可用，零外部依赖）** | ① **期间覆盖**：`groups` 首末日期与天数 vs 目标月天数 ⇒「你导的是 7 天，不是整月」② **均价异常**：`amountFen / qty` 落在 [1 元, 500 元] 之外 ⇒ 疑似**销量列与金额列搞反** ③ **0 元行**（已有 `zeroAmountQty`）④ **非整数销量**（已有 `nonInt`，已单列不静默）⑤ **同平台重复导入**（已有 `dup` 检测）⑥ **月份跨度**：`months` 多于 1 个月 ⇒ 提示 ⑦ **成本卡匹配率**：导入 N 道 / 有卡 M 道（已有 `unmatched` + `shortCardGap`） | **只需 M3 自己的数** | ✅ **照常做** |
| **二级（有则加强）** | 与 **M1 同月同平台外卖营收**对拍（差额 + 两条出路） | M1 已录该月该平台 | ➖ **降级：不做这一项，其余照做**，并在回执里**说清"没做这一项"**（不假装做过） |
| **三级（M3 自身历史）** | 与**同平台上一次导入**比日均销售额（差 ≥10 倍提示） | M3 自己的 `getSalesBills` 历史 | ✅ 照常做 |

🔴 **关键纪律（回答"取不到怎么办"）**：
1. **取不到 M1 = 不是错误、不阻断、不补数**（沿用 M1 的 `selfCheckMiss` 同一条纪律："不替用户编数"）。
   回执如实写「未做 M1 对拍（本月外卖营收未录）」+ 一个**去 M1 补录**的入口 —— **有出路、不死锁**。
2. **一级校验必须自己撑得住**：把"能自证的错"（期间、列错、月份跨度）在**导入当下**就报出来，
   不依赖任何其它模块。这才是 M3 独立性的正确用法。
3. **对拍放哪**：`utils/reconDerive.js::reconcile` 已经是「M1↔M3 率对率对账」的**单源**，
   M1 相关的那条腿（二级）应当**复用它**、不另写一份口径 —— 避免制造第二套对账算法。

### 6.3 由此调整 §5.5 的执行清单（本批范围）

**新增第 0 步（前置，必须先做）**：
0. **给 M3 复盘页自己的月份口径**：`getDishReview` 接收 `month`（缺省＝当前月）并按
   `biz_date` 前缀过滤；页面加月份选择（或"最近有数据的月份"默认）；**期间如实标注**
   （"本榜＝YYYY-MM，共 N 天数据"）。⚠️ 这是**云函数 + 前端**改动，样本期间口径要一致。
   守：`snapshot_month`（卡）与**数据期间**是两件事，页面上必须**分开讲清**。

**然后**才是 §5.5 的第 1~3 步（picker 收窄 / 承诺面回收 / 分级校验）。

> ⏸ **待拍板**：第 0 步动云函数（`getDishReview` 加入参 + 过滤），且会改变**现已上线**的榜单口径
> —— 存量用户看到的榜会从"跨月累计"变成"单月"，这是**行为变更**，我不擅自改。**请李老师点头。**

### 6.4 🔴🔴 决定性证据：**契约里本来就写了日期区间，是实现漏了**

这把我 §6.1 的"缺陷候选"从推测变成**实锤**，也**直接回答了李老师的问题** ——
**M3 根本不需要 M1：契约早就给了它自己的时间锚。**

**契约原文**（`specs/dev-specs/core/10_云函数清单与接口契约.md:69`）：

| | 契约写的 | 实现实际 |
|---|---|---|
| **入参** | `{ shop_id, **biz_date_from**, **biz_date_to**, platform?, client_request_id }` | `event.shop_id`（**只有这一个**） |
| **出参** | `{ shop_id, **range{from,to}**, **list[]**, **summary{}**, **unmapped[]** }` | `{ shop_id, mapping, dine_in, takeaway, unmatched, totals, coverageA, coverageC, buffet, truncated }` |

⇒ **入参、出参两端都与契约不符**：
- 契约要求按**日期区间**过滤 ⇒ 实现**完全不锯时间** ⇒ 跨月累计（§6.1）；
- 契约要求回 `range{from,to}`（**期间**）⇒ 实现**不回期间** ⇒ 页面**无从标注**"这榜是哪段时间"；
- 出参整体结构也不同（`list/summary/unmapped` vs `dine_in/takeaway/totals`）⇒ **契约这一行已过期**，须一并更新。

**为什么门禁没抓到（守卫盲区）**：
- `tools/check_fn_inventory.js`（R62）守的是「**函数清单 ≡ 契约文档**」—— 它只比**函数名在不在**，
  `getDishReview` **在** ⇒ **绿**；
- `tools/check_data_contract.js`（R97）守的是**跨函数字段名 / 主键语义**（C1~C4），不是"入参照不照契约"；
- ⇒ **"契约声明的入参/出参形状 vs 实现"这一层，本仓零守卫** ⇒ 该缺口恒绿。

**⇒ 修正 §6.2 的定性**：这不是"我新提一个月份概念"，而是「**把契约里已经写好、却从未实现的
`biz_date_from/biz_date_to` 补上**」—— 属于**补实现**，不是加需求。优先级应**高于** §5.5 的按钮项。

**⇒ 也因此，"取不到 M1 怎么操作"有了干净答案**：
M3 用自己的 `biz_date_from/to`（契约字段）**自成闭环**；M1 对拍**永远只是可选加强项**，
不构成任何依赖 —— 这与「M1 归档域不含销量行」（`check_archive_switch_snapshot.js:116` 钉住的**有意解耦**）
在架构上是**一致**的。

**新增守卫建议（本批一并做）**：`check_fn_contract_params.js` ——
「契约里声明了入参的云函数，其实现必须真的读取该入参名」+ 反恒真样本。
（先做 `getDishReview` 这一条，机器判、可变异；覆盖面下界 + 未实现者显式登记。）
