# M3 语义与自救路径审计（R715 · 2026-11-12）

> 李老师原话：「这个模块儿还是就是各个语义这个解释，你看看词不达意的地方有没有，或者说每个页面儿有没有让人误会，填的时候会比如说是是外卖的，但会联想到其他的东。就是有没有让大家觉得很模糊，不知怎么填数字，数字不知怎么往里入的那种的，包括入错了数字怎么办，对吧？表格导错了这个时候我们怎么纠正等等的这些个看看自己处理一下。」

拆成六问：
1. 词不达意的地方有没有
2. 每个页面有没有让人误会
3. 填的时候会不会联想到别的东西（例：外卖的联想到其他）
4. 不知怎么填数字、数字不知怎么往里入
5. 入错了数字怎么办
6. 表格导错了怎么纠正

---

## 一句话结论

**「填进去之前」做得比「填进去之后」好得多。**

输入的引导很扎实——成本卡页有出成率/损耗率的白话解释，原料页把换算系数做成了「1 箱 = 10 斤」的句子，营收手工页每个框下面一行「这个数去哪看」。这些地方挑不出毛病。

**问题全在两类：**

- **同一样东西起了两个名字、方向还相反**（问 3）。老板填完，两个数单看都对，合起来利润错一倍，而没有任何一处报错。
- **错了之后的回头路，入口不在出错的那个页面**（问 5、6）。导错了会发现「没法改」，改错了不知道会不会留痕。

本轮修掉 3 条（全部是问 3/5/6），另 3 条需要动计算或动流程，等拍板。

## 一、已修的三条

### ① 包材（成本）vs 打包费（收入）：同一个餐盒，两个名字

外卖页有两处要填餐盒钱：

| 位置 | 原字段 | 实际方向 |
|---|---|---|
| 「包材」区 | `临时包材金额（元）` | **成本**，从利润里扣 |
| 「平台参数」区 | `打包费（元）` | **收入**，加进顾客支付 |

代码证据（`utils/takeawayDerive.js:115-124`）：

```js
const packCost = packCostOf(packs, lookup);          // 包材 → 成本
const packFee  = Number(params.pack_fee_fen) || 0;   // 打包费 → 收入
const payment  = goodsTotal + packFee + deliveryCustomer;  // 进顾客支付
```

老板语言里「包材」和「打包费」就是同一个东西（餐盒）。他在两处各填一次 2 元，结果是**成本 2 元、收入 2 元、利润被算成两倍**。而且两个数单看都「对」——没有一处会报错。

**改法**：不解释，直接让标签自己说出方向（比加一段说明更有效，也不占首屏）：

| | 改前 | 改后 |
|---|---|---|
| 成本侧 | `包材` | `包材（你买的餐盒，算成本）` |
| 收入侧 | `打包费（元）` | `打包费·顾客付（元）` |

加一句跨区指路（两区隔了几屏，填包材时看不到打包费）：

> 这里填你买餐盒花的钱；顾客付的打包费在下面「平台参数」里填

### ② 配送服务费（商家付）vs 配送费·顾客承担（顾客付）：中间隔了 3 个字段

这两个字段在表单里的实际顺序是：

```
佣金率 → 佣金保底 → 配送服务费 → 配送补贴 → 推广费 → 打包费·顾客付 → 配送费·顾客承担
                      ↑ 支出                                              ↑ 收入
```

两个「配送费」中间隔了 4 项。老板从上往下填，看到第二个会以为是同一个东西要再填一次，或者干脆留空。

**改法**：`配送服务费（元）` → `配送服务费·商家付（元）`，与已有的 `配送费·顾客承担（元）` 完整对称（两组都是「·谁付」的写法）。

### ③ 「顾客支付」的数字从哪来的，页面一个字没说

外卖页的「顾客支付」= 成本卡售价 × 份数 + 打包费 + 顾客配送费。**它是标准单，不是这一单的实收。**

外卖普遍比堂食加价 2~5 元，还有满减、代金券。实收几乎永远不等于这个数。老板看到「顾客支付 32 元」，而他这一单实际收了 38 元 —— 结论只会是「这功能算错了」。

**对照：团购页把同一件事做对了。**

```
grouponPrice:   '团购价（顾客实付）'   ← 让老板填实付
grouponPricePh: '如 88'                ← 有例子
grouponRatePh:  '6'                    ← 有例子
grouponHint:    '佣金按顾客实付的团购价算，不是按原价'
```

外卖页既没有实付输入框，也没有任何来源说明，11 个输入框还全是空占位。

**改法**（本轮只补说明，不改变计算）：

> 「顾客支付」是用成本卡售价算出的标准单，不含外卖加价和满减，不等于这一单实收。

⚠️ 特意**没有**写成「建议改成本卡售价」——那会把堂食价带偏，是比现在更贵的错。

### ④ 表格导错了：清除入口在另一个页面

同一份销量数据有**两个导入入口**：

| 入口 | 能导入 | 能清除 |
|---|---|---|
| 外卖页 →「销量表导入」tab | ✅ | ❌ |
| 菜品排行榜页 | ✅（R707 加的） | ✅ `clearSalesBills` |

从外卖页导错的人，在这一页找不到任何「撤销 / 删除 / 重来」。他的结论会是「导错了没法改」。

清除功能本身是有的（`pages/m3/dishreview/index.js:1120` 逐条清除 + `:1152` 全部清除，都有二次确认）——**只是不在这里**。

**改法**：在导入按钮下方加一个折叠块「导错了怎么改」，展开说清路径，并给一个按钮直接跳过去：

> 导入只是把表里的数存进来，能撤销：去「菜品排行榜」页，每份已导入的账单旁边有删除，底部还有「全部清除」。删掉再重导一次就是干净的。

### ⑤ 顺便：11 个空占位补了 5 个例子

「不知填 15 还是 0.15」是这类表单最典型的卡点。补的是最容易搞错的五个：

| 字段 | 占位 |
|---|---|
| 佣金率（%） | `如 15` |
| 佣金保底（元） | `没有就填 0` |
| 固定佣金（元） | `如 4` |
| 打包费·顾客付（元） | `如 2` |
| 配送费·顾客承担（元） | `如 3.5` |

## 二、「入错了数字怎么办」—— 全部页面自救矩阵

这是问 5 的正面回答。逐页核过实际代码：

| 页面 | 数据落地 | 填错后能改吗 | 有无提示 |
|---|---|---|---|
| 成本卡编辑 | ✅ 存云端 | 能改，**改一次多一个版本** | 保存回执直接报成本/毛利/毛利率（R443） |
| 原料编辑 | ✅ 存云端 | 能改，覆盖 | 改价后弹「用到这个原料的 N 道菜，成本卡里还是旧价」+ 看影响面（R406） |
| 外卖单均 | ❌ 纯试算 | 改就行，不落库 | — |
| 团购单均 | ❌ 纯试算 | 改就行，不落库 | — |
| 渠道营收·手工 | ✅ 存云端 | 能改，覆盖式保存 | 「灰底不是这个月的数」防串月（R621） |
| 对账·在售菜品数 | ✅ 存设置 | 有独立「保存」按钮 | 说明它是覆盖率分母、影响什么（R712） |
| 销量表导入 | ✅ 存云端 | **只能在排行榜页清**（本轮补指路） | 重复导入检测（R271） |
| 成本卡批量导入 | ✅ 存云端 | 已保存标记可续做（R711） | 草稿落盘，隔天回来还在 |

**结论：都能改，没有死路。** 问题只是「入口在哪」不总是清楚——本轮补了最难找的那一处（销量导入）。

其中 **原料改价** 那条做得特别好，值得记下来当范本：系统不假装同步，直接说「成本卡不会自己跟着变」，还给一个「看影响面」的出口。这比「已自动更新」这种假承诺值钱得多（假承诺会让老板按没变的成本去定价）。

## 三、需要你拍板的三条

### 🟡 A · 外卖页无法单独指定这一单的售价

现在售价只能来自成本卡。外卖的实际售价（加价后 / 满减后）没法在页面里改，只能去动成本卡——而成本卡是堂食和外卖共用的。

**三个选项：**

1. **加一个「本单实收（选填）」输入框**，填了就覆盖售价。最贴近真实，要动 `takeawayDerive`。
2. 只在菜品行加一个可改的单价框（默认带出成本卡售价）。更灵活，但一单多菜时填起来累。
3. 维持现状，靠本轮补的那句说明。零成本，但老板仍然算不出真实这一单。

我倾向 **1**：一个框，选填，不填就退回现在的行为，改动面最小。

### 🟡 B · 对账的菜单毛利率按售价加权（R714 已提，未做）

青菜 12 元/成本 4 元、招牌鱼 88 元/成本 60 元，实卖 300 份 : 20 份：

```
菜单标准毛利率 = 36.00%
真实加权毛利率 = 55.22%
对账结论：实际比标准高 19.22 个点、差 1030.19 元   （没被抑制）
```

老板成本、售价、销量全对，账本和销量完全一致，系统照样说他「实际高了 19 个点」。而且这个偏差**方向永远为正**（餐馆天然便宜菜卖得多、便宜菜毛利高）。

### 🟡 C · 同名成本卡，销量归谁取决于数据库返回顺序（R714 已提，未做）

两张同名「酸菜鱼」卡（大份成本 30 元 / 小份 18 元），同一笔生意：

```
cards 顺序 [大份, 小份] → 毛利率 79.55%
cards 顺序 [小份, 大份] → 毛利率 65.91%
```

差 13.64 个点。建卡时已有 `confirmDupName` 软提示，但提示只说「会出现两张」，没说「销量只算到一张」。

## 四、做对的地方（没有动）

审计不能只报问题。以下几处是我原本准备挑、结果发现已经做对了的：

- **成本卡编辑页**：出成率、损耗率都有白话解释（`出成率：1 斤生料能出几两净料`），售价是预填来的会标注来源，`建议售价` / `辅助分摊（元）` / `制作损耗率（%）` 单位都齐全。
- **原料编辑页**：换算系数做成句子 —— `1 [箱] = [10] [斤]`，比「换算系数」四个字有用一百倍。
- **营收手工页**：每个框下面一行「这个数去哪看」，且明确区分「灰底不是本月」。
- **团购页**：`团购价（顾客实付）` + `如 88` + `佣金按顾客实付算，不是按原价`——这三件套是标准答案，外卖页本轮就是在向它对齐。
- **导入失败态**：分得很细（没数据 / 合计读不出 / 不像商品销量表 / 行格式不对），还给了「让 AI 帮你转表」的逃生口（R590）。
- **红线**：15 个页面无一处字号 < 28rpx。

## 六、如实登记：没动的

### 一处需要你在真机上判断的取舍

本轮在外卖页加了 3 个说明块（橙色浅底），各自紧贴要解释的字段：

| 位置 | 内容 | 字数 |
|---|---|---|
| 口径切换下方（原有） | 佣金计费基数 | 26 字 ≈ 2 行 |
| 本单菜品下方（新） | 顾客支付的售价来源 | 39 字 ≈ 2 行 |
| 包材下方（新） | 包材是成本、打包费在别处 | 29 字 ≈ 2 行 |

您上次说过「整个的得理一下，要不有点乱」，所以这里有个真实的取舍：**要讲清楚就得占地方**。

我的判断是先讲清楚——因为这三句都是「不讲就会算错数」，不是装饰。但如果真机上觉得橙色块太密，最该压的是中间那块（`dishPriceNote` 39 字），可以缩到 1 行：`「顾客支付」按成本卡售价算，不是这一单实收`（22 字）。代价是丢掉「加价/满减」这个解释——老板会少一个理解「为什么不一样」的抓手。

**这一点我不替你决定，等你扫真机看过再说。**
