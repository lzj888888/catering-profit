# PLAN_2026-10-09 · 已导入账单「查看 + 清除」方案（R252）

> 触发：R251 真机报障第 ④ 问 ——「菜品毛利复盘没有清除键 或者其他键正常吗？只有一个 去映射。」
> 诊断结论：**「去映射」名不副实**（跳的是「去建卡」页），而 `external_sales_daily`
> **全站只有写入、没有删除**（写 3 处 / 读 1 处 / **删 0 处**）⇒ 导错了无法挽回，
> 且**没有任何界面能看到"我到底导过什么"**。这是真缺口，本轮补齐。

## 一、缺口定性（源码坐实）

| 面 | 现状 |
|---|---|
| 写入 | `importSalesBill` 3 处 `.set()`（外卖账单 `:110` / 堂食菜品 `:193` / 形态C 外卖商品 `:311`） |
| 读取 | `getDishReview` 1 处 `da.listAll` —— **只读来算毛利，不告诉用户"有什么"** |
| 删除 | **0 处**。唯一"撤销"手段 = 同 `_id` 重导覆盖（`BILL_<店>_<平台>_<日期>` 是确定性的） |
| 界面 | 复盘页只有一个「去映射」按钮（实为跳 `/pages/card/index` = **去建卡**，名不副实） |

⇒ 用户真实遭遇：**导错平台 / 导错日期 / 导了空模板** ⇒ 数字脏掉，**既看不见、也删不掉**。

## 二、方案（两函数，读删分离，符合本仓"读侧鉴权+纯算法+validate 三层"）

### 2.1 `getSalesBills` —— 读侧：我导过什么

- **入参**：`{ shop_id, biz_date_from?, biz_date_to?, platform?, include_cleared?, client_request_id? }`
- **出参**：
  ```js
  { shop_id,
    list: [{ bill_id, kind:'bill'|'dish', platform, platform_name_key,
             biz_date, row_count, qty, amount_fen, cleared, cleared_at }],
    summary: { active_bills, cleared_bills, active_rows, platforms:['pos','taobao','jd_order'] },
    truncated, client_request_id }
  ```
- **聚合口径**（🔴 关键）：按 **`_id` 前缀分组**，不是逐行返回：
  - `BILL_<shop>_<platform>_<biz_date>` ⇒ 1 行 = 1 条"账单级"记录（`row_count` 恒 1）
  - `SALE_<shop>_<platform>_<biz_date>_<seq>` ⇒ 按 `(platform, biz_date)` 聚合成 1 条
    （`row_count` = 该组行数，`qty`/`amount_fen` 求和）
  - ⇒ 用户看到的是「**淘宝闪购 2026-10-08 · 51 道菜 · 118 份 · ¥1823.08**」这种可读行，
    而不是 51 行原始数据。**这正是 R251 里"看不见"的正解**。
- **`include_cleared`**：默认 `false`（只看生效的）；`true` 时含已清除（走 `listIncludingDeleted`
  + 手动滤 `is_deleted:true`），用于"我上次清掉的是哪条"的追溯。
- **鉴权**：`resolveAuth` + `assertShopOwner`。**不加付费墙**（用户要看自己导的数据 = 基础能力）。

### 2.2 `clearSalesBills` —— 写侧：撤销导入

- **入参**：`{ shop_id, targets:[{platform, biz_date, kind?}], all?:false, client_request_id }`
- **出参**：`{ shop_id, cleared_rows, cleared_bills, client_request_id }`
- **实现**：
  1. 🔒 幂等（重放形态）：`findPriorResult` 命中即返回首次结果（**在函数头部，早于任何业务写**）。
  2. **软删，绝不物理删除**：走 `common.dataAdapter` 同款 `is_deleted:true` + `delete_at` + `delete_by`
     （与全仓 `softDelete` 口径一致；`_id` 直接可用）。
  3. 🔴 **显式上限**：`MAX_CLEAR_ROWS = 5000`，超出 ⇒ `fail(INVALID_PARAM, '单次清除超过 N 行，请分批')`。
     理由：云函数有执行时限，无上限的循环删除会超时且**半途而废**（部分删部分没删 = 更坏的状态）。
  4. **`all:true` 需二次确认位**：`{ all:true, confirm_all:true }` 双字段齐备才执行全清
     （防误触把整店销量清空）。
  5. 审计：`writeAudit({ action:'CLEAR_SALES_BILL', before_data:{targets}, after_data:{cleared_rows} })`
     —— 留痕可追溯（**清除是危险操作，必须可回溯精确到删了哪些行**）。
- **鉴权**：`resolveAuth` + `assertShopOwner`（A 类，无需登记 PUBLIC_FNS）。

### 2.3 为什么不复用 `importSalesBill`

`importSalesBill` 的入参面是 **`fileID`（必须上传文件）**，职责是"解析并落库"。
「查看」是**零文件纯读**，「清除」是**按目标软删**——两者都**不涉及 xlsx 解析**，
塞进 `importSalesBill` 会让它的 `validate.js` 变成四不像。⇒ **新增 2 个函数**，
职责单一，各自 `validate.js` 独立（R56 立约）。

## 六、边界（明确不做）

- ❌ **不物理删除**（软删，与全仓一致；数据可追溯）。
- ❌ **不碰成本卡 / M1 / 台账**（复盘页只读红线不变）。
- ❌ **不做"清除后自动重算"** —— 清除只改 `is_deleted`，复盘下次读取自然不含（无需触发任何重算）。
- ❌ **不做定时清理 / 自动过期**（用户显式操作为准）。
