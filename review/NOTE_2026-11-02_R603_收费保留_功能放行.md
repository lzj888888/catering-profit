# R603 · 收费保留、功能放行（修正 R602 的方向错误）

> 日期：2026-11-02
> 触发：李老师「导出、套餐、外卖、复盘为什么要显示功能完善中？个人也支持这些功能呀。你先不改，先沟通。」
> 结论：**收费设计全部保留，功能全部恢复可用；主体类型只影响最后一层支付通道与提交材料。**

## 1 错在哪（一句话）

R602 把「关闭收费」实现成了「关闭功能」：闸门挂在 `utils/paywall.js::openPaywall`，
而它的 **11 个调用点全部是「付费域判定失败后的出口」**，不是购买按钮。
关掉之后真实表现是：

| 场景 | R602 之后的表现 | 用户感知 |
|---|---|---|
| 外卖点「计算 / 反算」 | `onCalc` 判未开通 → 弹「功能完善中」→ return | 算不了 |
| 团购点「算到手」 | 同上 | 算不了 |
| 单品毛利复盘 | 后端 `FEATURE_LOCKED` → 整页 locked | 打不开 |
| 导出（成本卡 / 月报） | `onExport` 判未开通 → 弹窗 → return | 导不出 |
| 套餐卡保存 | `saveCostCard` 返 `FEATURE_LOCKED` | 存不了 |
| 第 2 家店 / 超 20 张卡 | `checkQuota` / `getShopList` 命中上限 → `openPaywall('saveLimit')` | 建不了 |

而门禁 **227/227 全绿** —— 因为守卫只回答「闸门在不在」，没有一条回答「关掉之后功能还能不能用」。
这是本仓「守卫只守分支在不在，不守分支到不到」的同族第九例。

## 2 正确形态

| 阶段 | 功能 | 收费入口 | 开关 |
|---|---|---|---|
| ① 免费期（现在） | **全开** | 不展示、不建单 | `PAYWALL_ENABLED=false` ⇒ `FREE_ACCESS_MODE=true`；云端 `FREE_ACCESS=true` |
| ② 开卖 | 按权益 | 月 / 季 / 年 | `PAYWALL_ENABLED=true`；云端 `FREE_ACCESS=false` |

- 开关**派生**而非并列：`FREE_ACCESS_MODE = !PAYWALL_ENABLED`，从根上排除「关售卖但仍拦功能」的半开半关态。
- 配额（1 店 / 20 道菜）是**产品额度**，不是收费：免费期仍保留，但提示语改为「当前版本最多支持 N」，
  不再复用「功能完善中」（后者会让用户以为功能坏了）。

## 4 守卫与变异

新增两条正面判据（这次守「功能还能用」，不是「闸门还在」）：

- **L9-⑦**：关闭态下前端 `fetchEntitlement` 与后端 `hasFeature` 都必须有免费期短路，
  且短路必须**先于**取库；附带无短路影子样本必须判红。
- **L9-⑧**：云端 `FREE_ACCESS` === `!前端 PAYWALL_ENABLED`，且前端必须由开关派生。

L9-③ 扩面：`showNotOpen` 与 `showFreeLimit` **两个函数体**都扫禁词（新增「升级」「付费」），
防「配额弹窗里写升级后可开 N 家」被判绿。

真实变异 **3/3 全部按预期判红**（`review/evidence/r603_free_access/mut_free.py`）：

| 变异 | 结果 |
|---|---|
| M1 删前端 `fetchEntitlement` 短路 | L9-⑦ 红 |
| M2 删后端 `hasFeature` 短路 | L9-⑦ 红 |
| M3 云端 `FREE_ACCESS` 翻面 | L9-⑧ 红 |

还原后三文件 md5 与基线一致（脚本含 SIGTERM/SIGINT 显式还原，防残污）。

## 5 主体与收费模型

→ `review/PLAN_2026-11-02_收费模型与主体路线.md`（模块免费/收费矩阵、月季年档位、个人 vs 个体户差异、支付接入拆解）。

三条要点：

1. **功能零差异**：个人与个体户能用的功能完全一样。
2. **代码只差最后一步**：`wx.requestPayment` 与 `wx.requestVirtualPayment` 二选一；
   订单/权益/幂等/续费逻辑共用。现状两条路都还没接（前端只留了注释占位）。
3. **虚拟商品强制虚拟支付**（2026-04-01 起）⇒ 个体户的商户号对本业务用不上，
   主体选择实际不改变代码路径，只改变提交材料与限额。
