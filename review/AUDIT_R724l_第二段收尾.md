## 3. 各守卫的关键判据

### 3.1 pay/orders（30 断言）

最贵的不是订单渲染，是**续费入口三重门**：`PAYWALL_ENABLED && !isIOS() && (expire_at===0 || days_left<=30)`。
提审期入口可见 = 在小程序内售卖虚拟商品的表态；iOS 可见 = 苹果审核红线。
`onRenew` 还有**第二道纵深**（防 wxml 改版 / deep link 直达）：开关关 ⇒ `showNotOpen` 且绝不调 `payRenew`。
另守权益查询失败**静默吞掉**（不阻断订单列表）、`enable_real_payment=false` 弹联系客服、下拉刷新收起动画。

### 3.2 sandbox 两页（45 断言，放同一进程）

**为什么合一**：两页共享同一份 `getPlan` 数据。R297-④ 抓到过真 bug ——
反推方案在 compare 读顶层 `target_monthly_fen`、在 list 读 `snapshot.reverse.*`
⇒ **同一方案两页显示两个数**，单页桩永远证不了。F 组做跨页对拍。

测试样本特意把顶层设成**陷阱值 9999999 分（100000 元）**、reverse 块 1500000 分（15000 元），
谁读错一眼可见（否则断言恒真）。

其余守：勾选态算进 `plans`（WXML 不支持方法调用，R297-⑥ 的「点了没反应」）、最多 3 个、
跨场景提示但不阻止、`param_json` 原样透传实时重算、`onReady` 预热画布首击出图、
Excel 免费不主动弹墙（FEATURE_LOCKED 仅旧后端兜底）。

`check_bill_import_gate` 的 S-④ 原是 `/check_salesbills\.js/.test(verifyAll)` —— **对全文做正则**，

## 4. 顺带修正的一处判据设计缺陷

`L-⑥` 第三次因为「修得太快」判红（deferred 只剩 2 条，下界还是 3）。
连续两次为同一件事调数字，说明判据设计错了 —— **把「修复进度」和「台账完整性」绑在一起**，
等于每修一条就回来改一次门禁，还会诱使人为了喂绿去「留着不修 / 编造待办」。

改成 `deferred >= 1`，并拆清职责写进注释：
条目不许删 → L-①（总数 ≥17）；不许假装修 → L-⑤（fixed 必带 fix_evidence + challenge）；
待办不许没主人 → L-⑥ 后半；台账不许被清空 → L-⑥ 前半（真变 0 就该重新开盲区扫描，判红是对的）。
**这是最后一次调这个数。**
