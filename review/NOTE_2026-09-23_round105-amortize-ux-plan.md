## §2 逐条诊断

### F2 · 「一次性计入当月」没有金额入口（真缺陷）

**现象**：选「一次性计入当月」，该区块**什么都不出现**——没输入框、没跳转、没摘要。

**四层互证**：

**① UI 层** —— `pages/month/input.wxml:332-348`

```html
<!-- ② 装修设备 -->
<view class="cm-opt {{amortizeOn ? '' : 'on'}}" data-kind="amortize" data-val="0" bindtap="onPickMethod">
  <view class="cm-opt-h"><text wx:if="{{!amortizeOn}}">✓ </text>{{t.cmAssetOnce}}</view>
  <view class="cm-opt-d">{{t.cmAssetOnceDesc}}</view>
</view>
<view class="cm-opt {{amortizeOn ? 'on' : ''}}" data-kind="amortize" data-val="1" bindtap="onPickMethod">
  ... {{t.cmAssetAmortize}}
</view>

<block wx:if="{{amortizeOn}}">                    <!-- ⚠️ 只有"按月分摊"才渲染 -->
  <button class="btn ghost" bindtap="goAmortize">{{t.cmAssetGo}}</button>
  <view class="cm-state">{{assetSummary || t.cmAssetEmpty}}</view>
  <view class="hint">{{t.cmAssetHint}}</view>
</block>
```

未选「按月分摊」时**整个入口区不渲染** ⇒ 既没有金额框，也没有任何提示。

**② 文案层** —— `miniprogram/i18n/terms.js:566-567`

```
assetOnce:     '一次性计入当月',
assetOnceDesc: '金额不大，就当这个月的费用',        // ← 向用户承诺"会当月费用"
```

**③ 引擎层**（round94 已实跑留证）—— 开关关时 `effectiveAmortizeFen = 0`（`cloudfunctions/saveLedger/service.js:25`），且利润引擎入参面（`incomeItems/expenseItems/directConsumeFen/amortizeFen/inventory/pendingSettlementFen`）**没有任何"资产原值直接进费用"的通道**。

**④ 对照文案自相矛盾** —— `terms.js:392`（运营费用口径）

```
不包括设备与装修购置（走「摊销资产」分期摊）
```

⇒ 用户按开关文案理解 = 以为已计入（实际没有）；用户按费用段文案行事 = 不填这笔钱。
**两条路都通向"这笔钱不出现"** ⇒ 刚装修完开业的店，首月利润显著虚高。

**定性**：功能缺口，不是取舍。三个"应该存在"的地方（UI 入口 / 引擎入参 / 文案一致）**同时缺失**。

### F4 · 点「追加采购」窗口变透明、叠在原窗口上（真缺陷，根因已确证）

**根因：面板背景色与页面底色是两个完全相同的值。**

| 文件 | 选择器 | 角色 | 背景色 |
|---|---|---|---|
| `pages/month/amortize.wxss:8` | `.sheet` | 摊销页新增/编辑面板 | **`#f5f6f8`** |

### F3 · 点「编辑」数值没法改变（真缺陷，**根因未定性**）

**已回源排除的**：

| 排查项 | 结论 | 判据 |
|---|---|---|
| `onEdit` 取值是否算错 | **无问题**。`a.value` = `"120000.00"` → `Number(×100)` = `12000000` → `fenToYuan(...,2)` = `"120000.00"` | `amortize.js:187` |
| `fenToYuan` 是否输出千分位（会导致 `Number()` 得 `NaN`） | **无问题**。实现是 `(Number(fen)||0)/100` 后 `.toFixed(d)`，**无千分位** | `utils/api.js:61-65` |
| 输入框是否被 `disabled` | **未禁用** | `amortize.wxml:90` |
| 保存后是否重拉列表 | **会重拉**：`saveAsset` 成功后 `this.load()` | `amortize.js:240` |
| 后端编辑分支是否写 `value_fen` | **写了** | `saveAsset/index.js:47-53` |

**候选根因**（按可能性排序，**均须实测**）：

1. **与 F4 同源** —— 面板与底色同色 ⇒ 输入框视觉上难以辨认/难以定位 ⇒ 用户主观感受为"点不进去、改了没用"
2. **`catchtap=""` 空 handler 是否真的阻止冒泡** —— 若不阻止，点面板内部会冒泡到 `.mask` 的 `bindtap="onCancelForm"`，表现为**一点就关**。
   ⚠️ 但同一写法在 `input.wxml` 粘贴面板上**可用**（有历史验证记录）⇒ 此条可能性**下降**
3. **键盘 `adjust-position="{{true}}"`（`amortize.wxml:90`）顶起后布局错位** ⇒ 输入框被顶到屏幕外
4. **用户所指是"改完保存、回列表仍是旧值"** —— 若是，则问题在别处（但见上表，后端确实写了 `value_fen`）

**复现步骤（下批第一件事）**：模拟器 → amortize 页 → 新增一笔 → 点「编辑」→ 改金额 → 保存 → 看列表与页面 state `{showForm, formValueYuan, editing}`。

> 本轮**无法实测**：IDE 主窗口不在（`EnumWindows` 只探到 `237x39` 的两个条目，非 1875×1034 的 IDE 主窗）⇒ 模拟器通道起不来。见 §5。

### F5 · 命名 + 摊销种类 + 留存数据

#### (a)「追加采购」的语义覆盖率不足

**现状语义**：同一资产再投一笔 —— 新行 + `group_id` 指向首笔 + `batch_seq` 序号，**每笔从各自开始月独立起摊**（`amortize.js:162-178`、`saveAsset/index.js:62-64`）。

**李老师列举的场景 vs 该词适配度**：

| 场景 | 「追加采购」读起来 | 实际要做的事 |
|---|---|---|
| 首次装修 → **二次装修** | 别扭（装修不叫"采购"） | 再加一笔 |
| 买 1 台冰柜 → **再买 1 台** | 通顺 | 再加一笔 |
| **加盟费**（一次性） | 不存在"追加" | — |
| 招牌 / 制作 | 勉强 | 再加一笔 |
| **转让费 / 品牌使用费 / 进场费** | 不通 | 再加一笔 |

⇒ 该词**只覆盖"设备采购"一类**，而规范明确要求装修 / 加盟费 / 转让费 / 品牌使用费 / 进场费**走同一摊销模型**。

**规范原文** `specs/dev-specs/core/开发规范v1.0_ModuleM1_月度盈利核算.md:56-57`：

```
一次性花出、受益跨多月的资本性支出：装修（24/36 月）、设备（36–60 月）、加盟费（按合同）、招牌/制作等；
转让费、品牌使用费、进场费等按同一摊销模型处理（shop_amortize 无资产类型枚举，按名称自由录入即可）。
- 二次装修不覆盖旧账（旧资产继续摊完，新资产新开一条）。
```

⚠️ **注意最后一句**：规范对"二次装修"的取向是**新资产新开一条**（独立一组），而不是"同一资产追加一笔"。
⇒ 这直接影响命名与交互，**必须李老师拍板**（见 §3.4 / P3）。

#### (b)「留存数据」现状盘点

| 李老师想要的 | 现在有没有 | 数据够不够支撑 |
|---|---|---|
| 后面月份还剩余多少**未摊销** | **无**（页面不显示） | 够。`total_value − 已摊额`（引擎可逐月算） |
| **当月追加了多少** | 只能看到"已登记 N 笔资产"（`terms.js:571`） | 够。`group_id` + `batch_seq` + `start_month` |
| **对利润的影响** | 只有"当月摊销合计"（`amortize.js:49-50`）；录入页**拿不到**这个数 | 够。`getAmortSchedule.total_amount_fen` |

**关键落差：规范定义的 3 个字段没有落库**

| 规范要求字段（`ModuleM1:87/89/90`） | 含义 | `saveAsset` 是否落库 |
|---|---|---|
| `end_month` | 自然到期月（系统算，只读） | **否** |
| `monthly_amount` | 月摊销额（分） | **否** |
| `residual_loss` | 终止时未摊残值（转处置损失） | **否** |

`saveAsset/index.js:58-65` 实际落库的只有：`asset_id / id / shop_id / name / value_fen / start_month / total_months / terminate_month / group_id / batch_seq`。

⇒ 现在的做法是**全部现算**（三个引擎副本各自算），**没有以字段形式留档**。
对本轮的"留存数据展示"**不构成阻碍**（现算即可），但属规范与实现的既有落差，单列（见 P5）。

**并附一条必须拍板的前置**（P3）：**二次装修算哪种**？

| 选项 | 语义 | 后果 |
|---|---|---|
| ① 同一资产追加一笔 | 二次装修 = 首次装修那一组的 batch 2 | 组内两笔**独立起摊**，但**组名还是"装修"** |
| **② 新资产独立一笔** ⭐ | 二次装修 = 名字写"二次装修"的**新资产** | 两笔各自成组、各自摊完；**规范原文倾向此**（`ModuleM1:57`） |

### 3.5 F5(b) 留存数据展示（**方案**）

**摊销页每个资产组增加只读信息**（纯展示，不改任何计算）：

```
装修                                          [共 1 笔]
  资产原值        ¥240,000.00
  本月摊销        ¥ 10,000.00
  ────────────────────────────────────────
  已摊 12/24 期 · 剩余未摊 ¥120,000.00
  摊完月份        2027-12
```

多笔组展开后，**每笔各显示自己的一行**（`已摊 x/N 期 · 剩余未摊 ¥Y · 摊完 YYYY-MM`）。

**录入页**（round94 D5 已提过、本轮一并纳入）：摊销开关开时，在费用段显示一行只读
「本月摊销合计 ¥X（N 笔，点开看明细）」。

**技术实现（三原则）**：

1. **全部现算，不新增落库字段**
   - 已摊期数 = `clamp(当前月, 开始月, 截止月) − 开始月 + 1`（区间外为 0）
   - 剩余未摊 = `total_value − 已摊额合计`
   - 摊完月份 = 截止月（`naturalEnd` 或 `terminate_month`，规则已有）
2. **算法单源** —— 剩余额必须**调用引擎**（`cloudfunctions/getAmortSchedule/service.js` 的 `amountForMonth`），
   **不在前端重算**（对齐 `amortize.js:3` 的"计算下沉"纪律）。
   建议后端直接多返回两个字段：`paid_months` / `remaining_fen`，前端只格式化。
3. **零改动既有公式** —— 摊销计算规则（月摊取整到分 / 末月倒挤 / 含两端 / 终止当月仍摊）一字不动。

⚠️ 若要**落库** `monthly_amount` / `residual_loss` / `end_month`（规范要求），属**独立议题**（涉存量数据回填），
建议单列（见 P5）。本轮展示方案**不依赖**它。

## §6 F1 打包费：拿到图后我会看什么（把判据先说清楚）

**为什么这个问题重要**：系统按**总额法**录外卖收入 = `商品总价 + 打包费 + 商家活动补贴`（`terms.js:327`）。
若**账单的「商品总价」本身已含打包费**，用户再单独填一次打包费 ⇒ **打包费被重复计入 ⇒ 收入虚高**。

**系统的现有护栏**（不改口径，只提示）：
`terms.js:335` `recPack`：「差额与打包费金额相等，请核对账单「商品总价」是否已含打包费（避免打包费被重复计入收入）。」
—— 触发条件在 `utils/takeaway.js:253`（**差额恰等于打包费合计** ⇒ `packaging` 专项，先于"漏填"判断）。
⚠️ **但该护栏依赖用户填「账单商家应收款」这个选填项** ⇒ 只填总额的用户触发不到。

**拿到结算图后，我会按三条判据给确定结论**：

| # | 看什么 | 推断 |
|---|---|---|
| 1 | 账单是否**单列**「打包费」行 | 单列 ⇒ 商品总价**通常不含**打包费（两者并列） |
| 2 | 验算 `账单的商品总价` ?= `菜品明细金额之和` | 相等 ⇒ **不含**；差恰等于打包费 ⇒ **已含** |
| 3 | 该单来自哪个平台（美团 / 饿了么 / 抖音） | 平台规则不同，需按平台分别定论 |

**规范现状**：这一项在 `delivery/R85_外卖段录入_提示词:83` 里被明确标为**「未经真实账单验证」**的 V1–V3 之一
⇒ 那张图是**唯一能结案的证据**。图给我，我当轮出结论并落库到规范。
