## 三、发现（按严重性）

### 🔴 E-1 菜单毛利率按「售价」加权 ⇒ 数据 100% 正确也对不上账

`utils/reconDerive.js:37-42` 的注释自承「权重 = 售价，隐含各菜品销售额均匀假设」。

**复现**：青菜 12 元 / 成本 4 元（毛利 66.7%），招牌鱼 88 元 / 成本 60 元（31.8%）；实际卖青菜 300 份、鱼 20 份。

```
菜单标准毛利率（Σ成本÷Σ售价）  = 36.00%
真实加权毛利率（按实际销量）    = 55.22%
对账 diffPp = +19.22  diffFen = 1030.19 元  suppressed = false
```

老板**成本、售价、销量全部正确**，账本与销量完全一致，系统却告诉他「实际比标准高 19.22 个点、差 1030 元」。

**为什么必然发生**：餐馆的常态就是便宜菜卖得多、贵菜卖得少。便宜菜毛利高 ⇒ 真实加权恒高于售价加权 ⇒ 偏差方向**永远是正**。老板每次打开对账都看到同一句「你实际比标准高」，久了就不看了——而这页是他判断「成本是不是记漏了」的唯一入口。

**与已发现 A 的关系**：A 是「卡建多了」稀释分母；这条是**分母权重错误**，与卡数无关，无法靠填对在售菜品数修复。

**建议**：有销量表时按销量加权（排行榜已有每菜销量）；没有销量表时退回售价加权，但必须在页面上写明「这是按售价估算的，不等于你实际的菜结构」。

---

### 🟡 E-2 同名两张卡：销量归谁取决于数据库返回顺序，且后果没告知

`getDishReview/service.js:42-46` 用 `Map` 建「菜名 → card_code」，**后写覆盖先写**。`saveCostCard` 不做同名拒绝。

**复现**：两张卡都叫「酸菜鱼」，成本 30 元 / 18 元，卖 10 份 880 元。

```
cards 顺序 [大份, 小份] → 匹配小份  毛利 700 元  毛利率 79.55%
cards 顺序 [小份, 大份] → 匹配大份  毛利 580 元  毛利率 65.91%
```

同一笔生意，**只因 DB 返回顺序不同，毛利率差 13.64 个点 / 120 元**。

**已有什么**：建卡页 `confirmDupName` 会弹「已有同名卡，继续新建会出现两张同名卡」。提示存在，但**只说会出现两张，没说后果**——两张同名卡时，导入的销量只会算到其中一张，另一张永远显示 0 销量，且没有任何补救提示。

**建议**：`dupCardTip` 补一句后果；排行榜对「同名多卡」给一条提示。

### 🟡 E-3 半份销量被按全份结转成本（成本高估 20%）

豆包②题 7：拍黄瓜 200g、800 分/kg ⇒ 整份 160 分；20 整份 + 10 半份。正确答案 4000 分。

```
实际 4800 分  ❌  （把 10 份半份按全份 160 分结转）
```

**触发条件**：外卖/收银销量表**不区分规格**（平台通常就把半份也叫「拍黄瓜」），而老板建了半份卡。

**方向是保守的**（成本虚高、毛利虚低），不会让老板误以为赚钱，但仍错，且会把「该推的菜」推出榜单。

**已有什么**：如果两边菜名都带括号（「拍黄瓜（半份）」），NFKC 归一后能正确匹配（实测通过）。所以**唯一解是让用户建带规格后缀的卡**——需要一个引导，而不是改算法。

---

### 🟡 E-4 两个口径利润恒等，页面没说「为什么切换看不到变化」

`utils/takeawayDerive.js:127-137`：到手 `receipt − 菜品 − 包材`，总额法 `revenue − expense − 菜品 − 包材`，展开后**恒等**。

```
顾客支付 3200 / 佣金 480 / 配送 320 / 成本 1200
到手口径 profit = 1200      总额法 profit = 1200      差 = 0
```

会计上这是**对的**（无应收应付时两制相等）。但老板切了口径发现数字一分没变，会以为功能坏了——这正是李老师真机第 ④ 点「到手口径/总额法很多人不理解」的直接原因。

`TERMS.card.modeCashDesc / modeAccrualDesc` 写了两视角，但**没写「利润必然相同」**。

**建议**：两段说明各补一句——「两种算法算出的利润必然相同；差别在它怎么解释这笔钱：到手看现金流，总额法看利润表结构、和月报对得上。」

---

### 🟡 E-5 原料停用/删除后，成本卡仍按最后采购价计，且无提示

```
qty=10 成本 = 1000 分（按停用前最后采购价），无任何「原料已停用」提示
```

成本卡存的是**落库快照**（`total_cost`），这是正确设计（历史卡不该被追溯改写）。但「这张卡引用的 3 个原料已经停用了」是老板该知道的事——他以为成本还是当前价。

**建议**：卡片详情/版本页加一行「本卡引用的 N 个原料已停用或删除」。

### ⚪ 契约缺口（页面路径**不可达**，仅供未来调用方注意）

| 编号 | 现象 | 为什么现在不可达 |
|---|---|---|
| E-6 | `reconcile` 对 `coverage = NaN / 'abc' / Infinity` **放行**（`== null` 挡不住，`NaN < 0.6` 恒 false） | 页面在 `savedCount <= 0` 时已置 null；上游 `|| 0` 也不会产 NaN |
| E-7 | `rankReview` 对 `total_cost = 0` 的卡不标记，会以 100% 毛利排第一 | `doSave` 第 49 行拦空行、云端 `validate` 拦空数组 ⇒ 存不进空 BOM |
| E-8 | `rankReview` 遇空 `dish_key` 静默 `continue` | 写入侧 `importSalesBill` 已把空菜名归 unmatched |
| E-9 | version 是字符串时按字典序比较（`'10' > '3'` 为假 ⇒ 取错版本） | DB 存 number |
| E-10 | `settleSummary.netRatePct` 只有整数百分比，其他毛利率是 2 位 | 展示口径不统一，非计算错 |

E-6 值得提前修：H5 诊断/Excel 导出若复用它，`NaN` 会静默放行一个失真的对账结论。改动只有一行（判 `Number.isFinite`）。

## 四、通过的部分（可放心）

- **出成率夹紧**：`0 / 101 / -5 / null / '90'` 全部正确夹到 100，字符串数字也能解析
- **退货负数**：`+10 / −2` 正确冲销为净 8 份、成本 9600 分，不产生负库存
- **赠品成本**：实付 0 的 2 份仍计入成本 600 分，毛利算对 6400
- **菜名归一化**：`trim + NFKC` 生效（全角「ＡＢ」→「AB」）；内部空格与括号**刻意保留**是设计（靠映射表解决），59 份副本 MD5 **全一致无漂移**
- **半份规格系数**：主料 ×0.5、辅料 ×0.7、调料 ×1、包材 ×1 —— 这正是行业「半份定价 = 全份 65%」的成因，设计专业
- **空 BOM 双拦**：前端 `doSave` + 云端 `validate` 两道，拦得住
