# R370 · 活动卡：修错数 + 缩成「保本门槛」+ 纯堂食口径

> 2026-10-20 李老师：「听你的，然后这个活动**和外卖没关系**，这个是**纯堂食**的活动。」

## 一、修掉的那个必现错数

同一张卡上两个数对不上（实测 F=3500 / 毛利率 63% / 打 8 折 / 全部参与）：

| | 改前 | 改后 |
|---|---|---|
| 保本 | 5,556 → 6,512（**+17.2%**） | 5,556 → **8,140（+46.5%）** |
| 打平要多卖 | **46.5%** | 46.5% |

**根因**：`beAfterYuan = fixed / ga` 是**实收口径**，而 `beBeforeYuan = fixed / G0` 是**原价口径**，
两个不同口径相除 ⇒ 涨幅被系统性低估 29 个百分点。

**改法**：
- `beAfterYuan` 改为原价口径 `fixed / (G0 − cut − a·(1−cut))`；
- 新增 `beAfterNetYuan`（现金实收）只做说明用；
- 页面文案：`{a} → {b}（+{p}%，其中现金实收 {n}）` —— 主数是老板要做的流水，实收是括号里的补充。

## 二、纯堂食口径（他这句提醒纠正了一个隐性放大）

原来活动基准取 `r.margin_rate` = `(菜品毛利率 − 渠道费率)/100`，**已经扣过外卖抽成**。
拿它算**堂食**活动 ⇒ 把外卖佣金算成活动的代价 ⇒ **高估活动伤害**（渠道开得越大，错得越多）。

⇒ 改为 `this.data.marginPct`（菜品毛利率，菜单口径）。守卫里钉了一条：
`const marginPct = Number(this.data.marginPct);` 必须存在。

## 三、缩小成「保本门槛」：三控件 → 两输入

| 删掉 | 保留/新增 |
|---|---|
| 折扣档 chips（9/85/8/7 折） | **折扣后实收率**（%）：实收 ÷ 原价 |
| 几成订单 chips（10/30/50/80/100%） | **活动成本率**（%）：赠酒/奖品/自贴券 ÷ 实收 |
| `promoApproxNote`（单数近似说明） | —— 不再按订单占比算，自然不需要 |
| `onPromoD / onPromoW / PROMO_D / PROMO_W` | `onPromoCostInput / promoNetRateOf` |

理由（李老师此前也认同）：折扣档本质是在替老板反推实收率，而他手上直接有"实收 ÷ 原价"这个数；
多一组 chips 就多一层"我选哪个"的困惑。

## 四、公式（含豆包补充的活动成本项）

```
cut   = 1 − 实收率
numer = G0 − cut                    ← 占原价
net   = numer − a × (1 − cut)       ← a = 活动成本率（占实收）
GA    = net / (1 − cut)             ← 活动期毛利率（实收口径）
保本(原价) = F / net
现金实收   = F / GA
多卖 % = G0 / net − 1
```

## 五、实测（模拟器真跑，非纸上）

```
实收率 80%        → GA 56.3% · 保本 5,385 → 7,778（+44.4%，现金实收 6,222）· 多卖 44.4%  ✅ 两数一致
80% + 成本 5%     → GA 51.3% · 保本 5,385 → 8,537（+58.5%，现金实收 6,829）· 多卖 58.5%  ✅
实收率 120%       → 明确报错（bad），不再静默按 100% 算                        ✅
```

手算核对：`(0.65−0.2)/0.8 = 56.25%`、`3500/0.45 = 7,778`、`3500/0.5625 = 6,222`；
带 5% 成本：`net = 0.45 − 0.05×0.8 = 0.41` ⇒ `3500/0.41 = 8,537`、`GA = 51.25%` ✔

## 七、没做的（如实）

- **没做**"引流增幅"输入：增量是假设不是事实，硬算就是编（豆包同判）。
- **没做**活动 ROI：需要对照组/AB，我们拿不到。
- 储值卡、团购核销、品牌曝光 —— 明确不适用本模型（见 R369）。
