## 1. F4 —— 弹窗「透明叠加」（真缺陷）

**现象**：点「追加采购」，弹窗看起来是透明的，和原来的摊销窗口叠在一起，没法操作。

**根因（值级确证）**：

| 事实 | 位置 |
|---|---|
| `.sheet` 面板底色 `#f5f6f8` | `pages/month/amortize.wxss:8`（改前） |
| `page` 背景色 `#f5f6f8` | `app.wxss:7` |
| 遮罩是半透明黑 | `amortize.wxss` `.mask { background: rgba(0,0,0,.45) }` |

⇒ **面板底色与页面底色完全同值**，遮罩又是半透明的 ⇒ 面板「消失」在页面里，视觉上就是一层透明窗口叠在原窗口上。

**对照组（证明是底色问题、不是结构问题）**：`pages/month/input.wxss:72` 的 `.paste-sheet` 用 `#fff`，且是**同结构**（`.mask` + `*-sheet` + `catchtap=""` 阻止穿透），行为正常。

**改法**：

```css
.sheet { width: 100%; background: #fff; border-top: 1rpx solid #e6e8eb; border-radius: 24rpx 24rpx 0 0; … }
.sheet .field { background: #f7f8fa; }
```

面板改白底 + 顶部加一条细线定边界；**行底同时改灰** `#f7f8fa` —— 原设计是「白行配灰面板」，换成白面板后行必须变灰，否则行与面板糊成一片。

**同类扫查**：全仓 grep `#f5f6f8`，确认**不存在第二处**「把页面底色当面板底色」的写法。

## 2. F2 —— 「一次性计入当月」没有任何金额入口（真缺陷，且影响利润口径）

**现象**：装修设备选「一次性计入当月」，**整块什么都不显示**，没有数值输入框。

**根因**：`pages/month/input.wxml` 该段**只有 `wx:if="{{amortizeOn}}"` 一个分支**，**没有 `wx:else`** ⇒ 选「一次性」时整段渲染为空。

**危害（不是纯 UI 问题）**：文案已经承诺「金额不大，就当这个月的费用」，但全页没有任何地方能把这笔钱记进当月 ⇒ **当月利润虚高**。

这正是 round94 回执登记、一直挂着的 **D2 待拍板项**，本轮拍板取 **P1 = A**（补金额入口，进当月费用）。

**口径设计（需与摊销互斥，防同一笔钱算两遍）**：

| 口径 | 公式 |
|---|---|
| 经营参考利润 | `收入 − 费用 − 直接食材消耗 − 一次性投入` |
| 全要素真实利润 | `收入 − 费用 − 真实食材消耗 − 摊销 − 一次性投入` |

即**两式都减**（与摊销不同：摊销只影响真实利润，不影响参考利润）。`amortizeSwitchOn` 为真时 `effectiveLumpSumFen` 归 **0**。

**三副本同源**：`saveLedger/service.js`、`getLedger/service.js`、`calcMonthlyProfit/service.js` 各内嵌一份 `calcMonthlyProfit` ⇒ 三处同源同口径同步（前两者 `Math.round`、后者 `fenRoundN`，沿用各文件既有纪律）。

**前端**：在 `amortizeOn` 分支后补 `wx:else` 金额框（`type="digit"` + `adjust-position` + `cursor-spacing`），state `lumpSumYuan`，提交 `lump_sum_fen: this.data.amortizeOn ? 0 : api.yuanToFen(this.data.lumpSumYuan)`。

**可选入参缺省语义（铁律）**：`lump_sum_fen` 是**可选**入参，**缺省 = 本次不动**（沿用库内现值），**绝不退回全 0 并整体覆盖**（round103 的原始教训，本轮复用于新字段）。选「按月分摊」时前端**显式送 0** ⇒ 清旧值（老板主动清空是正当表达）。

## 3. F5a —— 命名与引导文案（P2 = ①，P3 = ②）

| 改前 | 改后 |
|---|---|
| 按钮「追加采购」 | **「再投一笔」** |
| `batchWord`「采购」 | 「**投入**」 |
| —— | `scopeHint` / `appendHint` 重写 |

`appendHint` 现在把「什么时候用再投一笔」讲清楚了：同一项支出再次投入用「再投一笔」（如再买一台设备）；**若其实是另一件事（如二次装修），直接新建一个资产，别混进同一笔**。

理由：摊销种类很多（装修 / 固定资产 / 加盟费 / 二次装修 / 多次采购），「采购」只覆盖其中一类，会误导老板把二次装修也塞进同一笔。改名前已确认守卫**只锁 key 不锁文案** ⇒ 改名安全。

## 4. F5b —— 留存数据（P4 = 采纳）

新增展示（**全部由后端引擎算、前端只格式化**）：

| 位置 | 文案 |
|---|---|
| 单笔资产行 | `已摊 k/N 期 · 剩余未摊 ¥Y` |
| 单笔资产行 | `摊完 YYYY-MM` / 提前终止时 `已终止（YYYY-MM 月）` |
| 资产组行 | `共 n 笔 · 剩余未摊合计 ¥Y` |
| 资产组行 | `末笔摊完 YYYY-MM` |
| 录入页摊销摘要 | `本月摊销 ¥X（n 笔，点开看明细）` |

**算法单源（硬纪律）**：剩余额**必须由引擎逐月调 `amountForMonth` 累加**，前端只做格式化，**绝不重算**（对齐 `amortize.js:3` 既有注释的「计算下沉」纪律）。

```
起 = start_month；止 = min(自然到期月, terminate_month)
paidMonths  = mi < start ? 0 : (min(mi, end) - start + 1)
remaining_fen = total_value − Σ amountForMonth(start .. min(mi, end))
```

**边界覆盖**：提前终止（剩余额留着作处置损失）；末月倒挤（tail-difference 恰好摊完）。

## 6. 自我纠正（3 处，全部如实登记）

### 6.1 `lump_sum_fen` 首版误传 `allowZero`（守卫没抓到，我自己回头核对时发现）

```js
const lumpSumFen = f(src.lump_sum_fen, 'lump_sum_fen', true);   // ❌ 第三个参数必须不传
```

`f()` 的第三参为真时，**缺省会返回 `0` 而不是 `null`** ⇒ 与「缺省 = 不动」直接矛盾，正是 round103「缺省即覆盖」的坑**原样复发**。已去掉第三参并在代码里写死注释。

### 6.2 `saveLedger/validate.js` 漏回收 `f()` 的错误对象（行为验证抓到）

`f()` 校验失败时**返回错误对象，不是抛异常** ⇒ 漏写 `if (x && x.error) return x;` 会让字符串 / 负数被**静默放过**，最终 `num0` 变成 0。

**发现方式**：行为验证脚本（`_r106_verify.js`）的 A4 / A5 转红（`error = null`）。已补回收行。

### 6.3 `A9-⑨` 首版判据假红（**改判据，不改代码**）

首版写成 `/TERMS\.amortizePage\.paidProgress/`，而代码是**先 `const T = TERMS.amortizePage` 再 `T.paidProgress(...)`** ⇒ 判据绑死了「直连调用」这一种写法。

改为**语义级**判据：方法体内 `paidProgress` 在位 + `TERMS` 有来源 + **函数体内零中文字面量**（页面零硬编码）。

> 这是本仓**第三次**「判据绑死局部写法」自伤（round103 A7-①、round104 A8-⑧、本轮 A9-⑨）⇒ 已登记进守卫注释。
