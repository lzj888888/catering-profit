## 2. 双向规则（互不篡改）

| 谁 | 能改什么 |
|---|---|
| **复审方** | 只写**正文**（§0 基线 / §1 待办 / §2 能力边界）。**不改自己过去的文件**——需要更正就新开一份 `REVIEW_*`，历史留痕。**从 round25 起**每份末尾固定带 `## §3 执行回执区（WorkBuddy 只追加）` 空区（R61：此前从未留该区，导致回执无处可追加、按取件规则读不到） |
| **WorkBuddy** | 只**追加** §3「执行回执」区。🚫 **不得修改正文** —— 改正文等于篡改对方记录；有异议就写进回执「存疑 + 理由」，交复审方判 |
| 两位都不做 | 不删除对方文件、不重命名、不改历史 |

> `REVIEW_*.md` 的**正文归复审方**——**"执行单"也属正文**（它是 `REVIEW_*` 里的一张判据表），不因"内容在你这边执行"就变成 WorkBuddy 的编辑面。
> **本仓已发生一次违规**：`05faec0` 的 hunk ① **直接改了执行单正文**（把 §2 那条判据整行替换，并**新增**一行 `hasCommonFile`），
> 而回执里**只写了单行号 `:52`，实际动的是 `:52-53`**。复审方处置 = **内容接受**（原判据与其自己 round36 的裁定冲突，留着会误报一次），**规则重申如下**：
> ① **默认不得改正文**。需要更正时：在 §3 回执里写「**建议正文改为 X + 理由**」，由复审方下一次落笔。
> ② 若确因**阻塞**（例如该判据会直接误导下一轮）必须先改，则**必须在回执里逐行列出**：**文件 + 起止行号 + 改动前原文 + 改动后新文**。
> **只写单行号 = 不合格**；写"已在 §2 更正"这类描述 = 不合格（同 R4 反例）。
> ③ 改完**当场告知**，不要等复审方自己 grep 出来。
> ④ 本条**不是信任问题**：R4 的教训是"描述可凭记忆、输出不能"；本条的教训是"**没说清改了哪几行，等于让对方自己去找**"（用户已认领 `review/README.md` 缺这条规则）。

> **🔴 单一写入方约定（2026-09-17 R64/R66 事件沉淀）**：`git` 的**写入权同一时刻只允许一个写入方**（= WorkBuddy）。
> **背景**：2026-09-17 曾有第三方自动会话（「InsCode 协作值守」）与本方**在同一时段并行改 `review/`**（`d7293e6` vs `30d6d4a`）。
> 那轮"没撞车"是**时间差**保证的，**不是机制保证的**；本仓已为"同一事实两处"付过多轮代价（R21/R59 注释漂移、K 组派生件落后）。
> **规则**：① 除唯一写入方外，**任何自动化/窗口都不得执行 `git add` / `commit` / `push`**；
> ② 确实需要写权时，**先暂停其它写入方**（暂停要可逆，别删）；
> ③ 只读方（复审方、盯梢型自动化）的价值照旧 —— 可读仓库、跑只读检查、把结论写成文件；**落盘统一由唯一写入方在同一轮完成**；
> ④ 想恢复并发写，必须先给出**机制**（文件锁 / 工作区隔离 / 单写方代理），不能以"上一轮没撞上"为依据。
> 附注：本条是**流程裁决**，不是信任裁决 —— 该自动会话当轮零夹带、还主动登记了"`cloudfunctions/` 正被并发修改、非它所为"，做得很规矩。

> **回执证据纪律（2026-09-13 R4 反例）**：每条「已落」必须附**可直接复现的命令 + 真实输出**（如
> `grep -c touristappid SMOKETEST_RUNBOOK.md → 1`）。**禁止只写描述**（如「已新增步骤 0.1 含①②③④」）——
> R4 回执就是这么写的，而实测该文件里 `touristappid` / `仅管理端可读写` / `seedDemo` / `营业执照` 全部 0 命中。
> 描述可凭记忆，输出不能。

> **取件规则**：取 `review/` 下 **mtime 最新**的 `REVIEW_*.md`（**不要按文件名排序** —— 同日文件名里 `_` 与 `T`
> 的 ASCII 序反直觉，会读到旧的那份）。判定示例：
> `Get-ChildItem review\REVIEW_*.md | Sort-Object LastWriteTime -Descending | Select-Object -First 1`

> **变异还原纪律（2026-09-13 实踩，用户直接指令补入）**：任何变异/注入验证（门禁、套件）必须**「注入 → 跑 → 还原」在同一次命令序列内完成**，
> 离开前**再复跑一次确认已恢复原状（exit 0）**；🚫 **不得跨调用/跨回合留残留**。
> 实例：`新手上云操作手册.txt` 尾部残留 `DRIFT-INJECTED`（变异没还原就离开），致门禁 exit=1，下一轮才发现。
> 还原方式：**从单源重生成派生件**（`.txt` 由 `.md` 重生），而非 `git checkout`（后者退回旧版、反让 K13 转红）。

### 6.1 窗口分工（两个窗口**别都出复审结论**）

| 窗口 | 角色 | 产出 |

### 6.2 沙箱边界：两档（**R60 修订，2026-09-17**）

> ⚠️ **为什么改（R60 的教训）**：本节原先把沙箱限制写成了**无条件的绝对句**（**没有任何条件从句** —— 没写"未申请放行时"），
> 结果**双方连着几轮都照它执行**：复审方每轮在结论里给"推送类"事实降级，执行侧也据此以为"对方验不到远端"。
> **被低估的恰恰是最该被核的那类事实**（是否真已推、全闸是否真绿），代价是结论等级被长期压低。
> ⇒ **红线：本节只写带条件的边界句（"在什么条件下、能核什么"）；无条件绝对句一律废弃。**

| 档 | 条件 | 能核 / 不能核 |
|---|---|---|
| **①档（默认，未申请放行）** | 直接可用 | ✅ 文件系统层静态核验：`Test-Path` / `Get-Content -Encoding UTF8` / `Get-FileHash` / 纯文本比对 / 读源码。<br>🚫 子进程类被拦：`git.exe` / `node.exe` / `powershell.exe` 等（曾实测 `spawn+pipe = EPERM(-4048)`、`git` SSH `Win32 error 5`、HTTPS `SEC_E_NO_CREDENTIALS`） |
| **②档（每轮申请一次放行后）** | 用户已接受"每轮一次"的代价 | ✅ `node verify_all.js` **端到端**（2026-09-17 实测 `总览：52/52 套件通过`、`VERIFYALL=0`）· ✅ 门禁 A–L · ✅ **远端 `git ls-remote origin dev`**（⇒「是否已推」**可核**）· ✅ 变异注入/还原 · ✅ `Get-FileHash` 交叉验证 |

- **「已推」的判定（2026-09-17 立；同日**自我更正**）**：**两方一致**即算已验 —— **远端** `git ls-remote origin dev` == **本地** `git rev-parse HEAD`。
  ⚠️ **`@{u}` 不作为证据**：本机 `.git/refs/remotes/**` 的写入**报成功却不落盘**（`git update-ref refs/remotes/origin/dev HEAD` → `rc=0` 但该文件不存在；`git fetch origin dev` 报 `* [new branch] dev -> origin/dev` 后**同一命令内** `ls` 仍找不到）⇒ `git branch -vv` 会显示 `[origin/dev: gone]`，而**远端一切正常**。要读本地引用，必须把 `fetch` 与 `rev-parse` **压进同一条命令**，并注明"仅同命令内有效"。原始证据见 `review/evidence/batch7_feed/_README.md §6.19.6`。
  单靠推送方回显的那一次**不算**已验事实。（R4 教训不变：**描述可凭记忆，输出不能**。）
- **git 读回的坑仍在**：`git -C` / `git show HEAD:path` / `git cat-file` 曾误报（2026-09-13 日记 `:52-55`）；
  即便在 ②档，判「文件存在/内容相等」仍**优先非 git 方法**（`Test-Path` / `Get-FileHash` / 直接读文件）交叉验证。
- **编码纪律（round25 复审方实踩）**：读文本一律 `-Encoding UTF8` —— `Get-Content` 默认编码读 **UTF-8 无 BOM** 文件会**行数与文本双错**（96 行量成 61 行 + CJK 花屏）；
  比内容一律 `Get-FileHash`，**不比行数**。
- **云端前提件（与沙箱无关，任何档都替代不了）**：A6/A7/`require('./common')`/`doc().get()` 等契约须靠 `smokeTest` 探针作答；
