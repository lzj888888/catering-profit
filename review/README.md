# review/ —— 复审方 ⇄ WorkBuddy 文件交接面

> **为什么要这个目录**：让复审结论与执行回执**以文件交换**，人不必在聊天窗之间大段粘贴。
> 本文件是**协议自述**，任何新会话/AI 读一次就知道怎么用。

---

## 1. 目录约定

| 项 | 约定 |
|---|---|
| 路径 | 仓库根 `review/` |
| 复审方产出 | `REVIEW_<YYYY-MM-DD>_<主题>.md`（**ASCII 文件名**；中文路径已坑过本仓两次） |
| WorkBuddy 报告 | **仍在 `.workbuddy/memory/<日期>.md`**（那是它的单一源，**不要再复制一份到 review/**，否则又是「同一事实写两遍」） |
| 为何放仓库根 | 在门禁 A–L 全部扫描面之外（门禁 ROOT = `specs/dev-specs/`；`check_requires` 只扫 `app.js`/`pages`/`miniprogram`/`utils`；L 组只扫 `cloudfunctions/`）→ 复审方写什么都不会让门禁变红 |
| 必须入库 | 本仓出现过「只落盘未入库 → 跨回合文件消失」（2026-09-13 日记 `:52-55`）→ 每轮落盘后立即 `git add review/ && git commit && git push dev` |

## 2. 双向规则（互不篡改）

| 谁 | 能改什么 |
|---|---|
| **复审方** | 只写**正文**（§0 基线 / §1 待办 / §2 能力边界）。**不改自己过去的文件**——需要更正就新开一份 `REVIEW_*`，历史留痕 |
| **WorkBuddy** | 只**追加** §3「执行回执」区。🚫 **不得修改正文** —— 改正文等于篡改对方记录；有异议就写进回执「存疑 + 理由」，交复审方判 |
| 两位都不做 | 不删除对方文件、不重命名、不改历史 |

与项目 `audit_log` 只 INSERT 同一纪律。

> **回执证据纪律（2026-09-13 R4 反例）**：每条「已落」必须附**可直接复现的命令 + 真实输出**（如
> `grep -c touristappid SMOKETEST_RUNBOOK.md → 1`）。**禁止只写描述**（如「已新增步骤 0.1 含①②③④」）——
> R4 回执就是这么写的，而实测该文件里 `touristappid` / `仅管理端可读写` / `seedDemo` / `营业执照` 全部 0 命中。
> 描述可凭记忆，输出不能。

> **取件规则**：取 `review/` 下 **mtime 最新**的 `REVIEW_*.md`（**不要按文件名排序** —— 同日文件名里 `_` 与 `T`
> 的 ASCII 序反直觉，会读到旧的那份）。判定示例：
> `Get-ChildItem review\REVIEW_*.md | Sort-Object LastWriteTime -Descending | Select-Object -First 1`

> **变异还原纪律（2026-09-13 实踩，用户直接指令补入）**：任何变异/注入验证（门禁、套件）必须**「注入 → 跑 → 还原」在同一次命令序列内完成**，
> 离开前**再复跑一次确认已恢复原状（exit 0）**；🚫 **不得跨调用/跨回合留残留**。
> 实例：`新手上云操作手册.txt` 尾部残留 `DRIFT-INJECTED`（变异没还原就离开），致门禁 exit=1，下一轮才发现。
> 还原方式：**从单源重生成派生件**（`.txt` 由 `.md` 重生），而非 `git checkout`（后者退回旧版、反让 K13 转红）。

## 3. 三条口令（用户只需说这三句）

| 场景 | 用户说 | 谁接 |
|---|---|---|
| 复审结论已落盘 | **「复审结论落 review/ 了，去看最新一份」** | WorkBuddy：读 → 执行 §1 → 追加 §3 回执 → commit |
| WorkBuddy 已执行 | **「回执落了」** | 复审方：读回执 + 日记 → 出下一份 `REVIEW_*` |
| 需要复核 | **「核一下」**（+ 日期） | 复审方：跑套件 → 读代码 → 独立变异 → 出结论 |

## 4. WorkBuddy 标准指令（整段粘贴一次，之后长期不用再说）

```
【长期生效 · review/ 交接协议】
1) 读仓库根 review/ 下文件名日期最大的 REVIEW_*.md（无新文件就别猜、别自造）。
2) 打开 §1「待办」逐条执行：先 🔴，再 🟡/🔵。每条含证据 + 精确修法 + 验收标准。
   落完在 §3「执行回执」区【只追加】一行：
   - [YYYY-MM-DD HH:MM] R<n> 已落/未落/存疑 · 证据：<命令> → <输出摘要> · commit <sha>
   🚫 不得修改该文件正文（正文归复审方）。
3) git add review/ && git commit && git push dev（本仓有过「只落盘未入库→跨回合消失」，必须入库）。
4) 某条你认为不成立/与规范冲突 → 不静默跳过，在回执写「存疑 + 理由」交复审方判。
5) 你本轮自己的报告仍写 .workbuddy/memory/<日期>.md（单一源），
   在回执里写一句「本轮报告见 memory/<日期>.md」即可，不要复制到 review/。
6) 复审方的能力边界（§2）请一并读：它跑不了 verify_all 端到端、核不了远端 push、
   云端前提须靠 smokeTest 探针——别把它的结论当成"云端已验证"。
```

## 5. 什么该回填重启键，什么留在 review/

| 内容 | 落点 |
|---|---|
| 本轮待办与回执、一次性核验细节 | **`review/REVIEW_*.md`**（可过期，不必回填） |
| **活过一轮**的 🔴/🟡、在案未修项、架构决定、判据变更 | **`specs/dev-specs/★知识存储点_2026-09-10.md §1.1`**（唯一状态节，换会话只读它就能接上） |
| 方法论/纪律 | `.workbuddy/memory/MEMORY.md` |

两处职责不同、**不重复**：`review/` 是流水，重启键是终态。

## 6. 复审方的沙箱能力边界（写进协议，避免高估结论）

### 6.1 窗口分工（两个窗口**别都出复审结论**）

| 窗口 | 角色 | 产出 |
|---|---|---|
| **3080（本会话，工作区 = `C:\Users\lzj\Desktop\deepseek  空间`）** | **唯一复审窗口**（2026-09-13 用户决定） | 落 `review/REVIEW_*`、跑套件、独立变异、出结论。代价：**写盘每轮需用户批准一次**（工作区不在仓库内）；用户已接受该代价 |
| 3081（可选的第二实例） | **备用 / 运维问答** | 只答「控制台怎么点 / 报错什么意思」；🚫 **不得产出 `review/` 结论文件** |

> **为什么选 3080 当唯一窗口**：复审方的价值大量来自**跨轮累积的上下文**（锚点、门禁 A–L、
> 十几条纪律、变异方法）。换到"工作区=仓库"的会话虽能零弹窗写盘，但**上下文不随文件迁移**，
> 而重启键 + `review/` 只能接回「状态」、接不回「判断力」。
> ⇒ **一次点击 < 上下文完整性**（用户 2026-09-13 拍板）。

> 为什么必须分开：两个窗口都出结论 → 立刻变成「同一事实写两遍」，正是本项目反复吃亏的那类病。
> 复审方的工作区在**会话启动时**由 `dsh web` 的**调用目录**决定（dsh README `:16`：
> *"The invoking directory is the default workspace root"*），**会话内无法更改**；工作区不是仓库时，
> 复审方写仓库需逐次申请放行（可行，但每轮一次）。
>
> ⚠️ **实测更正（2026-09-13）**：工作区是**会话创建那一刻**该实例的调用目录，**创建后固定不变**。
> **实例重启 / 换端口不会迁移已有会话的工作区**。实例：某复议会话在原实例创建（工作区 = Desktop 目录），
> 之后从仓库目录另起实例（`--port 3081`）并接管了它，但它的工作区**仍是 Desktop** —— 写仓库依旧要逐次放行。
> ⇒ 想要「工作区 = 仓库」的复审会话，必须在**从仓库目录启动的实例里新建一个会话**；旧会话不会自动获得新工作区。
> 判定当前会话工作区：看 `DSH_SESSION_JSONL` 的目录名，或直接 `pwd`。


- `verify_all.js` **端到端跑不了**：沙箱禁止管道型子进程（`spawn+pipe = EPERM(-4048)`，`stdio:'inherit'` 可）。只验过其**聚合逻辑**（全成功 exit0 / 单个失败 exit1 / 全 EPERM exit1，fail-closed）。
- **远端 push 核不了**：SSH（`Win32 error 5`）/ HTTPS（`SEC_E_NO_CREDENTIALS`）均不通。「已推 dev」一律记为**推送方回显确认**，不当已验事实。
- **云端前提核不了**：A6/A7/`require('./common')`/`doc().get()` 契约须靠 `smokeTest` 探针作答。
- **沙箱 git 读回不可信**：`git -C` / `git show HEAD:path` / `git cat-file` 会误报（2026-09-13 日记 `:52-55`）→ 复审方对「文件存在/内容相等」一律用**非 git 方法**（`Test-Path`/`Get-FileHash`/直接读文件）交叉验证。
