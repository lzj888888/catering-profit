## 2 三块内容（李老师点名的「指标 + 整改方向 + 时间」）

### 2.1 指标对照（可直接复用 M2 已有能力）

- 复用 `indicatorRef.evaluateIndicators` + `listBands`（单源 `cloudfunctions/common/indicatorRef.js`）
- **分母用 M1 的营业额** —— ⚠️ 但用哪个口径待定，见 §5-①（权责发生制收入 / 实收现金）
- 展示：指标名 / 你的值 / 行业参考带 / 评级。**方向必须分表**：
  成本类「偏高·过高」、毛利率「偏低·过低」（M2 已立此规，见 `TERMS.m2.indLevels` / `indLevelsGain`）
- M1 特有：**命中 M1.6 警戒线**的项要突出。
  ⚠️ M1.6 已定义四条红线，但**代码里零实现** —— 见 `13_上线前查缺补漏` 的
  「M1 规范 M1.6『四红线 + 保本达成率红绿灯』在代码中零实现」待裁决条目

### 2.2 整改方向（每个不达标指标给「可以往哪动」）

**不是罗列，要按「影响金额 × 可控性」排序**。草拟处方库（**待李老师增删 —— 这是他的经营经验，我编不出来**）：

| 指标 | 可考虑的方向 | 受什么约束 |
|---|---|---|
| 房租占比高 | 转租/分租部分面积、与房东重谈、搬更便宜的点位、压缩堂食面积做外卖 | 受**合同周期**约束（最难动） |
| 人工占比高 | 排班错峰、一人多岗、部分固定工资改「底薪+提成」、小时工替代全职 | 最快见效 |
| 毛利率低 | 换供应商/集采、调菜单结构（推高毛利菜）、小幅调价、减少赠送 | 1~2 个月 |
| 能耗占比高 | 设备错峰用电、查漏气/漏电、换节能设备 | 按账单周期 |
| 平台推广费高 | 换平台组合、把流量往自有私域迁、按实际产出砍投放 | 按平台合同 |
| 管理费高 | 与总部谈阶梯、核减不必要服务项 | 按合同 |

### 2.3 时间窗（多久能见效）—— 李老师点名要的一项

**必须给「区间 + 前提条件」**，不能拍脑袋。草拟（待拍板）：

| 类别 | 典型见效周期 | 前提 |
|---|---|---|
| 人工类 | 1 个月 | 招退工 / 排班调整可即时 |
| 能耗类 | 1 个月 | 按账单周期验证 |
| 毛利率类 | 1~2 个月 | 供应商切换 / 调价到位 |
| 平台费率类 | 1~3 个月 | 按平台合同 |
| 房租类 | 6~12 个月 | 受租约约束；未到期只能内部压缩面积 |

## 3 🔴 四条边界（对「你觉得对吗」的回答）

**对 —— 而且这是产品从「工具」变「顾问」的关键一步**：指标对照告诉客户「你在哪」，
整改方向告诉客户「往哪走」，时间窗告诉客户「多久见效」。三件合起来才配得上李老师那句
「本身我们提供的就是让客户找到方向」。

但落地必须守四条，否则会反噬：

1. **不许变成承诺**：整改方向是「可考虑的做法清单」，不是「这样做就能赚钱」。
   文案一律用「可以试试 / 常见做法是」。🔴 **禁止**「保证提升 X%」「一定能回本」「稳赚」。
2. **必须过禁用词守卫**：本仓 `tools/check_terms_forbidden.js` 守金融红线词（投资回报 / ROI / 收益承诺）
   —— 整改文案进 `terms.js` 前必须过它（连带 `check_page_terms`（R124）与 R127 零成本率文案面守卫）。
3. **时间窗必须有依据**：§2.3 每条都写了「前提」。**无依据的周期不许写**（宁缺勿编）。
4. **优先级不是罗列**：房租超标但合同还剩 8 个月 ⇒ 处方应该是「先把毛利率拉起来」，
   而不是「去谈房租」。需要一个**决策排序逻辑**（影响金额 × 可控性 × 时间窗）；
   否则 6 条建议平铺 = 客户不知道该先动哪个 = 等于没给方向。

## 4 技术方案（round114 二稿 · 补「四层分离 · 可变更性设计」）

> 李老师当轮原话：「这些指标后期要变动，所以看小程序怎么写方便以后变更升级。」
> ⇒ 本节的落点**不是「把指标加上」**，而是**让指标以后能改，且改一处不牵连别处**。

### 4.1 🔴 先看清事实：M1 台账科目 ≠ M2 指标口径

查码结论（`miniprogram/i18n/terms.js:198` + `cloudfunctions/getLedger/index.js`）：
M1 的支出**只有 4 个大类**，但 M2 指标需要 **5 个成本项**，**对不齐**：

| M1 支出大类 | 其细项 |
|---|---|
| `operation` 运营费用 | 房租 / 物业费 / 水费 / 电费 / 燃气费 / 垃圾清运费 / 宽带网费 |
| `labor` 人工费用 | 工资绩效 / 社保 / 员工宿舍 / 员工餐 / 工装福利 |
| `marketing` 营销费用 | 外卖平台佣金 / 配送服务费 / 活动补贴 / 推广费 / 团购佣金 / 线上广告 … |
| `other` 其他费用 | 代账费 / 其他杂项 |

| M2 指标 | M1 里在哪 | 结论 |
|---|---|---|
| `labor` 人工 | 大类 `labor` | ✅ 直接对应 |
| `rent` 房租 | `operation` 的**细项**「房租」 | ⚠️ 需下沉到细项 |
| `energy` 能耗 | `operation` 的细项「水费+电费+燃气费」**三项之和** | ⚠️ 需合并 |
| `manage` 管理费 | ❌ **无对应科目**（沾边的只有「物业费」「代账费」） | 🔴 待拍板（§5-⑦） |
| `mkt` 推广费 | 大类 `marketing` | ⚠️ 口径不同（M2=费率，M1=金额） |

**若按中文细项名匹配**（`name === '房租'`），埋三个隐性缺陷：
① 改文案（「房租」→「租金」）⇒ 指标**静默失效且不报错**；
② 用户可**自定义细项名**（`TERMS.ledger.presetPickCustom`）⇒ 匹配不上；
③ 新增细项（如「取暖费」应归能耗）⇒ 必须改匹配代码。

### 4.2 四层分离（哪一层会变，就只改哪一层）

1. **① 归属层**（偶尔变）— `terms.js` 的细项由字符串升级为 `{ name, indTag }`：
   ```js
   { name: '房租', indTag: 'rent' },     { name: '物业费', indTag: 'manage' },
   { name: '水费', indTag: 'energy' },   { name: '电费', indTag: 'energy' },
   { name: '燃气费', indTag: 'energy' }, { name: '垃圾清运费', indTag: null },
   ```
   `indTag` = **机器键**，与中文名解耦 ⇒ 改文案、改叫法，**归属不动**；
   自定义细项 `indTag: null`（不参与任何指标）。
   ⚠️ `name` 仍是**用户可见文案的唯一来源**（三处同步纪律不变），`indTag` 只是并列的机器键。
2. **② 计算层**（极少变）— `getLedger/service.js` 按 `indTag` 汇总出
   `by_ind: { rent, labor, energy, manage, mkt }`（单位**分**；缺项**不出键**，见 §5-⑥）；
   原 `category` 汇总保留，**不改旧行为**。
3. **③ 参考带层**（🔴 **最常变 · 唯一改动点**）— 复用 `cloudfunctions/common/indicatorRef.js`：
   - `getLedger/` 目录里**已有** `cx_indicatorRef.js`（`sync_common` 派生副本）
     ⇒ require 一行即用，**零新增依赖**；
   - 调 `evaluateIndicators({ revenueFen, fixedFen, grossMarginPct, platformPct })`；
   - 🔴 **`fixedFen` 的键是 `rent|labor|utility|manage`（注意是 `utility`，不是 `energy`）**
     ⇒ `energy ↔ utility` 的映射**必须由后端出**（在 `indicatorRef` 加 `indFenKeyOf()` 或映射表），
     **前端不许自己猜**（round114 M2 已立此规，见 `INDICATORS.from`）。
4. **④ 展示层**（零阈值）— `pages/month/result.*` 只渲染后端算好的
   `{ key, pct, lo, hi, level, redlineHit }`，**自己不写任何数字**；
   中文名走 terms；方向**必须分表**（成本类「偏高/过高」、毛利率「偏低/过低」）。

### 4.3 变更成本一览（这就是「怎么写方便升级」的答案）

| 以后想改 | 改哪 | 影响面 |
|---|---|---|
| 科目中文名（房租 → 租金） | `terms.js` 一行 | **零影响**（indTag 不动） |
| **参考带数值**（行业数据更新，最常发生） | `indicatorRef.js::BANDS` **一处** | **M1 + M2 同时生效** |
| 新增一个细项 | `terms.js` 一行（带 indTag） | 一项 |
| 换分母口径 / 算法 | `getLedger/service.js` | 要跑门禁 |
| 新增一个指标 | `INDICATORS` + `BANDS` 各一行 | 两端自动出现 |

### 4.4 出参与守卫

- 出参：`indicators`（对照表）+ `actions`（动作 id 数组，**中文由前端 terms 映射**，后端不存中文）
  + `horizon`（月数区间）
- 术语：新增 `TERMS.resultPage.ind*` 与整改文案库
  （🔴 **双副本逐字节一致** `miniprogram/i18n/terms.js` ≡ `specs/dev-specs/i18n/terms.js`
  + 页面 `t` 映射 —— 「新可见文案=三处」，少一处 wxml 取空串）
- 守卫：
  - 延续 R127：整改文案不得出现「食材成本率」类表述（已守）
  - **新增**：整改 / 时间窗文案不得出现承诺式表述（保证 / 一定 / 稳赚 / 回报率）
  - **新增（形态类 · 立用例表单源）**：`result.*` 里**不得出现硬编码阈值数字**
    —— 一旦有人在页面上写死 `15` / `20`，指标改带后页面不跟 ⇒ 用守卫挡住
  - 断言数同步（唯一声明处那条须跟）
- **不做**闭店模型：李老师 2026-09-24 明确「闭店模型以后单独做，暂时不做成第四个模块」
  ⇒ 本节**只做「单项指标的改善动作」级别**，**不做**关停决策打分。
