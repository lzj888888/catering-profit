## 二、本轮攻克：环境 ID 占位符静默回落缺口

**根因（可证伪，不是猜）**：`miniprogram/config/env.js` 原写法
`return this.ENV_MAP[this.ACTIVE_ENV] || this.ENV_MAP.dev;`
对「ACTIVE_ENV 指向的环境 ID **仍是占位符**」无任何防护 —— 一旦有人把 `ACTIVE_ENV` 切成 `'prod'`
而真实 prod 环境尚未建/ID 未填，就会把 `catering-prod-xxxxxxxx` 这个**不存在的环境 ID** 交给
`wx.cloud.init`（`app.js:21` 单源取环境）⇒ **全站云调用失败，且没有任何日志**。

**为什么现有门禁没兜住**：H 组（`check_error_codes.js`）守的是**云函数侧** initDb/seedDemo 的
dev/prod 拦截与 `DEV_ENV_ID` 白名单；**不覆盖小程序端 env.js**。这是两个面。

**修复（fail-closed + 可观测，运行时行为不变）**：
- `isPlaceholder(id)`：非字符串/空/含 `xxxxxxxx` 一律判占位符（fail-closed）；
- `getEnv()`：占位符 ⇒ **回落 dev + `console.error('[ENV_FALLBACK] …')`**（不静默、不白屏）；
- 新增 `envStatus()`：`{active, envId, isPlaceholder, fellBack, devReady}` 供自检与守卫读取。
- ✅ 当前 `ACTIVE_ENV='dev'` 且 dev 为真实 ID ⇒ 防护不触发，**行为与改动前逐字一致**（守卫 N4 反证：告警 0 次、fellBack=false）。

**新套件 `env-ready`（第 66 个）** `tools/check_env_ready.js`：
- E1 环境 ID 单源（业务代码零硬编码，扫 52 文件）／E2 `getEnv()` 内须有占位符判定+告警／E3 实跑断言「返回值永远不得是占位符」；
- N1~N4 **正负样本互证**（含"不该红时不红"的反向证据）；S1/S2 自失效护栏。

🔴 **守卫误报一轮，改的是守卫不是代码**：`/getEnv\s*\(/` 命中了第 15 行的**注释**
（与 round47 iOS 守卫同一个坑：注释干扰）⇒ 改认函数定义形态 `^\s*getEnv\s*\(\s*\)\s*\{`。

**变异回灌已做**（脚本 `_gui/mutate_env_ready.py`，过程件不入库）：
① 抽掉占位符防护 ⇒ 守卫转红 **3** 条；② 把 `ENV_MAP.dev` 改占位符 ⇒ 转红 **4** 条；恢复后回绿。
