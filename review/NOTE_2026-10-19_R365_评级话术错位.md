# R365 · 「已有铺面」的评级为什么读起来像选址指标

> 2026-10-19 李老师提问：「不建议拿」更像找店铺的指标；已有店铺更关心房租确定时，
> 不同人工/毛利率出来不同的利润，或者按预期利润反推。**他的判断对吗？**

## 一、结论：对，但要分成两件事看

| 层 | 判断 | 依据 |
|---|---|---|
| **算法**（6 项指标 vs 行业带，取最差） | **不算错** | 这是"体检"，签铺前和开业后都成立；换成"已有店铺"也不该换算法 |
| **话术**（结论卡从标题到四句总结） | **确实错**，是选址口吻 | 见下表：整张卡都在讲"要不要拿这个铺子" |
| **动作建议** | **错位** | "压价或换铺"——店已经开了，这话说了等于没说 |

页面事实：这里从 R323 起**恒为「已有铺面」**（反推搬去矩阵页），但文案没跟着搬。

## 二、证据：这张卡原本的每一句都在讲"拿不拿"

| 位置 | 改前 | 问题 |
|---|---|---|
| 卡标题 | 这个**铺子**健不健康 | "铺子"是选址对象 |
| 优秀 | **划算** | 是"值不值得买"的词 |
| 良好 | 还行 | 同上 |
| 偏紧 | 有点压力 | 中性，但下一句露馅 |
| 偏差 | **不建议拿** | 最刺眼的选址词 |
| 优秀说明 | **租金**在安全区间，**可以谈** | 谈判场景 |
| 良好说明 | 还在合理范围，**能拿** | 同上 |
| 偏紧说明 | 偏高了，**压价或换铺** | 店已开，换铺不是可执行动作 |
| 偏差说明 | **房租吃掉了**太多流水 | 只盯房租，而房租对已开业的人基本不可动 |

> 但有一处**已经是对的**：`verdictNoteByItem` 的逐项诊断全是经营口吻
> （"优化排班或提升单店产出" / "砍岗位或提客单" / "重做菜单定价或换供应商"）——
> 说明设计者本来的意图就是经营诊断，只是**总标签没跟着改**。

## 四、他说的第二件事：不同人工 × 不同毛利率 → 不同利润

**这个能力今天就有**，只是藏在矩阵页：

- `pages/sandbox/matrix.js` 的 `dims` 里本来就有 `rent / labor / margin / target` 四维，
  且注释写着「矩阵的核心价值是"多请一个人会怎样"」；
- 但用户只能从「场景矩阵测算 / 寻找铺面」两个入口进 —— **名字全是选址语义**，
  已经有店的人不会想到"要看人工和毛利率的组合"要去点那里。

⇒ 建议（下一步）：矩阵页**按处境定默认维度**
  - 已有店铺（`mode=forward` 进来）⇒ 默认 **人工 × 毛利率**
  - 寻找铺面（`mode=reverse`）⇒ 默认 **租金 × 毛利率**（现状）

## 五、他说的第三件事：按预期利润反推

现有反推是**租金反推**（"这个铺子租金最多能扛多少"= 选址口径），**不能直接复用**给
"我想月赚 X，毛利率要多少 / 人工要压到多少"。要做需单独立项：
- 目标利润 → 最低毛利率：`毛利率 = (固定费用 + 目标利润) / 预期营收`，**闭式解可直接算**（纯前端）
- 目标利润 → 人工上限：`人工上限 = 营收×毛利率 − 其他固定费用 − 目标利润`（同样闭式）
⚠️ 闭式解依赖"其他不变"，与引擎里摊销/渠道的耦合要逐项核对，不能想当然。
