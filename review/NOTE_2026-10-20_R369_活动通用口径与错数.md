# R369 · 活动的通用核算方式（国内外口径）+ 现有活动卡的一个必现错数

> 2026-10-20 · 李老师：活动能不能覆盖各场景？有没有通用核算法？能不能让客户自己算一个数我们引用？
> 还是这个模块整体不要了？与豆包再商量、看看国内外做法。

## 一、先纠正我自己上一轮的一个错误

R368 里我写「`m' = m − (让利率 + 赠品率)/100`」——**这是线性近似，是错的**。

精确式（也是仓里 `utils/promoImpact.js` 一直在用的）：
```
cut = (1 − 折扣率) × 参与占比         ← 让价占原价的比例
GA  = (G0 − cut) / (1 − cut)          ← 活动期毛利率
```
例：G0=65%、打 8 折、全部参与 ⇒ 线性给 45%，精确给 **56.25%**。**差 11 个百分点。**
⇒ 我上一轮的说法作废，以本节为准（`promoImpact.js` 的公式本来就是对的）。

## 二、有通用核算法，而且是行业标准：**实收率 / 活动成本率**

不问"你做的是什么活动"，只问两个账上已有的数：

| 输入 | 定义 | 老板从哪拿 |
|---|---|---|
| **实收率 r**（或让价率 cut = 1−r） | 实收 ÷ 原价流水 | 收银日报 / 平台账单 |
| **商家出资活动成本率 a** | (赠送+奖品+自贴券) ÷ 实收 | 采购 + 活动台账 |

**国内口径（有据）**
- 思迅 SaaS《优惠构成统计》：`实收金额 = 售价金额 − 优惠金额`，`折扣金额 = 流水 − 实收`；
- 餐饮业财融合通行式：**`折扣后实收率 = 折扣后门店应收 ÷ 商品原价`**；
- 美团/饿了么：必须区分「**商家承担折扣**」与「**平台承担补贴**」—— 平台补贴不算门店让利，
  否则会把平台的钱算成自己的成本；
- 行业经验阈值：**活动成本占实收 15%** 就要降一档（来自美团运营实践总结）。

**国外口径（有据）**
- 标准概念是 **contribution margin**（净销售额 − 食材 − 包装 − 支付费 − 渠道佣金 − 配送补贴），
  与我们的 `m` 同构；
- 标准算法是 **breakeven lift**：`L = m0/m1 − 1` —— 即"要让这次活动不亏，营业额至少要多 X%"，
  正是我们已有的 `needTrafficPct`；
- 更严谨的一层是 **incrementality**（增量性）：用对照组/A-B 估计"本来就会来的客人"占多少。
  ⇒ **这一层我们拿不到数据，也不该假装能算**。

**结论：通用输入是可行的，而且比"描述活动形态"更准** —— 因为实收率天然把
折扣、除外、分时段、满减、券、赠送**全部吸收**成一个数。

## 三、能不能覆盖各场景（逐条）

| 场景 | 怎么进这两个数 | 注意事项 |
|---|---|---|
| 啤酒免费 | 收入不变，进 **a**（赠送成本率） | 若"免费"指零元购，则同时影响 r |
| 锅底除外 | 体现在 **r**（加权实收率） | r 由实收/原价自然得出，不用单独描述 |
| 前3天8折后4天6折 | 体现在 **r** | 分段的现金流差异被月均掩盖 |
| 抽奖 | 进 **a**（按期望奖品成本） | 方差大：爆一次大奖是真实现金流出 |
| 满减 / 第二份半价 | 体现在 **r** | 客单价结构变化需重算加权 G0 |

公式（含豆包补充的活动成本项）：
```
m1 = (G0 − cut)/(1 − cut) − a − f      f = 渠道费率（按实收计）
L  = m0/m1 − 1                          m0 = G0 − f
m1 ≤ 0 ⇒ 不存在有限门槛（固定奖品另计：(F + A)/m1）
```

## 四、要不要砍：【豆包】的判断与我一致 —— **缩小，不砍**

【豆包】原话：「缩小，不要原样保留，也不必直接砍掉。保留两个输入和保本增量门槛，
砍掉活动形态枚举、销量预测和 ROI 结论，改名为'活动保本门槛'更准确。」

我同意。理由：
- 它能回答老板真正的问题：**"这活动我得比平时多卖多少才不亏"**；
- 它答不了"能带来多少增量" —— 那是增量实验的活，硬答就是编。

## 五、🔴 顺手查出一个必现错数（现有活动卡，不是新功能）

同一张卡上两个数**互相矛盾**（实测，F=3500 / G0=63% / 打 8 折 / 全部参与）：

```
页面显示：保本 5,556 → 6,512（+17.2%）
下一行  ：打平要多来 46.5% 的客人
```

两者本应一致（都是"保本门槛涨多少"），差 29 个百分点。

**根因**：`promoImpact.js` 返回的
- `beBeforeYuan = F / G0` ⇒ **原价口径**（流水）
- `beAfterYuan = F / ga`（ga 是实收口径毛利率）⇒ **实收口径**

`beIncreasePct = b/a − 1` 把两个不同口径相除 ⇒ 必然偏小。
正确值 = `F / (G0 − cut)` = **8,140（+46.5%）**，与 `needTrafficPct` 完全一致。

**危险方向**：17.2% 让老板以为"打八折只要多卖 17%"，实际要 46.5% —— 又是"看着更好"的错。

**建议修法**（改 1 个函数 + 1 个自测）：
1. `beAfterYuan` 改为原价口径 `F / (G0 − cut)`（与 beBefore 同口径）；
2. 需要实收视角时另给 `beAfterNetYuan = F / ga`，文案单独说"其中现金实收 X"；
3. `selftest_promo.js` 的 A-④/A-⑤ 期望值同步；
   **C-④「保本涨幅 < 客流涨幅」这条判据本身把错误固化成了预期**，应改为"两者相等（同口径）"。

⚠️ 这是业务口径改动，**按先审后合，等你点头再动**。
