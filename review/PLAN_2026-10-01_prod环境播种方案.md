## 〇 一句话结论

**「建 prod 环境」本身不难（控制台点一下），难的是把两张种子表塞进去。**
本方案给出**零代码路径**：**dev 控制台导出种子 → prod 控制台导入**，不需要跑 `initDb`、不需要碰门禁、不需要任何凭证。

## 二 阻塞点精确定位

```
initDb/index.js:30   const g = gate(env, process.env.DEV_ENV_ID);
collections.js:243   function gate(envRaw, devEnvIdRaw) {
                       const isDevEnv = (DEV_ENV_ID ? env === DEV_ENV_ID : /dev/.test(env))
                                        && !/prod/.test(env);
```

⇒ **prod 一旦出现，`initDb` 必然被拒**。这不是 bug，是**刻意设计的政策门禁**（防止有人在生产库上跑建表脚本）。

## 三 三条路径对比

| 路径 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **① 控制台导入导出**（✅ **推荐**） | dev 控制台 → 目标集合 → **导出 JSON** → prod 控制台 → **导入该 JSON** | **零代码、零凭证、可审计**、李老师自己能在控制台完成；导入是平台能力，不存在"脚本写错"风险 | 手工两步；需注意 `_id` 处理 |
| ② HTTP API 一次性播种脚本 | 复刻 `tools/apply_indexes.js` 的架构，走官方 HTTP API 插记录 | 可重复、可进 CI、适合将来"多环境一键起" | 要新写脚本（引入 `tools/` 同步面）+ 要 AppSecret（**账号级凭证，用后须轮换**）+ **端点细节须现查官方文档**（本次未确证，不写死） |
| ③ 给 `initDb` 加一次性白名单放行 prod | —— | —— | ❌ **不做**：等于**拆掉门禁**，是最不该动的安全边界 |

**⇒ 推荐 ①。** ② 留作将来「环境数量 ≥3」时的自动化选项，本次不引入。

## 四 主方案（路径 ①）执行步骤

> 括号内标注**谁做**。**李老师**= 只能在控制台/后台做；**我**= 仓内脚本或文件改动。

### S1 建 prod 环境（李老师）
- 云开发控制台 → 新建环境（名称含 `prod`）→ 记下**真实环境 ID**（形如 `cloud1-xxxx`，**不是短名**）。
- ⚠️ **绝不把 dev 改名成 prod** —— 那样 dev 的测试数据会**原地转正**（CHECKLIST §2-A 已警告）。

### S2 建 27 张集合（李老师，控制台手工）
- 政策要求：**集合一律控制台手工建**，`initDb` 绝不部署到 prod。
- 清单**现读** `cloudfunctions/initDb/collections.js::COLLECTIONS`（**别抄本文件数字**，会漂）。

### S3 建 45 条索引（我，走既有脚本）
```bash
# 先 dry-run 看将提交什么（默认就是 dry-run，不联网）
node tools/apply_indexes.js --env <prod_id> --only <单集合>      # 建议先单集合试水
# 真建（AppSecret 从本地文件读；用后立刻在 mp 后台轮换）
node tools/apply_indexes.js --env <prod_id> --apply --secret-file <文件>
```
- ✅ **零改造**：该脚本的 `--env` 参数**已支持**（`valOf('--env') || DEV_ENV_ID`），无 `--env` 时仍从单源现读。
- 🔴 AppSecret 纪律（脚本头注第 5–8 条）：**永不打印、不写文件、不进云函数环境变量、用后即轮换**（账号级凭证，重置会让同账号已签发 token 全部失效）。

### S4 配 27 张集合的权限档（李老师，控制台）
- 逐集合选档位；以单源 `specs/dev-specs/core/15_集合权限矩阵.md` 为准。
- 🔴 两个入站集合（`external_sales_daily` / `shop_dish_mapping`）= **「仅管理端可读写」**（即控制台第 4 档「所有用户不可读写」）—— **客户端零直连**。

### S5 播种两张种子表（李老师，🔴 **本方案补的那条缝**）
1. **dev 控制台** → `subscription_plan` → **导出**（JSON，含 `_id`）→ 下载。
2. **prod 控制台** → `subscription_plan` → **导入**该 JSON。
3. 同法处理 `feature_permissions`。
- **判据**：prod 两张表的**记录条数 ≡ dev**，且逐行字段值一致（见 §六 校验）。
- ⚠️ 导入的是 dev 的**实际值**（含历次控制台改动，如额度上限）—— 这正是我们要的，**别用 `initDb` 里的常量**去推。

### S6 部署 43 个函数到 prod（我）
```bash
# 逐函数、必带 -r（本仓铁律：漏 -r 会覆盖云端 wx-server-sdk ⇒ 前端全站「网络不可用」）
# 用现成部署器，ENV 现读；逐个推进，一次一个
python review/evidence/_deploy_fns.py <fn1> <fn2> ...
```
- ❌ **`initDb` 不部署到 prod**（政策）。
- 🔴 **先定 timeout 再部署**：`config.json` 的 `timeout` **不被采纳**（2026-09-18 决定性实验），值只存在于控制台
  ⇒ **dev 定过 ≠ prod 生效**，必须重走「控制台定值 → 部署 → `cli cloud functions info` 逐个回读」。
- 🔴 **凭证不随环境走**：`ADMIN_SETUP_TOKEN` 等需在 prod 侧重配。

### S7 前端切环境（我）
- `miniprogram/config/env.js::ENV_MAP.prod` 填 S1 的真实 ID（不再是 `xxxxxxxx`）。
- 同文件 `ACTIVE_ENV` 改 `'prod'`。
- 判据：守卫 `tools/check_env_ready.js` 转绿且**无 `ENV_FALLBACK` 告警**。
- ⚠️ `env.js` 有**占位符保护**：prod 槽没填就切 `ACTIVE_ENV` ⇒ **回落 dev + `console.error`**（不白屏、但会**悄悄继续用 dev 库**）⇒ E1/E2 必须成对完成。

### S8 验收（我 + 李老师）
1. 正式版录一条测试数据 → prod 控制台**能看到**、dev 控制台**看不到**。
2. `cli cloud functions info -e <prod_id> --names <fn>` 逐个回读 `timeout` 与更新时间。
3. 付费链路点一次（付费墙能弹、下得去单）。

## 七 🔴 四条容易踩的（每条都有前车之鉴）

1. **播种 ≠ 更新**：`initDb {only:'seed_missing'}` 的语义是「**缺才补插**」，**已存在的行不会被更新**。
   改**已存在行的值**（如额度 `5 → 20`）⇒ 补种**不生效**，必须**改那条记录本身**。
   ⇒ 本方案走「导出/导入」是为了**连值一起搬**，避开这个坑。
2. **别把 dev 改名成 prod**（唯一会把测试数据"转正"的操作）。
3. **`rc` 永不作部署判据**（cli 失败也返回 0）⇒ 判据一律「日志某行同时含函数名 + ASCII `true` + 完成行」。
4. **AppSecret 是账号级凭证**（仅 S3 用到）⇒ 用后立刻轮换；回执**不回显任何令牌值**。
