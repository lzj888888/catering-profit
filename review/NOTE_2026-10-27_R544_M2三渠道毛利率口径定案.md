## 1 为什么「三处不同毛利率」不成立（这是本轮最硬的一条）

设渠道 i 的收入占比 sᵢ（Σsᵢ = 1），食材率 fᵢ，该渠道费率 feeᵢ。

- 「分渠道毛利率」写法：`CM = Σ sᵢ × (1 − fᵢ − feeᵢ)`
- 「本仓现行」写法：`CM = 1 − f − Σ sᵢ × feeᵢ`

当 **fᵢ 全部相同（fᵢ = f）** 时：

```
Σ sᵢ(1 − f − feeᵢ) = Σsᵢ − f·Σsᵢ − Σ sᵢ·feeᵢ = 1 − f − Σ sᵢ·feeᵢ      ← 逐项恒等
```

⇒ **两者数学上完全相同**。三处不同毛利率唯一的增量，是允许「食材率随渠道变化」。

而食材率随渠道变化在真实业务里几乎不存在：**同一批菜、同一张成本卡**，堂食和外卖用的是同一份原料。
差异全部落在**收入侧**——平台抽成、打包费、配送费、团购折扣——这些本来就在「渠道费率」层。
豆包判断该增量 ≤ 1~2 个百分点，与本仓判断一致。

⇒ 结论：让老板填「三个毛利率」= 用 3 个他算不准的复合数，去换 1~2 个点的理论精度，
**净结果是更不准**。

## 2 自我更正：上轮「保本虚高 27%」是我算错了（必读）

上一轮我给豆包提的第 3 条异议，说「团购折扣按费率直减 ⇒ 低估 10 个点、保本虚高 27%」。
**这个结论是错的，本轮撤回。** 错因是把两个不同分母的贡献率直接相比：

- 豆包算式 `1 − f/折扣系数 − c` 的分母是**折后实付**（每 1 元实付）
- 我们 `1 − f − (d + c)` 的分母是**菜单原价**（每 1 元挂牌价）

按菜单原价分母重算（f = 40%、折扣 d = 20%、团购抽成 c = 5%、固定成本 30000）：

| 口径 | 边际贡献率 | 保本额（菜单原价） | 说明 |
|---|---|---|---|
| 现状 `1 − f − (d + c)` | 35.00% | 85,714.29 | 少算 c·d 这一项 |
| 修正 `1 − f − (d + c − d·c)` | 36.00% | 83,333.33 | **与真实值完全相等** |
| 真实值 `(1−d)(1−c) − f` | 36.00% | 83,333.33 | 基准 |

⇒ 现状误差 = `c·d` = 0.05 × 0.20 = **1 个百分点**，保本 **虚高 2.86%**，**不是 27%**。
⇒ 折后实付口径的保本额 = 83,333 × 0.8 = **66,666.67**；83,333 ÷ 66,667 = **1.25**（这才是那个「25% 观感差」的来源，与 27% 无关）。

**元教训**：跨人讨论公式时，先对齐**分母**再谈对错。两个都对、只是单位不同，
直接相比会凭空造出一个 10 倍的"误差"，这种假误差一旦进了定案，会驱动一次不必要的重构。

## 3 豆包两轮结论（与本仓独立收敛，非采信）

| 问题 | 豆包结论 | 本仓判断 | 是否一致 |
|---|---|---|---|
| A 架构：分渠道毛利率 vs 统一食材率 + 分渠道费率 | 保留后者。准确性 4 / 实操性 5，对比 3.5 / 2，**胜负项是实操性** | 同 | ✅ |
| B 是否加「分渠道 / 综合」互斥开关 | **不加**。现有逐项渠道开关即够，全关自动退化为综合口径 | 同 | ✅ |
| C 最少要加什么字段 | **0 个必需字段**；团购折扣算式改 `d + c − d·c` 即可 | 同 | ✅ |
| 保本额展示口径 | 保留**菜单原价**口径 + 一行提示，不切折后分母 | 同 | ✅ |

豆包对「互斥开关」给的两条风险，是本轮新增的有效论据：

1. **认知负担**：老板无法判断自己该选哪个模式，容易直接放弃填写。
2. **口径混淆（更危险）**：在「综合模式」下填了**已扣过佣金**的毛利率，再打开渠道开关 ⇒
   **佣金被扣两次，结果完全失真，而用户自己发现不了**——属于典型的静默错账。

⇒ 「不加开关」不只是省事，是**避掉一个用户不可自查的错误通道**。

## 4 本轮唯一要落地的两件事（归入 ⑦，本批**不改码**）

### 4.1 团购费率项：`(d + c)` → `(d + c − d·c)`

位置：`subpkg/tools/sandbox/index.js` `recomputeChannel()`

```js
// 现状
const grouponComm = off ? 0 : r2(rg * ((Number(c.groupPlatformRate)||0) + (Number(c.discountRate)||0)) / 100);
// 修正（删除重复计的 d·c 交叠部分）
const gRate = (Number(c.groupPlatformRate)||0) + (Number(c.discountRate)||0)
            - (Number(c.groupPlatformRate)||0) * (Number(c.discountRate)||0) / 100;
const grouponComm = off ? 0 : r2(rg * gRate / 100);
```

依据：佣金基数 = **顾客实付的团购价**（`utils/grouponDerive.js` 红线③ 已定死），
所以「折扣」和「抽成」在 0.8 × 5% 这一小块上**交叠**，直减会重复扣 `d·c`。

改完需同步：`tools/check_m2_*` 相关断言 + `selftest`。**尚未改码。**

### 4.2 保本额口径提示（文案级）

开团购且折扣 ≠ 0 时，保本额的隐含单位是**菜单原价流水**，不是团购后台的实付金额。
必须在保本 hero 下方补一句：**「按菜单原价流水算；团购折扣越大，实际到手流水会低于这个数。」**

若不写这句：团购占比高的店，老板拿后台实付数字对标会差 20%+，**会以为算错了**。
