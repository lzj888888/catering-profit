## §1 为什么必须一起修

R586 修 DSI-1 后，同一份"重导残留"问题在三个老通道里原样存在：

| 通道 | 场景 | 后果 |
|---|---|---|
| 形态 A（堂食《菜品销售统计》） | 表里删了几个菜重导同一天 | 尾部旧行留下 ⇒ 堂食毛利虚高 |
| 形态 C（外卖商品销量） | 平台改口径、换时间段重导 | 外卖毛利虚高 |
| 形态 D（京东订单导出） | 同上 | 同上 |

**只修新通道等于给老板一个"新的对、旧的错"的系统** —— 比两个都错更糟（他没法判断该信哪个）。

## §2 做法：一份实现，三处调用

抽出 `pruneStaleGroup(db, shopId, platform, bizDate, writtenIds, now)`：

```
① 查该 (platform, bizDate) 组已存在的行 _id（失败 ⇒ 不清理，新数据仍正确）
② 差集 = 旧 _id − 本次写入的 _id
③ 逐条软删（is_deleted:true），返回 { pruned, failed }
```

三处接入：
- 形态 A：写完那一天后调一次；
- 形态 C·D：每个 `g.bizDate` 组写完后调一次；
- DSI-1：**把 R586 那段内联逻辑删掉**，改成调用同一个函数。

> 🔴 最后这条是刻意做的：R586 我把清理内联在 DSI-1 handler 里，如果这轮再给 A/C 各写一遍，
> 就是**三份会分叉的实现** —— 而"同一套语义多份实现"正是这两天反复踩的坑（DISH_SHAPES 副本、
> 提取器写死 A/B/C）。所以宁可回头改掉自己昨天写的代码。

## §3 返回值：三个通道都报 `pruned` / `pruneFailed`

前端也改了：`pruned` 的拼接从"DSI 分支内"移到**公共位置**。
理由：老通道清了旧行却不告诉老板，就是静默改动他的数据。

| 场景 | 显示 |
|---|---|
| 任通道 `pruned > 0` | 「…（替换了之前的 N 条旧记录）」 |
| 任通道 `pruneFailed > 0` | 「⚠️ 有旧记录没清理干净，金额可能偏高。请再导入一次同一份表，就会覆盖干净。」 |

## §4 断言（第 225 套件 50 → 52）

- D6-④ 改为**在 DSI-1 handler 段内**判「写 → 清」的先后（原来钉的是已删除的变量名 `toPrune`）
- D6-⑥ 🔴 **三个通道都接了清理**（全文件 `await pruneStaleGroup(` ≥ 3 处）—— 防"只修一个"
- D6-⑦ **清理只有一份实现**（`async function pruneStaleGroup(` 恰好 1 处）—— 防"各 handler 各写一遍"

第 226 套件 16 条保持，C-④/C-⑤/C-⑥ 现在同时覆盖老通道（因为拼接逻辑走公共位置）。

## §5 语义代价（有意的，写进函数注释）

**同一天同一渠道分两次导不同部分 ⇒ 第二次覆盖第一次。**
我们的表本来就是"一整天的完整导出"，分次导属误用。数据正确性优先于容忍误用。

如果将来真有人这么用，正确的解法是**在预览期提示"这一天已有 N 条数据，会被覆盖"**，
而不是放弃清理（放弃清理 = 金额虚高，更危险）。

## §6 已知边界

- 单组旧 `_id` 取 500 条，超了会漏清尾部（餐饮单店单日单平台不会到这个量级）；
- 软删非物理删，数据仍在（可恢复、可审计），占存储；
- 清理失败不阻断导入，只回报（新数据已正确，最坏是残留几条旧行）。
