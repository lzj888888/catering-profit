## 2. 真正的缺口（连锁 + 共用智库的剩余工作）

### 2.1 连锁总部 / 跨店聚合（最大缺口）
- 现状：每个 shop 是 `globalData.shop_id` 隔离的孤岛，**没有多店合并视图**。
- 缺：①"经营主体 / 连锁"实体（`shop` 无 `parent_shop` / `chain_id` 字段）；②跨店汇总口径（关联交易抵消、总部费用分摊、跨店租金、并表 vs 分表）——**必须复用 M1 口径锁 + 单源纪律**，否则"汇总越快、错得越可信"；③`getCostCard/resolve.js:16,32,35` 已有 `opts.chainMerge` **预留注入点**（"连锁后期注入，单店期不传"）——成本卡合并的钩子已留好，接上即可。

### 2.2 连锁成员 / 角色模型（缺失）
- 现状：只有后台 `adminAuth.js` 的 `super/op`（超管/运营），**没有店铺级 店长/会计/只读 角色**；微信无组织体系。
- 缺：用户-门店-角色三元关系 + 行级权限（前次豆包要点）。这是**付费墙红线**——防店长共用老板微信绕过 M1 一家店真拦（`manageShop` + `check_paywall_coverage`）。

### 2.3 跨业态公平对标（纪律约束，非新功能）
- 不同 `biz_type` 的毛利率/回本期**不可直接平均**（前次豆包也强调）。跨店对比必须先按 **业态 × 城市** 分层再比；`indicatorRef` 已分业态，复用即可。

### 2.4 智库"共用"还差两处
- **M2（开店盈亏矩阵）尚未消费 anomalyRules / indicatorRef 做"这家店型在你的业态里是否健康"的诊断**。M2 是前瞻模拟，最自然的接法是：用 `indicatorRef` 的分业态带比对模拟结果，给出"该店型在你们业态里处于什么位置"。
- **"10–20 张原创/授权知识卡片（整改方向文案）"未建**：`anomalyRules` 只说"去核单据"，不给知识卡。这是会诊里**最 optional** 的一块，且必须原创/授权（绝不抓抖音/公众号洗稿）。

## 3. 建议的落地路径（修订版）

### 议题一（连锁 + 跨业态）——"在 dev 上加两层"，不是 M4 抽象
- **P1（最低成本、复用最多）**：
  1. 扩 `shop` 加 `chain_id`（或独立 `chain` 集合）；把 `getCostCard/resolve.js` 的 `chainMerge` 接上（成本卡跨店合并）。
  2. 新增**只读跨店汇总**云函数：按统一口径聚合 per-shop ledger，复用 M1 口径锁/单源守卫。
  3. 建**成员角色表**（老板/店长/会计/只读）+ 行级鉴权；付费墙把"店长共用老板微信"列为红线。
- **计费**：直接复用 `free_limit` / `hit_free_limit`（第 2 店起付费已是钩子）；业态模板不单列收费（防避税，前次共识）。

### 议题二（共用智库）——已经半落地，剩余两块
- **必做（低工作量）**：让 M2 接入 `indicatorRef` 做"店型健康度"比对（M1 已有 anomaly、M3 已有象限，M2 补齐即三模块共用闭环）。
- **可选（最低优先级）**：原创/授权知识卡层（整改方向文案）。建议暂缓——规则引擎已能"指向问题"，知识卡是锦上添花且涉内容合规。

### 豆包第三司（程序化征询，2026-10-30 续）

> 经 `doubao-bridge`（endpoint `ep-20261011210929-mgqd6`，见 `review/_prompt_三司会审_三决策.md` → `review/doubao_会审_三决策.md`）。豆包在拿到真实代码现状后逐决策给推荐+理由。

- **决策一（连锁聚合第一步）**：推荐 **A＝先做只读跨店汇总**。
  理由：现有 `chainMerge` 预留注入点、多店数据隔离、`getShopList` 跨店 entitlement 计费、`getShopList` "第 2 店起付费"钩子均已就绪；只读聚合**复用单店已核算指标、不重算口径**（符合口径锁），且**不新增账号权限、不改计费主体**，杜绝"店长共用老板微信绕过 M1 一家店真拦"的付费墙风险。B（一步到位角色模型）无角色基础、鉴权 fail-closed 风险高；C 浪费预埋资产。
- **决策二（M2 接 indicatorRef 出店型健康度）**：推荐 **做（带严格规则约束）**。
  理由：`cx_indicatorRef` 已是分业态×城市分层的**单源**参考带，完全符合"不编行业基准、跨业态不直接平均"纪律；接入时严格按 `shop.biz_type` + 城市层级匹配，**仅输出"是否落在参考区间"判定**，无匹配规则时直接 fail-closed 不展示，**不臆造健康分/损失金额**。
- **决策三（原创/授权知识卡层）**：推荐 **当前阶段不做（暂缓）**。
  理由：非核心增值文案层，现有规则引擎（异常清单 + 参考带 + 菜品象限）已能直接支撑经营决策；原创/授权内容生产 + 合规审核成本高，若无"绑定规则 ID 的来源单源审核机制"易引侵权/不实建议风险，不符 fail-closed。

豆包优先级排序：**① 决策二（M2 接 indicatorRef，最低成本补全三模块诊断闭环）→ ② 决策一（只读跨店汇总，复用 chainMerge，不碰付费墙/口径红线）→ ③ 决策三暂缓**。
**与 workbuddy 完全一致**：先做 M2 接入 + 只读跨店汇总，都不碰知识卡。
