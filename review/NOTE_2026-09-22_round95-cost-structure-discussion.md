### Q1 「餐饮常见费用做成固定字段，剩下的客户自己补」

**现状（事实）**

- 费用项清单**已有单源 19 项**：`cloudfunctions/initDb/collections.js::SEED_EXPENSE_ITEMS`
  - 运营 7：房租、物业费、水费、电费、燃气费、垃圾清运费、宽带网费
  - 人工 5：工资绩效、社保、员工宿舍、员工餐、工装福利
  - 营销 6：外卖平台佣金、外卖配送服务费、外卖活动补贴、外卖配送补贴、外卖推广费、团购平台佣金
  - 其他 2：代账费、其他杂项
  - 前端 `miniprogram/i18n/terms.js::ledger.expense` 与之一致（19 项），术语层是渲染实际用的那一份
- 但**界面上初始一项都不显示**：
  - `pages/month/input.js:201-219 initGroups()` 初始 `rows = [{subItem:'', amountYuan:''}]`（**每类只有 1 行空行**）
  - `input.js:429 decorateRows()` 分派为 `g.category === 'dine_in' ? this.decorateDineRows(rows) : markFixedRows(rows, g.items)`
  - `utils/dineChannels.js:98 markFixedRows()` **只在已有行上打 fixed 标**，不铺全集 ⇒ 初始那个空行的 `subItem=''`，一个标都打不上
  - ⇒ 费用四大类默认形态 = **4 个「整类总额」框**（标签见 `input.wxml:250`，`g.label + t.classTotalSuffix`）
- 用户要加明细，只能点「+ 添加细项」→ `input.js:380-392 addRow()` 加的是**空白行**（`{subItem:'', amountYuan:'', custom:true}`），**名字要手打**，且没有「从 19 项里挑」的入口
- 而**堂食侧完全相反**：`utils/dineChannels.js:67-73 normalizeDineRows()` 用 `presets.map(...)` **把清单里的渠道全部铺出来**（没填就是空行），并给 `fixed:true`（`input.wxml:243-247` 据此不给输入框、不给删除键）

### Q2 「顾客补充的细项（收入/支出）数据会保存吗？」

**会保存，且收入/支出同构。**

- `cloudfunctions/saveLedger/index.js:99-106 toSnake()`：
  ```js
  { category, name, amount_fen, sub_items: [{ sub_item, amount_fen }] }
  ```
  收入用 `incomeItemsSnake`、费用用 `expenseItemsSnake` 落进同一条 `shop_monthly_account` 文档（`index.js:111`）
- 校验侧 `saveLedger/validate.js:24-67 cleanItems()`（收支共用）：
  - `sub_item` 字符串 **≤20 字**、可为空（`SUB_ITEM_MAX_LEN = 20`）
  - 有 `sub_items` 时**大类金额由云函数汇总**（Σ 细项），**前端传的 `amount_fen` 不采信**（计算下沉铁律）
  - `category` / `name` 是**自由字符串**，**无类别白名单、无条数上限**
- ⇒ 自定义细项在机器侧**没有任何门禁**，全靠前端引导

**但有一个重要限制：自定义细项不跨月继承。**

- `input.js:273` 只读单月：`api.call('getLedger', { month: this.data.month })`；`input.js:280 rebuildFromItems()` 从**当月** `expense_items` 重建
- 全仓 grep `copyLast|prevMonth|上月|复制` —— **没有任何「复制上月」功能**
- ⇒ 用户这个月手打了「垃圾袋」，**下个月要再打一遍**

这一条是本轮我认为**最影响「剩下的让客户自己补」体验**的事实：能存，但**不可复用**。

### Q3 「是整体按月份建的吧？可以一个月一个账套吧」

**是，而且已经就是这样实现的。**

- 一条 `shop_monthly_account` = **一个店 × 一个月**：`saveLedger/index.js:58` 按 `{ shop_id, month }` 查、`index.js:129-135` upsert
- 唯一索引封堵并发重复：`initDb/collections.js` → `idx_acc_shop_month` **unique (shop_id, month)**
- 归档即封账：`archiveMonth` 置 `is_archive=true`，`saveLedger/index.js:60-66` 归档后**全字段只读**，仅归档后 **7 天**内且显式 `archive_override` 才允许补录（超期返回 `ARCHIVED_LOCKED`）
- 台账（摊销资产）**不受归档约束**：`pages/month/amortize.js:78` 注释「摊销资产不属于月度归档（可跨月管理）；归档守卫只作用于记账录入」⇒ 归档后改资产不回算历史月（round94 D6）

**另有一组「设计表」没接线（值得你知道它的存在）**

`initDb/collections.js:11-16` 声明了：
- `shop_monthly_income` / `shop_monthly_expense`（**收支分开**的月度明细表）
- `shop_income_item` / `shop_expense_item`（**每店自定义收入/费用项字典**，带 `sort_order` / `enabled` / `is_system`）

全仓 grep（限 `*.js`）：**这两组表除了集合名与索引声明外，没有任何云函数读写它们**。
- `shop_expense_item` 的种子写入代码**只存在于原型脚本** `specs/dev-specs/prototype/init_db.js:253-262`，云函数 `initDb` 里**没有**对应写入调用
- ⇒ 本地证据表明：**云端这两张表很可能是空的**（真云 `count()` 未核，需一次探针才能定论，属「待核」而非结论）

这个「字典表」恰好就是 Q2 缺口（自定义项不可复用）的**现成落点**——见 §3 方案 B。

### Q4 「费用类需要合计吗？」

**需要，而且现有实现已经有「两处有、一处缺」。**

| 位置 | 有没有费用合计 | 锚点 |
|---|---|---|
| 后端（算 + 落库） | **有**：`expense_total_fen` | `saveLedger/service.js:18,26-27`；落库 `index.js:117` |
| 结果页 | **有**，且**可点下钻**到大类 → 细项 | `pages/month/result.wxml:48-62`（收入侧同样有，40-46） |
| 月度列表页 | **有** | `pages/month/index.js:114,122` |
| **录入页（input）** | **没有** | 全仓 grep：录入页只有 `syncDineSum()`（堂食）与 `syncTakeoutSum()`（外卖），**费用侧无任何实时小计** |

⇒ 建议补两层：**类内小计**（展开了才显示）与**费用总计**（常驻，含未展开的类），并明确标注「**不含摊销**」（见 Q5）。

**⚠️ 一个必须点明的口径裂缝**：用户心智里「费用」= 所有支出，但系统里的「费用合计」**不含摊销**。
`saveLedger/service.js:26-27`：

```js
operationRefProfitFen    = 收入 − 费用 − 直接食材成本            // 参考利润：不含摊销
totalFactorRealProfitFen = 收入 − 费用 − 真实食材成本 − 摊销     // 真实利润：含摊销
```

所以在结果页上「收入 − 费用」**不等于**利润，差额里还藏着摊销。这需要在 UI 上给出解释，否则用户会认为算错了。

### Q5 「固定资产摊销算不算费用？加盟费/装修摊销和费用有关系吗？管理位置要不要调整？」

**这是本轮最该拉直的一条。事实分三层，三层不一致：**

1. **利润公式里：算。** 真实利润减掉 `effectiveAmortizeFen`（`service.js:27`）
2. **费用行里：不算。** 摊销**不进** `expense_items`，是从台账 `shop_amortize` 算出来的**独立减项**
   - 入账侧 `saveLedger/index.js:76-85`：开关开时 `amortizeFen = amortizeTotalForMonth(assets, month)`
   - 页面侧 `pages/month/amortize.js` 标题即「列表 + **当月合计** + 新增/编辑/报废」，本月合计来自 `d.total_amount_fen`
3. **参考利润里：不算。** `operationRefProfitFen` 不含摊销（`service.js:26`）

⇒ 回答「算不算费用」：**实质是费用，形式上不是费用行**。三种口径同时存在，用户不可能自己推出来。

**加盟费 / 装修费「要一直摊下去」——台账已经装得下：**

- 资产字段：`{ asset_id, name, value_fen(原值分), start_month, total_months, terminate_month }`
  （`getAmortSchedule/index.js:32-33,43-44`；`calcAmortize/validate.js:64-75`）
- **资产名是自由的**：官方自测里就出现「装修」「冰柜」「招牌制作」「旧空调」「**加盟费**」
  （`calcAmortize/selftest.js:37-41`）⇒ 加盟费无需新增字段，直接建一条资产即可
- 支持「追加采购」形成摊销分组：`group_id` + `batch_seq`（`tools/selftest_batch8c.js:41-46`）

**但有三个缺口：**

1. **台账没有类别字段**（无 `category`/`type`）⇒ 不能按「装修 / 设备 / 加盟费」分组，也没有分类报表
2. **提前报废的残值不进损益**（round94 D1，本轮复核确认）：`amortizeTotalForMonth` 只累加当期摊销额（`saveLedger/service.js:45-61`，末月 `return base`），**残值从不入账**；而页面文案 `terms.js:475` 对用户承诺「未摊余额将作为处置损失计入」⇒ **承诺与实现相反**
3. **「一次性计入当月」选定时这笔钱在利润里一分不出现**（round94 D2）：开关关闭 ⇒ `effectiveAmortizeFen=0`，而利润引擎**没有**「资产原值直接进费用」的入参

**「管理位置要不要调整」——是个真问题，现状如下：**

- 摊销页的入口链：录入页 → 「核算方式」→ 「装修设备」→ 选「按月分摊」→ `input.wxml:309-313` 才出现「前往管理」按钮
- ⇒ **开关没打开时，摊销页入口根本不存在**；开了之后，也只是「已登记 N 笔」一行（不显示本月金额，round94 D5）
- 建议方向（供讨论）：**把「本月摊销」作为费用段里一行只读项**（如「本月摊销合计 ¥X（N 笔，点开看明细）」），而不是藏在核算方式里

### Q6 「弄完费用，接下来才是食材成本，对吗？库存差 or 按采购直接填」

**对，次序就是「收入 → 费用 → 食材成本 → 摊销」，而且食材成本的两种口径都已经是现成机制。**

- 直接用（按采购填一个数）：`direct_consume_fen`（`saveLedger/index.js:112`）
- 库存倒轧：`realConsumeFen = 期初 + 采购 − 期末`（`service.js:19-21`），开关 `inventory_switch`
- 两者的**口径锁**（已有约定，别动）：**参考利润用直接填值；真实利润才用倒轧值**
  ```js
  operationRefProfitFen    = 收入 − 费用 − directConsumeFen        // 用直接填值
  totalFactorRealProfitFen = 收入 − 费用 − realConsumeFen − 摊销   // 用倒轧值
  ```
- `profit_diff_fen` = 两者差额（`service.js:28`），即「库存口径带来的利润差」

⇒ 食材成本这一段**先不用重构**：双模式齐全，M1 口径锁也在。要谈的是**顺序与依赖**：食材成本是独立段（`input.wxml:271-295`），不依赖费用段，可以并行做；**但摊销的归属必须先定**，因为它同时影响费用段的展示与真实利润的构成。

## 3. 方案（**待李老师拍板，本轮不动手**）

### 3.1 费用录入：建议做成「快速 / 分项」双模式，与收入侧对称

李老师上轮已确认的框架是「**快速模式 = 记账；分项模式 = 对账**」。费用侧照此对称：

| 模式 | 形态 | 适用 |
|---|---|---|
| **快速**（现状） | 每类一个「整类总额」框（4 个框填完即可） | 只想快速记个数 |
| **分项**（建议新增） | 常用项**常显** + 其余「一键加入」 + 自由细项 | 想对账 / 想看清钱去哪了 |

「分项」的实现路径（复用现成机制，不发明）：
- 把 `normalizeDineRows` 的「预设全集常显」模式抽成通用函数，费用类调用它
- 保留 `markFixedRows` 作为「非全集」场景的打标器

### 3.2 费用项分层（供讨论的具体建议）

**A 档 · 常显（默认就在页面上，空着也要看得见）**

| 类别 | 建议常显项 |
|---|---|
| 运营 | **房租、水费、电费、燃气费（燃料费）** ← 你点的这 4 项 |
| 人工 | 工资绩效、社保 |
| 营销 | 外卖平台佣金、外卖配送服务费 |
| 其他 | 无（保留总额行） |

**B 档 · 一键加入（折叠在清单里，点一下即成为一个空行，不用手打）**

- 运营：物业费、垃圾清运费、宽带网费、**低值易耗品**、**维修保养**、**保险费**、**办证年检**、**软件系统年费**、**刷卡/扫码手续费**
- 人工：员工宿舍、员工餐、工装福利、**招聘培训费**
- 营销：外卖活动补贴、外卖配送补贴、外卖推广费、团购平台佣金、**堂食推广费**
- 其他：代账费、**税费**、**押金/保证金（可退，打标排除）**

（加粗 = 19 项种子之外、建议新增的）

**C 档 · 自由细项**：空白行手打（现状保留），但**必须配套下面 3.3 的「可复用」**。

### 3.3 让「客户自己补充的项」可复用（两个选项）

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **B-1 复制上月**（轻） | 新建月账时，把上月出现过的自定义细项**名字**带过来（金额空） | 立刻解决 F4；不动数据模型；纯前端 + 一个读接口 | 上月没记过的项仍要手打；跨店不通 |
| **B-2 启用项字典**（重） | 接线 `shop_expense_item`（**表已存在、已有索引与权限**），把「常用项」升级为「种子 + 店铺自定义」的可积累字典，页面读它 | 一次定义长期复用；跨月可统计；天然为「自定义项报表」铺路 | 要加读写云函数 + 权限 + 守卫；前端渲染源要从 terms.js 切到「terms ∪ 店铺字典」 |

我的倾向：**先 B-1（小、快、无数据风险），B-2 作为下一步**。因为 B-2 会动「项清单单一数据源」，而 F11 说明这个区域**已经有分叉未平**，先扩源会让守卫面更复杂。

### 3.4 摊销与费用的关系：建议拉直成一条规则

**建议统一口径为：摊销是费用的一部分，只是来源不同（台账自动算 vs 手填）。**

落地方式（供讨论）：
- 费用段底部加一行**只读**：「本月摊销合计 ¥X（N 笔 · 点开看明细）」，与手填费用**并列但可区分**
- 费用「总计」行拆成两个数：**手填费用合计** / **含摊销的费用合计**
- 结果页在「费用合计」旁标注「不含摊销」，或在摊销行显式单列（已经是单列，只需文案说明）
- 真实利润的公式**不动**（`收入 − 费用 − 食材 − 摊销` 保持不变）

这样用户看到的就是「一笔一笔都在」，而不是「利润数字比我自己算的少了一块」。

### 3.5 摊销资产：要不要加类别

供讨论的两个选项：
- **不加**（保持自由命名）：够用，改动最小；代价是不能分类统计
- **加**（如 `asset_category`：装修 / 设备 / 加盟费 / 其他）：能出分类报表（如「设备类本月摊了多少」）；代价是台账字段扩展 + 老数据回填

我的倾向：**先不加，等「费用分项」做完再看是否真有分类需求**——避免为一个尚不明确的需求扩字段。
