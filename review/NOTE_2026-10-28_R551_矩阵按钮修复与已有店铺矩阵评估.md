## 二、🔴「点按钮没反应」的真因（真 bug，不是没接线）

**现象**：点了之后装修 / 设备 / 加盟费这些没被带过来。

**排查**：写探针（`_probe_r551.js`）把 `matrix.js` 的 Page 对象真实加载起来，
桩掉 `wx` / `Page`，直接调 `onReadSeed()` / `onResetDims()`，打印 `data.global`。

**病根**（`applySeed` 内部顺序反了）：

```
applySeed():
  ① setData(patch)                     // 经营类型/城市
  ② setData(set)   ← 写入种子里的真实值：装修 120000 / 设备 80000 …
  ③ this.syncBuildDefault()            // ❌ 放在最后
```

而 `syncBuildDefault()` 里的 `fill()` 是**无条件覆盖**：

```js
fill('decor', 'buildDecorYuan', 'buildDecorYears', 3);   // 有预设写预设值，没预设写空串 ''
fill('equip', ...); fill('franchise', ...); fill('transfer', ...);
if (!this.data.fieldTouched.area) g.area = AREA_DEFAULT[bk];
```

⇒ 老板填的 12 万装修、8 万设备、5 万转让**全被冲成空串**，面积被换成业态默认值。
界面上表现就是"点了没反应"——**零报错、零提示，只是数字没变**。

**修法**：先铺默认、再写用户真实值。

```
① setData(patch)  →  ② syncBuildDefault()  →  ③ setData(种子值)  →  ④ 重算汇总行
```
④ 是必须的：`buildSumText`（合计/月摊销那行）依赖 `global` 最终值，`syncBuildDefault` 里算的那次早了。

**探针修复前后对照**：

| | 修复前 | 修复后 |
|---|---|---|
| `buildDecorYuan` | `""` | `"120000"` |
| `buildEquipYuan` | `""` | `"80000"` |
| `buildTransferYuan` | `""` | `"50000"` |
| `area` | `40`（默认） | `"60"` |

**守卫**：`check_m2_matrix` 新增 R551 顺序判据（`syncBuildDefault` 必须在 `set['global.'` 之前），
185 → **186**；已做变异回灌（把顺序改回去 ⇒ 该条转红），证非恒绿。

## 三、已有店铺矩阵 · 四类真实场景跑数（真引擎）

用 `cloudfunctions/calcSandbox/service.js`（纯函数，未改口径）复算，
参数取四类典型店（房租/人数/毛利率/目标利润/装修设备/面积/人工总额/管理费/渠道占比均按常见值）。

| 场景 | 菜品毛利率 | 扣点合计* | **实际可用毛利率** | 固定成本/月 | 保本月营收 | 目标月营收 | 房租占目标 | 回本(月) | 营收下滑容忍度 |
|---|---|---|---|---|---|---|---|---|---|
| ① 面馆 快餐 · 二三线 | 60% | 13.5% | **46.5%** | 3.25 万 | 7.00 万 | 9.15 万 | 8.7% | 25 | 23.5% |
| ② 中式正餐 · 一线 | 58% | 11.6% | **46.4%** | 11.85 万 | 25.54 万 | 32.00 万 | 9.4% | 30 | 20.2% |
| ③ 火锅半自助 · 二三线 | 55% | 13.7% | **41.3%** | 7.59 万 | 18.37 万 | 23.21 万 | 8.6% | 42.5 | 20.9% |
| ④ 咖啡茶饮 · 一线高外卖 | 65% | 16.3% | **48.7%** | 5.23 万 | 10.74 万 | 13.82 万 | 14.5% | 35.3 | 22.3% |

\* 扣点合计 = 渠道佣金 + 其他杂支 + 业态预设的变动费率（面馆预设里另有约 2 点）。

### 3.1 这张表解决了什么

1. **把"多请一个人会怎样"变成可算**——这是矩阵的核心问句（R335 原话）。
2. **把"毛利率做到多少才活"变成可算**——毛利率 ±5 点对保本线的影响一眼可见。
3. **给出"我离保本还差多少"的绝对数**（保本月/日营收），不是抽象的毛利率。
4. **房租贵不贵有横向参照**——房租占目标营收 8.6~9.4%，落在 BANDS 5~10% 健康带内；咖啡 14.5% 明显偏高。

### 3.2 🔴 最值钱的发现：毛利率 ≠ 能付房租的钱

四个场景里，**菜品毛利率 55~65%，但实际能用来覆盖房租人工的只有 41~49%**——差 11.6~16.3 点。

老板心算"我毛利 60%，保本 = 固定成本 ÷ 0.6"会**系统性低估**保本线约 29%（60 ÷ 46.5 ≈ 1.29）。
这就是 R549 那个"口径填反导致保本虚高 51%"的镜像问题。

⇒ **建议**：矩阵默认列应有「**实际可用毛利率**」。老板对 60% 没感觉，
对"每 100 块营收只有 46.5 块能用来付房租人工"才有感觉。

### 3.3 指标该不该留（逐列判断）

| 列 | 判断 | 理由 |
|---|---|---|
| 保本月营收 / 保本日营收 | ✅ **核心** | 日营收更直觉（"一天至少卖 2332"） |
| 目标月营收 | ✅ 核心 | 对应"想月赚 1 万" |
| 目标日营收 | 🔶 冗余但有用 | = 目标月 ÷ 30，日常盯盘用；可留更多列 |
| 房租占目标营收 | ✅ 有用，**但必须标口径** | 分母是"目标营收"不是"现状"，老板会误读成"我现在就这样" |
| 回本月数 | 🔶 对已有店铺**意义弱** | 钱已经花了，回本是心理安慰不是决策依据；R548 已移出默认列 ✓ |
| 营收下滑容忍度（原「淡季安全垫」） | ✅ 对已有店铺**很有用** | 但名字有歧义——它算的是"营收比目标低多少仍保本"，不是季节性；**建议改名** |
| 涨租杠杆 | ✅ 有用 | 被藏在更多列；"房租涨 1000 要多卖多少"是老板会问的 |
| 现金保本/月 | 🔶 小众 | 给懂的人看 |

### 3.4 🔴🔴 最大的缺口：矩阵不知道"你现在卖多少"

矩阵只回答"要卖多少"，不回答"**我离它差多少**"。
已有店铺老板手里有真实流水（首页「预计月营业额」、M1 的实际收入），但：

- 首页的 `expectYuan` **没有进种子**（R551 的种子也没带）；
- 矩阵里没有任何"你现在这一档"的标记。

⇒ 他没法定"我现在在亏还是在赚、差几千"。这是从"算账"到"决策"的关键一步。

**建议**（改动中等，需拍板）：
1. 种子里补 `expectYuan`（实际/预计月营收）；
2. 明细表每一行加一列或加标记：「**你差 X / 超 Y**」；
3. 把"离你最近的那一档"高亮出来，让他一眼看到自己站在哪。

### 3.5 🔴 一个会让结论失真的维度问题（已确认，待拍板）

**老板填了「人工每月总额」后，「人工人数档位」就完全失效。**

实测（面馆、人工总额 18000）：

| 人数档位 | 3 | 4 | 6 |
|---|---|---|---|
| 实际用的人工 | 18000 | **18000** | **18000** |
| 没填总额（按人均 4500） | 13500 | 18000 | 27000 |

原因：`assembleItems` 里**总额优先**（R296 拍1 的设计），`laborTotal > 0` 时不再按"人数 × 人均"。

后果：矩阵的核心问句「多请一个人会怎样」**变成假的**——三条档位算出同一个保本线，
而界面不提示，老板会得出"多请一个人不要紧"的错误结论。

⚠️ 注意：这不是 "火锅预设固定人工" 造成的（那个我验过，会随人数变：3人 15000 / 8人 40000）。

**三个可选修法**（我推荐 C）：

| 方案 | 做法 | 代价 |
|---|---|---|
| A 提示 | 检测到总额已填 ⇒ 档位区显示"改人数不影响结果，因为填的是总额" | 最省事，但核心功能形同虚设 |
| B 换维度 | 有总额时把"人数档位"换成"人工总额档位"（如 1.8万/2.1万/2.4万） | 语义正确，但要改档位标签与默认值 |
| **C 人均增量** | 有总额时，每 +1 人按**当前人均**（总额 ÷ 当前人数）递增：3人18000 → 4人 24000 | 保留"多请一个人"的核心，符合直觉；需改 `laborOf`/装配入参并在界面注明 |
