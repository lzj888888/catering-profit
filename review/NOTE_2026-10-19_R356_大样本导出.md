# R356 · 大样本导出：撞到 1MB 响应上限，被误报成「网络不可用」

> 日期：2026-10-19 · 脚本 `r356_big.js` / `r356_max960.js` · 报告 `r356_big.json`

## 一、先说结论

| 规模 | 结果 |
|---|---|
| 144 行 | ✅ 11.8 KB 请求体 · 6.0 秒 · 导出 144 行 |
| 288 行 | ✅ 23.0 KB · 3.0 秒 · 导出 288 行 |
| **960 行** | ❌ **0 行、3.6 秒失败**，页面提示「**网络不可用，请检查网络连接**」 |

## 二、根因：云端响应超过 1MB

抓到的原始错误：

```
errCode: -501000
errMsg: response size exceeded 1048576 bytes
        (EXCEED_MAX_RESPONSE_SIZE)
```

矩阵分支一次返回**每行的完整引擎结果**（约 1.1 KB/行）：
`960 × 1.1KB ≈ 1.05MB` > 云开发 1MB 响应上限。

**为什么这条特别坏**：`utils/api.js` 把所有 `callFunction` 抛错都归到 `NETWORK_ERROR`
⇒ 老板看到「网络不可用」⇒ 他会去检查 WiFi、换网络、反复重试，
而真正的原因是「你选的档位太多」——**提示把他引到完全错误的方向**。

## 三、修法

### ① 分批请求（150 行/批）
```js
const CHUNK = 150;
for (let off = 0; off < cleanArr.length; off += CHUNK) {
  const part = cleanArr.slice(off, off + CHUNK);
  const d = await api.call('calcSandbox', { action: 'matrix', clean_array: part });
  // 按顺序拼接 rows；rejected 的 index 补上批次偏移
}
```
每批 ≈165KB，安全。行序与 `meta` 一一对应，不改变下游任何逻辑。

### ② 明确上限提示
云端 `clean_array` 上限 1000 ⇒ 前端先挡：超了直接说
`档位组合 {n} 行，超过上限 {max} 行，请减少档位`（文案进 terms 双副本）。

## 四、修后实测（960 行）

```
调用次数 7 批 · 总耗时 6.3 秒 · 行数 960 · rejected 0 · 无 toast · errMsg null
```

## 五、判据（168 条，+3）

- 必须存在 `CHUNK` 分批循环且用 `allRows` 拼接
- 不得再出现一次性 `clean_array: cleanArr`
- 必须有 `MAX_ROWS` 上限提示（且文案走 terms）

变异：把 `clean_array: part` 改回 `clean_array: cleanArr` ⇒ ❌；还原 ⇒ 168/168。

## 七、顺带确认

「导出行数 = 页面行数」在 144 / 288 行都成立（144=144、288=288），
每行列数恒为 14 ⇒ **前端没有偷偷截断**，问题只在云调用的响应体。

## 八、没做的（如实）

- 只做到 960 行（云端上限 1000），1000 行未单独跑
- 分批是**串行**的：7 批 6.3 秒可接受，但更大规模会更慢（未做并发）
- 失败时未做「部分成功」提示：任一批失败即整体失败（保持原语义，未改）
