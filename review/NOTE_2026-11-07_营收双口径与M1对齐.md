## 1 两套口径的完整定义（真源在代码，不在这里）

### A 现金流入（老板对现金账口径）

```
现金流入 = 现金 + 充值 + 扫码 + 挂账还款
```

- 用途：**只对现金账**。钱有没有进抽屉、有没有进银行，用它核。
- 特征：收付实现制 —— 收到钱就算。
- 代码：`utils/revenueDailyParse.js` → `cashInflow`，带 `purpose: 'cash_reconciliation'` 标签。
- ⚠️ 表里那列「营业收入」= 这个数，**永远不当营收用**（守卫 D/E 组钉死）。

### B 经营营收（M1 权责发生制，**这才是营收**）

```
营收 = 堂食 + 外卖
  堂食 = 现金 + 扫码 + 储值卡消费 + 挂账消费 + 团购核销
  外卖 = 美团外卖 + 京东外卖 + 淘宝闪购（总额法，佣金另记营销费用）
```

- 用途：**M1 利润、M3 一切对外结论**。
- 依据：`TERMS.ledger.income`（M1 记账页权威类目表）堂食七项：
  现金收款 / 微信扫码收款 / 支付宝收款 / 银行卡POS刷卡 / **储值卡消费** /
  **个人单位挂账消费** / **团购代金券核销**。
- 代码：`revenueM1`；`M1_DINEIN_MAP` / `M1_TAKEAWAY_MAP` 是**显式映射数据**，守卫 F 组与
  `TERMS.ledger.income` 机器对齐。

## 2 🔴 我上一轮错在哪（必须记）

上轮报告我写：

> 「M1 营收 → 现金+扫码+**挂账还款**（实收）+ 储值消费 + 平台到手额，预存单列」

**错在「挂账还款」。** 挂账还款是**收回旧账**，那笔收入在当初赊出去时就该确认；
当期算它就是重复确认。正确的是 **`挂账消费`（新赊出）** 才算当期营收 —— 已消费未收款。

这与 M1 类目「个人/单位**挂账消费**」一致，M1 里没有「挂账还款」这个类目。
⇒ 本轮按 M1 类目纠正，并写进 `M1_DINEIN_MAP` 作为数据，不靠记忆。

## 3 真数据（9.1–9.13，24 个业务班次）

### 3.1 两套口径

| 口径 | 数值 | 说明 |
|---|---|---|
| **A 现金流入**（表里「营业收入」列） | **59,700.80 元** | 现金 3,676.50 + 充值 22,673 + 扫码 31,284.30 + 挂账还款 2,067 |
| **B 经营营收**（M1 权责制） | **64,547.08 元** / 6,454,708 分 | 堂食 61,850.70 + 外卖 2,696.38 |
| 差额 | **+4,846.28 元（+8.12%）** | 见 §3.2 |
| 未确认项 | 茶楼 550.00 | 含义未知，**不计入营收**，单列 |

堂食 61,850.70 = 现金 3,676.50 + 扫码 31,284.30 + 储值卡消费 22,126 + 挂账消费 1,504.50 + 团购核销 3,259.40
外卖 2,696.38 = 美团 232.19 + 京东 385.84 + 淘宝 2,078.35

### 3.2 差额桥：两个数为什么不一样（四组互换，无第五项）

| 方向 | 项目 | 金额 |
|---|---|---|
| 老板**多算**（钱到了但还不是当期收入） | 充值（预存） | 22,673.00 |
| | 挂账还款（收回旧账，早确认过） | 2,067.00 |
| | **小计** | **24,740.00** |
| M1 **多算**（消费了但钱没走收银） | 储值卡消费 | 22,126.00 |
| | 挂账消费（吃了没付钱） | 1,504.50 |
| | 团购核销 | 3,259.40 |
| | 外卖 | 2,696.38 |
| | **小计** | **29,586.28** |
| | **净差 = 29,586.28 − 24,740** | **+4,846.28** ✅ |

**恒等式**（守卫 E-⑤ 每次跑都验，不成立立刻红）：

```
(M1 多算 − 老板多算) ≡ M1 营收 − 现金流入
```

这条恒等式的价值：**它机器证明了「差额没有第五个来源」**。
以后老板改动任何一个列，只要恒等式还成立，我们就知道没漏算；一旦失衡，说明有新的口径差没被识别。

### 3.3 本月为什么差额只有 8%（不是 40%）

9 月充值和会员消费几乎相等（22,673 vs 22,126，差 547），两组互换后互相抵消。
**但这是巧合，不能依赖**：若某月搞充送活动（充值冲到 8 万而消费只有 2 万），
现金流入口径会把营收虚高 6 万。这正是李老师说「不能给人错误信息」的场景。

## 4 本表是手工表吗？（李老师问）

- **是手工表**：18 列、**零公式**（`openpyxl` 以 `data_only=False` 读，公式单元格数 = 0）、
  列宽与填法都是人手填的痕迹（如「9.1」不是日期格式、挂账写成「岳60」这种人名+金额文本）。
- **但列名来自美团收银系统**：现金 / 充值 / 扫码 / 茶楼 / 会员消费 / 挂账人·金额 /
  挂账还款人·金额 —— 这正是美团管家收银后台「支付构成 / 交接班」的口径。
  ⇒ 老板是**照着美团收银首页/交接班报表手抄的**，所以他抄到的「营业收入」就是美团那个含充值的数。
- 收款系统：**美团收银**（M1 `fastHint` 给的导出口径也是「美团管家 → 报表 → 营收概览 → 月报」，
  与现场一致）。

**⇒ 由此定一条操作口径**：以后老板若直接贴美团收银的「营业收入」，
我们必须**当场标注它不是营收**，并给出 M1 口径的数与差额。不能默默展示。

## 5 代码怎么保证准确（不是靠文案，靠机器）

`utils/revenueDailyParse.js` 输出三块，各有守卫：

| 输出 | 内容 | 守卫 |
|---|---|---|
| `cashInflow` | 现金流入 + `purpose:'cash_reconciliation'` + 表里那列的对账结果 + 逐行差异 | D 组（不得硬编码、公式单源）、E-⑦（防误用） |
| `revenueM1` | 堂食/外卖/合计 + `pendingOther`（茶楼单列） | E-①②③⑧⑨ |
| `bridge` | 差额 + 两侧明细 + **恒等式** | E-⑤⑥ |

**关键判据（都做了变异复核，改坏必红）**：

- **E-④ 差分测试**：把「充值」放大 10 倍 ⇒ **营收必须一分不变**、现金流入跟着涨。
  这比读源码强得多 —— 它验的是行为。变异①（把充值塞进营收）时它立刻报「营收 291,277（应不变）」。
- **F-②**：M1 堂食类目里**不得出现「充值」**（M1 自己都不收，M3 更不能收）。
- **F-③**：我们的映射表必须覆盖 M1 堂食**全部七项**，M1 将来加项我们没跟就红。
- **F-⑤**：「其他外卖」本表无对应列 ⇒ 作为**显式缺口**记录，不许假装覆盖。
- **F-⑥**：茶楼不在 M1「其他业务收入」类目里 ⇒ 印证「不计入」是对的（M1 该类只有废品变卖/预制菜零售）。
- **F-⑧**：M1 那条红线文案还在 —— 它是我们两套口径的**立论依据**，被删就等于失去依据。
