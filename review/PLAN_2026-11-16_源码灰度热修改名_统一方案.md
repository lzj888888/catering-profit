# 一、源码在不在？完不完整？

## 1.1 结论：在，且完整
| 项 | 实测 | 含义 |
|---|---|---|
| 提交数 | **1728 次** | 从第一天到现在每一次改动都有记录 |
| 分支 | `dev`（主力）+ `main` + 3 个 wip/skill 分支 | 双分支分离 |
| 远程 | `github.com:lzj888888/catering-profit.git` | **GitHub 有一份完整副本** |
| 未推送提交 | **0（已核对）** | 本地与远端一致 |
| 跟踪文件 | 10803 个 | 含全部源码 + 测试 + 文档 |
| `.git` 体积 | 546 MB | 历史全在（含二进制证据件） |

**最关键的结论：源码 = 整个 `catering-profit` 目录 + GitHub 仓库。**
只要这个仓库在，换任何电脑、任何账号、任何开发者，都能完整重建。

## 1.2 有没有"只在云端、仓库里没有"的东西？（这是真盲区）
有，但**都是可重建的配置或数据**，不是源码：

| 项 | 在哪 | 丢了怎么办 |
|---|---|---|
| **小程序 AppID** | `project.config.json:3`（仓库里有） | 后台可查，不丢 |
| **云环境 ID** | `miniprogram/config/env.js`（仓库里有） | 控制台可查 |
| **4 个定时触发器** | `*/config.json`（仓库里有声明） | ⚠️ **必须手工上传**，代码里有≠云端生效。丢了重传 |
| **云函数环境变量** | 仅 `initDb` 一个（`DEV_ENV_ID`，仓库 config.json 里有） | 重配 |
| **数据库 33 张集合 + 索引** | `initDb/collections.js`（仓库里有定义） | 跑 `ensureCollections` 重建结构（**数据要另备份**） |
| **数据库里的数据** | 云端 | **只有 `dbBackup` 的月度备份**（云存储 60 天留存） |
| **云存储文件** | 云端（备份 + 用户上传的 xlsx） | 备份件丢了就没了 |
| **小程序后台配置** | 微信后台（名称、类目、隐私指引、服务器域名） | 手工重配 |
| **支付商户号** | 微信支付后台 | 重新申请 |

**⇒ 真正的风险不是"源码丢"，而是「云端配置与数据没有版本管理」。** 这一条要在运维手册里固化。

## 1.3 一个必须纠正的认知
**"源码在手上" ≠ "能随时重建"。** 能重建的前提是：
① 仓库完整（✅ 已具备）
② 知道要改哪几处配置（✅ 只有 2 处：appid + env）
③ 知道云端要做哪几步（✅ `ensureCollections` + 部署 + 触发器）
④ **手里有小程序账号的登录权**（这是唯一"钱买不到"的东西，必须您保管）

# 二、源码怎么管（规范）

## 2.1 分支策略（沿用现有，不折腾）
| 分支 | 用途 | 谁能推 |
|---|---|---|
| `dev` | **日常开发主力**，所有改动先落这里 | 我 |
| `main` | **发布主线**，只在要提审/上线时从 dev 合并 | 您点头后我合 |
| `hotfix/*` | 线上紧急修复（从 main 拉，修完合回 main + dev） | 我 |
| `wip/*` | 实验性改动，随时可弃 | 我 |

## 2.2 版本标记（现在缺，必须补）
**每个上线版本必须打 Tag**：`v1.0.0`、`v1.0.1`…
```
git tag -a v1.0.0 -m "首次上线：M1/M2/M3 全量，免费期"
```
**为什么必须**：出问题要回滚时，`git checkout v1.0.0` 一秒回到那天的状态。没有 Tag，就只能靠翻 1728 条提交记录猜"当时是哪个版本"。

## 2.3 备份（三层）
| 层 | 现状 | 要补的 |
|---|---|---|
| 代码 | GitHub（已有） | 建议再加一个私有镜像仓（防 GitHub 异常） |
| 数据库 | `dbBackup` 月度 + 60 天留存（已有） | **上线后改每日**（现在月度对生产不够） |
| 云存储 | 无 | 用户上传的 xlsx 定期清理（现在永久留着，是成本也是隐私负担） |

# 三、上线后用户报 bug 怎么修（**最关键的一节**）

## 3.1 这个项目有个天然优势：算钱逻辑全在云函数
**云函数可以热更新**（改代码 → 部署 → 立即生效，**不用发版、不用审核、用户无感**）。
而前端（页面/样式/交互）必须走「上传 → 提审 → 发布」，通常 1~7 天。

⇒ **bug 分两类，修复成本差 100 倍**：

| 类型 | 例子 | 修复方式 | 用户看到变化 |
|---|---|---|---|
| **云函数内**（绝大多数） | 算错钱、导入解析错、诊断结论错、配额判错 | **热修**：改 → 部署 → 生效 | 秒级，无需用户更新 |
| **前端页面** | 按钮没反应、文案错、布局错、跳转错 | 发版：改 → 提审 → 发布 | 要等审核 + 用户下次打开 |

**这个项目的 M1 利润、M2 沙盘、M3 成本/毛利/对账、导入解析、诊断引擎，全在云函数** ⇒ 绝大多数真 bug 可以当天修好，不用等审核。

## 3.2 三级响应机制（建议固化为纪律）

| 级别 | 判定 | 响应 | 时限 |
|---|---|---|---|
| **P0 算错钱 / 全线不可用** | 用户账目数字错、所有人都用不了 | ① 若根因在前端：**立刻撤销分阶段发布 / 回退线上版本**；② 若在云函数：**云函数流量切回旧版本（秒级）**；③ 再慢慢修 | 30 分钟内止血 |
| **P1 部分功能坏** | 某页报错、某导入失败 | 云函数热修（当天）；前端等下个版本 | 当天 |
| **P2 体验问题** | 文案、样式、提示不清 | 攒到下个版本一起发 | 按节奏 |

## 3.3 云函数回滚怎么操作（**必须提前演练**）
云开发的「版本 + 流量比例」机制：
1. 平时：100% 流量走 `LATEST`
2. 上线前：把当前 `LATEST` **发布为版本 A**（快照），流量 100% → A
3. 改代码更新 `LATEST` → 设 10% 流量给 `LATEST`（灰度）
4. 观察没问题 → 提比例到 100%
5. **出问题 → 把 `LATEST` 流量设为 0%**（秒级回到 A）

⚠️ 关键点：**用户维度灰度**——同一个用户始终走同一个版本，不会一会儿新一会儿旧（体验一致）。

## 3.4 前端回滚
- 后台「版本管理」→ 可**回退到上一个全量发布版本**
- 限制：若上一个版本是「分阶段发布且已撤销」，则不可回退（官方规则）
- ⇒ 所以**分阶段发布时要谨慎撤销**，别把回退路径堵死

# 四、灰度怎么做

## 4.1 两套灰度，分开用
| 对象 | 机制 | 粒度 | 生效速度 |
|---|---|---|---|
| **云函数** | 版本快照 + 流量比例 | 可按百分比 + 用户维度固定 | 秒级 |
| **小程序前端** | 「分阶段发布」 | 按百分比，**15 天内必须全量或撤销** | 发布后立即按比例推送 |

## 4.2 建议的上线节奏
| 阶段 | 动作 | 观察 |
|---|---|---|
| 内测 | 体验版（白名单） | 自己 + 3~5 个真实老板 |
| 提审 | 提交审核 | 1~7 天 |
| **首发** | ⚠️ 第一个版本**必须全量发布**（官方规则，没有灰度选项） | 首周紧盯健康巡检 |
| 后续版本 | 10% 灰度 24h → 50% → 100% | 每档看 P0/P1 是否出现 |

## 4.3 已经有现成的"功能开关"体系
项目里已有 `utils/featureFlags.js`（`PAYWALL_ENABLED` / `BILL_IMPORT_ENABLED` / `FREE_ACCESS_MODE`）。
**新功能一律加开关**，出问题只需关开关，不用回滚代码 —— 这是最轻的止血手段。

# 五、改名规划

## 5.1 好消息：改名的工作量比想象小
| 认知 | 实际 |
|---|---|
| "店算"要改一大片 | ❌ 代码里**用户可见的只有 3~5 处**（诊断包标题、2 句文案），其余全在注释里 |
| 小程序名在代码里 | ❌ **真正的小程序名称在微信后台**（设置→基本设置→小程序名称），代码改不改与注册无关 |
| 导航栏标题就是小程序名 | ❌ `app.json` 的 `navigationBarTitleText` 是**页面标题**，现在是「开店算账」 |

## 5.2 要改的三层（顺序不能反）
| 层 | 位置 | 注意 |
|---|---|---|
| ① **微信后台小程序名称** | 后台设置 | 注册时就要定；**名称不可与已有小程序重名** |
| ② **备案名称必须与①完全一致** | 备案信息 | ⚠️ 官方明确：备案信息与小程序名称不一致会被警告/封禁功能 |
| ③ 代码里的品牌字样 | `i18n/terms.js` 3~5 处 + `app.json` 标题 | 改动分钟级 |

## 5.3 起名建议（供参考方向，最终您定）
好名字的标准：**能注册（不重名）+ 说清做什么 + 老板听得懂 + 不踩违禁词**。
- 避坑：不要带「盈利/赚钱/回本/收益」等违禁词（仓库已有禁用词表，备案敏感）
- 方向建议：体现"算账/成本/看清楚"这类中性工具语义
- ⚠️ 我不能替您查重名——**重名要在微信后台输入时才知道**，建议准备 3~5 个备选

## 5.4 改名执行清单（定了名字之后）
1. 后台改名称 → 2. 备案名称同步改（或备案时直接用新名）→ 3. 我改代码 3~5 处 + 导航栏标题 → 4. 跑门禁 → 5. 出码验证

# 六、数据安全与恢复（补上一版没说完的）

| 场景 | 能否恢复 | 怎么做 |
|---|---|---|
| 用户误删某月账 | ✅ 15 天内 | 软删未物理删除，后台可恢复（需写恢复入口） |
| 用户注销 | ⚠️ 30 天后不可恢复 | 注销即匿名化，30 天后物理删 |
| 云函数改坏了 | ✅ 秒级 | 流量切回旧版本 |
| 前端发版出问题 | ✅ | 后台回退上一全量版本 |
| 数据库整体损坏 | ✅ 但有损 | 月度备份恢复（**最多丢一个月** ⇒ 所以建议上线后改每日） |
| 代码丢失 | ✅ | GitHub + 建议加私有镜像 |

# 八、一句话总结

**源码在、完整、有 GitHub 备份；换账号只是改 2 处配置 + 部署。**
**上线后绝大多数 bug 能热修（因为算钱逻辑在云函数），前端问题靠灰度 + 回退。**
**改名主要是后台改个名 + 同步备案，代码只动 3~5 处。**
真正的风险不在这些，而在 **① 云端配置/数据没有版本管理 ② 备份只有月度 ③ 没有 Tag** —— 这三件现在补，成本最低。
