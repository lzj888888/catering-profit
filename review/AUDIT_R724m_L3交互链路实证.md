## 2. 🔴 本轮最重要：探针污染 dev，且「已还原」是假的

### 事故链（三次连跑才看出来）

1. **第 1 次跑**：备份了「当前店名 Abc」；A 把当前店改成 `__L3探针_937995`；B 切到对照店 999。
   `finally` **没有切回原店**，直接在 999 店上执行「还原」，把 **999 改名成了 Abc**。
   随后 reLaunch 首页，读到 Abc ⇒ 输出 `✅ 数据已还原`。
   **这个 ✅ 是假的**：当时停在 999 店，读到的正是刚被改错的那个名字；原 Abc 店仍留着探针名。
2. **第 2 次跑**：开头备份读到 `__L3探针_937995`（不是 Abc），且同一个 shop_id 上次叫 999、这次叫 Abc
   ⇒ 串起来才发现污染。独立查 `getShopList` 确认：
   `...2528523`（原 Abc）→ `__L3探针_144820`、`...5514629`（原 999）→ `__L3探针_937995`，其余 3 家未动。
3. **紧急修复**：按 `shop_id` 逐个调 `saveShopSetting` 改回 `Abc` / `999`；
   `remark` 实测全为空串、**未被污染**（探针传的也是空串）。
   再由**独立脚本**复核 5 家店名：`Abc / 999 / 888 / 顺水鱼馆 / 李家小面` ✅ 无残留。

### 根因不是「忘了清理」，是两处判据设计缺陷

- `finally` 没有把 `shop_id` 切回原店 ⇒ 还原操作作用在**错误的店**上；
- 还原校验只看「首页店名」⇒ 恰好被上一处错误喂成恒真，形成**自我印证的假绿**。

### 探针三重加固（`tools/probe_l3_interaction.js`）

1. 备份从「当前店名」改为 **全量店名快照**（所有店 id + name）；
2. `finally` 先 `SWITCH_SHOP(原店)`，再 `RESTORE_ALL` 按 `shop_id` **逐店写回**；
3. 校验改为 `getShopList` **全量逐条比对**，任一家不一致判红、保留备份文件；
   **绝不退化成「读首页店名」** —— 那正是假成功的来源。
4. 另提供 `--restore` 逐店兜底；头注释把事故原委写死，防后人「简化」。

第 3 次重跑验证：备份 5 家快照 → A/B 坐实 → `finally` 切回原店、逐店写回 5 家、全量比对一致。
**之后又用独立脚本单独查了一次云端**，不采信探针自己的输出。

## 3. C 链路：首版判据恒真，自我证伪并撤回

C 想验 R719 的「首屏缓存串店窗口」。首版时间轴四个点全是 `__L3探针_*`，判据拿 `before.name`（Abc）
去比 ⇒ 永远不匹配 ⇒ `pass=true` **恒真**。

更根本的问题：**采样发生在「切店后、重新导航前」**，页面实例没重建，data 按小程序生命周期本来就不会变，
四点同值是必然、**零信息量**。反过来读，这组数据恰恰说明「切店后当前页仍显示上一家店名」这个窗口真实存在，
但本探针**没资格**给它下结论。

处置：
- `C.pass` 改为 `null`（**未验成**，绝不写 true 冒充通过），写明原因；
- 加**反恒真自检**：喂一个确实含旧名的构造样本，检测函数必须抓到（实测 ✅，证明判据本身有分辨力）；
- 汇总输出改成「A/B 两条链路坐实；C 未验成」，不再包装成「三条全绿」；
- 台账另开 **R4-2（P1 deferred）**：撤回的是假绿，不是把问题验完了。
