## 挑错清单

### 1) `wx:elif="{{hasLedger}}"` 仍有漏点

- **成功无账可能两不靠**：若前一支是 `wx:if="{{!r}}"`，无账成功时 `r` 为真、`hasLedger` 为假，两个分支都不命中；除非另有 `wx:else`，否则会白屏。
- **空态、异常态、加载态未分开**：catch 时应显示网络/系统错误，不能和“未建档”共用；请求未返回时 `hasLedger=false` 还可能先闪一下空态。
- **tab 切换 / 返回会吃缓存**：页面若只在 `onLoad` 拉数，tab 切换、下钻返回、amortize 返回后走 `onShow`，可能保留上一个月或修改前的 `d.account_id`。
- **快速切月有竞态**：旧请求晚返回会覆盖新月份数据，导致 `account_id`、红带、空态错位；需要请求序号或 abort。
- **amortize 异步落账**：若摊销页保存后立即返回，月度账本可能尚未聚合/复制完成，结果页会短暂误判为空。
- **利润为 0 本身不应误判**：`hasLedger` 只看 `account_id`，和利润数值无关；真实零利润月份只要返回有效 `account_id` 就应进结果态。
- 但要防后端把“全零账本”序列化成无 `account_id`，或老数据/导入数据的 `account_id` 是 `0`、`""`，此时 `!!d.account_id` 会误判为空态。
- 若“默认空账”本身带默认账户的 `account_id`，这次修改会完全失效。
- 红带应继续由“利润是否小于 0”单独决定，不能和账本存在性混用。

### 2) `account_id` 不严格等于“有月度账本”

- `account_id` 只说明账户实体存在，不说明该月有账本记录；新建账户、占位账户、复制账户都可能有 ID 但无当月行。
- 账户已归档、软删、无权限时，也可能仍返回 `account_id`，但月度账本不可用或为空。
- 反过来，月度记录可能存在，但因投影、join 失败、数据修复、导入、历史版本等原因未带 `account_id`。
- 若老系统用数字主键，`0` 会被 `!!` 错判成无账本。
- 非事务性保存可能先建 account、后写月度账，失败后留下“有 ID、无账本”的脏数据。
- 更稳的契约是后端显式返回 `ledger_exists` / `ledger_id` / 月份记录状态，而不是前端拿 `account_id` 推断。

### 3) `existing.archived_at || 0` 会误杀，且语义不完整

- 会误伤：`archived_at=null` 可能是“老数据已归档但没时间戳”，也可能是“根本未归档”；`||0` 会把两类都当成 1970 年归档并拒绝保存。
- 若 null 实际表示未归档，这一改会直接阻断正常账本编辑，投诉风险最大。
- `0` 是过载哨兵：不同端可能把它解释成“无归档时间”“已过期”或 falsy 值，行为不一致。
- `||` 还会把 `""`、`false`、`0` 一起吞掉；即使要处理 null，也应先明确 schema，再考虑 `??`。
- 更稳的是服务端三态判断：
  - 未归档：直接允许；
  - 已归档且有时间戳：用服务端时间判断是否在宽限期；
  - 已归档但无时间戳：先回填归档事件时间，无法回填时走明确的迁移/补偿策略。
- 宽限是写权限，必须在云端判定并返回 `can_edit`，不能依赖前端 `withinGrace`；前端结果只能用于展示。
- 上线前应统计 `archived=true/archived_at=null` 的存量，否则误杀规模不可知。

### 4) `nowMs` 激活后的隐患

- `typeof nowMs === 'number'` 会接受 `NaN`、`Infinity`，应使用 `Number.isFinite(nowMs)`。
- 它会静默忽略 `Date` 对象和数字字符串；若历史调用方传的是 `new Date()` 或 query 中的字符串时间，会意外回退到当前时间。
- `0` 现在会被当成合法时间 1970-01-01；若有调用方用 `0` 表示“不传”，行为会变。
- 秒级时间戳会被当成毫秒，直接导致宽限判断错误。
- 若该函数用于安全拦截，调用方可任意构造 `nowMs` 绕过；权限判断必须用服务端时间。
- 需排查所有第二参调用点，防止原来传入的是 options、回调或其他无意义值，现在被解释成时间。
- 若缓存了 `withinGrace` 的结果，跨宽限边界会变陈旧，应重新计算。

### 5) 守卫不应靠正则谈“可达性”

- 正则只能证明字符串存在与否，不能证明 WXML 分支可达；把断言改“软”而没有行为测试，本质可能是放水。
- 旧守卫变红说明它拦住了实现变更，但新守卫必须锁住真实场景：未建档成功、建档零利润、亏损、网络异常、加载中。
- 建议把分支判断收敛成显式状态，如 `loading | error | empty | ready`，WXML 只消费状态；再对状态计算函数做单测。
- 若坚持静态守卫，也应禁止 `r` 真值分支并约束显式状态，而不是继续硬钉第 6 行或具体字符串；空格、换行、引号变化都会绕过正则。
- 还缺 API 契约测试：getLedger 无账时必须明确 `exists:false`，不能返回让前端猜的“默认空账”。
- 归档宽限要补云端直调测试，防止绕过前端直接调用 `saveLedger`。
- 需覆盖 tab 切换、下钻返回、amortize 返回、快速切月、分享直达等生命周期路径。

## 最终结论

- 仅把 `r` 改成 `!!d.account_id` **不够**，可能白屏、闪空态、吃缓存或遭遇请求竞态。
- `account_id` **不等价于**月度账本存在。
- `archived_at || 0` **会误杀 null 老数据及未归档数据**，应先回填并在服务端做三态判定。
- `nowMs` 参数修复应加 `Number.isFinite`，且不能用于服务端权限判断。
- 守卫应升级为**状态/行为测试**，而不是把脆弱正则换成另一个脆弱正则。
