## Q1：5 条 P0 真伪判定

1. **真炸，且是最严重的一条。** `order_no` 唯一索引 + 回调 insert 新流水用同一个 `out_trade_no` ⇒ 第一次回调就 `Duplicate entry` 报错，事务回滚，用户付了钱拿不到权益；微信重试 N 次全部失败，最终进「支付成功但未发货」投诉。同时原 pending 单永不回写 paid，对账永远对不平。这不是「接支付即炸」，是「第一笔真实支付即炸」。
2. **真炸，拆成两个独立缺陷都成立。** attach 没落库没透传 ⇒ 回调拿不到 plan_id，权益发放直接失去依据（配合第 3 条就是发 0 天）；金额不比对 ⇒ 可被构造低价 `total_fee` 的回调（或微信侧金额与订单不符时）静默发货，属于资损 + 合规双重问题。金额校验是硬性要求，不是惯例。
3. **真炸。** `days=0` 走 `expire_at = max(now,原值)+0` ⇒ 等于 now，权益当场过期，用户付 19.9 拿到 0 秒诊断额度。这是「收钱不办事」，比第 1 条更容易直接触发退款和投诉。
4. **真炸，但属于「慢性炸」。** 无主动查单 ⇒ 回调丢失/延迟时订单永久 pending，用户已扣款无权益；无对账 ⇒ 资金差错只能等用户投诉才发现。上线首月就会积累。
5. **高估了，降为 P1。** 无唯一约束不会让支付流程当场失败，只会让重复回调产生重复流水（配合第 1 条修好后才会暴露）。但 `transaction_id` 无索引会让查重全表扫，量起来后回调超时——**先加唯一索引，别只加普通索引**，否则等于没修第 1 条的查重逻辑。

**结论：1、2、3、4 是真 P0；5 是 P1，但修法必须是唯一约束而非普通索引。**

## Q2：你没列、必踩的前 3 坑（概率 × 损失排序）

1. **虚拟支付二级商户号资质与类目被拒/回退。** 触发：个体工商户 + 餐饮工具 + 卖虚拟商品，微信对「虚拟支付」类目审核严，且个体户结算账户、经营范围常与「软件/信息服务」不匹配。后果：商户号下不来，整个付费墙无法上线，前面所有改造白做。**这是当前最大单点风险，且不归你代码管。**
2. **iOS 端虚拟支付限制。** 触发：小程序在 iOS 上卖虚拟商品，微信规则限制虚拟支付能力（历史上 iOS 端虚拟支付长期受限）。后果：iOS 用户看到付费墙但付不了，或审核直接驳回；你的付费点（导出/毛利/多店）在 iOS 上等于全免费或全不可用。**提审前必须确认当前 iOS 虚拟支付政策，别假设能付。**
3. **退款/售后无入口 + 无客服。** 触发：你提审期「零客服入口」，但虚拟商品一旦收费，微信要求可联系的售后路径；用户付了钱发现第 3 条那种 0 天额度，第一动作是投诉而非找你。后果：投诉率触发平台风控，商户号被限。**客服入口不是惯例，是虚拟支付类目的硬性配套。**

## Q3：不依赖商户号、现在就能改的前三件（性价比排序）

1. **把回调改成「更新原单」而非「插新单」：** `UPDATE orders SET status='paid', transaction_id=?, paid_at=? WHERE order_no=? AND status='pending'`，影响行数=0 则视为重复回调直接返回成功；`shop_payment_flow` 的 `transaction_id` 立刻加**唯一索引**。半天工作量，堵死第 1、5 条。
2. **下单时把 `plan_id`/`days`/`grants`/`amount` 写进订单表并随支付请求透传 attach；回调先按 `order_no` 读订单，校验 `total_fee == order.amount` 且 `attach == order.plan_id`，不一致直接拒绝发货并告警。** 一天工作量，堵死第 2 条，且让第 3 条的 grants 分支有数据可依。
3. **补 grants 分支 + 主动查单定时任务（哪怕先手动触发）：** 回调里 `grants='diag_credit'` 走发额度而非加天数；加一个每 5 分钟扫 `pending` 超 2 分钟订单、调微信查单接口回写的 job。一天半，堵死第 3、4 条。

**顺带直说：** 你「提审期零价格零客服」的做法在免费期没问题，但接支付前必须把客服入口和退款说明补上——这不是行业惯例，是虚拟支付类目审核会卡的点，别等被拒了再补。
