## 1 事故链（为什么会有这一轮）

`.gitignore` 与 `packOptions.ignore` 是**两套互不相干的机制**：

| 机制 | 作用面 | 对 `_m3/`（116 MB 调试截图堆，从未进 git） |
|---|---|---|
| `.gitignore` | 版本库（防误提交） | ✅ 已挡（round179 就写了） |
| `packOptions.ignore` | **微信打包**（预览 / 上传） | ❌ **没挡 ⇒ 被当源码打进包** |

后果：入包 118 MB ⇒ `code 10 · source size 118969KB exceed max limit 2MB` ⇒ 预览码连败 6 轮。
⇒ 结论：**`.gitignore` 写了不等于打包干净**；「本地磁盘有什么」才是打包的真实上限。

## 3 新守卫 R182 · `tools/check_pack_size.js`

判据三段，共 **11 条断言**（实跑 `11 通过 / 0 失败`）：

* **S 自失效护栏（4）**：S1 扫描面非退化（未忽略文件数 ≥ 60，实测 108）· S2 关键入口（`app.js`/`app.json`/`app.wxss`/`pages/card/index.js`/`pages/takeaway/index.js`）真在入包集合内 · S3-a/S3-b 匹配器四类 × 正负样本互证。
  > 为什么必须有 S：本守卫的核心判据是**上限**（总量 ≤ 预算）⇒ 一旦扫描面被扫空，`0 字节 ≤ 预算` 会**恒绿**。S1/S2 补的正是这一格。
* **P 入包体积（3）**：P-① 总量 ≤ 预算 · P-② 预算常量自洽（预算 < 微信硬上限，防「改大预算绕过」）· P-③ 单个未忽略顶层条目 ≤ 顶格（**失败行点名罪魁**）。
* **G 规则完整性（4）**：G-① 必备 20 条逐条在位 · G-② 条数下界 · G-③ `type ∈ 官方六种` · G-④ 未用 `regexp`/`glob`（本守卫未实现其匹配 ⇒ 出现即 fail-closed，不许静默漏判）。

**阈值取值（都取实测值的保守侧，不凭估）**

| 常量 | 取值 | 依据 |
|---|---|---|
| `TOTAL_BUDGET_MB` | 1.5 | 实测 0.615 ⇒ 约 2.4 倍余量；仍能抓到任何 ≥ 0.9 MB 的新增垃圾 |
| `PER_TOP_CAP_MB` | 0.8 | 实测最大合法顶层项 = `pages` 0.426 ⇒ 约 1.9 倍 |
| `MIN_KEPT_FILES` | 60 | 实测 108 的保守下沿（下界只防「扫空」，不承担防「变小」） |
| `MIN_RULES` | 16 | 实测 20 |

**边界（别高估）**：只守体积与规则形态；包里「该不该有某个业务文件」判不出来。上限类判据**只能发现变多、发现不了变少** —— 靠 S1/S2 兜底。
