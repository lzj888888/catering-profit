> 触发：李老师 2026-11-15「关于摊销这一块，做 2 轮交叉审计。从严审计。填几个月的数据去测试。」

| 关 | 2026-11 | 5,277.78 | 5,277.78 | ✅ |
| 关 | 2026-12 | 5,277.78 | 5,277.78 | ✅ |

**结论：四份 service 副本本身 100% 一致，数字全对。**

### 但这正是最大的盲区

service 层全绿，不代表链路对 —— **错可能在上游喂参**。继续查调用点，抓到：

### 🔴 P0-1：`getLedger` 调引擎时漏传 `month`，时间闸门在主链路上根本没生效

`cloudfunctions/getLedger/index.js:172` 原代码：

```js
const result = calcMonthlyProfit({
  incomeItems, expenseItems, directConsumeFen, amortizeFen,
  inventory, amortizeSwitchOn, inventorySwitchOn,
  lumpSumFen,
});   // ← 没有 month
```

引擎副本的时间闸门读 `clean.month`，拿不到 ⇒ 恒 `false` ⇒ 走老逻辑「按开关归零」。

**后果（fixture 实测）**：

| 月份 | 台账应摊 | 漏传后计入 | 修好后计入 | 每月利润偏差 |
|---|---|---|---|---|
| 2026-10 | 5,277.78 | 0.00 | 0.00 | 0（老月份本来就该 0） |
| 2026-11 | 5,277.78 | **0.00** | 5,277.78 | **少扣 5,277.78 元** |
| 2026-12 | 5,277.78 | **0.00** | 5,277.78 | **少扣 5,277.78 元** |

连带两个次生错误：
- `amort_extra.switch_on` = `result.amortRuleV2 ? true : …` ⇒ 恒 false ⇒ 结果页对**已计入**的月份显示「未开启摊销」
- `switches.amortizeSwitchOn` 同上 ⇒ 月报列表页 `amortText` 整段消失

**讽刺点**：我在 `saveLedger` 补 month 时写了注释「漏传等于规则失效」，却没给 `getLedger` 补。

**修**：补 `month: v.month`，并把「漏传」这件事做成守卫（E-②）。

## 三、第二轮：呈现面纵向（`r737_audit_2.js`，36 条）

**方法**：同一家店、同一月，让 **页面重算 / 导出件 / 摊销页** 三个出口比数字，并检查导出件表内加减是否成立（老板拿计算器核这张表）。

最脏的场景先测：**R736 部署前保存的 2026-11**（当时开关关着 ⇒ 落库 `amortize_fen = 0`），现在直接导出、不重存。

### 🔴 P1-1：导出件完全不认 v2 规则，与页面互相打脸

`cloudfunctions/exportData/index.js` 原来：

```js
const amOn = !!sw.amortizeSwitchOn;          // 落库快照（可能是部署前的 false）
const amort = nz(row.amortize_fen);          // 落库值（可能是 0）
```

后果（实测）：

| 项 | 修前 | 修后 |
|---|---|---|
| 导出件摊销行 | 0.00 | 5,277.78 |
| 页面（getLedger 重算） | 5,277.78 | 5,277.78 |
| 摊销页合计 | 5,277.78 | 5,277.78 |
| 利润表「参考 − 摊销」 | 与「真实利润」差一整笔 | 相等 |
| 差异行「开关关闭·本月未计入」 | **出现**（误导） | 不出现 |
| 口径说明「摊销开关」 | 关 | 不适用（2026-11 起一律计入） |

**修**：v2 月份从台账重算 + `amOn` 按 v2 取真。

这打破了既有的 `check_export_delivery` E6 禁令「禁止在导出里重算摊销公式（再写一份 = 静默错账）」。**这是真实的设计冲突，不是误报** —— E6 已被改成精确约束：

- E6 内嵌副本必须与摊销引擎**逐字同源**（只许差下划线前缀）
- E6-② 导出侧只允许**一份**实现
- E6-③ 必须标注「收进 common 时一并删除」
- 行为面由 `check_amort_rule_v2` F 段逐月真跑兜底

### 🔴 P1-2：导出件的「差异行」用近似公式，注定与明细对不上

原代码算台账应收额用 `round(原值 / 月数)`，**没看起摊月与到期月**：
- 已摊完的资产照样被算进去
- 未开始的也被算入
- 末月尾差不算

⇒ 差异行与「摊销来源」逐笔明细一加就对不上。改为与合计行同一个精确函数。

### 🔴 P1-3：归档月被「v2 重算」倒灌改写（R736 引入）

`getLedger` 的 v2 重算没有排除归档月。后果：

> 2026-11 归档（落库摊销 527,778）→ 老板删掉「设备」这条资产 → 再打开月报，封账月的摊销与利润被改成新值。

「已归档 = 只读」第四次变成假话（前三次：开关快照 R257、归档快照 R735、结果位 R735）。

**修**：`(amortV2Now && !isArchiveNow)` —— 归档只读**优先于** v2 重算。exportData 同步加 `!isArchiveRow`。

**验证**（场景 G，4 条）：

| 状态 | 台账 | 落库 | 导出件摊销 | 判定 |
|---|---|---|---|---|
| 归档后删设备 | 仅装修 | 527,778 | **527,778**（冻结） | ✅ |
| 未归档删设备 | 仅装修 | 0 | **361,111**（立刻反映） | ✅ |

### 我自己写的两个假绿（都被当场抓到）

1. **M-2 第一版判据太宽**：拿「口径说明表写不写关」当判据，但那行由 `amortV2` 决定、与 `amOn` 无关 ⇒ 恒绿。改成硬事实：**v2 月份只要出现差异行就是错**。
2. **E-④ 第一版判据太宽**：只要求「文件里某处出现 `!isArchiveRow`」。我变异掉摊销取数那一行、留着 `realP`/`diffFen` 两处，断言照样绿。改成钉**真正决定金额的那一行**的形态。

## 五、页面层：v2 月份从来没被测过（补齐 7 条）

`check_amort_display_caliber` 原来只跑 `MONTH = '2026-10'`（老月份）。而李老师真机打开的正是 **2026-11** —— 那个月开关已删、服务端出参恒报「已计入」。

补 K 段（7 条）：

| 断言 | 结果 |
|---|---|
| K-① 2026-11 + 开关关 ⇒ 页首报 4,333.33 | ✅ |
| K-② 2026-11 ⇒ 附注为空（计入了就别解释没扣） | ✅ |
| K-③ 页面拿到的开关是服务端**生效值** true | ✅ |
| K-④ 每笔资产「月应摊额」照常展示 | ✅ |
| K-⑤【对照】2026-10 开关关 ⇒ 仍是 0.00 | ✅ |
| K-⑥ 2026-11 下开关开/关数字完全相同 | ✅ |
| K-⑦ 变异 `amortRuleV2` 恒 false ⇒ K-① 转红 | ✅ |

顺带修掉一个**桩的假绿**：原来桩里 `amortize_switch_on: scheduleSwitchOn` 是手搓的布尔，无论传哪个月页面拿到的都是桩给的值 ⇒ 「服务端在 v2 月份恒报 true」这条事实在页面层**完全没被测到**。改用生产函数 `amortRuleV2` 派生。

## 六、测试脚本自身的 3 个错（诚实记录）

审计脚本自己也会骗人，这几个必须先修掉才能相信结果：

1. **单位混用**：导出件金额是「元」，我按「分」比 ⇒ 8 条全部误报红。
2. **末月算错**：装修 2026-09 起 36 期，末月是 **2029-08**，我写成 2031-08。
3. **金额列定位写死 `[1]`**：利润表金额在 `[1]`，摊销来源表在 `[6]` ⇒ 差异行判 NaN。改成从右往左找第一个数字。
