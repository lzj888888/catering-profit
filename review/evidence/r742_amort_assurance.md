# R742 · 摊销「万无一失」不变量守卫（李老师五问落地）

## 一、李老师的五问

> 关于摊销这块，尤其跨月数据是否正常，包括**增加新的摊销、重叠摊销是否随店铺随月份变动**，
> 这点很重要，你有何良策，把这块数据能确保后面万无一失？**包括数据库的正常。**

逐句拆成可验证的断言：

| 原话 | 对应风险 | 本轮回应的断言 |
|---|---|---|
| 跨月数据是否正常 | 同一资产逐月摊销求和会蒸发/错位 | **C 闭包**：摊销和 + 残值 ≡ 资产原值 |
| 增加新的摊销 | 中途加一笔，它之前的月份被偷偷改动 | **D 可加性**：新增资产只从 `start_month` 起生效，之前月份一文不差 |
| 重叠摊销随店铺/月份变动 | 同月多笔被合并尾差、或漏计；跨店串数据 | **E 重叠不重复** + **F 店铺纯度** |
| 随店铺变动 | 换店读到别店的资产 | **F**：引擎是纯函数，根本不认 `shop_id` |
| 数据库的正常 | 脏数据（重复行/孤儿 shop/非法字段/归档漂移） | **G 模拟对账**（四类脏数据都能扫出） |

外加一道**隐藏风险**（会诊顺带挖出）：三份生产引擎副本 + 一套 POC 引擎从未被比对过。

## 二、先摸现状（不采信自述，全靠读码 + 实测）

- **生产三副本逐字同源**：`getLedger` / `saveLedger` / `getAmortSchedule` 的 `amountForMonth` **目前一字不差**（A-①② 实测通过）。但**没有任何守卫钉死**——谁改一处忘改另一处会悄悄漂移。
- **第四套引擎（calcAmortize，批次2 POC1）走 UTC 锚点**，与朴素版从未比对。实测 336 点（4 类资产 × 84 个月）结果全一致（B-①），但这是"恰好没改"，不是"有人守着"。
- **店铺隔离扎实**：全仓 6 处 `shop_amortize` 读取（`getLedger`/`getAmortSchedule`/`saveLedger`/`exportData`/`calcAmortize`）每一处都带 `{shop_id}`；引擎纯函数 → F 通过。
- **归档锁已接上**：`saveAsset` 的新增/编辑/删除三条路径都过 `decideArchiveLock` + `applyLockPlan` → 新增一笔 `start_month` 早于已归档月的摊销会被拒（D 的边界被守住）。
- **唯一剩下的 DB 缺口**：同一笔实物资产被录两次（两个不同 `asset_id`）→ 摊销翻倍。当前没有"按签名判重"（同 `shop_id+name+start_month+value_fen+mode`）。这是 G-① 要抓、但**写入端还没堵**的点。

## 三、良策：四层防御（本次交付第一、二层）

### 第一层 · 引擎同源 + 双口径一致守卫（已交付 `tools/check_amort_invariants.js`，21 条）
- **A**：三份生产副本 `amountForMonth` 逐字同源（防漂移）。
- **B**：朴素版 vs UTC 版对 336 点结果一致（防两套时区口径分叉）。
- 每条带**变异回灌**：把尾差倒挤改掉 ⇒ C/B 必须转红（证明不是恒真）。

### 第二层 · 数学不变量守卫（同文件）
- **C 闭包**：`逐月摊销和 + 残值 ≡ 原值`（自然到期残值=0；提前终止残值=未摊余额）。
- **D 可加性**：新增资产只从 `start_month` 起生效。
- **E 重叠不重复**：同月多资产各自独立尾差，`total ≡ 各明细之和`，绝不合并。
- **F 店铺纯度**：换 `shop_id` 结果不变。
- **G 模拟对账**：重复行 / 孤儿 `shop_id` / 非法金额 / 归档月漂移 四类脏数据都能扫出。

### 第三层 · 写入防呆（**需您拍板，改写入行为**）
- **去重**：`saveAsset` 新增时按 `shop_id+name+start_month+value_fen+mode` 判重，已存在则改走编辑（upsert），从根上消灭"同一笔资产录两次 → 摊销翻倍"。
- 归档锁已 OK，不动。

### 第四层 · 真实云端对账（**需您拍板，新增只读云函数 + 一次部署**）
- `reconcileAmort`（只读）：扫描 dev 环境 `shop_amortize`，跑 G 的四类扫描 + 逐归档月"现算 vs 落库快照"漂移，出报告。读操作不写库，fail-safe。
