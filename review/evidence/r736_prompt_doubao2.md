# 我方技术核实（请重点质证这条）

**这是 DeepSeek 的一段建议，我认为它误判了：**
> 「对存量 `amortize_switch=false` 且有 `mode='amort'` 的行，切换时执行『剩余未摊金额 ÷ 剩余期数』的未来适用重排，避免总额少摊。若不重排，历史关闭期间未摊金额会永久缺失。」

**我的核实**（给了实际代码）：
```js
// getAmortSchedule/index.js::progressOf —— 台账进度
const start = monthIndex(asset.start_month);
const naturalEnd = start + asset.total_months - 1;
const end = asset.terminate_month ? min(terminate_month, naturalEnd) : naturalEnd;
const paidMonths = mi < start ? 0 : (min(mi, end) - start + 1);
const paidFen = Σ amountForMonth(k) for k in [start .. min(mi, end)];
const remaining_fen = asset.total_value - paidFen;
```
这段**完全不读 `amortize_switch`**。

也就是说：开关关着的那些月，台账期数**照常前进**、剩余未摊额**照常递减**、摊完月份**不变**。
关掉开关的后果只有一条：那些月的**利润表**里没减这一笔。

所以「未摊金额永久缺失 / 需要重排」是**把「利润没扣」误当成「台账没摊」**。真实后果是：那些月的利润当时多算了（因为没扣摊销），而不是台账少了钱。

**请你判断：我这个反驳成立吗？** 如果成立，则切换时**不需要动任何台账数据**，只需改引擎一处开关判断 + 定切换时点。如果不成立，请指出我漏了什么。

# 我发现的真实风险（请评估严重度并给处理方案）

**风险R**：已归档月份的展示走 `shop_ledger.switch_used` 快照。若删开关后把引擎改成「一律计入摊销」，但**忘记保留历史月的快照分支**，那么老板翻看 7 月报表时会突然发现利润比当时少了 4,333 元 —— 历史账目被事后改写。

我的处理思路：**引擎分两路** —— 归档月只认 `switch_used` 快照（老数据照旧），未归档月才按新规则（一律计入）。这样历史一字不改，只有"从今往后"变。

**风险S**：某店现在开关是关的，新版本上线后，**当月**（还没归档）会突然开始扣摊销，利润掉 4,333。老板会以为系统出错。

我的处理思路：上线后的**第一个未归档月**，在摊销页/结果页给一条一次性提示：「本月起摊销按台账计入利润，本月摊销 ¥4,333」。

请分别判断 R 和 S：严重度（高中低）、我的处理思路对不对、有没有更好的做法。
