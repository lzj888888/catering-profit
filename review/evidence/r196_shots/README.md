## 一 结论先给

**布局的真问题只有一个：全站 22 页、零底部导航。**
M3（菜品成本毛利）是使用频率最高的模块、含 4 个子功能，但入口最窄、层级最深。

**推荐方案 B：加底部三入口导航（核算 / 成本 / 我的）。**
改动集中在 `app.json` 一处 + 3 个入口页，**全站 22 页从此都能 1 次点击回首页**；
到 M3 菜品卡列表从 **2 步 → 1 步**。方案 C 作为第二批（先看B 顺不顺手）。

## 二 现状（实测，非印象）

### 2.1 页面与导航结构

| 项 | 实测值 |
|---|---|
| 页面总数 | **22 页**（`app.json::pages`） |
| 底部tabBar | **零**（`app.json` 无 `tabBar` 字段 ⇒ 22 页全靠页面内按钮互跳） |
| `navigateTo` | **33 处**（堆栈跳转，越摞越深） |
| `navigateBack` | 16 处 |
| `reLaunch` | 3 处 |
| `switchTab` | 1 处（且 R191 已证**实跑 0 次**——仓内有同名本地函数覆盖） |
| 各页 `navigationStyle` | **零个**⇒ 全站用**默认原生导航栏**（无自定义导航） |

### 2.2 首页（`pages/index`，27 行 WXML）四张卡

| 卡片 | 标题 | 副文案 |
|---|---|---|
| 1 | 默认店铺 · 当前店铺 | 切店铺标签 |
| 2 | 月度盈利核算 | 每月到底能剩多少，一算就清楚 |
| 3 | 开店盈亏平衡点测算 | 先算清这家店能不能开，再掏钱 |
| 4 | 菜品成本毛利核算 | 一道菜成本多少、卖多少不亏，自动算 |
| — | 底部两个 `btn ghost`：设置 / 我的 | 全站**唯一直达入口** |

🔴 **实测出的三个真问题**（机读+ 截图双证）：

1. **四张卡同质**：`.card2` 样式完全一致（`app.wxss:8` 起），只有文字不同 ⇒ 扫不出优先级，
   视觉上「四张白卡飘在灰底上」（这是 R192 自己给 M3 枢纽页写的病因描述，首页同病）。
2. **M3 入口最窄**：M3 实际有 **4 块业务**（菜品成本卡 / 原料库 / 外卖菜品成本 / M1↔M3 对账），
   首页只给 **1 个入口** ⇒ 老板点进去之前不知道里面有什么。
3. **深层回不去**：首页 → M3 枢纽 → 卡片列表 = **2 层**；再进编辑/版本 = 3–4 层。
   想回首页只能连按返回，回不去就退出小程序重来。**底部空荡，拇指够不到任何出口。**

### 2.3 全站最好的一页已在证明方向

`pages/m3/hub`（R192 改过）用**渐变 hero + 96rpx 彩色图标块 + 副文案说明用途**，
是全站唯一「有主体感」的页。**方案 B 的三入口沿用这套视觉语言**，不发明新样式。

## 三 三个方案

### 方案 A · 只重排首页卡片（最省，治标）

把 M3 卡提到第一位、给卡片加图标块与色阶。

| 项 | 值 |
|---|---|
| 到 M3 卡片卡 | 2 步（不变） |
| 改动面 | `pages/index.*` 约 30 行 |
| 遗留 | **仍无底部导航**；深层页回不去；M3 四个子功能仍需进枢纽页才知 |

### 方案 B · 底部三入口导航 ★推荐

`app.json` 加 `tabBar`，三个入口：

| tab | 落地页 | 内容 |
|---|---|---|
| 核算 | `pages/index/index` | M1 月度盈利核算 + M2 开店盈亏测算 + 店铺切换 |
| 成本 | `pages/m3/hub` | M3 四块（卡片卡 / 原料库 / 外卖 / 对账），沿用 R192 视觉 |
| 我的 | `pages/mine/index` | 订单有效期 / 使用指引 / 客服 / 隐私 / 版本（原样搬） |

| 项 | 值 |
|---|---|
| 到 M3 卡片卡 | **2 步 → 1 步**（底部点「成本」，枢纽页首屏就是它） |
| 任意深层页回首页 | **1 次点击**（原来要连按 3 次返回） |
| 改动面 | `app.json`（加 `tabBar`）+ 3 个入口页微调 + 图标资源 |
| 副作用 | ① tabBar 页**不能带参数** ⇒ M1/M2 需在核算首页内部再选一层<br>② `switchTab` 会**替换**当前页栈（回退语义变简单，正好符合预期） |

### 方案 C · 三入口 + 首页平铺直达（第二批）

在 B 之上，首页把 M3 四块直接平铺（带张数），M1/M2 两张大卡。

| 项 | 值 |
|---|---|
| 到 M3 全部子功能 | **1 步** |
| 改动面 | B 之上再改 1 页 |
| 代价 | 首页承担「导航 + 概览」双职，首屏信息量最大；「设置/我的」要不要留双份需定|

**我的建议**：先做 B，用起来顺不顺手是**可观察的**；再决定 C 要不要铺开。
不一次性做满，避免首屏信息过载（这是 R191「减数量 + 压行数」纪律的反向）。

## 四 可行性已验实（不是纸上谈兵）

| 风险点 | 实测结论 |
|---|---|
| **tabBar 要icon 资源** | 🔴 **全仓零图标资源**（`find` 无任何 `.png`/`.svg` 在 `pages/`、`miniprogram/` 下）⇒ 需新增 6 个 81×81 png（3 tab × 选中/未选中）。官方允许纯文字 tabBar，但视觉单薄，**建议做图标** |
| **包体积** | ✅ `node tools/check_pack_size.js` = **11 通过 / 0 失败**；入包 **0.6809 MB / 预算 1.5 MB**，余量 0.82 MB ⇒ 加图标无压力 |
| **`packOptions.ignore`** | 已有 20 条规则（含 `specs`/`review`/`cloudfunctions`/`tools`），新增图标放`images/` 即可自动入包 |
| **导航栏冲突** | ✅ 全站用**原生导航栏**（零个 `navigationStyle:custom`）⇒ 加 tabBar **不与自定义导航打架**，无二次改造 |
| **`switchTab` 实跑 0 次** | 🔴 R191 已证仓内有同名本地函数遮蔽⇒ 落地时**必须用 `wx.switchTab` 原生调用**并实测，别复用同名封装 |
| **门禁同步面** | 若改`app.json` 页面清单，需同步 `check_page_manifest`（提审 §4 页面清单 ≡ `app.json`）—— 门禁会抓 |

## 五 🔴 我自己的错判与撤回（留痕，防下一轮误判）

**错判①「页面标题与返回箭头重叠」——不成立，已撤回。**
初看模拟器截图（`pages/card/index`、`pages/month/index`、`pages/sandbox/index`），
我判断"标题文字压在返回箭头上"。**放大 3 倍后确认是误判**：原生导航栏标题**居中**、
返回箭头在左、微信胶囊在右，三者各就各位，标题离箭头近但**没有压在一起**。
真相：那些标题是 `ui.setTitle()` 设的**原生导航栏标题**（如 `pages/card/index.js:104`
`ui.setTitle(TERMS.card.listTitle)`），全站仅 `pages/material/pick.json` 自定义了标题文案。

**错判 ②「`.container` 顶到 `t=0/12` 是被导航栏压住」——判据设错，已撤回。**
原生导航栏是**浮层（overlay）**，页面内容本来就该从 `t=0` 起算 + 自己的 padding。
我设的判据「首元素 `top < statusBarH+44` ⇒ 被遮挡」对 overlay 导航栏**不成立**
⇒ 机读报了 10 页"🔴OVERLAP"是**假阳性**。
⚠️ 记档纪律：**原生导航栏下，"页面首元素 top 小"不是缺陷**；
要判"被遮挡"得比**可见文字**与**导航栏带**的交叠，不是比容器。

### 🔴 通道纪律（R196 又踩了一次，固化）

`automator.connect` **必须 `await`** —— 同步取会得到空壳对象，
表现为 `mp.evaluate is not a function`。另`mp.disconnect()` **不存在**，别调。
可用的只有：逻辑层 `wx.reLaunch` 导航 + `mp.evaluate(fn, arg)`（只透传第一个参数）。
