# R741 · 已归档月与口径变更 —— 三司会诊汇总与裁决

## 一、三司一致的两条（直接采纳）

### ① 不自动重算已归档月

- **DeepSeek**：「自动重算会让归档这个动作失去语义。归档的全部价值在于『这个数从此不再动』，一旦系统能在口径变更时悄悄改它，归档就退化成『一个可能随时变的缓存标记』，用户对封账的信任一次性透支。」
- **豆包**：「餐饮老板对『归档/封账』的认知是『已经核对完、可用于对账/报税的定数』，后台私改封账数值会直接击穿产品信任，后续封账功能没人敢用。」
- **我方**：同意。理由不是合规 —— **归档月自动重算是"擅自调账"，比留着一个已知的旧数更危险**。

### ② 不做「口径版本号」框架

- **DeepSeek**：「版本号不做。判据是『变更频率 × 单次成本』……这是为不存在的场景写框架。真到第二次口径变更时再补。」
- **豆包**：「开发量至少是本次需求的 3 倍……投入产出比为负。真要最低成本护栏，记一个『规则生效时间』，10 行代码能搞定。」
- **我方**：同意，且我在底稿里的怀疑被两司同时证实 —— 这跟 R736 犯的是同一个错（为不存在的场景写代码）。

## 二、两司各自成立、但互不相同的一条

### DeepSeek：披露必须满足三条件，缺一不可

> 「对餐厅老板，别用『口径变更』这个词。用『这个月的算法和现在不一样，利润可能差 X 元，要不要按新算法重算？』」

| 条件 | 含义 |
|---|---|
| 可见 | 归档月旁边有明确标记，不是藏在日志里 |
| 可比 | 给出「按现口径重算值」作为对照，让用户知道差多少 |
| 可操作 | 提供「取消归档并重算」的入口 |

**我方补注**：第三条件在本仓**已经天然存在** —— `archiveMonth` 本就支持 `archive: false`，用户取消归档后重新保存即按现口径重算。所以只需把前两条做出来，并在文案里指一句「如需按新算法，可取消归档后重新保存」。

### 豆包：别全量撤销模拟期归档

> 「真要处理别全量撤，只筛 11 月 15 日那 6.5 小时内保存过的归档月处理，范围极小、风险可控。」

豆包给的三条副作用里，有两条我原先确实没想到：

1. **撤销会留下「归档可以随便撤」的代码路径** —— 这次因为未上线所以无害，但路径一旦存在，上线后就会有人（包括未来的我）用它。「撤销脚本必须是一次性、带硬编码月份白名单、跑完即删，不能留成通用功能。」
2. **单开发无 DBA，批量改归档标记没有兜底** —— 条件写错就是扫全表，且没有回滚备份。

**我方裁决**：**连"小范围撤"也不做。** 理由：我们**没有云端数据库读取通道**（`cli` 无 db 查询子命令），连"哪些月是归档月"都不知道 ⇒ 任何批量操作都是盲写。为一个概率极低的模拟期错数去盲写生产库，风险收益完全倒挂。

## 三、豆包提的一条：本仓架构上已经不成立

> 豆包：「**核心盲点**：利润趋势图、累计利润汇总默认必须用封账原值计算，绝对不能偷偷用现算值，否则老板会把规则导致的差异当成经营波动。」

**核实结论：这条担心是对的，但本仓已经消除了。**

`subpkg/biz/month/result.js::loadChecklist` 取历史月的路径是逐月调 `getLedger`：

```js
const snapshots = [curLedger];
for (const m of built) { const d = await api.call('getLedger', { month: m }); ... }
const cl = anomaly.buildChecklist({ month: target, months: snapshots });
```

而 `getLedger` 是**唯一出口**，归档与否在它内部决定（`isArchiveNow ? 落库 : 台账`）。

⇒ **冻结实现在「数据源出口」而不是「某个页面」** ⇒ 趋势图、异常核对、导出、月报全部自动继承同一口径，结构上不可能出现「某页用现算」。这是本仓一个**值得保留的架构性状**，不是巧合。

## 四、我方独立发现（两司都没看到，且比原议题更急）

### 🔴 P0-1：R740 拆闸门时，把 R735 修过的「同月两页打脸」重新长出来了

| 出口 | 归档月摊销额取哪个 |
|---|---|
| `getLedger`（结果页 / 趋势图 / 月报） | `acct.amortize_fen`（**落库快照**） |
| `getAmortSchedule`（摊销页页首大数字） | `sched.total_amount_fen`（**台账现算，无归档分支**） |

`cloudfunctions/getAmortSchedule/index.js` 里 `total_amount_fen` 的赋值只有一行 `sched.total_amount_fen`，**没有任何 `isArchive` 分支** —— 而同一个函数上面明明读了 `isArchive`，只用它决定"页面是否只读"。

⇒ 归档月一旦漂移（落库值与台账现算不等），**摊销页显示 A、结果页显示 B**。这正是 R735 修过的病（「同一月份两个页面互相打脸」），R740 在拆闸门时把它重新长了出来。

**为什么守卫没抓到**：`check_amort_display_caliber.js` 的 I 段测的是 `amortize_switch_on`（开关参数），桩里 `is_archive: false` 是**硬编码**的 —— **从来没有一个断言测过"归档月页首到底显示多少钱"**。守的是参数，不是金额。

### 🔴 P0-2：`archiveMonth` 会给「从没录过的月」造一条全 0 假账

```js
let acct = (exRes && exRes.data && exRes.data[0]) || null;
if (!acct) {
  await da.insert('shop_monthly_account', { ..., amortize_fen: 0, income_total_fen: 0, ...,
    real_consume_fen: 0, gross_profit_fen: 0, total_factor_real_profit_fen: 0,
    is_archive: v.archive, archived_at: v.archive ? now : 0 });
  return ok({ ... });
}
```

用户对准一个没有任何数据的月份点「归档」⇒ 系统造一条**利润全 0 的假账**并立即封账，之后永远只读（`ARCHIVED_LOCKED`）。

⇒ 会计上这是「凭空生成一处零申报」，必须 **fail-closed**：找不到该月账 ⇒ 拒绝归档。

## 五、裁决（最终方案）

| 编号 | 决定 | 理由 |
|---|---|---|
| **D-1** | 不做任何数据迁移、不撤模拟期归档 | 无 DB 读取通道 ⇒ 任何批量都是盲写；两司一致反对 |
| **D-2** | 修 P0-1：摊销页归档月改读落库快照，并同时给出「按现台账重算值」作对照 | 修回归 + 一次性满足 DeepSeek 的「可见 + 可比」 |
| **D-3** | 修 P0-2：无账月归档 fail-closed | 造假账比缺功能危险 |
| **D-4** | 不做口径版本号框架 | 两司一致判为过度设计 |
| **D-5** | 补守卫：钉「归档月页首金额」而不是「开关参数」 | 守卫测参数不测金额，是本仓反复复发的病根 |

**「可操作」条件怎么满足**：`archiveMonth` 已支持 `archive: false`。前端文案直接指路「如需按现在的算法重算，取消归档后重新保存即可」 —— **零新增入口、零新增代码**。

---

## 六、一句话结论

> **历史不追、错数不改、但把「这个月是按旧规则封的」说出来，并且让用户自己决定要不要重算。**
