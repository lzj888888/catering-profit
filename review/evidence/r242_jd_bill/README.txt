四、逐行勾稽等式（实测成立率 46/115，其余 69 行是保险单）
--------------------------------------------------------------
**应结金额 = Σ(营业收入列) + Σ(支出列)**
= 订单原价 + 餐盒费 + 包装费 + 商家自送配送费 + 平台运费补贴
  + 商家承担货款补贴 + 商家承担运费补贴 + 总服务费(货款+运费+餐盒费)
  + 配送费（开票） + 商家承担小费 + 基础服务费 + 平台补贴暂扣
  （其中「商家承担*」「服务费」「配送费」列本身即负数，原样相加）

· 正向订单 23/23 成立 · 交易额转推广费 23/23 成立
· 🔴 **保险单 69/69 不成立** —— 其扣费**只落在「应结金额」列**，分项列（营业收入/支出）全为 0
  ⇒ 保险类行**不可分解**，只能整行取「应结金额」，禁止试图用分项列复算。
· 例（正向订单）：43.01 + 1 − 15.5 − 4 − 1.42 − 3 = **20.09** ✓

🔴【B】跨平台串味（本轮最重要的新发现）
`utils/billParse.js:44` 的注释白纸黑字写着「**「结算金额」= 淘宝独有**」：
```js
if (cols.indexOf(COL.taobao.net) >= 0) return 'taobao';   // COL.taobao.net = '结算金额'
```
而京东 SKU 表**第 11 列就叫「结算金额」** ⇒ 实测 `detectPlatform(R1)` 返回 **`"taobao"`**。
⇒ 京东 SKU 表会被**当成淘宝**走淘宝分支解析。这比订单级的「读不进来」**危险得多**：
   订单级 = fail-closed（安全）；SKU 级 = **能走通并算出错数**（静默错账风险）。

🔴【C】变体实测：误判后到底算成什么（`mk_jd_sku_variant.js` + `probe_jd_sku_variant.js` / 用例 D）
真表是空的 ⇒ 测不出后果 ⇒ 造**合成变体**（⚠️ 非真实平台文件；原表一字未改）：

 （2 个订单号：JD0001 = 正向商品 88.00 + 推广费 −8.80 + 保险 −0.50；JD0002 = 72.00）。

| 口径 | 正确值 | 实测值 | 判定 |
|---|---|---|---|
| amountFen | 15070 | **15070** | ⚠️ 碰巧对（都是加减法）|
| **qty（订单数）** | **2** | **4** | 🔴 **虚高一倍**（按 SKU/费用行数当订单数）|
| **bizDate** | 2026-09-30 | **`""`（空串）** | 🔴 全空（该表没有「账单日期」列）|
| checkGradeA | — | ❌ fail | ✅ 被门禁拦下（`SCHEMA_BIZDATE`+`REQUIRED_BIZDATE`）|

⇒ **结论**：解析器**确实会产出错数据**（qty 虚高、bizDate 空），
   但**甲级门禁兜住了**（bizDate 空 ⇒ fail-closed ⇒ 不会静默入库）。
   ⇒ 所以当前风险等级 = **"能算出错数、但落不了库"**，非"静默入库"。
   ⇒ 🔴 但这依赖「门禁恰好校验 bizDate」这一条 —— 属**侥幸护栏**，不是设计上的防御。
