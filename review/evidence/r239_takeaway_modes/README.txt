【实测结果】

■ 结论1：4 个按钮是【两层两两分组】，不是并列 4 项
  第一层（页面顶部大 tab，pages/takeaway/index.wxml:3-6）
      单均测算（tab=calc） / 账单导入（tab=import）      ← 决定「干哪件事」
  第二层（只在「单均测算」内部，index.wxml:11-14）
      到手口径（mode=cash） / 总额法口径（mode=accrual）  ← 决定「结果按哪个视角展示」

■ 结论2：两个口径**输入区完全一样，只有结果区不同**
  依据 index.wxml：mode 只出现在 ① 口径说明行（:15）② 结果区（:101-114）。
  菜品/包材/平台参数/补贴五个区块、以及「挂牌价反算」「保存参数」全部无 mode 条件
  ⇒ 切换口径**不改变任何输入控件**。
  结果区差异：
    到手口径   → 6 行：顾客支付 / 商家实收 / 菜品成本 / 包材成本 / 单均利润 / 到手率
    总额法口径 → 3 行：收入 / 费用 / 单均利润
  且 utils/takeawayDerive.js:117-141 显示：**引擎一次把两套都算出来**，
  切按钮只是换显示（不是重算）。

■ 结论3：两个口径**不是同一个**，差异**只来自三项**（引擎实跑，probe_modes.out.txt）
  同一单输入：商品总价30.00 打包费1.00 配送费(顾客承担)3.00 佣金20%(基数=商品总价)6.00
              配送服务费3.00 配送补贴2.00 推广费1.50 商家承担补贴7.00 菜品成本18.00 包材1.20
    到手口径  ：顾客支付 P=34.00  商家实收 R=16.00  单均利润 = -3.20   到手率 47.06%
    总额法口径：收入 38.00        费用 19.50        单均利润 = -0.70
    差 = -2.50 = 配送费(顾客承担) 3.00 − 商家承担补贴 7.00 + 推广费 1.50   ← 逐项对上 ✅
  对照实验：把这三项全部填 0 ⇒ 两套利润**完全相同**（0.80 = 0.80）✅
  边界实验：只填商品总价+佣金、其他全 0 ⇒ 两套利润也相同（6.00 = 6.00）✅

■ 结论4：复盘（单品毛利复盘）算成本的前提是【菜品卡】，不是【原料库】
  依据 cloudfunctions/getDishReview/service.js:62
      cardCode = nameToCode.get(normalizeDishName(dishKey))
      ⇒ 按【菜品卡名字归一后】匹配；成本取卡的 total_cost（卡内锁定值，:68）
  原料库只是**间接**前提：卡的成本是建卡时按原料库+BOM 算出来并锁定的。
  实跑 probe_match.out.txt：
    场景A 2张卡+1个无卡菜 ⇒ 无卡者单列 unmatched（份数与营收照计，成本不参与）**不报错**
    场景B 一张卡都没有   ⇒ 已匹配 0 条 / 未匹配 3 条 / 成本合计 0.00 / 毛利率算不出来
    场景C 「  耙牛肉 」带空格 ⇒ 归一后仍能匹配（说明轻微异体不致命）
    场景D 卡建了但成本=0 ⇒ 毛利率显示 100.00%（看着很美，其实是没填价）

■ 结论5：单均测算**不走账单**，但它和复盘是【两件事】，且**都在付费域**
  - 单均测算 = 事前试算：手选菜品卡 + 填平台参数 ⇒ 这一单赚不赚（数据源 getCostCard，index.js:190）
  - 单品毛利复盘 = 事后复盘：导入账单的真实销量 × 卡锁定成本（数据源 external_sales_daily）
  - 付费墙（都在服务端）：
      pages/takeaway/index.js:308-313  → 点「计算」时 openPaywall('takeaway')  「外卖需开通」
      cloudfunctions/getDishReview/index.js:50-51 → 无权益**在取数之前**就 return FEATURE_LOCKED
      ⇒ 不是前端假拦，是服务端先拦
