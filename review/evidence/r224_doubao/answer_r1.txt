卤鸡半自助火锅文档，三情景测算表是正式基准，租金梯度表是前置参考草稿，以三情景测算为准。

Q1 判断、理由、失效边界

判断：优先放入 var_items（费率项），你的倾向成立，是当前引擎不动前提下成本最低、复用现有计算链路的方案。

理由

架构同构：和 M2 现有 “房租由固定金额转为营收费率” 变换逻辑完全对齐，复用引擎原有var_items流水扣减的计算通路，完全不改动核心源码，只新增入参形态、上层 UI 与业态参数包配置，符合仓内硬约束。

业务语义匹配：品牌加盟管理费 = 营业额 × 扣点比例，属于随营收动态变化的变量成本，不属于每月刚性固定开销，语义上就归属于 var_items，而不是 fixed_items 固定金额科目。

兼容两套使用模式：上层渠道层做 UI 分支：

模式 A（加盟）：开启营收扣点费率，var_items 加载该扣点；

模式 B（自营无品牌扣点）：费率填 0，等价于不生效；

历史存量逻辑不受影响。

该方案会算错的具体业务场景

管理费存在保底门槛（加盟常见条款）：例如 “品牌管理费：营业额 3%，最低每月 3000 元”

var_items 纯费率模型只能算营业额×3%，无法处理保底下限。当反推出来的理论管理费＜保底金额，真实成本应该取保底固定值，此时这套入参变换模型结果失真。

处理预案（引擎不改，上层后置渠道层处理）：业态参数包额外增加「管理费保底金额」入参；后置层做结果校验：若营业额×扣点＜保底，抛出 UI 强提示：⚠️本加盟协议存在管理费保底 X 元，当前测算未纳入保底约束，结果存在偏差，请切换至专业模式手工使用固定金额管理费。不去修改引擎，只做提示告警，不强行修正计算结果。

扣点的计算基数不等于总营业额：部分加盟合同，管理费仅对堂食营收计提，外卖营收不计扣点。当前引擎 var_items 统一基于全部营业额做基数，这种场景直接计算会偏大。

预案：上层渠道做提示，该特殊合同条件下，本模型仅为近似测算，建议进专业模式手工调综合毛利率做等效拟合。

小结：绝大多数普通自营、无保底加盟场景下 var_items 方案完全可用；保底、部分营收不计扣点两类特例靠上层提示告警，不侵入引擎。

Q2 统一公式：保本营业额 = 月固定成本 ÷ (综合毛利率 − 营收扣点费率) 的失效具体条件

前提：该公式成立的底层假设：

①综合毛利率恒定，不随营业额规模变化；

②所有营收扣点费率完全以总营业额作为计算基数；

③全部固定成本严格为每月刚性不变，不随营收、客流发生阶梯跳变。

下面是真实可落地的失效场景：

固定成本存在阶梯跃迁

举例：门店营业到一定规模必须新增雇佣人员；月营业额突破 18 万，需要新增 1 名全职，月人工 + 6000。此时固定成本不再是常数；保本点前后固定成本数值不一样，单一常数固定成本代入公式直接失效。

案例：火锅夜宵店，低流水 2 人够用；流水上去必须加到 3 人。

综合毛利率随营业额发生明显漂移

场景 A：半自助业态，营业额提升带来档位升级率变化。小鸡快跑案例，营业额拉高，48.8 全配占比上涨，整体综合毛利率上行；毛利率不是常数。

场景 B：外卖占比大幅提升，外卖平台扣点、包装成本改变整体综合毛利率。固定一个毛利率代入公式，高低营业额区间同时失真。

营收扣点不是线性比例，存在阶梯、保底、封顶（加盟常见）

例如：管理费，营业额 0‑15 万扣 3%；大于 15 万部分扣 2%；或者前面提到每月保底 3000。不再是单一恒定费率，公式不成立。

存在部分成本既不完全固定，也不和营业额线性挂钩

例如：按客流人头计费的第三方服务，和桌数 / 人数强相关，但不和营业额严格成正比；同样营业额，高客单少人数 vs 低客单多人数，该类成本差异巨大。

重要：不是说公式不能用；它是基准近似模型，适合中性情景；上层 UI 必须输出提示：本测算假设毛利率、扣点费率、固定成本保持不变，规模变化实际结果会发生偏移。

Q3 是否坚持回本周期独立放在 M3 模块

依然坚持模块拆分，但是做「跨模块轻量化预览」折中方案，不把完整回本计算逻辑塞进 M2 引擎。

理由

业务本质差异：

M2 选址反推输入集合：房租、人员、业态、盈利目标；只涉及月度经营损益（利润、保本流水），完全不触碰一次性初始投入（转让费、装修、设备、押金、备用金）。

回本周期 = 总一次性初始投入 ÷ 月净利润；强依赖一次性投资参数。

如果要 M2 原生输出回本，M2 就必须接收一整套投资录入表单，M2 原本 “快速选址反推” 的小白轻量化页面会被大量投资输入项污染，违背 M2 产品定位。

折中方案（引擎零改动，上层渠道层实现，小白体验不割裂）

不改动引擎，不把回本计算放进 M2 核心链路，上层做 UI 预览：

① M2 页面完成测算后，在页面底部增加只读预览卡片（非完整计算，属于预估算引导）。

卡片文案示例：

📌回本周期预估（仅预览，未录入装修 / 转让费 / 押金）

按当前测算月净利润 XX 元，【假设总投入 XX 万】，粗略预估回本约 XX 个月。

➡️点击跳转 M3 投资回本模块，录入真实装修、转让费、押金获取精准回本结果。

② 预览卡片里面的总投入，可以由业态参数包带出一套该业态的参考总投资（例如 100㎡半自助火锅参考投入 26.2 万），作为预填充的假设值，仅供预览展示，不参与引擎运算。

关键点：预览的回本数字只是上层 UI 做简单除法，不走核心引擎，明确标注是假设预览值，不是精确结果，同时强引导跳转 M3 录入真实投资拿到正式结果。

收益

遵守模块职责边界，M2 保持轻量化，不新增大量投资录入项；

小白在 M2 页面可以一眼看到回本的粗略参考，不会完全看不到回本指标；

又明确区分「预览假设值」和 M3「精准计算值」，不会给用户造成 “M2 已经算完回本” 的错觉；

完全不触碰底层引擎，全部上层渠道层实现，符合仓内硬约束。

反例，如果硬要 M2 输出真实回本：就必须让 M2 接收转让费、装修、设备等一大堆输入，M2 页面膨胀，小白用户填表负担急剧上升，违背 M2 快速反推的定位。两份 BP 文档是完整商业报告，所有投资参数已经全部给定；但是小程序用户是小白，很多人在选址阶段还完全没有确定装修、转让费，拿不出这些数字。

本轮小结摘要（方便 WorkBuddy 内部记录）

管理费扣点走var_items入参变换，引擎不动；仅对保底、部分营收不计扣点场景做上层告警提示。

统一保本公式是基准近似模型；4 类具体业务条件下会失效，页面必须附加假设提示。

M2/M3 模块边界维持拆分；M2 底部增加非引擎驱动的回本预览卡片（业态包带出参考总投入做假设），强跳转 M3，兼顾小白感知，不污染 M2 核心链路。

卤鸡火锅文档以三情景测算表为准，租金梯度表是草稿笔误。
