理由

该方案会算错的具体业务场景

var_items 纯费率模型只能算营业额×3%，无法处理保底下限。当反推出来的理论管理费＜保底金额，真实成本应该取保底固定值，此时这套入参变换模型结果失真。
处理预案（引擎不改，上层后置渠道层处理）：业态参数包额外增加「管理费保底金额」入参；后置层做结果校验：若营业额×扣点＜保底，抛出 UI 强提示：⚠️本加盟协议存在管理费保底 X 元，当前测算未纳入保底约束，结果存在偏差，请切换至专业模式手工使用固定金额管理费。不去修改引擎，只做提示告警，不强行修正计算结果。
扣点的计算基数不等于总营业额：部分加盟合同，管理费仅对堂食营收计提，外卖营收不计扣点。当前引擎 var_items 统一基于全部营业额做基数，这种场景直接计算会偏大。
预案：上层渠道做提示，该特殊合同条件下，本模型仅为近似测算，建议进专业模式手工调综合毛利率做等效拟合。
小结：绝大多数普通自营、无保底加盟场景下 var_items 方案完全可用；保底、部分营收不计扣点两类特例靠上层提示告警，不侵入引擎。
Q2 统一公式：保本营业额 = 月固定成本 ÷ (综合毛利率 − 营收扣点费率) 的失效具体条件
前提：该公式成立的底层假设：
①综合毛利率恒定，不随营业额规模变化；
②所有营收扣点费率完全以总营业额作为计算基数；
③全部固定成本严格为每月刚性不变，不随营收、客流发生阶梯跳变。
下面是真实可落地的失效场景：
固定成本存在阶梯跃迁
举例：门店营业到一定规模必须新增雇佣人员；月营业额突破 18 万，需要新增 1 名全职，月人工 + 6000。此时固定成本不再是常数；保本点前后固定成本数值不一样，单一常数固定成本代入公式直接失效。
案例：火锅夜宵店，低流水 2 人够用；流水上去必须加到 3 人。
综合毛利率随营业额发生明显漂移
场景 A：半自助业态，营业额提升带来档位升级率变化。小鸡快跑案例，营业额拉高，48.8 全配占比上涨，整体综合毛利率上行；毛利率不是常数。
场景 B：外卖占比大幅提升，外卖平台扣点、包装成本改变整体综合毛利率。固定一个毛利率代入公式，高低营业额区间同时失真。
营收扣点不是线性比例，存在阶梯、保底、封顶（加盟常见）
例如：管理费，营业额 0‑15 万扣 3%；大于 15 万部分扣 2%；或者前面提到每月保底 3000。不再是单一恒定费率，公式不成立。
存在部分成本既不完全固定，也不和营业额线性挂钩
例如：按客流人头计费的第三方服务，和桌数 / 人数强相关，但不和营业额严格成正比；同样营业额，高客单少人数 vs 低客单多人数，该类成本差异巨大。
重要：不是说公式不能用；它是基准近似模型，适合中性情景；上层 UI 必须输出提示：本测算假设毛利率、扣点费率、固定成本保持不变，规模变化实际结果会发生偏移。

Q5 判断：加回折旧会不会重复计算？
你的潜在担忧原话：M2 固定成本已经扣掉折旧；现金流口径回本又把折旧加回来，会不会重复计算？
不会发生重复计算，但需要理清两层，这里容易混淆：
1）引擎内部损益计算链路：
月毛收入 − 各类可变成本 − 固定成本（内含月折旧摊销） = 月净利润
折旧在这里是会计成本扣减，没有真实现金流出，引擎输出的月净利润已经减掉折旧。
2）现金流口径上层预览计算（纯 UI 层，完全不回写、不修改引擎内部任何数字）：
经营现金流 = 月净利润 + 月折旧摊销
只是上层把引擎输出的两个结果做算术相加；没有修改引擎的输入、没有再次从成本中扣 / 加折旧，只是对输出结果做后置变换。
容易踩错的错误理解（你提问中潜在误区）
错误想法：“我把折旧加回去，等于固定成本不再扣折旧”。
事实：引擎内部损益完全不变；+折旧仅仅是上层拿到输出值之后的后置数学运算，不会反向改写 M2 的固定成本、不会二次参与引擎测算，因此不存在重复扣减或者重复加总。
关键点：加回折旧发生在渠道后置层，只读引擎输出，不回写入参，完全隔离引擎，符合硬约束。
Q6 折算法 vs 独立参数法；小白层推荐方案
背景案例：半自助浪费系数 1.25，升级转化率 40%
折算法：预先在业态包把浪费、升级转化全部折算成单一综合毛利率、加权混合客单价，不再保存原始浪费系数、升级率；
独立参数法：参数包单独存浪费系数、升级转化率，上层做入参变换，再输出等效综合毛利率、等效客单价给到引擎。
折算法（当前 BP 文档的做法）会在什么场景误导用户
用户修改小白层【综合毛利率】：原本 53% 已经内置 ×1.25 浪费损耗；用户手动上调 / 下调毛利率，隐藏的浪费系数直接丢失，损耗逻辑消失，用户完全无感知。
做敏感性分析的时候，无法单独做 “如果浪费变大 / 变小，对结果影响多少”，只能整体改综合毛利率，不能隔离变量；无法回答：浪费从 25% 恶化到 35% 门店会怎么样。
半自助业态小白用户很难理解：“为什么我的理论菜品毛利 60%，系统给到 53%”，看不到中间损耗折算过程，变成黑盒。
独立参数法会在什么场景误导用户
小白层如果暴露浪费系数、升级转化率：这些属于高度专业概念，小白完全不知道填什么，违背 L1 小白层 “少填” 的设计目标。
如果上层入参变换逻辑出错：浪费系数、升级转化率经过运算后输出给到引擎的等效毛利率 / 客单价算错，会带来底层结果错误；多了一层转换链路，QA 工作量上升。
小白层最终推荐：独立参数法做底层存储；小白层做结果屏蔽，不直接暴露原始系数
理由：
符合引擎零改动约束：底层存浪费系数、升级转化率；渠道层预先做入参变换，算出等效综合毛利率、等效客单价，再喂给引擎，引擎接收的仍然只是普通毛利率、客单价，不需要引擎新增字段。
L1 小白 UI 只展示变换之后的等效综合毛利率、混合客单价；原始浪费系数、升级转化率完全折叠到 L3 专业模式。
L2 进阶层：只展示等效毛利率、客单价，不展示原始系数；
L3 专业模式：同时展示「原始输入（浪费系数、升级转化率）」以及「经过折算后给到引擎的等效毛利率 / 客单价」，让专业用户看到变换关系。
对比折算法的优势：后续用户进入专业模式，可以单独调浪费系数做敏感性测试；同时上层可以展开【本次测算假设】面板，告诉小白 “本半自助业态已经考虑自助食材损耗 25%，折算后综合毛利率 53%”，消除黑盒。
折算法不具备这个溯源解释能力。

字段定义（全部属于业态参数包元数据，不入引擎入参）
每条成本项增加结构体标记cost_meta：
json
{
 "cost_key":"水电燃气",
 "cost_form":"fixed|area_linear|headcount_linear|revenue_rate|step",
 "params":{...}
}
fixed固定金额：params:{base: 数字}
area_linear面积线性：params:{base: 基础金额，per_sqm: 每平米增量}，例火锅面水电：base=2600，per_sqm=20

revenue_rate营收百分比：params:{rate: 小数}，例品牌管理费 3%
step阶梯：params:{steps:[{"trigger": 阈值，"value": 金额},…]}，例卤鸡火锅水电随租金档位阶梯

C1：上层做面积 / 人头→金额预处理，敏感性分析会不会出现口径裂缝？如何防范
风险真实存在：
敏感性分析如果是上层循环遍历面积 / 人数，每迭代一次，上层要重新跑一遍形态计算，生成一套全新 fixed_items 入参，再调用引擎。
风险裂缝场景：上层只改界面显示，忘记同步重算整套 fixed_items 入参直接复用旧入参给引擎；页面展示一套，引擎计算另一套，结果不一致。
✅三道防御手段（全部上层实现，不改引擎）
单源输入原则：面积、人工人数为全局唯一真值；任何触发面积、人工人数变更事件，必须完整重算全部cost_meta形态项，生成全新 fixed_items 数组再调用引擎；禁止复用旧的 fixed_items。
输出回显校验：引擎返回计算结果后，上层把喂给引擎的 fixed_items 全部回显在【测算明细‑原始入参】折叠面板，用户 / 测试可直接核对：引擎收到的水电、杂费金额是否和当前面积 / 人数计算结果一致。
敏感性扫描不做引擎外数学模拟；每一组扫描变量，都完整执行一次「上层形态计算→生成入参→调用引擎」全链路，不在上层直接硬套公式算保本，所有扫描点全部走真实引擎调用，杜绝上层、引擎两套公式。
禁止：上层自己写一套保本公式做敏感性，只把初始值丢给引擎；所有数据结果来源必须是引擎输出。

不修改引擎；上层根据开关，选择是否把 B 组金额加入总投入再做除法。
C3：卤鸡火锅文档两处写 “店铺管理费 3%”，是否同一笔钱重复计算？
判定：是同一笔费用，不是两笔；文档两处只是表述位置不同，不能配置两处参数。
原文解析：
1）一处：参数定义：店铺管理费按营业额 3%（属于 var_items 营收扣点费率）；
2）二处：结果说明行 “含店铺管理费用 3% 计入保本线”，只是验算说明文本，不是第二条成本科目。
验算：5.66万 ÷ (53%‑3%) =11.32万，只用扣减一次 3%，如果再额外叠加一笔固定金额管理费，保本营业额会进一步抬高，与文档 11.3 万结果对不上。
✅参数包处理规则：
业态参数包只配置一处：营收扣点费率 = 3%（归入 var_items）；结果输出文案写明 “本测算已包含店铺管理费（营收 3%）”，不新增第二条管理费科目。
禁止：同时配置一笔 var_items 费率 3%，再加一笔 fixed_items 固定金额管理费，造成重复扣减。
本轮纪要摘要（便于内部存档）
1.A：业态参数包需要增加cost_meta成本形态元标记（fixed /area_linear/headcount_linear /revenue_rate/step）；形态运算全部上层执行，输出金额喂引擎 fixed_items/var_items，引擎源码零改动。
2.B：输出三层模式字段可见性完整表格；半自助特殊原始参数仅 L3 可见；L1/L2 展示等效折算后值，用户手动改写后触发标记与告警；建店投入全部归属 M3，M2 仅做只读预览参考。
3.C1：上层预处理存在口径分裂风险；三条防御：变更面积 / 人员必须重算整套 fixed_items；引擎入参明细回显；敏感性扫描每个点完整走 “上层计算‑调用引擎”，禁止上层私自模拟保本。
4.C2：转让费、备用金存在可回收属性，全额计入分母会高估回本；上层 UI 做复选开关，两套口径可选，M2 预览默认沿用 BP 习惯全部计入，附带风险提示，M3 可自由切换。
5.C3：卤鸡火锅两处 “管理费 3%” 为同一笔，一处是参数，一处是结果说明；参数包仅保留 var_items 营收扣点一份，禁止重复配置科目。
