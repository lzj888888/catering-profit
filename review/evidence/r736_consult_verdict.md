## 一、三家一致的三条

### ① 用户的产品判断成立

豆包原话：「老板『摊销区不该有这个开关』的结论**成立**。」  
理由三条：

1. 分期摊销的核心是「成本按受益期匹配」，随意停摊直接破坏利润核算的准确性；
2. 「选摊销再关开关」是一条**不符合核算逻辑的错误路径**，产品不该提供显性入口；
3. 这个开关本质是**利润表口径设置**，不属于摊销资产台账的功能范畴。

### ② 开关的困惑来自「对象错位」

豆包：「开关物理位置紧贴分期资产列表，用户默认它管的是『这笔资产摊不摊』，实际管的是『全店本月利润表取不取摊销』，二者完全不匹配。」

同一个事实，在我们自己代码里就有铁证 —— `terms.js` 的开关说明原文：

> `amortSwitchHint: '关掉后，下面登记的摊销资产不计入利润'`

这句话写的是「**资产**不计入」，而实现是「**店铺**利润表不取」。文案本身就在误导。

### ③ 方向：删掉用户可见开关，选择前移到「新增资产时二选一」

DeepSeek：「删除开关方向正确，但必须『未来适用、不追溯历史』。」  
豆包：「删除用户可见开关，新增资产时只保留『一次算清 / 分期摊销』二选一。」

## 二、关键质证：DeepSeek 的一处误判（已推翻）

**DeepSeek 原判**：

> 「对存量 `amortize_switch=false` 且有 `mode='amort'` 的行，切换时执行『剩余未摊金额 ÷ 剩余期数』的未来适用重排，避免总额少摊。若不重排，历史关闭期间未摊金额会永久缺失。」

**我方核实**（`getAmortSchedule/index.js::progressOf`）：

```js
const start = monthIndex(asset.start_month);
const naturalEnd = start + asset.total_months - 1;
const end = asset.terminate_month ? min(terminate_month, naturalEnd) : naturalEnd;
const paidMonths = mi < start ? 0 : (min(mi, end) - start + 1);
const paidFen = Σ amountForMonth(k) for k in [start .. min(mi, end)];
```

**这段完全不读 `amortize_switch`。** 开关关着的那些月，台账期数照常前进、剩余未摊照常递减、摊完月份不变。

⇒ 「未摊金额永久缺失」是把「**利润没扣**」误当成「**台账没摊**」。真实后果是那些月利润当时多算了，不是台账少了钱。

**豆包第三轮裁决**：

> 「**你的反驳成立。** 就给出的代码看，DeepSeek 把『利润表没扣摊销』误判成了『台账没摊』。……所以不存在『剩余未摊金额永久缺失』，也不需要做『剩余金额 ÷ 剩余期数』重排。」

**结论：切换时不需要动任何台账数据、不需要补摊、不需要重排。只改引擎一处判断 + 定生效边界。**

## 三、真正的风险（两家都确认）

| 编号    | 风险                               | 严重度   | 处理                           |
| ----- | -------------------------------- | ----- | ---------------------------- |
| **R** | 历史报表被事后改写 —— 老板翻 7 月发现利润少了 4,333 | **高** | 历史月一律走 `switch_used` 快照，一字不改 |
| **S** | 当月利润突然下降 —— 老板以为系统算错             | **中** | 生效月前提示 + 明细保留「本期摊销」行         |

豆包补充了一条我没考虑到的边界：

> 「边界不应只依赖『是否归档』，而应按**结账截止时点**判断。否则某个月虽然没归档，也可能在上线后被悄悄改写。」

这条我认为**部分成立、但方案要换**：本产品只有「归档」这一个冻结机制，没有「结账」。若按归档态判断，老板今天归档明天取消归档，逻辑就会跟着翻——不稳定。

⇒ 改用**时间闸门**（见下方方案）。

## 四、我方裁决方案

### 核心：时间闸门 + 三处改动

```
AMORT_RULE_V2_FROM = '2026-12'      // 生效月，部署后第一次改这个常量即可
```

| 月份区间           | 摊销计入规则                                               |
| -------------- | ---------------------------------------------------- |
| `month < 生效月`  | **老逻辑原封不动**：有 `switch_used` 快照读快照，没有读实时开关            |
| `month >= 生效月` | **新逻辑**：一律按台账计入，`effectiveAmortizeFen = amortizeFen` |

**为什么用时间闸门而不是归档态判断**：

- 归档态会随老板操作变化（可取消归档），闸门是纯函数，不会翻；
- 历史 100% 不变，**包含未归档的历史月**——比豆包提的「按结账时点」更保守；
- 回滚只需把常量改成一个未来日期。

### 三处改动（按投入产出比排序，与豆包第三轮排序一致）

**第 1 步 · 引擎路由（改利润数字，必须先做）**

- `cloudfunctions/calcMonthlyProfit/service.js`：`effectiveAmortizeFen` 按月份分支
- 三副本同源：`calcMonthlyProfit/service.js` / `saveLedger` / `getLedger`
- 归档月快照分支保留，作为 `< 生效月` 的唯一路径
- 老板感知：历史报表一字不变；生效月起，摊销自动计入利润

**第 2 步 · 删开关 + 选择前移**

- `subpkg/biz/month/amortize.wxml`：删掉 `switch-row` 整块
- `subpkg/biz/month/amortize.js`：删 `onToggleAmortize`
- 选择前移到 `assetEdit`（新增/编辑页）的「一次算清 / 分期摊销」二选一 —— 那里**已经有** `mode` 字段的编辑入口，只需确认文案到位
- 老板感知：摊销页只剩台账，不再有第二个"要不要摊"的问题

**第 3 步 · 摊销页口径彻底对齐**

- 页首标题：`本月摊销合计` → **`本月计入利润的摊销`**（新月份恒等于下方之和）
- 行内金额：`月摊销` → **`月应摊额`**（明确是台账属性）
- 历史旧规则月份：加一行灰色说明「该月按旧规则未将摊销计入利润」
- 老板感知：页首和明细天然对得上，不会再出现"上面 0、下面 4,333"

## 五、历史遗留证据（证明这个开关是"半具尸体"）

`miniprogram/i18n/terms.js` 里 round107 自己的注释：

> 「② **取消「一次性计入当月 / 按月分摊」二选一** —— 那一对选项写的是 shop 级 `amortize_switch`，结构上就排除了『本月既有一笔摊销、又有几笔小额一次算清』，而这正是真实场景。现在两类投入**可以同时存在**。」

⇒ round107 当时已经判定这个开关的**上半身**（互斥口径）是错的、并拆掉了它。  
但它**下半身的开关本体留了下来**，变成一个悬空的「要不要算摊销」。

李老师这一轮问的，正是这具残骸。
