## D · 判读（与原文分栏）

1. **3 秒不是本项目的决策，是平台默认值**：全仓没有任何地方声明过它（C 组三条）。
2. **与本仓铁律直接冲突**：本仓按 **60s** 设计（`core/06:410` 明写"60 秒超时铁律"），线上实际 **3s**。
3. 🔴 **严重度 = 🔴（按复审 round37 的预先裁定升级）**：复审方原文为「若回读发现 `initDb`/`adminExport` 也是 3s，请按 🔴 处理」。
   - `initDb` 实测 **= 3** ⇒ **触发升 🔴**。
   - ⚠️ `adminExport` **无法回读**：它**不在线上**（A 组只列出 2 个函数）⇒ 该条的"是否也是 3s"**当前不可观测**，不得推断。
4. **风险表述（不得超出证据）**：`initDb` 要建 **25 集合 + 40 索引 + 种子**，3 秒内跑不完 ⇒ **可能在建到一半被杀**，留下"部分建库"现场。
   ⚠️ **这是按风险处理，不是观测结论**：`initDb` 已初始化过，"已存在即拒绝"的前置会把重跑直接拦下
   （这正是那条 fail-closed 设计的本来目的）⇒ **无法用"重跑一次"测时长**，因此**不得写成"已经会失败"**。
5. **其余 44 个仓库函数**：**未部署** ⇒ 其 timeout 当前**不可观测**；部署时若同样吃 3s 默认，`
   adminExport`/`exportData`/`calcAmortize`/`adminQueryUser` 这类重活都会撞。
6. ⚠️ **判超时值只能看 `info` 的 `timeout` 列**：界面「测试结果：成功」只表示**调用**成功，与函数是否跑完无关。

## F · 第二步「单点试」已执行（2026-09-18 05:2x）—— 结论：`config.json` 的 `timeout` **不被采纳**

> ⚠️ 本节性质与前四节不同：**含一次云侧写入（重发部署）**，单列以免污染"纯读"结论。
> 实验文件 `cloudfunctions/smokeTest/config.json` 已**删除还原**，本节是它唯一的留痕。

**实验设计（单点、可回退、dev-only）**：给 `cloudfunctions/smokeTest/config.json` 写 `{"timeout": 20}` → 重发部署 → 回读。

| 观察点 | 结果 | 出处 |
|---|---|---|
| 部署是否成功 | `success=true` / `13 files` / `packSize=14.6 KB`（上次 14.5 KB） | `cli cloud functions deploy` 输出 |
| 文件是否随包上传 | ✅ 探针 `fsDiag.root` 里出现 `config.json` | 同目录 `48_result_raw_afterdrop.txt` |
| 部署是否生效 | 「最后更新时间」`2026-09-18 03:34:55 → 05:24:52` | 控制台函数列表（点"刷新"后） |
| **超时值** | ❌ **仍是 3**：`smokeTest \| Active \| timeout 3` | `cli cloud functions info` |
| **超时值（权威面）** | ❌ **仍是 3**：高级配置 → **执行超时 = `3` 秒** | 控制台 → 云函数 → 版本管理 → 「配置」 |

⇒ **该字段随包上传 ≠ 该字段生效力。** `cloudfunctions/<fn>/config.json` 的 `timeout` 不被 IDE CLI 部署通道采纳。

**唯一可行路径（第三步 · 退控制台）**：
控制台 → 云函数 → 选函数 → **版本管理 → 「配置」→ 高级配置 → 执行超时（±秒）**；
取值 **1–300 秒**（官方「上传云函数配置」接口 `type=3` 的 `timeout`，单位秒，默认 3 秒）。⚠️ **须人工手点**。

**顺带读到**：该函数「配置」对话框 → 基础配置 → **运行环境 = `Node.js 16.13`**（与 `info` 的 `runtime` 一致）；执行方法 `index.main`；提交方式 `微信开发者工具`。
