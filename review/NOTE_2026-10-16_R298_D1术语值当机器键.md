## 一、一句话结论

**M1-B9「术语值被当机器键」全仓 3 处已修**，做法不是"把字面量换个地方写"，而是
**在 `terms.js` 增设语义锚点（`TERMS.semantic`）并把预设清单与业务逻辑**同时**指向它 ⇒ 真单源**；
跨端那一处（云端 ↔ 前端）改为**机器码契约**（云端只回 `high/low/ok`，中文只在术语表）。
配 **3 个套件扩面** + **7 例变异回灌**（注入必红 → 还原字节级干净 → 回绿）。

⚠️ 本轮**最该记住的不是这 3 个修复，而是我的守卫被我自己的注释绊倒了两回**（详见 §5）。

## 二、缺陷（3 处，改动前基线 = 全仓仅 4 个中文串比较点）

| # | 位置 | 旧写法 | 改名后的**静默**后果 |
|---|---|---|---|
| 1 | `pages/month/input.js` `updateRow()` | `rows[ridx].subItem === '外卖活动补贴'` | 费用侧「手改上锁」失效 ⇒ 用户手改被自动值**覆盖** |
| 2 | `pages/month/input.js` `syncSubsidyCarry()` | `mg.rows.findIndex((r) => r.subItem === '外卖活动补贴')` | 收入侧补贴**带不过去** ⇒ 费用少一笔、利润虚高 |
| 3 | `pages/m3/dishreview/index.js` 的 `load()` | `bm.actualFlag === '偏高'`（云端同回中文串） | 「成本偏高」的**警示色消失**，老板看不到红色告警 |

共同点：**外显词被当机器键**，改文案 ⇒ 逻辑静默失灵、零报错、门禁全绿。
与项目血泪教训同族（M2 `BANDS`：细项名当机器键 ⇒ 改名静默失效）。

🔴 **修正 PLAN 里的一处误述**：第 3 处的 `'偏高'` **不是** `TERMS.m2.indLevels.warn`——
那两项只是**字符串碰巧相同、语义无关**（一个在费用率评级、一个在自助餐成本率）。
真形态是「**云端与前端各自硬编码同一个中文串做接口契约**」，两端还可能不同人改。

## 三、修法（6 个文件，全部最小化改动）

### 3.1 增设语义锚点组（真单源）

`miniprogram/i18n/terms.js`（**两份副本必须逐字一致**，见 §4.1）：

```js
const SEMANTIC = {
  // 营销费用 · 「外卖活动补贴」细项名（input.js「手改上锁」与「补贴自动带出」的定位基准）
  expenseMktSubsidy: '外卖活动补贴',
};
const TERMS = {
  semantic: SEMANTIC,          // ← 业务逻辑统一引用它
  ...
        items: ['外卖平台佣金', '外卖配送服务费', SEMANTIC.expenseMktSubsidy, ...],
```

- 业务逻辑 2 处改为 `TERMS.semantic.expenseMktSubsidy`。
- **`items` 里也引用同一常量** ⇒ 改名只需改一处，**逻辑与预设清单不可能分叉**（这才叫真单源）。
- 代价：`check_expense_item_seed::parseFrontExpense`（正则解析 `items: [...]`）需能把
  `SEMANTIC.<键>` 解析回字面量 —— 已加 4 行解析器（解析不出时**原样保留 token** ⇒ E3 判红，fail-closed）。

### 3.2 跨端契约机械化（第 3 处）

| 端 | 改前 | 改后 |
|---|---|---|
| 云端 `cloudfunctions/getDishReview/service.js` | `actualFlag = '偏高' / '偏低' / '合理'` | `actualFlagCode = 'high' / 'low' / 'ok'`（字段名同步改为 `actualFlagCode`） |
| 前端 `pages/m3/dishreview/index.js` | `bm.actualFlag === '偏高'` ？`'warn'` : … | `TERMS.card.buffetFlag[code]` 取**文案**；`BUFFET_FLAG_CLS[code]` 取**色号** |
| 术语表 | — | `TERMS.card.buffetFlag = { high: '偏高', low: '偏低', ok: '合理' }` |

契约从此是**机器码**（跨端点只看码），中文只在术语表一处。
⚠️ 代价：**云端与前端需同批部署**（不然 `actualFlagCode` 缺失 ⇒ 短暂显示 `40%` 而无括号文案；
代码里已用 `|| ''` 兜底，不会崩）。

## 四、守卫（3 个套件扩面，全部带影子样本）

### 4.1 `tools/check_page_terms.js` 新增**判据③**（15 通过，原 8 条 ⇒ 该套件不在断言数 CASES，零同步成本）

- **判据的精确形态 = 「含中文 **且** ∈ 术语值集」两个条件合取**（缺一不可）。
  - 只判"∈ 术语值集" ⇒ 误杀**机器码**：`TERMS` 里 `category: 'dine_in'` 这类项**既是键又是值**，
    实测 **54 处假阳性**（而 `g.category === 'dine_in'` 恰恰是正确写法）。
  - 只判"含中文" ⇒ 误杀一切正常中文判断，且脱离"术语单源"语义。
- 扫描面 = `pages/ + utils/ + miniprogram/ + app.js`（56 个 .js，277 处比较型字面量），命中 **0**。
- 影子样本 5 条：正（`'外卖活动补贴'` / `'偏高'` 必红）、负（非术语中文 / **机器码 `'dine_in'`** / 注释里的术语值 必绿）。
- 自失效护栏 S5：比较型字面量 ≥150 且术语值集 ≥800 串。

### 4.2 `tools/check_expense_item_seed.js` 新增 **E8**（21 通过，原 17 ⇒ 断言数已同步 2 处）

E8 契约：每个锚点必须 ① 声明为非空字符串 ② ∈ 对应 category 的预设项 ③ **在 terms 源里被
`SEMANTIC.<键>` 引用**（= 预设清单真的引用了它，不是孤立副本）+ ④ 判据自证。
③ 专门钉住"**有没有被改回字面量副本**"。

### 4.3 `tools/check_dishreview_engine.js` 新增 **⑬ 段**（107 通过，原 99 ⇒ 断言数已同步 2 处）

**行为级**判据（真调 `computeCoverage` 算三档，不是读源码字面）：

## 五、🔴 我的守卫被我自己的注释绊倒了两回（本轮最大教训）

两次都是同一类：**守卫的判据用文本扫描，而我在同一段代码里写了"举例说明缺陷形态"的注释**。

| # | 现象 | 根因 | 处置 |
|---|---|---|---|
| 1 | `check_page_terms` P3-1 报"命中 0"，但 **P3-2/P3-3 正样本同样返回空** | 我沿用了既有的 `stripComments` —— 它把**字符串内容替换成空格** ⇒ 这条"看字面量"的判据**全盲**（我的量面探针也一并瞎了，"0 命中"是假阴性） | 新写 `stripCommentsKeepStr`（只剥注释、**保留串内容**）并把"正样本必须命中"写进断言 |
| 2 | 变异回灌 **M3 没被抓到**：把 `items` 改回字面量后 E8-③ 仍判绿 | E8-③ 在 `termsSrc` 里数字符串，而**我的说明注释里正好写了 `SEMANTIC.expenseMktSubsidy`** ⇒ 注释顶了数 | E8-③ 改为在**剥注释后的代码**里计数 |

同族第三例：`check_dishreview_engine` 的 13-⑧（前端不得再按 `bm.actualFlag` 取色）也被我写的
「旧写法 `bm.actualFlag === '偏高'`」注释绊红 ⇒ 该判据循环前先剥注释。

⇒ **沉淀为纪律**：凡"扫文本"的判据，**先剥注释**；且**必须配正样本证明判据真的会命中**
（"0 命中"在探测器坏掉时长得一模一样 —— 与 R297「链路通 + 门禁绿证明不了数字对」同源）。

## 六、顺带修复：M1-B2（新用户首页显示 ¥0.00）

- **取证**：`cloudfunctions/getLedger/index.js:4` 明确「**无记录返回默认空账**（不报 RESOURCE_NOT_FOUND）」
  ⇒ 该店的 `operation_ref_profit_fen` 也是 `0` ⇒ 只判"是不是数字"就会把「**从没录过**」渲染成 **¥0.00**。
- **修法**（纯前端，**零云端改动、零新增文案**）：响应里已有 `account_id`（`acct ? … : ''`）——
  `account_id` 为空 ⟺ 无账本记录。判定改为 `if (d && d.account_id && typeof fen === 'number' && Number.isFinite(fen))`。
  有记录但利润恰为 0 **仍显示 0.00**（那才是真算出来的 0）。
- 守卫：`check_home_ui_v3` A-⑭（触发条件必须含 `account_id`）+ A-⑮（影子样本：旧写法判不过）。
- 📌 采纳了豆包的论证（强于原注释）：老板看到 ¥0.00 会归因"这月不赚不赔/生意差"，
  还可能**拿这个 0 去做决策** ⇒ 属"误导性的诚实"，比留空态更糟。
