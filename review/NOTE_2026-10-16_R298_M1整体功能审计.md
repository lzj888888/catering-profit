## 2 本轮发现

### M1-C1 ·【P1】月结果页「空态」分支**不可达** ⇒ 未建档月份挂**红带「亏损」**+ ¥0.00

**现象（老板视角）**：在**从没录过任何数据**的月份点【查看结果】，页面顶部是一条**红色带**写着「亏损」，
下面满屏 `¥0.00`；老板会以为"这月亏了"。

**根因（四步推导，可机器复核）**：

| 步 | 事实 | 证据 |
|---|---|---|
| L1 | `getLedger` 对**无账记录**的月也**无条件**返回 `result` 对象（默认空账） | `cloudfunctions/getLedger/index.js:4` 注释 + `:195` `result: {` 不在任何条件内 |
| L2 | `result.js` **无条件**把 `r` 赋成对象（不在任何条件里） | `pages/month/result.js:138` `r: {` |
| L3 | `result.wxml` 空态分支 = `loading` 与「`r` 为真」的**补集** | `pages/month/result.wxml:6` `wx:elif="{{r}}"`、`:174` `wx:else` |
| **L4** | ⇒ 由 L2/L3：`loading===false` 时 `r` **恒真** ⇒ **空态分支不可达（死分支）** | — |

**后果链**：
1. **红带误报**：`result.js:125` `if (trueFen <= 0) { bandClass = 'red'; ... }`，空账 `trueFen = 0` ⇒ `0 <= 0` 命中 ⇒ **红带「亏损」**。
2. 满屏 `¥0.00`（与 C-① 同族，但比首页更刺眼：首页只是数字，这里有**红带结论**）。
3. 导出按钮不受任何"有账本"条件约束（`result.wxml:168`）⇒ **空月也能导出报表**。
4. ✅ 已正确降级的两处（登记为非缺陷）：故事线卡 `showPer100 = incomeFen > 0` = false ⇒ 自隐；
   行业对照 `pct === null ⇒ has=false` ⇒ 显示「本月没填」而非 0%。

**同族先例（关键）**：这条判据的**正确写法在同一个仓库里已经有了** ——
`pages/index/index.js:98`（C-① 修法）：`if (d && d.account_id && typeof fen === 'number' && Number.isFinite(fen))`
⇒ 单源判据 = **`account_id` 非空 ⟺ 有账本记录**（`getLedger:177` 已出参）。
而 `result.js` 连 `account_id` 都没取。⇒ **同一条判据在首页写了，在结果页没写**。

**为什么既有守卫没拦住（本轮的元发现）**：`tools/selftest_ui_fix.js` 的「修 1 · result 三态」
（`:13-24`）**8 条断言全是形态/存在性**，无一条含账本信号：

```
- 存在 loading 独立分支 (wx:if={{loading}})
- 存在结果分支 (wx:elif={{r}})
- 存在空态分支 (wx:else) 且含 resultEmpty
- 空态分支不含「加载中」
- 空态有去录入出口 (goInput + resultEmptyGoInput)
- result.js 有 goInput 方法跳 input
- result.js 空态文案引用 uiFix.resultEmpty
- 旧 wx:else=加载中 已移除（无 !loading && r 写法）
```

**而该守卫自述的意图是**「三态拆分 —— 空态（**无账本**或接口异常）」⇒ 意图是「无账本 ⇒ 空态」，
判据却用 `{{r}}` 去表达"无账本"。**守卫验证的是"分支在不在"，不是"分支到不到"。**
> 🔴 与 R297 复核记录 §4 的教训**完全同族**：**链路通 + 门禁绿，证明不了语义对**。

**建议修法（待拍板）**：判据由 `r` 改为「有账本记录」，复用 C-① 的单源判据：
`result.js` 的 `data` 增 `hasAccount`（取 `d.account_id`），`result.wxml` 的 `wx:elif` 改判
`{{hasAccount}}`（`loading` 分支不动、`wx:else` 空态文案与出口**都已就绪，零新增文案**）。

### M1-C3 ·【中】归档 7 天宽限：**前后端判据不等价**（云端 fail-open）⇒ **同族病第七例**

| 端 | 代码 | `archived_at` 缺失/为 0 时 |
|---|---|---|
| 前端 | `utils/ui.js:40` `if (!archivedAtMs) return false;` | **不在宽限 ⇒ 只读**（fail-closed） |
| 云端 | `cloudfunctions/saveLedger/index.js:64` `const archivedAt = existing.archived_at \|\| **now**;` | **在宽限 ⇒ 放行补录**（fail-open） |

**行为级实测**（真调前端实现 + 云端表达式复算）：

| 输入 | 前端 `withinGrace` | 云端复算 | 同向？ |
|---|---|---|---|
| `archived_at` 缺失/为 0 | `false` | `true` | ❌ **相反** |
| 刚归档（1 秒前） | `true` | `true` | ✅ |
| 超 7 天 | `false` | `false` | ✅ |

⇒ **只有"缺值"这一格分叉**，且分叉方向 = 云端更宽松。
**危害**：一旦命中，带 `archive_override` 即可**永久改写已归档月份** ⇒ 7 天硬锁（会计不可变性）静默失效。

**可达性（诚实标注，不夸大）**：**当前代码路径下 = 0** ——
`archiveMonth` 的两条写路径（INSERT `:55` / UPDATE `:63`）在 `archive=true` 时都写 `now`；
`saveLedger:161` 新建一律 `is_archive: false`。⇒ 需**存量数据 / 手工改库 / 云控制台编辑**
使 `is_archive:true` 而 `archived_at` 缺失，才命中。
⇒ 本轮**定级为「防御缺口 · 两端判据不等价」**（不是"当前可复现缺陷"），但**基线方向是 fail-open**，
与 B3 的 W1/W2（可达性 0）同级；差别在于这条是**写锁**（完整性），且属本仓已抓到六次的同族病。

**建议修法（待拍板，一行，零合法流程影响）**：
`cloudfunctions/saveLedger/index.js:64`：`existing.archived_at || now` → `existing.archived_at || 0`
（与前端 `|| 0` + `if (!x) return false` 同口径：**未知即锁**）。
⚠️ 正常归档路径 `archived_at` 恒为 `now` ⇒ 宽限照旧生效，**不改变任何现网行为**。

### 7.5 本轮自身踩到的两个工具级坑（如实登记，附处置）

**坑 1：`Edit` 会把**原本是 LF 的文件**写成 CRLF ⇒ 全量 diff（差点把一次 1 行改动伪装成 433 行重写）。**

| 文件 | HEAD CR | 改后 CR | 全量 diff | 处置后 |
|---|---|---|---|---|
| `tools/check_archive_grace.js` | 0 | 268 | 268 增 / 209 删 | `tr -d '\r'` ⇒ **59 增 / 0 删** |
| `specs/dev-specs/core/13_..._总览.md` | 0 | 433 | 433 / 433 | `tr -d '\r'` ⇒ **1 / 1** |
| `specs/dev-specs/★知识存储点_2026-09-10.md` | **1235** | 1235 | 1 / 1 | **不动**（它本来就 CRLF ⇒ 必须对齐 HEAD，不能一刀切） |

- **诊断法（可复用）**：`git diff --numstat --ignore-all-space` —— 若它给出**小而合理**的数字，而 `git diff --numstat` 给出全量 ⇒ **必是行尾/空白问题**，不是内容问题。
- **判别是「原生 CRLF」还是「我引入」**：`git show HEAD:<file> | tr -cd '\r' | wc -c` vs 工作树同式计数。
  ⇒ **逐文件对齐 HEAD 的行尾约定**（本仓是**混用**的，★知识存储点 就是 CRLF 特例）⇒ 一律 `tr -d '\r'` 反而会制造新的全量 diff。
- ⚠️ `grep -c $'\r'` 在本机 Git Bash 下**不可靠**（对本例返回 0 而实际 268）；可靠的是 `tr -cd '\r' | wc -c`。

**坑 2：`check_suite_assert_counts`（R107）在挂 preload 时会「假红」。**

- 它用 `execFileSync(NODE, [套件])` **实跑**套件取真值 ⇒ 这条 spawn **被 preload 拦截、喂旧缓存值** ⇒
  声明 42 ≠ 缓存实跑 38 ⇒ 判红；而不挂 preload 则 node→node 被沙箱 **SIGTERM**（实测）。
- 处置：`mk_force.py` 刷缓存**两循环**（`CODEBUDDY.md §3` 的定式）⇒ 循环 1 结束后仍可能在**同一循环内**先跑到
  消费者、后刷新被消费者 ⇒ **循环 2 才稳定转绿**（实测：循环 1 报 `rc=1`，循环 2 无）。
  ⇒ 这解释了"为什么要两循环"，而不是"跑两次碰运气"。
- 另：**主门禁 `run_gate_py.py` 不走缓存**（Python 侧 `subprocess` 直跑）⇒ 它的结果不受缓存影响；
  受缓存影响的只有"套件内部再 spawn 的进程"（本仓 12 个套件有 `child_process`）。
