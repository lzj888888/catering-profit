## §0 一句话结论

**堂食、外卖的菜品明细今天能抓到，团购抓不到；但抓到的数据缺一个「时间粒度」维度，
在今天的基础上直接做任何"按日"的诊断都是错的（实测虚高 7 倍、零报错）。**

三条真缺口，按严重度排：

| # | 缺口 | 现状 | 后果 | 是否本轮已补 |
|---|---|---|---|---|
| **G1** | **粒度不可表达** | `external_sales_daily` 只有单一 `biz_date`，堂食 7 天区间汇总被写成"某一天" | 按日诊断（趋势/日均/跨平台对比）全错且零报错 | ✅ 契约层已能识别（§4），schema 补字段待批 |
| **G2** | **团购零采集** | `subpkg/biz/groupon` 只是**手填试算页**，不导文件、不落库 | 团购这道渠道做不了任何菜品诊断 | ⬜ 需先拿到核销明细样例 |
| **G3** | **京东无商品销量表** | 只有订单导出（形态 D，商品混装一列）；SKU 对账单被**有意**排除 | 京东只能出"原价口径"明细，到手额要另走账单 | ⬜ 等 R284 承诺的表到货 |

**今天已经可以做**的诊断：菜品毛利排行、菜单工程（销量×毛利）范围内的**月度总量**结论。
**今天还不能做**：任何带"某一天""趋势""跨渠道对比""套餐内部拆解"字样的东西。

## §3 G1：粒度错配（本轮最值钱的发现）

### 3.1 实证

堂食那张表是 **7 天汇总**，但入库链路 `extractBizDate` 取的是**区间最后一个日期**：

```
extractBizDate(R2) → 2026-09-13        （R2 原文是「2026/09/07 至 2026/09/13」）
↓
_id             = SALE_<shop>_pos_2026-09-13_<seq>       ← 36 行全在这一个日期下
external_ref_id = DISH:pos:2026-09-13:<菜名>
```

下游 `getDishReview/service.js::countDataDays` 按 `biz_date` **去重**数天数：

```js
function countDataDays(rows) { const set = new Set(); for (…) set.add(s.biz_date); return set.size; }
```

⇒ 这份堂食只贡献 **1 天**。量化：

| | 值 |
|---|---|
| 真实覆盖 | 7 天 |
| 下游统计 | 1 天 |
| 少记 | 6 天 |
| 2026-09-13 这天"堂食收入" | = 真实日均的 **7 倍** |
| 报错 | **0 个** |

而同一家店同一区间的外卖是**逐日 7 行**。两路数据混进同一张表后**不可区分**。

### 3.2 为什么这是"接口缺了一维"，而不是"一个 bug"

`SALES_SCHEMA`（`utils/gradeGate.js`，与云端双副本）的字段是：
`shop_id / biz_date / external_ref_id / dish_key / qty / amount / platform / source / created_at`。

**没有任何字段能表达"这行代表一段时间"** ⇒ 当时的实现只能选一个日期。
这不是谁写错了，是表结构没给地方写。所以修法也不是改一行，是**先把维度补出来**。

### 3.3 关于形态 B（顺带澄清，别把它当"团购缺口"）

`index.js:206` 见到《套餐销售明细》直接 **fail 拒收**，原因是「套餐组分已并入菜品销售表」，
重复入库会**双计**。这条是**有意且正确**的，不是漏做。
真正想要的是「套餐里哪个单品卖得好」——那需要**父-子行关系**（`combo_parent` 字段），
属于接口补齐范畴（§4.2），不是把 B 放开。

## §4 本轮已落的接口层：`utils/dishIngestContract.js`

> 原则：**功能冻结不动，但接口必须先成型**。零云改动、零 UI 改动、纯逻辑、零 IO、可被守卫机器判。

### 4.1 它解决什么

把「哪条通道能采到什么颗粒度」从**注释里的知识**变成**机器可查的事实**。
在此之前，任何新写的诊断模块只能默认「一行 = 一天」，也就是踩 §3.1 那个 7 倍坑。

### 4.2 提供什么

| 导出 | 用途 |
|---|---|
| `GRANULARITY` | `daily` / `interval` / **`unknown`**（fail-closed：查不到就承认不知道，绝不猜 daily） |
| `AMOUNT_CALIBER` | `actual_income`（可直接减成本）/ `list_price`（原价，不能直接减）/ `net_settle`（结算净额） |
| `DISH_CHANNELS` | 🔴 全仓**单源**通道能力表（8 条）：channel / platforms / shape / hasDishDetail / grain / caliber / status / note |
| `inferGranularity(platform, shape)` | 现有行里没有粒度字段时的推断入口 |
| `describeRow(raw)` | 把一行行 uffice 数据描述成规范形态（含 `span_days`） |
| `assertComparable(a, b)` | 🔴 **跨平台对比准入闸**：粒度/天数/口径任一不等 ⇒ 拒绝并给修法 |
| `toDailyAverage(raw)` | 区间摊日均；**跨度未知返回 null**，绝不摊出假的日均 |
| `hasDishDetailSource(channel)` | 该渠道今天有没有菜品级来源（诊断准入门） |

### 4.3 立刻见效的一条

```js
assertComparable({ platform:'pos', shape:'dish_sales', period_from:'2026-09-07', period_to:'2026-09-13' },
                 { platform:'taobao', shape:'waimai_goods' })
// → { comparable:false, reason:'粒度不一致：interval vs daily',
//     fix:'把 INTERVAL 侧摊到日均再做对比，或改用「区间总额 vs 区间总额」' }
```

今天这个组合是**零报错直接比**的 —— 这条闸门存在的意义就在这里：
这条闸门现在存在了，将来任何诊断只要调它就不会再犯同一个错。

### 4.4 建议将来补的 schema 字段（**待批，本轮未动**）

补进 `external_sales_daily` / `SALES_SCHEMA`（双副本同步）：

| 字段 | 作用 | 缺省语义 |
|---|---|---|
| `granularity` | `daily` / `interval` | 缺 = 查契约层能力表（本文件的设计缺省草本机能用） |
| `period_from` / `period_to` | 区间端点（单日则两端相同） | 缺 = 未知，`span_days` 返回 null，**不许按 1 天用** |
| `item_ref` | 原始订单/行标识（去重与追溯） | — |
| `combo_parent` | 所属套餐（拆"套餐里哪个单品卖得好"） | — |

⚠️ 现有 R249 那条 `is_deleted` 的教训：新增字段若不_markk 写入侧补齐，读侧永远看不到
⇒ 补字段必须**同步改写入路径 + 双副本 schema + 新增/更新守卫**，缺一不可。

## §5 诊断能力 ←→ 数据依赖（这才是"能不能打基础"的答案）

| 诊断 | 需要什么 | 今天能做吗 | 卡在哪 |
|---|---|---|---|
| **① 菜品毛利排行** | 菜品销量 + 销售额 + 成本卡 | ✅ 能 | `getDishReview` 已跑通（`saveDishMapping` 读写闭环） |
| **② 菜单工程（销量×毛利）** | 同上 | ✅ 能（**只能给月度总量结论**） | 不能给"某天/某时段"版本 |
| **③ 跨渠道对比（同道菜堂食 vs 外卖）** | 两平台明细 + **粒度一致** + 成本卡 | ⚠️ 今天做了会错 | **G1**；须先过 `assertComparable` |
| **④ 趋势 / 工作日 vs 周末 / 爆品发现日** | **逐日**明细 | ❌ 堂食侧不行 | **G1**（堂食只有区间汇总） |
| **⑤ 套餐内部拆解（哪个单品带利润）** | 父-子行关系 | ❌ | 形态 B 拒收 + 缺 `combo_parent` |
| **⑥ 团购渠道诊断** | 核销明细 | ❌ | **G2**：完全没有采集 |
| **⑦ 搭配推荐（菜和菜一起被点）** | **订单级**购物篮 | ❌ | 订单级导入按 R282 维持关闭 |
| **⑧ 到手口径的单品贡献** | 明细 × 账单分摊规则 | ❌ | 明细是原价口径（②⑤ 之外还要一套分摊口径） |

**结论**：②③④ 是"接口补齐 + 口径明确"就能点亮的，⑤⑥⑦⑧ 需要**新数据源**。
⇒ 冻结期应把 ①②③ 的接口底座夯实（本轮做的），⑤⑥⑦⑧ 先不承诺。
