## 2. 🔴 P0：满减等效折扣的客单价缺口（页面不可达分支）

### 2.1 引擎和页面的分工

`utils/promoCalc.js::discountOf('threshold')`：

```js
const a = Number(q.avgPrice);
const base = (isFinite(a) && a > 0 && a > x) ? a : x;   // 有客单用客单，否则用门槛
const note = (isFinite(a) && a > 0 && a < x) ? 'below_threshold' : '';
const d = (base - y) / base;
```

引擎**是对的**：满 100 减 30，客单 100 → 7 折，客单 150 → 8 折，客单 80 → 按门槛 7 折 + `below_threshold` 提示。

### 2.2 页面把这条路堵死了

`subpkg/tools/promo/index.js::showOf('threshold')` 只有 `{ threshold: true, cut: true }`；
`data.rule` 的 12 个字段里**没有 `avgPrice`**；`index.wxml` 也**没有 `data-f="avgPrice"` 的输入框**。
第二段有 `avgPriceYuan`（客单价）输入，但 `recalc()` 只把它喂给 `promoCalc`（第二段）和 `reverseFromMargin`（第三段），
**没有喂给第一段的 `promoConvert`**。

### 2.3 机器取证（`review/evidence/r762_audit/probe.js` §2）

```
NG  2-① 页面存在客单价输入 data-f="avgPrice"  [没有]
NG  2-② showOf(threshold) 暴露 avgPrice 输入  [threshold: { threshold: true, cut: true }]
NG  2-③ 页面算出的折扣 = 客单150时应有的8折  [页面=7折 / 客单150独立算=8折]
OK  2-④ 引擎支持 avgPrice（差异在页面未接线，不在算法）  [引擎传150时=0.8]
NG  2-⑤ below_threshold 提示在页面可达  [引擎note=below_threshold / 页面rule字段里无avgPrice]
```

页面桩真跑：只填 `threshold=100 / cut=30`，`conv.discountText === '7折'`。
用同一个引擎传 `avgPrice:150` 得 `d=0.8`（8折）——**差一折，且随客单价Continuous漂移**：
客单 200 时真实 8.5 折，页面仍 7 折。

### 2.4 定级与影响

- 定 🔴 而非 🟡：R759 纠偏明确「买 2 送 1 相当于几折是 80% 心智、主入口」，满减又是最常见活动形式之一；
  主入口的**核心输出数字不准**，不是边角提示。
- 偏差方向是「显示得比实际更狠」（保守），不会直接让老板以为赚钱其实亏钱；
  但会让老板错误比较活动力度（例如误以为「满 100 减 30」和「7 折」等价），
  且误差随客单价连续漂移（客单越高，页面显示的折扣与实际差得越多）。
- `below_threshold` 提示分支在真实页面**永远不可达**：自测 A-② 覆盖了引擎，但页面守卫没覆盖接线 ⇒ 假覆盖。

### 2.5 修法建议（本轮不动，待拍板）

1. `showOf('threshold')` 增加 `avgPrice: true`，`index.wxml` 加一行客单价输入 `data-f="avgPrice"`（老板手填，仍不依赖店里数据）。
2. `recalc()` 把 `avgPrice` 一起传给 `promoConvert('threshold', rule)`；第一段的「不依赖毛利率」原则不受影响——客单价不是毛利率。
3. 客单价留空时**别声称就是实际折扣**：沿用按门槛算，但把 `below_threshold` 文案改成「未填客单价，按门槛 X 元估算」，
   让老板知道这是保守估值。
4. 补页面守卫（进 `verify_all.js`）：满减填客单 150 ⇒ 8 折；不填 ⇒ 按门槛 + 提示在场。
   **必须同时做第 4 条**，否则会出现「引擎自测绿、页面错一折而全仓无红」的假绿。

## 3. 🟡 守卫盲区：两处回退形态抓不到（变异证据）

变异脚本临时改坏产品源码，跑守卫，要求 `exit!=0` 且点名目标断言，然后字节级恢复（`git status` 确认无残留）。

| 变异 | 改坏了什么 | 守卫 | 结果 |
|---|---|---|---|
| M1 | 券口径退回旧算法 `d=(x−face)/x` | selftest / 三段守卫 | ✅ 均判红并点名 `A` / `A-①`（80代100 不再是 8 折） |
| M2 | 反算折扣公式倒置 `(100−G1)/(100−G0)` | selftest / 三段守卫 | ✅ 均判红并点名 `I761-①` / `B-①` |
| M3 | 客流倍数分母写成 `g0`（忘减折扣率） | selftest | ✅ 判红并点名 `B-①`（业界基准对拍） |
| M4 | 页面第三段 `reverse.discountText` 改成 `back.discountText` | 三段守卫 | ✅ 判红并点名 `B-③` |
| **M5** | 页面三段拆成**两次 `setData`**（正是 R759 真机踩过的丢数形态） | 两段守卫 / 三段守卫 | ❌ **两个都 rc=0，抓不到** |
| **M6** | 满减 `base` 写死成 `x`（正是当前页面的实际行为） | 两段守卫 / 三段守卫 | ❌ **两个都 rc=0，抓不到**；只有引擎 selftest 红 |

**根因**：页面桩的 `p.setData` 是同步 `Object.assign`，重现不了真机异步回调丢结果；
页面守卫的判据是「字段字符串是否出现在 wxml / recalc 里」，证明不了「数值随输入变化」。

**当前产品代码是正确的**（一次 `setData({conv, back, reverse})`），所以 M5 不是现存缺陷，
是**防回潮能力缺失**。建议：① 加源码形状断言「`recalc` 内单次 `setData` 同时含 conv/back/reverse」；
② 把 §2.5 的数值型页面断言补进守卫（同时覆盖 M6）。
