## 2 三条"看似真、实则假"的核心证据细读

### 2.1 配料行：李老师和三司都觉得要做，数据说不用

```
$ python -c "读 r232_formc_sample/商品下载_...xlsx 统计 是否配料"
HEADERS: [... '是否配料', '是否售罄', '销售额', '销量' ...]
是否配方 分布: {'否': 354}     ← 355 行，一个"是"都没有
配料行中 销量!=0 或 销售额!=0 的条数: 0
```
全仓扫描 xlsx 表头含"配料"的 → **只有这一份**。

⇒ 我上一轮写的"配料被当菜计入销量"是**想象出来的风险**。更关键：即便真有配料行，其销量/销售额通常为 0 或极小，不会造成金额错账。

### 2.2 双计：注释里写着"两个平台各导一次会翻倍"，但 R271 已经拦了

```
service.js:995  R271：跨平台重复导入检测
service.js:1004 判据要求「日期+菜名+销量+金额」逐行全等
service.js:1006-1008 老板常同时做美团与淘宝闪购 ⇒ 只按日期/菜名判会误杀 ⇒ 设三道下限
```
这个设计**比我们讨论的质量高**——"宁可漏判不可误杀"是错账红线下的正确取舍。我上一轮居然把它当"待修 bug"报给三司，是**没读代码先开脑洞**（SOUL.md 明令禁止的那一类）。

### 2.3 手填：我把它当"已存在的替代路径"讨论了两轮，它从未存在

`external_sales_daily` 的写入方 grep 只有 `importSalesBill`（+ 清理/备份/校验类）。`source` 枚举里虽有 `manual`，但**那是 schema 预留，不是实现**。
我据此推演了"手填+导表双计""手填覆盖率分母"两轮，全是空中楼阁。

## 3 错误模式（这才是要沉淀的东西）

### 模式 A：**把 schema 预留/注释警告当成现存故障**
- `source` 枚举有 `manual` ⇒ 我当成"手填存在"
- 注释写"两平台各导一次会翻倍" ⇒ 我当成"没防"
- 真规则：**枚举 ≠ 实现；注释里的"为什么必须拦"往往下面就是拦的代码**

### 模式 B：**把"理论上可能"当成"真实发生"**
- 配料行、跨口径金额、手填覆盖——全是没有一个真实样本支撑的推演
- 真规则：**先数样本里到底有几条，再决定要不要防**

### 模式 C：**三司互相引用未经验证的结论，形成回音室**
- 我 R1 说"双计必修" → 写进 R2 题面 → DeepSeek R2/R3 都当事实接 → 豆包 R3 也接
- **三司"一致"不等于正确**——它们共享了同一个错误前提
- 真规则：**题面里的每条"事实"必须附代码行号或文件路径，且接收方要独立核实**

### 模式 D：**提案前没扫已有实现**（SOUL.md S9 三扫的違反）
- R245 P7 别名表、日期归一、R271 检测——全在仓库里，我提案时一次都没 grep
- 真规则：**"如果这东西仓库里已经有了，它最可能叫什么名字？"——答不上来不许开工**

## 4 可复用的防错闸门（建议补进 `preflight-no-false-start` S9）

在提任何"新增/改造"前，除 S9 三扫外，加一问：

> **"我这条判断，能用一条 grep 或一份真样本证伪吗？"**
> - 能，且已证伪 ⇒ 停，不提
> - 能，未跑 ⇒ **先跑再提**
> - 不能 ⇒ 标"存疑+理由"，不当事实写进题面

配套：`三司题面模板` 里每条"现状事实"强制带 `file:line` 或 `evidence/路径`，否则接收方有权拒答。
