## §1 一句话结论

`extractPaste` 的「合计行护栏」写在了**行**上 —— `if (/合计|总计|total|小计/i.test(line)) { hasTotal = true; continue; }`。
它只在**标签与金额同行**（Excel 常规复制：`合计⇥7140.00`）时生效；
而平台账单里非常常见的**「标签占一行、金额在下一行」**（`合计` ⏎ `7140.00`）**完全绕过护栏**，
合计值被当普通明细加进求和 ⇒ **4380 + 2760 + 7140 = 14280（翻倍）**，
而界面照旧提示「已提取并填入」——**零告警、静默算错钱**。

已改为「**合计标签 → 金额**」**配对**识别（两种形态都排除），并在「排除后一个明细数字都不剩」时**兜底填入合计值 + 换专用提示**；
同时把**账单形态钉成 28 条用例表**（单源）并常驻双向校验。

## §2 缺陷本体

### 2.1 四种形态的实测对照（修复前）

| 粘贴内容（账单常见形态） | 修复前提取到的数 | 修复前填入 | 后果 |
|---|---|---|---|
| `4380.00`⏎`2760.00`⏎`合计⇥7140.00` | 4380, 2760 | `7140.00` | 正确（护栏生效） |
| `4380.00`⏎`2760.00`⏎`合计`⏎`7140.00` | 4380, 2760, **7140** | **`14280.00`** | 🔴 **翻倍** |
| `4380.00`⏎`2760.00`⏎`小计`⏎`7140.00` | 4380, 2760, **7140** | **`14280.00`** | 🔴 **翻倍** |
| `合计⇥7140.00`（只有这一行） | —（无明细） | `''` → 提示「未提取到数字」 | ⚠️ 该填却没填 |
| `合计`⏎`7140.00`（只有这一行） | 7140（被当明细） | `7140.00` | ⚠️ 碰巧填对，但语义错（`hasTotal=false`、无提示） |

同一份账单**换个写法就翻倍**，且**同一语义两种结果**——这正是它最危险的地方。

### 2.2 为什么算「静默算错钱」第 3 例

同一条链上：

| 轮次 | 缺陷 | 症状 | 当时的处置 |
|---|---|---|---|
| R85 | `firstNumber` 正则 `\d{1,3}(?:,\d{3})*` 对「≥4 位且无千分位」只取前 3 位 | `4380.00` → **438** | 改了**一处正则** |
| R85 | 平台账单「归属账期 / 下单时间」列被当金额 | `2026-09` 被加进求和 | 加了 `stripNonMoney`，仍是**点补丁** |
| **R120（本轮）** | 合计护栏挂在**行**上，换行形态绕过 | 明细 + 合计 = **翻倍** | 改为**配对** + 立用例表 |

三次的共同点：**都是「某一处判断写窄了」，都在 UI 上零告警**。
前两例都只修了「那一处」，所以第三例照旧复发 —— 这是本轮不满足于点补丁的直接理由。

## §3 修复

### 3.1 配对策略（`utils/takeaway.js::extractPaste`）

```
遍历每一行：
  · 该行无数字 且 含「合计/总计/小计/total」  ⇒ hasTotal = true，开启 pendingTotal
  · 该行有数字 且 含合计字样                  ⇒ 归入 totalValue（形态一：同行），**不进 numbers**
  · 该行有数字 且 pendingTotal 为真           ⇒ 归入 totalValue（形态二：悬空标签后的第一个数字行），**不进 numbers**
  · 其余                                      ⇒ sum += n; numbers.push(n)
```

- `pendingTotal` **跨越其间的纯文字行**（如 `合计` ⏎ `（单位：元）` ⏎ `7140.00`），由紧随其后的**第一个数字行**归合计；
- `totalValue` 采用**后者覆盖前者** ⇒ 无明细时兜底取「最后出现的合计」（账单阅读顺序里最终合计在最后）；
- 返回值新增 `totalValue`（`number|null`）。

### 3.2 兜底（`pasteFillValue`）

- **有明细** ⇒ 只按明细求和（与旧行为一致）；
- **无明细但有合计** ⇒ 填合计值（旧行为给空串 ⇒ 用户以为没粘上）；
- 🔴 **必须显式判 `null`/`undefined`**：`Number(null) === 0` 且 `Number.isFinite(0) === true`，
  弱化成 `Number(res.totalValue)` 会让**空文本 / 纯表头被误填成 `0.00`**（用例 E1/E2 钉住这条，变异 M4 已实测转红）。

### 3.3 页面接线（`pages/month/input.js::onPasteExtract`）

- 判据由 `res.numbers.length === 0` 改为 **`pasteFillValue(res) === ''`**（= 「**最终**能不能填出值」）；
- 新增纯函数 `pasteFilledFromTotal(res)`：本次填入是否来自合计兜底；
- toast 分流：兜底 ⇒ `pasteFromTotal`（`已按合计行填入，请核对是否与明细重复`，`icon:'none'`）；
  正常 ⇒ `pasteDone`；
- 确认弹窗**只在「有明细 + 有合计」时触发**（`res.hasTotal && !fromTotal`）——
  纯兜底场景没有明细可确认，不再多问一次；
- `twPasteRaw` 留存记录新增 `fromTotal` 字段（本地草稿可回溯时能看出这次是兜底填的）。

### 3.4 文案（`terms.js` 双副本，逐字节一致）

- 改 `pasteConfirmBody`：`粘贴内容里含「合计 / 总计」行，已按明细行求和、合计行本身不计入。要继续吗？`
  （旧句尾巴「若合计行本身是唯一金额，可能重复计算」在新行为下已不成立，删除）；
- 新增 `pasteFromTotal: '已按合计行填入，请核对是否与明细重复'`。
